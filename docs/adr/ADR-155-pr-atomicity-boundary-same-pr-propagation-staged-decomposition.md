# ADR-155: The Pull Request Is the Atomicity Boundary — Same-PR Propagation and Staged Large-Task Decomposition

**Date:** 2026-07-31
**Status:** Accepted (relaxes ADR-141 Decision item 6, ADR-142 Decision item 1, ADR-154 Decision item 1 and a Consequences bullet, and an ADR-119 Consequences bullet)
**Affects:** `.claude/README.md` (Cost policy rules 1, 6, 7), `CLAUDE.md` (Guidelines, Agent Orchestration, Raw FFI and Generated Bindings), `.claude/agents/scope-shaper.md`, `.claude/agents/doc-sync-checker.md`, `.claude/skills/codex-pr-review-loop/SKILL.md` and `reference/finding-routing.md`, `.claude/skills/adr-number-reservation/SKILL.md`, `docs/j2534-2-support-plan.md`, `j2534-0404-service/docs/implementation-notes.md`, `docs/adr/ADR-141`, `docs/adr/ADR-142`, `docs/adr/ADR-154`, `docs/adr/ADR-119` (Status lines and inline Update annotations on each)

## Context

Two independent governance questions turned out to share one answer.

**Question 1 — is "same commit" the right atomicity unit for a propagation/doc-sync duty?** ADR-141 Decision item 6 requires a fix to the ADR-136 taint rule to propagate, "in the same commit," to every named consumer copy (`.claude/README.md`'s summary, `implementer.md`, `cargo-runner.md`, `scripts/ci-checks.sh`, ADR-113's parallel list). CLAUDE.md's Guidelines state the same commit-level requirement for docs-with-code generally, and Cost policy rule 6 states it for a bindgen deferral record. This repeatedly created a real conflict this session hit directly: the top-level system prompt's git-safety protocol says to always create new commits rather than amending, but if a Codex review round finds a missed copy after the original commit already landed in the PR, strict same-commit compliance pushes toward amending that commit — the two policies fight, with no move that satisfies both.

This repository's documented convention (`.claude/skills/codex-pr-review-loop/SKILL.md`'s merge step) directs squash-merging every pull request, and this session's own merges follow it, though the convention is not mechanically enforced repo-wide (`58ad37e`, the PR #12 merge, 2026-07-29, is a genuine two-parent merge commit, postdating the convention) — a detail that turns out not to be what actually matters here. **None of the three duty families this ADR covers (Decision item 1) has ever been enforced by an automated CI gate.** `scripts/ci-checks.sh adr-check` verifies ADR numbering and `INDEX.md` linkage only; `gate-sync-check` verifies one specific duty — the ADR-142 paraphrase-gate text staying byte-identical across its embedded copies — and nothing broader; CI's bindgen-drift check covers only the native target, with the other four pre-committed targets an accepted procedural-trust residual already (ADR-109/154). General propagation-duty completeness (ADR-136/141/142/154's "all N copies"), CLAUDE.md's docs-with-code duty, and cross-target bindgen completeness beyond native have always been enforced by *process*, not CI: `doc-sync-checker`'s mandatory dispatch under Cost policy rules 1/3, the Codex automated review loop (`chatgpt-codex-connector[bot]`, re-triggered on every push), and CLAUDE.md's Pull Request Workflow step 3 close-out sweep before merge — this very PR's several review rounds are direct, current evidence the loop catches exactly this class of omission. That process predates this ADR; commit-level atomicity never added a CI guarantee these duties didn't already lack. What the process actually reviews is the PR's cumulative state at request time (Codex re-reviews the full current diff on every `@codex review`; `doc-sync-checker`, per Decision item 5, now explicitly audits the PR's merge-base-to-working-tree diff, not a single commit) — so relaxing the atomicity unit from commit to PR changes nothing about what gets checked before merge; it only changes which commit boundary a caught omission's fix may land in.

**Question 2 — should a Large task be split into staged, independently-mergeable PRs?** Cost policy rule 1's "Large or risky" tier had no staging guidance. A prior effectiveness analysis (this session, before this ADR) found that a blanket "split Large tasks into stages" instruction would rarely apply as written, because most Large tasks (protocol semantics, concurrency, FFI) also touch a same-commit propagation or doc-sync duty, and those duties — under the *old* same-commit reading — cannot span multiple PRs without leaving `main` in a durably inconsistent state between merges (exactly the class of gap ADR-136 rounds 11 and 19 found the hard way, this time made permanent rather than transient). The analysis also found a working precedent already in this codebase: the J2534-2 effort is staged as ADR-152 (Phase 0, foundational decisions) and ADR-153 (Phase 1, discovery mechanism), each landing its own ADR, docs, and code as one internally-consistent PR — staging works precisely when each stage is complete with respect to every duty it triggers.

These two questions converge on a single principle: **the pull request, not the commit, is the atomicity boundary for a same-change consistency duty — and that boundary is never crossed by staging**. Relaxing same-commit to same-PR resolves Question 1's conflict at no added risk: the review process that actually catches an incomplete duty (`doc-sync-checker`, Codex review, the close-out sweep) already operates on the PR's cumulative state, not per-commit, so it was never protecting against anything commit-level atomicity uniquely provided. Stating the same principle as a hard limit resolves Question 2 safely: a Large task may be staged across PRs, but no stage boundary may ever split a duty whose copies, docs, or records a single change obligates — because once a PR merges, its final state is permanently part of `main`'s history, and there is no review pass spanning two separate, already-merged PRs to catch a duty left incomplete between them.

## Decision

**1. Same-PR propagation, three duty families.** Wherever a governance document currently requires a propagation, doc-sync, or record duty to complete "in the same commit," the atomicity unit is now the pull request: all required copies, docs, or records must be consistent in the PR's final merged state (whether that lands on `main` as one squashed commit or several), and a copy missed by an earlier commit in the PR is completed by a later commit in that same PR — never by amending the earlier one. This applies to three duty families:
   - **Duplicated-copy propagation** (ADR-136/141/142/154's "all N copies change together," and the crate-local enumerated-copy-set duties this pattern also covers, e.g. `j2534-0404-service`'s seven-struct-literal duty in `docs/implementation-notes.md` — in scope for vocabulary consistency even where the compiler independently enforces it).
   - **CLAUDE.md's docs-with-code duty** (a documentation update required by the same change that requires it).
   - **Cost policy rule 6's bindgen deferral/regeneration-record duty** (ADR-154).

   This relaxation is premised on the review process — `doc-sync-checker`'s dispatch, the Codex review loop, and CLAUDE.md's Pull Request Workflow close-out sweep — operating on the PR's cumulative state before merge, not on any CI job or on squash-merging. No CI job in this repository verifies general propagation-duty completeness across these three families (`adr-check` and `gate-sync-check` verify narrower, specific things — ADR numbering/`INDEX.md` linkage, and the ADR-142 gate text specifically — see Context), so this was never a CI-enforced guarantee, under the old same-commit rule or this one; it has always rested on the review process actually running before merge. That process already reviews the PR's cumulative diff, not individual commits (Codex re-reviews the full current diff on every request; `doc-sync-checker`, per Decision item 5, audits merge-base-to-working-tree), so nothing about *which commit* a completing fix lands in changes what gets checked. If a PR is ever merged without that review process actually completing — the close-out sweep skipped, a Codex round never requested, a mandatory `doc-sync-checker` dispatch omitted — this Decision's guarantee does not hold for that PR, exactly as it would not have held under the old same-commit rule either.

**2. No duty ever spans multiple PRs — the hard limit.** Every merged PR's final state becomes permanently part of `main`'s history — as one commit under this repository's squash-merge convention, or as multiple commits if that convention is bypassed, either way irreversibly durable once merged. A duty split across two PRs would leave `main` in a real, non-transient inconsistency window between the two merges — precisely the failure class ADR-136 rounds 11 and 19 record, this time permanent rather than caught by a later review round. The review-process argument that justifies relaxing same-commit to same-PR (item 1) stops exactly at the PR boundary — there is no review pass spanning two separate, already-merged PRs — and never extends across PRs. This clause is canonical here; every other file stating it (Cost policy rule 1, `scope-shaper.md`) cites this ADR rather than restating the reasoning.

**3. Staged decomposition for Large tasks, bounded by (2).** Cost policy rule 1's "Large or risky" tier gains a preference for splitting a Large task into independently mergeable stages (separate PRs), each leaving `main` self-consistent — the J2534-2 phase plan (ADR-152/153) is the existing model. The one hard constraint is Decision item 2: a stage boundary must never split a same-change consistency duty (any of the three families in Decision item 1) across PRs. When `scope-shaper` is gated in (Cost policy rule 3), it proposes and checks stage boundaries against this constraint as part of its normal scoping output; otherwise the orchestrator applies the same test inline before opening the first PR of a staged sequence.

**4. Reading rule for historical text — narrative is untouched, forward-looking duty text is amended.** The dividing line is not "is this text inside an accepted ADR" but whether the specific passage *describes what a past PR or round did* (historical record) or *states an ongoing instruction a future change must still follow* (a live duty). Historical-record text is read as satisfying same-PR semantics without being rewritten — this repository's convention (per ADR-142/ADR-144's own precedent) is to annotate a superseded/relaxed decision's Status line rather than rewrite accepted body text. A forward-looking duty passage gets the same Status-annotation-plus-inline-"Update (ADR-155)"-paragraph treatment as any live operative copy, even inside an already-accepted ADR — an ADR's Decision section is this repository's own normative source, so a stale forward-looking clause left there is exactly the drift this ADR exists to close, not an exempt category. This ADR's own first pass under-scoped the exclusion (an earlier draft exempted every already-accepted ADR body wholesale); a Codex review round on this PR caught three more ADRs whose Decision/Consequences sections state forward-looking same-commit duties, not narrative — corrected below. Applying the test:
   - `.claude/agents/cargo-runner.md`'s "a local pass and a CI pass on the same commit must mean the same thing" is about one commit's content matching between two verification contexts — a genuine single-commit identity property, not a duty's atomicity unit. It is untouched by this ADR.
   - ADR-136 itself is left untouched: its own "same commit" occurrences are round-record narrative describing how a past fix landed, not a forward-looking duty statement — the forward-looking duty text lives in ADR-141 Decision item 6 (relaxed here) and Cost policy rule 7's summary (updated here). ADR-141 Decision item 1 ("ADR-136 remains the normative source, unchanged") is unaffected: ADR-136's normative content is taint *classification*, not commit granularity, so its precedence over the summary is undisturbed by this ADR.
   - ADR-142's Context section (describing what ADR-141 said, and what happened in a past review round) is narrative and untouched; its Decision item 1 names doc-sync-checker's check 6(c) "same-commit propagation-duty completeness" — a forward-looking definition — and is amended.
   - ADR-154's Decision item 1 (the deferral-record and regeneration-record duties) and a Consequences bullet (the rule-2/rule-8/CLAUDE.md three-copy propagation duty) are both forward-looking and amended; its other "same commit" mentions (none found beyond these) would be narrative by the same test.
   - ADR-119's Consequences bullet on the dual-implementation (skill vs. workflow) keep-in-sync duty is forward-looking and amended; the rest of that ADR's text describes the reservation mechanism itself, not a same-commit duty.

**5. `doc-sync-checker` operates on the PR's cumulative diff.** Under same-PR semantics, `doc-sync-checker`'s completeness checks (its core doc-sync mandate and check 6(c)'s propagation-duty passage-touch coverage) must be judged against the PR's cumulative diff — branch head versus merge-base with `main` — never a single review-round commit's diff alone. Otherwise a duty legitimately completed across two commits within one PR would false-positive as incomplete. A dispatch brief asking `doc-sync-checker` to verify a review-round fix must hand it the cumulative diff, not just the latest commit.

**6. Four ADRs amended by Status annotation, not rewrite.** ADR-141, ADR-142, ADR-154, and ADR-119 each have their Status line annotated to note which Decision or Consequences item's atomicity boundary this ADR relaxes, and the named item's own body gains an inline "Update (ADR-155)" paragraph rather than being rewritten in place, consistent with the same annotation convention ADR-144 already established for ADR-142.

## Consequences

- The amend-vs-new-commit conflict this session hit repeatedly is resolved: a review round finding a missed propagation copy, doc update, or bindgen record now lands as a new commit in the same still-open PR, never an amendment.
- Large tasks gain a documented, working staging pattern (already proven by ADR-152/153) with an explicit, hard-enforced boundary preventing the exact failure mode that would make staging unsafe.
- An intermediate push within a PR may still draw a `doc-sync-checker` or Codex-review finding of incompleteness until the completing commit lands later in the same PR — acceptable and self-correcting, since merge is still gated on the review process passing against the PR's final state, not any intermediate commit. No CI job enforces this independently (see Context), so this was already true before this ADR, not a new exposure it introduces.
- The never-spans-multiple-PRs clause (Decision item 2) now exists in three places (this ADR, canonically; Cost policy rule 1; `scope-shaper.md`) — itself a propagation duty this ADR's own Decision item 1 governs. Future edits to that boundary's scope must land in all three in the same PR.
- Residual: historical "same commit" phrasing persists, by design, in narrative passages of already-accepted ADR bodies (ADR-136's round records; the Context/narrative sections of ADR-142/154/119) under the Decision item 4 reading rule. This is intentional, not an oversight — rewriting accepted ADR text wholesale is against this repository's own convention, and the reading rule exists precisely so no future session "fixes" narrative phrasing unnecessarily; it does not exempt a forward-looking duty passage merely for being inside an accepted ADR, per item 4's corrected scope.
- Cost policy rule 1's Small-tier propagation carve-out text (the several-hundred-word explanation of `doc-sync-checker`'s three check-6 triggers) is consolidated into a shorter summary-plus-precedence-pointer in the same PR as this ADR, per the Process Feedback section's mandatory companion-consolidation rule (rule 1 was already at the ~60-line growth threshold before this ADR's own staging-carve-out addition) — the full, canonical wording of the three triggers now lives in `doc-sync-checker.md` alone; `.claude/README.md` no longer duplicates it.
- **Accepted residual: squash-merging is a documented convention, not a mechanically-enforced guarantee.** `58ad37e` (the PR #12 merge, 2026-07-29) is a genuine non-squash, two-parent merge commit, postdating the convention (`.claude/skills/codex-pr-review-loop/SKILL.md`'s merge step). This does not undermine same-PR atomicity's core guarantee, since that guarantee never rested on squash-merging (Decision item 1: it rests on the review process, which examines the PR's cumulative state regardless of commit count). It does mean `main`'s commit-level history is not uniformly one-commit-per-PR, which matters only for history-level tooling (`git bisect`, checking out an individual historical commit mid-PR) — out of scope for what any duty in this ADR needs. Enforcing squash-only merging mechanically (e.g. GitHub branch protection) was not evaluated or actioned by this ADR; it is a candidate hardening step for a future session to raise, not something decided here.
- **Accepted residual: no CI job verifies general propagation-duty, docs-with-code, or non-native-bindgen completeness.** This was true before this ADR and remains true after it — this ADR does not add CI coverage for the three duty families in Decision item 1, only restates the atomicity unit the existing, process-based enforcement (`doc-sync-checker` + Codex review + the close-out sweep) already operates at. A mechanical CI check for a stated propagation-duty's named copies was not evaluated here and is a candidate follow-up, not a blocker for this Decision: the same process-based enforcement is what this repository has relied on for these duties since before this ADR, unchanged by it.
