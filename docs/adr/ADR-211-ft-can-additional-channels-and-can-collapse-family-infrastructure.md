# ADR-211: SAE J2534-2 Clause 7 Additional Channels (`_CHx`) — Shared CAN-Collapse-Family Infrastructure Fix, and Extend to Fault-Tolerant CAN

**Date:** 2026-09-02
**Status:** Accepted (Decision item 5's CAN FD/ISO15765-on-CAN-FD `_CHx` deferral fulfilled by [ADR-213](ADR-213-can-fd-additional-channels.md))
**Affects:** `j2534-0404`, `j2534-0404-service` resources/names/rpc_link, `j2534-0404-mock`, docs, `tests/grpc_mock/fault_tolerant_can.rs` (or equivalent)

## Context

SAE J2534-2 clause 7 Additional Channels (`_CHx`) support (ADR-156 Decision 3/Phase 2b) has been extended to 13 of the 18 in-scope protocol families across ADR-206 through ADR-210, each a standalone protocol with a simple `_PS`/`_CHx` id pair and no cross-family relationship. 5 families remain out of scope, explicitly flagged by ADR-206's own original investigation as needing "a dedicated design/audit pass first," not a drop-in repeat of the 13 closed families' pattern: CAN FD (`FD_CAN_PS`, Phase 3a/ADR-158), ISO15765-on-CAN-FD (`FD_ISO15765_PS`, Phase 3b/ADR-159), Single Wire CAN (`SW_CAN_PS`/`SW_ISO15765_PS`, Phase 4/ADR-164), and Fault-Tolerant CAN (`FT_CAN_PS`/`FT_ISO15765_PS`, Phase 6/ADR-168).

Unlike the 13 closed families, these are all **CAN-collapse variants**: `resources::base_protocol_id` (the ADR-157 normalization funnel every "Plane B" call site uses) has an explicit match arm for each of these 6 `_PS` ids collapsing it onto its true base family, `CAN` or `ISO15765` — not a self-referential fixed point the way every closed family's own `_PS` id is (e.g. `base_protocol_id(PROTOCOL_J1939_PS) == PROTOCOL_J1939_PS`, since J1939 has no explicit arm and self-identifies). CAN FD/ISO15765-on-CAN-FD are additionally a **connect-time state-machine substitution** (`rpc_link::J2534Service::apply_fd_mode`), not an independently-selectable identity at all — the client never names `FD_CAN_PS` directly; the adapter infers and applies it from staged Working ComParams at `ConnectComLogicalLink` time.

A `design-advisor` consult (dispatched 2026-09-02, briefed with an up-front `code-scout` investigation independently re-verified by direct code reading before the brief was written — this session's established methodology for every family in this series) confirmed two concrete, previously-undiagnosed hazards a naive application of the 13-closed-families' pattern would introduce, and recommended a three-round implementation plan. Both hazards were independently re-verified by direct code tracing before this ADR was written (per the same "never trust an investigation blindly" discipline applied at every prior step of this series):

1. **`base_protocol_id`'s existing fallback does not correctly normalize a `_CHx` id from a CAN-collapse family.** `resources.rs`'s `base_protocol_id` falls through to `other => chx_base_protocol_id(other).map(|(base, _index)| base).unwrap_or(other)` for any id with no explicit arm. `chx_base_protocol_id`'s own reverse-lookup table (`chx_block_base`'s inverse) is keyed to return whatever id `chx_block_base` was itself keyed on — for every closed family, that key IS the true base (self-referential, as above), so this fallback happens to be correct today. For a CAN-collapse family, `chx_block_base` would be keyed on the family's own `_PS` id (mirroring every closed family's established convention, e.g. `PROTOCOL_FT_CAN_PS => Some(PROTOCOL_FT_CAN_CH1)`), so `chx_base_protocol_id(FT_CAN_CH3)` would return `(PROTOCOL_FT_CAN_PS, 3)` — and the naive fallback would set `base_protocol_id(FT_CAN_CH3) = PROTOCOL_FT_CAN_PS`, NOT `CAN` (the value `base_protocol_id(PROTOCOL_FT_CAN_PS)` itself already correctly returns via its own explicit arm). Every "Plane B" call site relying on `base_protocol_id()` to determine CAN/ISO15765-family behavior for a live, already-connected `_CHx`-qualified FT/SW/FD link would silently see the wrong value. **The identical bug exists independently in `j2534-0404-mock/src/lib.rs`'s own `base_protocol_id`-equivalent function** (confirmed directly: its `PROTOCOL_FT_CAN_PS => PROTOCOL_CAN`/`PROTOCOL_SW_CAN_PS => PROTOCOL_CAN` arms are exact-match, and its own `chx_base_protocol_id(protocol_id)` fallback tail returns the tuple's `base` element unrecursed, the same shape as the service-side bug) — this was found independently during this ADR's own drafting, not flagged by the `design-advisor` consult itself.
2. **`names.rs::resolve_channel_selection`'s compound-`_CHx`-name route silently downgrades a CAN-collapse family to plain CAN/ISO15765.** Its `requested_index.is_some()` branch computes `base_hw_protocol_id = resources::base_protocol_id(raw_hw_protocol_id)` then `chx_protocol_id(base_hw_protocol_id, requested_index)` (`names.rs:1966-1967`). For every closed family this is a no-op (`base_protocol_id` of a self-referential `_PS` id returns itself), so `chx_protocol_id` computes the family's own `_CHx` sibling correctly. For a CAN-collapse family's `_PS` id, `base_protocol_id` returns the true base (`CAN`/`ISO15765`) — so `chx_protocol_id` would compute a *plain* `CAN_CHx`/`ISO15765_CHx` id instead of the family-qualified one, silently discarding the caller's FT/SW/FD intent. **This bug is currently masked, not live**: an FT/SW resource row's own `resolve_pin_selection` arm (`names.rs:925` for FT) always returns a non-`None` pin selection (clause 9/20 define no default pin at all), so `resolve_channel_selection`'s own earlier `pin_selection.is_some()` mutual-exclusion rejection (`names.rs:1938`) fires first today, before this compound-name branch is ever reached for an FT/SW row — with a misleading "mutually exclusive" error rather than a silent downgrade. Adding the standard `requested_index.is_some()` bypass every closed family's arm has (Decision item 4 below) removes that masking rejection, so this fix and the bypass must land together or the masked bug becomes live.

`resolve_channel_selection` has a THIRD route with the identical hazard, caught by an `edge-case-hunter` pass on this ADR's own implementation (not by the up-front investigation, and not by this ADR's own original drafting) after the first two routes above were already fixed: the `already_chx` branch, reached for a *directly*-named `_CHx` id (`raw_hw_protocol_id` itself already in the `_CHx` vocabulary — a bare numeric `ResourceId`/`ResourceName`, or `RscData::ProtocolId(PROTOCOL_FT_CAN_CH1)`, not a compound-suffixed name). This branch computes `resources::chx_base_protocol_id(raw_hw_protocol_id)` directly and returns the extracted base unrecursed — the same un-normalized-intermediate-value bug as Context item 1, at a third call site item 1's own fix (Decision item 2, `base_protocol_id`'s own recursion) does not reach, since this branch never calls `base_protocol_id` at all. Reproduced directly (a temporary test asserting `resolve_channel_selection`'s return value, verified failing pre-fix, fix applied, verified passing) rather than assumed. Confirmed downstream consequences: `rpc_link.rs`'s `connect_flags` computation and `rpc_misc.rs`'s post-`CLEAR_MSG_FILTERS` filter-family reinstallation each do exact-equality checks against `CAN`/`ISO15765` and silently mis-route for a directly-`_CHx`-named FT_ISO15765 connect specifically — the identical logical connection reached via the compound name already got correct behavior from the Context item 2 fix; only the direct-numeric-id route was still broken. Fixed the same way: compose the extracted base through `resources::base_protocol_id` before returning it (Decision item 3 below now covers all three routes, not two).

`apply_fd_mode` (CAN FD's own connect-time substitution) already explicitly rejects FD-mode staging when `link.channel_index.is_some()` (`rpc_link.rs:5529-5535`, `:5605-5611`) — confirmed directly: this is existing, correct, deliberate behavior (not a bug to fix), and is the reason a `_CHx`-selected link staging FD ComParams gets a clean rejection today rather than a silent substitution. Any future CAN FD `_CHx` round must not weaken this guard without a considered decision (deferred to that round, Decision item 5 below).

SAE J2534-2 clause 21.3.2.5.1 / 22.3.2.6.1 (paraphrased, not quoted, per this workspace's copyright policy) describe a CAN FD Additional Channel as staying electrically inactive until the data-phase rate is configured, then attaching to vendor-assigned connector pins with no J1962 pin-selection step at all — consistent with `design-advisor`'s reading that a D-PDU client's only way to express "FD on Additional Channel N" is `channel_index=N` plus staged FD ComParams (clause 7's own no-J1962-pins rule for every Additional Channel), not a directly-named `FD_CAN_CHx`/`FD_ISO15765_CHx` id (for which no client-facing verb exists — clause 21/22 define no unqualified base id and no direct-naming route). This confirms CAN FD's own future round is `apply_fd_mode`-substitution-only, not direct-naming, when it is undertaken.

## Decision

1. **Three separate rounds, in order Fault-Tolerant CAN → Single Wire CAN → CAN FD/ISO15765-on-CAN-FD, each its own ADR** (matching the ADR-206 through ADR-210 one-family(-pair)-per-round convention). Fault-Tolerant CAN goes first as the minimal pathfinder for the shared infrastructure fix (Decision items 2-3 below): it has no family-specific ComParams, IOCTLs, or RxStatus handling of its own (ADR-168 Decision 5), so its round exercises the infrastructure fix against the smallest possible surface (4 non-test service call sites plus 1 mock site, confirmed directly — see Decision item 6). Single Wire CAN goes second: same resource-table-driven mechanism as FT, but a larger surface (ComParams/IOCTLs/RxStatus of its own, ADR-164 Decision 2) plus a confirmed vendor-header naming inconsistency specific to this family (its `_CHx` blocks are `PROTOCOL_SW_CAN_CAN_CH1..128`/`PROTOCOL_SW_CAN_ISO15765_CH1..128`, both prefixed `SW_CAN_` — matching SAE J2534-2's own clause 24 table naming, not a header defect — rather than the `SW_CAN_CH1`/`SW_ISO15765_CH1` naming every other family's `_CHx` block uses relative to its own `_PS` id's prefix; verified directly against `j2534-0404-sys/src/bindings/j2534_v0404.h`). CAN FD/ISO15765-on-CAN-FD goes last: it needs the infrastructure fix already proven correct by the first two rounds, plus its own state-machine change to `apply_fd_mode` (out of scope for this ADR — deferred to that future round).

2. **Fix `resources::base_protocol_id`'s fallback to recurse once**, so `chx_base_protocol_id`'s extracted base is itself passed back through `base_protocol_id` rather than returned raw: `other => chx_base_protocol_id(other).map(|(base, _index)| base_protocol_id(base)).unwrap_or(other)`. This is a strict no-op for every one of the 13 currently-wired families (each `_PS` id is already a self-referential fixed point of `base_protocol_id`, confirmed directly by tracing J1939/TP2.0/GM UART's own arms — applying `base_protocol_id` a second time changes nothing), so this fix carries zero behavior change for any already-shipped family. Apply the identical fix to `j2534-0404-mock/src/lib.rs`'s own `base_protocol_id`-equivalent function (its `PROTOCOL_FT_CAN_PS => PROTOCOL_CAN`-style exact-match arms plus its `chx_base_protocol_id(protocol_id)` fallback tail carry the same shape and the same bug, confirmed directly during this ADR's own drafting).

3. **Fix all three of `names.rs::resolve_channel_selection`'s routes to produce the true, fully-normalized base:**
   - The compound-name branch computes the `_CHx` id from the raw, un-normalized row id, not the `base_protocol_id`-normalized value — i.e. `resources::chx_protocol_id(raw_hw_protocol_id, requested_index)` directly, not `chx_protocol_id(base_protocol_id(raw_hw_protocol_id), requested_index)`. `chx_block_base`/`chx_protocol_id` are keyed on the qualifying `_PS` id itself (matching every closed family's own convention), not on the true CAN/ISO15765 base — normalizing first, as the code used to, is exactly what causes the silent downgrade described in Context item 2.
   - The `already_chx` branch (directly-named `_CHx` id) composes its own extracted base through `resources::base_protocol_id` before returning it — `resources::base_protocol_id(resources::chx_base_protocol_id(raw_hw_protocol_id).unwrap().0)` in effect, not the raw extracted value — per Context item 2's own third-route addendum.
   - The `_PS`-direct-naming route (`resolve_pin_selection`) already composed through `resources::base_protocol_id` before this ADR; unchanged.
   For every closed family all three are a no-op (raw id, extracted base, and normalized id all coincide), so these fixes carry zero behavior change for any already-shipped family.

4. **`resources::is_ft_protocol_id`/`is_sw_protocol_id` themselves stay strict two-value checks, untouched** — they remain correct for `names.rs`'s own arm-gate purpose (`resolve_pin_selection`'s FT/SW arms) and the mock's `pins_assigned` initialization gate, the same "narrow predicate stays narrow, a new family-wide predicate is added alongside it" precedent every closed family already established. New `is_ft_family_protocol_id` (this round) and `is_sw_family_protocol_id` (Single Wire CAN's own future round) range-inclusive predicates are added for the family-wide, non-arm-gate call sites (Decision item 6).

5. **CAN FD/ISO15765-on-CAN-FD's own `_CHx` support is out of scope for this ADR**, deferred to that family's own future round per Decision item 1. When undertaken, that round's own investigation must independently confirm (not assume from this ADR) whether `_CHx` support means relaxing `apply_fd_mode`'s existing `channel_index.is_some()` rejection to allow index-aware promotion/reversion (this ADR's Context section's reading of clause 21.3.2.5.1/22.3.2.6.1 favors this shape — no direct-naming route exists for a client to express FD-on-a-specific-Additional-Channel any other way), or some other shape; ADR-158 Decision 1/3 and ADR-159 Decision 1 will need a partial-supersession Status-line annotation at that time, not this one.
   **Update ([ADR-213](ADR-213-can-fd-additional-channels.md)):** that round's own independent spec re-read found this paraphrase's "no direct-naming route exists" claim inaccurate at the raw J2534 layer — clause 21.3.2.1.4/22.3.2.2.1 (Table 89/96), not 21.3.2.5.1/22.3.2.6.1, list `FD_CAN_CHx`/`FD_ISO15765_CHx` as directly-nameable `<ProtocolID>` values, and the vendor header defines the matching native `_CH1..128` blocks. Index-aware promotion/reversion turned out to be the right shape anyway, but for a different, still-valid reason: this adapter's own already-shipped D-PDU resource contract (ADR-158/159) has no resource-table row for either `_PS` id and recomputes FD-ness from staged ComParams on every connect, so a directly-named FD id (`_PS` or `_CHx`) would simply be reverted at connect — see ADR-213's own Context section for the full corrected reasoning.

6. **Fault-Tolerant CAN's own `_CHx` wiring** (this round), scoped by direct call-site verification against the current tree (not the `design-advisor` consult's own generic 5-family estimate):
   - `j2534-0404/src/lib.rs`: re-export `PROTOCOL_FT_CAN_CH1`/`PROTOCOL_FT_CAN_CH128`/`PROTOCOL_FT_ISO15765_CH1`/`PROTOCOL_FT_ISO15765_CH128` (vendor header: straightforward, `_PS`-id-consistent naming — `PROTOCOL_FT_CAN_CH1..128` at `0x9480`-`0x94FF`, `PROTOCOL_FT_ISO15765_CH1..128` at `0x9500`-`0x957F`, confirmed directly, no naming inconsistency for this family unlike Single Wire CAN's own future round).
   - `resources.rs`: `chx_block_base` gains two entries (`PROTOCOL_FT_CAN_PS => PROTOCOL_FT_CAN_CH1`, `PROTOCOL_FT_ISO15765_PS => PROTOCOL_FT_ISO15765_CH1`); `chx_base_protocol_id`'s `BLOCKS` array widens by 2 (now `[(u32,u32); 15]`, accounting for this round only — Single Wire CAN's own future round widens it further). New `is_ft_family_protocol_id` predicate (`_PS` OR the full `_CH1..128` range for both ids), mirroring `is_j1708_family_protocol_id`'s established shape exactly.
   - `connect_discovery_check` (`resources.rs:2280,2284`) and `bustype_default_name_for_hw_protocol_id` (`resources.rs:1945`): re-key from the narrow `is_ft_protocol_id` to the new `is_ft_family_protocol_id`.
   - `rpc_link.rs`'s `GetResourceStatus`/`GetConflictingResources` query-candidate-matching sites (confirmed directly at `rpc_link.rs:1352` and `:1642`, both currently `is_sw_protocol_id(id)/is_ft_protocol_id(id)` against a raw candidate id — a genuinely new call-site class this round is the first in the series to touch, since none of the 13 closed families needed resource-status query matching re-keyed this way; the same underlying reason UART Echo Byte's ADR-207 needed a `GetResourceStatus` `_CHx`-qualifier-gate widening for its own family, generalized here to a raw-candidate-id match against a family-wide predicate): re-key to `is_ft_family_protocol_id` so a `_CHx`-connected FT link can be found by a raw-id resource-status query the same way a `_PS`-connected one already can.
   - `rpc_link.rs`'s `apply_fd_mode` (`:5521`, `:5596`): re-key the FT-vs-FD-mode rejection guards from `is_ft_protocol_id` to `is_ft_family_protocol_id` — once this round ships, a `_CHx`-connected FT link that somehow reaches this function (a client staging FD ComParams on it) must still be recognized and rejected as FT, not silently treated as plain CAN/ISO15765 and promoted to `FD_CAN_PS`/`FD_ISO15765_PS`. This is `apply_fd_mode`'s own code, but the fix is required by THIS round wiring the new FT `_CHx` shape into existence, not by any change to FD's own logic — CAN FD's own future round (Decision item 5) does not need to revisit this guard again.
   - `names.rs`'s FT arm in `resolve_pin_selection` (`:925`) gains the standard `requested_index.is_some()` bypass every closed family's arm has, landing together with Decision item 3's fix per Context item 2's own masking analysis.
   - `j2534-0404-mock/src/lib.rs`: mirrors the `chx_block_base`-equivalent table widening (2 new entries) and gains a new `is_ft_family_protocol` predicate for the mock's own family-wide call sites (paralleling the service-side split); the narrow `is_ft_protocol`'s own `pins_assigned`-gate call site (`:1663`) stays on the narrow predicate, unchanged, matching every closed family's identical mock-side convention.
   - New regression tests (a new `tests/grpc_mock/fault_tolerant_can.rs` or an addition to wherever this family's existing tests live): raw-`_CH1`-id connect, compound-name connect, `connect_discovery_check`/`bustype_default_name_for_hw_protocol_id` coverage for the `_CHx` case, a `GetResourceStatus`/`GetConflictingResources` query-match test for a `_CHx`-connected link (the new call-site class this round introduces), and a test proving `apply_fd_mode`'s own FT-vs-FD rejection still correctly fires for a `_CHx`-connected FT link (not just the `_PS` case).
   - **`resources::chx_device_info_supported_parameter`/`discovery.rs::check_chx_capacity`** (found by a second Codex automated-review round on this ADR's own implementation, not by the up-front investigation or this ADR's own original drafting): a sibling mechanism to `connect_discovery_check` above, but for clause 7's per-family `_CHx` channel-count cap rather than whether a family is supported at all, with the identical raw-vs-normalized-id hazard `connect_discovery_check`'s own doc comment already names. Fixed the same way: two new guard arms keyed on the raw, pre-normalization id (mirroring `connect_discovery_check`'s own FT arms), checked before the existing 7-family fallback, which itself now normalizes internally. `j2534-0404-mock/src/lib.rs`'s `DEVICE_INFO_FT_CAN_SUPPORTED`/`DEVICE_INFO_FT_ISO15765_SUPPORTED` arms also had to move from the mock's flat, always-supported capability group into the `chx_capacity`-packed group every other capacity-governed family uses, or the mock could never report a nonzero `_CHx` count for this family even after the service-side fix — confirmed by direct reproduction (6 of 9 `fault_tolerant_can.rs` tests failed with the mock unfixed). See `j2534-0404-service/docs/implementation-notes.md`'s Prioritized Backlog entry for this ADR for the full mechanism and the test-discrimination gotcha found along the way.

## Consequences

- `_CHx` Additional Channels now covers 15 of the 18 protocol families once this round ships (correcting this bullet's own earlier "14 of the 18" draft figure to match `j2534-0404-service/docs/implementation-notes.md`'s and `CLAUDE.md`'s already-converged count — Fault-Tolerant CAN and Fault-Tolerant ISO15765 count as two of the fifteen, matching `chx_protocol_id`'s own family-counting convention). The 3 families still remaining out of scope are CAN FD, ISO15765-on-CAN-FD, and Single Wire CAN (this ADR's own Decision items 1/5, each with its own future round), still needing their own dedicated rounds per the reasoning above.
- The shared infrastructure fix (Decision items 2-3) is a strict no-op for every already-shipped family, verified by direct tracing rather than assumed — no regression risk to the 13 closed families' own existing behavior.
- `resources.rs`'s `chx_protocol_id_round_trips_every_in_scope_base_protocol_id_mapping` test (and its mock-side analog, if one exists) does not currently cover any `_PS`-only family (it only exercises the 6 native-base-keyed families from ADR-156's own original scope) — this round's own new unit test for `is_ft_family_protocol_id` plus a dedicated `base_protocol_id`/mock-equivalent round-trip assertion for the FT `_CHx` case is this round's own coverage for the fixed behavior, not an extension of that pre-existing test.
- Single Wire CAN's own future round inherits the infrastructure fix already proven here, plus must independently verify (not assume from this ADR) the exact call-site list for its own larger surface (ComParams/IOCTLs/RxStatus) and its own vendor-naming inconsistency (`PROTOCOL_SW_CAN_CAN_CHx`/`PROTOCOL_SW_CAN_ISO15765_CHx`).
- CAN FD/ISO15765-on-CAN-FD's own future round inherits the infrastructure fix and must resolve the `apply_fd_mode` design question (Decision item 5) as its own first step, independently confirming clause 21.3.2.5.1/22.3.2.6.1's own text rather than trusting this ADR's paraphrase alone.
- `native-mixed-format` interaction (`resources.rs::mixed_format_can_protocol_id`) and `rpc_link.rs`'s own native-mixed-format connect gate (`:3900`, per the `design-advisor` consult's own risk note) were not found to have any FT-specific call site in this round's own direct verification — clause 8.1's native-mixed-format pairing is CAN/ISO15765-only in this codebase's current implementation, with no FT-specific interaction confirmed; flagged here as an accepted residual to revisit only if native-mixed-format is ever extended to Fault-Tolerant CAN specifically, not chased further in this round.
- **Accepted residual, surfaced but not fixed by the second Codex review round (Decision item 6's `chx_device_info_supported_parameter` bullet):** that function covers only 9 of the 15 `_CHx`-in-scope families as of this round (the 7 ADR-156-original families plus Fault-Tolerant CAN) — GM UART, SAE J1939, UART Echo Byte, Honda DIAG-H, SAE J1708, and TP2.0 have no arm, so `check_chx_capacity` silently no-ops (never enforces a channel-count cap) for all six. GM UART's own gap was already a named accepted residual (ADR-189 Decision 5); the other five were not previously documented anywhere. Out of scope for this Fault-Tolerant-CAN-only round; tracked in `j2534-0404-service/docs/implementation-notes.md`'s Prioritized Backlog, most naturally picked up alongside Single Wire CAN's round 2.
  **Update:** Single Wire CAN's own round (ADR-212) closed two more of these six; a later, mechanical extension of the same guard-arm pattern (no new design decision, so no new ADR) closed the remaining five families this bullet named (SAE J1939, UART Echo Byte, Honda DIAG-H, SAE J1708, TP2.0). Only GM UART's own already-separately-accepted residual (ADR-189 Decision 5) remains. See `j2534-0404-service/docs/implementation-notes.md`'s Prioritized Backlog for current status.
