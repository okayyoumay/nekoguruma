## Agent (`crates/agent`)

- **P1**: Write-job journal: nothing records write steps yet, so an interrupted write cannot resume (design 5.5 "journaling of each step", 5.6 `Interrupted -> Writing` transition). Add a minimal on-disk journal in the agent that records each step and the last confirmed block (progress only), and resume from it after restart: a transfer that had started is redone in the order of ADR-229 (VIN and ECU hardware identity read, then the declared safety preconditions, then teardown with ECUReset only if they all hold, otherwise a confirmed session expiry, then VIN and state check, then a full 8.9 precondition check, a replay of the procedure's pre-erase steps, the 8.9 preconditions again, erase and RequestDownload; design 8.2.5). Record the ECU hardware part number, the pre-erase software version, a RequestTransferExit intent marker committed before the request is sent, the post-transfer progress and the per-stage resume count in the journal and in the checkpoint summary sent to the server for handover. Add the session-timeout field, the no-valid-application response (the negative response code that conclusively means no application is present), the retry limit for the recovery version read, the ECU startup time after a reset and the session-confirmation retry window, a required-external-power-supply precondition, and the mapping from the VIN, hardware part number and software version to the procedure's services and response fields that the procedure declares to the IR schema, plus the runtime input that reports whether the supply is connected (`crates/diag-ir/schema/ir.fbs`). Add the server operation that reserves a recovery attempt (atomic per-stage increment checked against the limit, idempotent on the attempt key) to `api/asyncapi.yaml`, with a migration in `db/migrations/` that stores the per-stage counts and the attempt keys, unique on job, stage and key. Done when: a test kills the agent mid-transfer and the restarted agent either redoes the transfer (VIN and ECU hardware identity read, safety preconditions, ECUReset, positive VIN and hardware identity match, state check, 8.9 preconditions, pre-erase steps, 8.9 preconditions again, erase, RequestDownload) and completes, or ends in `OnSiteInterventionRequired`, never in an undefined state, both when it reconnects within `sim-ecu`'s session timer and after it has expired; and a procedure whose `recovery_required_from_step` covers the interrupted step ends in `OnSiteInterventionRequired` without erasing again; a restart where `sim-ecu` stays silent for a while after acknowledging the ECUReset, or whose ECUReset response is lost while it restarts, still confirms the default session and completes; a server reservation whose response is lost is retried under the same attempt key and consumes only one attempt; a restart that takes the passive teardown (for example because the ECU refuses ECUReset), confirms the default session and then completes the transfer; a decoded VIN mismatch aborts before any ECUReset is sent, while a negative response to the VIN read leads to the passive teardown; an ECU whose hardware part number differs from the journal's, or whose hardware identity cannot be read, gets no ECUReset; an ECU that answers the software version read with the procedure's declared no-application response after the erase is still restarted, while a version read that times out, gets another negative response or returns a version that cannot be decoded ends in `OnSiteInterventionRequired` after the retries; a worker crash mid-transfer follows the same restart order; an ECU that refuses the reset or leaves it unanswered and cannot be confirmed back in its default session ends in `OnSiteInterventionRequired`; no ECUReset is sent while a safety precondition fails or cannot be established; the job never proceeds past step 3 without a decoded, matching VIN and hardware identity; a precondition that fails on restart (for example the engine started meanwhile) ends in `OnSiteInterventionRequired` without erasing; repeated handovers stop at the resume limit because each receiving agent increments the per-stage count on the server before recovering; repeated agent crashes during recovery on the same device stop at the resume limit because the count is incremented and committed to the journal before the first request to the ECU; a handover after same-device recoveries counts those attempts, because each was reserved on the server before it started, and a recovery that cannot reach the server before the start deadline passes expires without contacting the ECU; a handover whose summary lacks the RequestTransferExit marker tears down passively without an ECUReset; a crash after RequestTransferExit was sent but before its response was recorded, and any interruption after it was sent but before the procedure's post-transfer steps (such as CheckMemory) completed sends no ECUReset and redoes the transfer, so those steps run in order; an interruption during TransferData of a job that reflashes the already installed version is redone, not skipped; and an interruption after the post-transfer steps completed goes to read-back verification without erasing or another ECUReset; a precondition that already fails at the start of step 4 (for example a disconnected power supply) ends in `OnSiteInterventionRequired` before any programming session or setup step is replayed.
