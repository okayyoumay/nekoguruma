# ADR-221: `vci-service`'s Shared gRPC Listener Gains Bearer-Token Auth and gRPC-Web; `vci-service-manager`'s Proxy Is Removed

**Date:** 2026-09-09
**Status:** Accepted (Decision item 7's route-preservation for `DELETE /vci-libs/{id}/endpoint` superseded by ADR-225, which removes that route entirely; Consequences' native-client-enrollment and unauthenticated-admin-route accepted residuals closed by ADR-226)
**Affects:** `vci-service-launcher` (`vci_server.rs`, `jsonrpc/dispatch.rs`), `vci-service-manager` main (spawn, routing, `InstanceStatus`), `docs/QUICKSTART.md`, `docs/worker-crates.md`, `docs/glossary.md`, `docs/rpc-api-guide.md`, `vci-service-manager/docs/implementation-notes.md`, `docs/adr/ADR-220-vci-service-manager-grpc-endpoint-selection.md`, `docs/adr/INDEX.md`

## Context

`vci-service-manager`'s `ANY /vci-libs/{id}/endpoint` route was meant to be a gRPC/gRPC-Web reverse proxy in front of each spawned service instance. Direct code reading confirms it never worked, for two independent, architectural reasons:

1. It always builds the backend request URI as a hardcoded `http://{endpoint}/` (or `/?{query}` with the query string appended) — it never forwards the actual incoming request path. Generated gRPC clients (tonic) always send an absolute path per RPC (e.g. `/vci.service.VciService/GetModuleIds`); tonic's `Channel`/`Endpoint` has no mechanism to prepend a configured base path (like `/vci-libs/{id}/endpoint`) in front of that. So even a wildcard route capturing trailing path segments would never see a matching request from a standard generated client — **selecting the target instance via a URL path segment is fundamentally incompatible with how generated gRPC clients connect, not a routing bug that can be patched.**
2. Its "gRPC-Web support" is only a `Content-Type` header rewrite (`application/grpc-web*` → `application/grpc`) — no actual wire-format conversion (base64 codec for `application/grpc-web-text`, HTTP/2 trailer ↔ gRPC-Web trailer-frame conversion) is implemented.

Net effect: essentially no RPC call has ever worked through this proxy, for any client. (ADR-220 separately shows the proxy's own target address was never even correctly derived until recently, so it is plausible this mechanism has never been exercised successfully end to end.)

All three service binaries (`iso22900-service`, `j2534-0404-service`, `j2534-0500-service`) build their gRPC listener through **one shared code path** — `vci_service_launcher::start_service` → `vci_server.rs`'s `Server::builder().add_service(VciServiceServer::new(service)).serve(...)`. Per ADR-052, this listener is always bound to loopback only (`127.0.0.1`/`[::1]`, never non-local) and has zero authentication today. Each instance's actual `SocketAddr` (not merely a port — ADR-052 supports IPv6-only hosts) is already discoverable via `GET /vci-libs/{id}` (route later split into `GET /vci-libs/{id}/instance` by ADR-225), per ADR-220.

Operational assumptions established separately with the user (recorded in `vci-service-manager/docs/WEB_API_IMPROVEMENT_PLAN.md` items 2 and 12 pending this ADR's close-out of both) and taken as given here:

- `vci-service` (manager and every `-service` process) is never exposed to a remote machine. Remote diagnostic access, if ever needed, is a separate SOVD-compliant service's responsibility, not this workspace's.
- Local processes on the same machine are **not** trusted, even though the legitimate client set (a SOVD service, plus an open-ended set of other local services) runs under the same OS user as the manager. Because of this, OS-level isolation (Unix domain socket file permissions, named-pipe ACLs) is not an effective defense — a same-user attacker process has identical access to those mechanisms as a legitimate client.
- The primary threat to defend against is a malicious **browser page** reaching the loopback-bound listeners — ordinary browsers do not special-case loopback addresses, so any open tab can issue `fetch()`/blind-POST requests against `127.0.0.1:PORT`.
- Given the same-OS-user threat model, the only effective control is cryptographic authentication at the listener itself, with credentials issued/held so a same-user attacker process cannot trivially read them from disk/environment.

Two architectures were considered for both fixing the proxy's defect and adding the now-required auth enforcement point (full analysis: `design-advisor` consult, this PR):

- **案A (manager-centralized proxy):** rebuild `proxy_to_instance` as a real streaming L7 reverse proxy with a working instance-selection mechanism (e.g. a metadata header) and a hand-rolled gRPC-Web wire-format codec, plus a step that verifies the client's credential and substitutes the manager↔service spawn-time credential before forwarding downstream. This is three previously-unbuilt subsystems, in code that has never worked end to end, funneled through one process for every RPC.
- **案B (shared per-service listener gets auth + gRPC-Web directly):** add a bearer-token auth interceptor and gRPC-Web support directly to the one shared `vci_server.rs` listener-construction code; clients (native and browser) connect **directly** to each instance's own `SocketAddr` (ADR-220), bypassing the manager for RPC traffic entirely. The manager remains responsible only for discovery/start/stop and for minting the bearer tokens clients present to the service listener.

## Decision

Adopt **案B**, with one addition that removes its only real drawback (revocation): the credential is a **per-instance HMAC-SHA256 key**, generated by the manager at spawn time and pushed to the child over the already-private stdio JSON-RPC channel — never handed to any client. The manager mints short-lived bearer tokens from that key on request; the child verifies tokens itself using the same key. Re-sending the key (or stopping the instance) revokes every outstanding token for that instance immediately, so 案B's usual "no centralized revocation" cost does not apply here.

`proxy_to_instance`, `format_proxy_url`, `InstanceStatus.proxy_url`, the manager's `proxy_client`, and the `hyper`/`hyper-util`/`http-body-util` dependencies they required are removed outright — not deprecated, not kept as a fallback.

### Mechanism

`vci-service-launcher`:

1. New `vci_server::auth` module: a token is `vci1.<base64url(payload)>.<base64url(HMAC-SHA256(key, payload))>`, where `payload` is JSON `{"exp": <unix_secs>, "iat": <unix_secs>, "sub": "<opaque client label>"}`. Verification splits the token, checks the MAC in constant time, then checks `exp > now`. A missing key (before the manager's first `set_auth_key` call) fails closed with `UNAUTHENTICATED` — the listener never serves an unauthenticated RPC once this ships.
2. `vci_server.rs`'s `Server::builder()` call gains, in this order: an outer `tower_http::cors::CorsLayer` (must answer `OPTIONS` preflight before any auth check runs), a `tonic_web::GrpcWebLayer` (`accept_http1(true)` is required alongside it for browser/HTTP-1.1 traffic), and the service itself registered via `VciServiceServer::with_interceptor(service, verify_auth)` so every RPC — native or gRPC-Web — passes through the same bearer-token check. CORS uses an explicit allowed-headers list (`authorization`, `content-type`, `x-grpc-web`, `x-user-agent`, `grpc-timeout`) and exposed-headers list (`grpc-status`, `grpc-message`, `grpc-status-details-bin`) rather than `tonic-web`'s own bundled permissive default, so the actual header contract is visible in this workspace's own code rather than a dependency's default.
3. `JsonRpcHandler` gains a `set_auth_key` method (`jsonrpc/dispatch.rs`'s method-dispatch match), taking `{"key": "<base64 32 bytes>"}` and replacing any previously-installed key outright — this is both the initial provisioning call and the revocation mechanism (a new key invalidates every token minted against the old one).
4. A `#[cfg(debug_assertions)]`-only environment override (`VCI_SERVICE_INSECURE_NO_AUTH=1`) bypasses the interceptor for direct, manager-less dev runs (`docs/QUICKSTART.md`'s existing "run a service binary standalone" path) — compiled out of release builds, mirroring ADR-073's existing debug-only environment-variable pattern.

`vci-service-manager`:

5. `spawn_instance` generates 32 random bytes and sends them via `set_auth_key` immediately after spawn, before the first `get_status` poll — startup fails if this call errors, since an instance the manager cannot authenticate to is not usable.
6. `POST /vci-libs/{id}/token` mints a token (fixed 10-minute TTL, not yet configurable) from the stored per-instance key and returns it alongside the endpoint address the client needs to connect to (`{token, expires_at_ms, grpc_endpoint}`).
7. `ANY /vci-libs/{id}/endpoint`, `proxy_to_instance`, `proxy_client`, `format_proxy_url`, and `InstanceStatus.proxy_url` are deleted. `DELETE /vci-libs/{id}/endpoint` (stop) is preserved as its own route now that it no longer shares a path with the removed proxy. **Superseded by ADR-225:** once the instance-scoped operations were later split onto their own `/vci-libs/{id}/instance` sub-resource, `/vci-libs/{id}/endpoint` had nothing left to preserve — ADR-225 removes the route entirely rather than keeping it as `DELETE`'s home.
8. A `Host`-header allowlist middleware is added across the whole manager router, rejecting any request whose `Host` is not a loopback literal (`localhost`, `127.0.0.1`, `[::1]`) matching the bound port. This closes a DNS-rebinding gap the design-advisor consult identified in this same design: without it, a page served from an attacker-controlled domain rebound to `127.0.0.1` could still reach the manager same-origin, read a minted token from the (currently CORS-unrestricted-by-design) `/token` response, and use it against a service listener — defeating the rest of this mechanism. With the allowlist in place, a cross-origin page can neither obtain a token from the manager nor call a service directly.

### Scope boundary

This PR delivers a fail-closed listener for every current and future `vci-service` binary, and blocks the confirmed primary threat (an arbitrary browser page) end to end. It explicitly does **not** design who is allowed to call `POST /vci-libs/{id}/token` in the first place — that is native-client enrollment (which local processes are legitimate clients at all) and the browser bootstrap-token exchange (how a browser tab acquires a token without ever exposing a long-lived credential to the page). Both were already flagged, independently of this ADR, as unresolved design questions needing their own dedicated ADR effort (`WEB_API_IMPROVEMENT_PLAN.md`'s "資格情報配布方式の設計" section, items 2 and 3): enrollment needs an attacker-unforgeable trust root (e.g. human-approval consent), and the browser bootstrap flow has an unresolved race between a native client handing a bootstrap code to a freshly-launched browser and another same-OS-user process reading that code off the browser's command line before the legitimate exchange completes. Neither can be soundly designed as a side effect of this PR; both are recorded as open backlog items instead (see Consequences). **Update (ADR-226):** native-client enrollment is now designed and shipped by ADR-226 (a peer-identity trust root over a local IPC listener, gating manager-minted session tokens); the browser bootstrap-token exchange remains the one item still open.

The manager's own REST management routes (`GET/POST/DELETE /vci-libs/{id}/instance`, per ADR-225's later route split — start/stop) remain unauthenticated in this PR — a same-machine untrusted process (not a browser, since the manager sets no permissive CORS on these routes and now enforces the Host allowlist) could still issue blind start/stop requests. This is a pre-existing gap (`WEB_API_IMPROVEMENT_PLAN.md` item 2's CSRF analysis), independent of the proxy fix this ADR makes, and is left open rather than folded in here. **Closed by ADR-226**, which gates every such route behind a manager-minted session token.

## Consequences

- Every `vci-service` gRPC listener is fail-closed by default (`UNAUTHENTICATED` with no key installed) the moment this ships, for all three current binaries and any future one that reuses `vci_service_launcher::start_service` — the auth and gRPC-Web mechanisms are added once, in shared code, not per service.
- `vci-service-manager` no longer proxies gRPC/gRPC-Web traffic at all; native and browser clients connect directly to the `SocketAddr` `GET /vci-libs/{id}` reports (ADR-220; route later split to `GET /vci-libs/{id}/instance` by ADR-225), presenting a bearer token minted by `POST /vci-libs/{id}/token`. `docs/QUICKSTART.md`'s client-connection instructions, `docs/worker-crates.md`'s architecture description, and `docs/glossary.md`'s gRPC-Web description all change accordingly (same PR, per CLAUDE.md's doc-sync rule).
- `InstanceStatus.proxy_url` and the `[config.manager].base_url` setting it depended on are removed from the manager's public REST surface — a client-visible, breaking change, but one with no in-repo consumer (confirmed by ADR-220's own repo-wide grep) and with `docs/QUICKSTART.md`'s already-nonfunctional example being the only documented user.
- Credential revocation is effectively immediate and per-instance: re-sending `set_auth_key` (or stopping the instance) invalidates every outstanding token for that instance without needing a central token-revocation list.
- **Accepted residual, tracked as open backlog items in `vci-service-manager/docs/implementation-notes.md` (not fixed here):**
  - The browser bootstrap-token exchange (how a browser tab acquires a token without it ever becoming a long-lived, URL-visible credential) is undesigned, including the identified command-line race between a native client launching a browser with a bootstrap code and another same-OS-user process reading it first.
  - A `SubscribeEvent` stream already in progress when its token expires or its instance's key is rotated is not itself torn down — the only current revocation lever for a live stream is stopping the instance outright.
  - This mechanism does not defend against a same-OS-user attacker capable of `ptrace`-style process/memory inspection (the manager↔service key transits stdio and is held in both processes' memory); it defends against the confirmed primary threat, an ordinary browser page, which has no such capability.
- ADR-220's own text (which still describes `proxy_to_instance` as this workspace's client-facing gRPC entry point) is corrected to reflect that the proxy no longer exists and clients connect directly to the reported endpoint.
