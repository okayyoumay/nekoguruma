# ADR-080: `shared_channels` Is the Outermost Lock of the Three-Mutex Hierarchy

**Date:** 2026-07-12
**Status:** Accepted
**Affects:** `j2534-0404-service/src/service/rpc_misc.rs` (`ioctl_start_msg_filter`, `ioctl_clear_tx_queue`, `rpc_io_ctl_legacy`'s `CLEAR_MSG_FILTERS` arm), `j2534-0404-service/src/service/rpc_link.rs` (`rpc_connect_com_logical_link`, `rpc_disconnect_com_logical_link`, `rpc_destroy_com_logical_link`, `ensure_uudt_companion_channel`), `j2534-0404-service/src/service/rpc_primitive.rs`, `j2534-0404-service/src/service/events.rs`

> **Note (ADR-122):** `sync_channel_fc_pass_all_filter`, cited below as
> historical precedent for holding `shared_channels` across a nested `api`
> call, has since been removed entirely (the zero-mask pass-all fallback it
> managed was spec-non-conformant). The lock-hierarchy rule this ADR
> establishes is unaffected — it is independently exemplified by every other
> call site still listed above.

## Context

`J2534Service` guards its state with three independent `tokio::sync::Mutex`es: `shared_channels` (per-physical-channel `SharedChannel` records, including `ref_count`), `logical_links` (per-CLL `LogicalLinkState`, including `client_filters`), and `api` (the J2534 DLL wrapper, serializing all hardware calls).

Two Codex-review fixes on PR #80 each independently added a check-then-act sequence meant to keep one CLL's client-installed message filter (`PDU_IOCTL_START_MSG_FILTER`) from silently affecting a sibling CLL sharing the same physical channel:

- `ioctl_start_msg_filter` (`rpc_misc.rs`) rejects installing a filter when its CLL's channel already has `ref_count > 1`.
- `rpc_connect_com_logical_link` (`rpc_link.rs`) rejects a second CLL joining a channel that already has a non-empty `client_filters` on any of its current CLLs.

Individually these are correct, but a further Codex review found they were not atomic *with respect to each other*: `ioctl_start_msg_filter` read `ref_count` under a briefly-held `shared_channels` lock, released it, then did the hardware `PassThruStartMsgFilter` call and the `client_filters` write much later under separate `api`/`logical_links` locks. In the window between the `ref_count` read and the `client_filters` write, a concurrent `ConnectComLogicalLink` could see `client_filters` still empty, pass its own check, and join the channel — after which `ioctl_start_msg_filter` would go on to install a (possibly `BLOCK_FILTER`) filter on what had, unbeknownst to it, just become a shared channel.

Closing this required either a new synchronization primitive or reusing an existing lock as the single source of truth across both handlers. No ADR previously documented an acquisition order for these three mutexes — each call site picked one independently.

## Decision

**`shared_channels` is the outermost lock whenever more than one of the three is held.** `logical_links` and `api` may be acquired (and must be released) underneath a held `shared_channels` guard, but `shared_channels` must never be acquired while `api` or `logical_links` is already held. This was verified to be the order every existing call site in the crate already follows — `rpc_connect_com_logical_link` already holds `shared_channels` across its whole check-create-insert sequence (including a nested `logical_links` read and, via `connect_new_physical_channel`/`spawn_new_shared_channel`, a nested `api` call), and `sync_channel_fc_pass_all_filter` already holds `shared_channels` across a nested `api` hardware filter install/stop. No reverse-order site (`api` or `logical_links` held, then `shared_channels` acquired) exists anywhere in `j2534-0404-service/src/service/*.rs`, including the poll task in `events.rs`, which never touches `shared_channels` at all. (This last clause is now stale in its literal form — ADR-123 Finding I is what first gave the poll task's own `handle_channel_hard_error` a `shared_channels` acquisition; ADR-139 later widened that already-existing acquisition's scope to also stay held across its per-CLL `cancel_link_cops` sweep; and, per ADR-193's round-16 amendment, that acquisition now nests an `api` fence acquisition too. Nor is `handle_channel_hard_error` the poll task's only `shared_channels` touchpoint — `events.rs` acquires `shared_channels` at multiple other locations throughout the poll task, not just this one function. But the ordering claim this clause supports still holds at every one of those sites: each is the sanctioned `shared_channels`-outermost shape this ADR describes, not a reverse-order violation.)

`ioctl_start_msg_filter` now follows this hierarchy explicitly: it acquires `shared_channels` once, before the `ref_count` check, and holds it continuously through the ISO15765/`LOCK_PHYSICAL_COM_PARAMS`/duplicate-`FilterNumber` checks (each of which briefly acquires `logical_links` underneath), the hardware `PassThruStartMsgFilter` install loop (which acquires `api` underneath), and the final `client_filters` write (`logical_links` again) — releasing it only when the function returns. This makes it mutually exclusive with `rpc_connect_com_logical_link`'s own `shared_channels`-held check-and-join sequence: whichever handler acquires `shared_channels` first completes its entire check-then-act atomically before the other can proceed, so neither can observe stale state.

A follow-up Codex review found the same gap on the *teardown* side: `rpc_disconnect_com_logical_link` and `rpc_destroy_com_logical_link` each drained/removed a CLL's `client_filters` (making it invisible to a racing joiner's reciprocal check) under only a briefly-held `logical_links` guard, then separately re-acquired `shared_channels` much later just for the `ref_count` decrement — the same shape of gap, in the opposite direction (a joiner could slip in believing the channel is now unfiltered, before the hardware filter is actually stopped or before `ref_count` reflects the departure). Both now acquire `shared_channels` first and hold it continuously from before the `client_filters` drain (`rpc_disconnect_com_logical_link`) or the CLL's removal from `logical_links` (`rpc_destroy_com_logical_link`) through the hardware `stop_message_filter` calls and the `ref_count` decrement, dropping it only afterward before any subsequent `PassThruDisconnect`/`stop_periodic_message` call (which no longer needs it once `ref_count`/channel removal is resolved). `ensure_uudt_companion_channel`'s reciprocal join guard (added in the same review round as `rpc_connect_com_logical_link`'s) already followed this hierarchy from the start, being a single check-then-bump under one continuously-held `shared_channels` guard.

A third follow-up Codex review found the legacy raw `CLEAR_MSG_FILTERS` IOCTL arm (`rpc_io_ctl_legacy`, `rpc_misc.rs`) had the same gap from a different angle: it neither reads nor writes `ref_count`, but its hardware `PassThruIoctl CLEAR_MSG_FILTERS` call plus its `client_filters` purge (added to reconcile the legacy channel-wide clear with the newer per-CLL `client_filters` bookkeeping) were not synchronized with `ioctl_start_msg_filter`'s own `shared_channels`-held install-then-record sequence at all. This let the legacy clear interleave *inside* a concurrent `ioctl_start_msg_filter` call: the hardware clear (and this arm's purge, which found nothing to purge yet) could run after `START_MSG_FILTER` successfully installed a filter on hardware but before it had recorded the filter_id in `client_filters`, so `START_MSG_FILTER` went on to record a filter_id that no longer existed on hardware. This arm now also acquires `shared_channels` before the hardware clear and holds it through the `client_filters` purge, dropping it before its separate, independent re-installation of the pass-all/ISO15765 filters afterward (which already re-acquires `shared_channels` on its own for a different reason, reading `connect_flags`).

## Consequences

- No lock-order inversion is introduced: this fix only makes an already-universal order explicit and enforces it in more call sites.
- `ioctl_start_msg_filter`'s critical section is now wider — it holds `shared_channels` across a hardware FFI call (`PassThruStartMsgFilter`) — serializing all `shared_channels` users (connect, disconnect, TX-queue lookups, COP-status checks) for that duration. This is correctness-neutral and already precedented by `sync_channel_fc_pass_all_filter`. The same applies to `rpc_disconnect_com_logical_link`/`rpc_destroy_com_logical_link`'s now-wider critical section around their filter-stop calls.
- **Any future code that acquires `api` or `logical_links` and then tries to acquire `shared_channels` violates this hierarchy and risks deadlock.** A quick audit for this is `rg 'shared_channels\.lock' j2534-0404-service/src/service` followed by confirming each call site's `shared_channels` guard is acquired before, not after, any `api`/`logical_links` guard already held in the same call stack.
- This ADR does not introduce a new mutex; it documents and enforces an order that was already implicit and consistent everywhere else, now extended to every check-then-act sequence that touches both `client_filters` and `ref_count`/channel membership.
