## 1. Current State (baseline this plan builds on)

See `docs/j2534-0404-architecture.md` for the live description of the J2534 v04.04 subsystem's layers and its current "Out of Scope" list — now just J2534 v05.00+ (a separate crate), DoIP, and the K-line 5-baud-vs-fast-init auto-detection gap. ADR-017 previously made everything outside the J2534-1 protocol list explicit *out-of-scope* (now superseded by ADR-152, Phase 0 — see §3).

**DoIP (ISO 13400) is not covered**: none of J2534-2's 20 feature areas define a DoIP protocol; Phase 16's `ETHERNET_NDIS` only binds a raw NDIS/RNDIS Ethernet adapter, adjacent infrastructure a future DoIP implementation could build on, not DoIP message-level support itself (checked for overlap with any separately-planned DoIP work before investing there — the check came back negative, per ADR-194).

One piece of J2534-2 predates this plan: ADR-062 adopted J2534-2's clarified `TxFlags` bit-table *definition* (which bits mean what) to fix a J2534-1-era ambiguity — a documentation/interpretation fix, not new protocol support.

## 2. What SAE J2534-2 adds

J2534-2 (DEC2020) is an addendum: unless a clause says otherwise, everything in J2534-1 v04.04 continues to apply unmodified (§1.2). It defines **20 independent, individually opt-in optional feature areas** (clauses 6–25), plus a consolidated value-table appendix (clause 26) and a feature-enablement convention (clause 5).

### 2.1 Feature-enablement convention (clause 5)

A DLL only exposes J2534-2 behavior if the caller's `PassThruOpen` `pName` argument is a NULL-terminated string beginning with the literal prefix `"J2534-2:"` (optionally followed by a vendor-specific device name, to select among multiple attached devices). `pName == NULL` means J2534-1-only behavior must be assumed; any other non-NULL, non-`"J2534-2:"`-prefixed value has no defined meaning per the spec.

### 2.2 Capability discovery (clause 25, value tables in 26.7–26.8)

Two `PassThruIoctl` calls, `GET_DEVICE_INFO` (device-wide capabilities, keyed by `DeviceID`) and `GET_PROTOCOL_INFO` (per-protocol limits, keyed by `DeviceID` + protocol), let an application query support parameter-by-parameter (each reports its own `Supported`/`NOT_SUPPORTED` flag — there is no single aggregate "J2534-2 version" number). Clause 5 treats implementing both, fully, as the closest thing the spec has to a blanket "is this device J2534-2-compliant" gate. Legacy per-feature Windows registry keys (referenced in clauses 10.4.3, 11.5, 24.4) are documented as retained only for older applications; new applications are expected to use this discovery mechanism instead.

## 3. Governance impact

- **ADR-017 has been superseded**, not edited in place, per the ADR supersession rule (`docs/adr/TEMPLATE.md`): [ADR-152](adr/ADR-152-j2534-2-foundational-decisions.md) (Phase 0) is the superseding ADR, and is where most of the cross-cutting design questions in §4 below were recorded (items 2/3/5/6, marked "RESOLVED by ADR-152"). - ADRs that establish extension points this plan will exercise repeatedly, and should be read (not necessarily amended) before touching their area: **ADR-023** (`ChannelProtocol` abstraction — a phase introducing a genuinely new D-PDU protocol needs a variant, per §5 step 3's conditions), **ADR-069** (D-PDU resource-ID table — same condition as ADR-023, plus the D-PDU-side mapping must be freshly established for whatever protocol a new phase covers, see §4.4), **ADR-027**/**ADR-028** (ComParam ID / native CONFIG ID separation and per-protocol support table — only a phase adding a genuine channel/protocol-scoped `SCONFIG` param with a D-PDU ComParam equivalent needs entries, per §5 step 5), **ADR-079** (`GetObjectId` IOCTL name table — every new IOCTL needs a name mapping if exposed the same way), **ADR-107**/**ADR-131**/**ADR-132** (module lifecycle — the discovery mechanism and device-config IOCTLs are `DeviceID`-scoped like these), **ADR-062** (existing J2534-2 TxFlags precedent).
- `docs/j2534-0404-architecture.md` §8 "Out of Scope" and `ADR-017`'s Consequences section both explicitly point forward to "a future revision that targets J2534-2" — this document is that pointer's target; §7 below cross-links them.

## 4. Design questions raised at plan time (resolution status per item)

These were identified at plan time as cross-cutting decisions affecting every phase below, intended to belong in one ADR written at Phase 0 rather than being re-litigated per phase. That intent held for items 2/3/5/6 (each marked "RESOLVED by ADR-152" below); it did not for items 1 and 4 — see each item's own text for what actually happened:

1. **Feature-enablement plumbing.** This was already solved before Phase 0, not new work: each configured module's `pname` (`vci_service_launcher::config::ModuleConfigEntry`, ADR-107) is converted to a `CString` once at startup and passed verbatim as `PassThruOpen`'s `pName` argument (`j2534-0404-service/src/config.rs` -> `j2534-0404`'s `PassThru::open`). Setting `pname = "J2534-2:<device>"` on a `modules` entry already expresses both the opt-in and the optional device name — no new `config.toml` key or wrapper path was needed. [ADR-152](adr/ADR-152-j2534-2-foundational-decisions.md)'s Context section records this explicitly, but its own Decision only resolves §4.2/§4.3/§4.5/§4.6 (see ADR-152's Context) — it does not decide this question's two secondary parts. Those remain genuinely open, confirmed unaddressed in the current code (`config.rs` has no `"J2534-2:"` prefix validation at config-load time, so the shipped behavior is "accept any `pname` value as-is" by omission, not by decision): whether to validate the prefix format at config-load time, and how a `pname` that *doesn't* start with that prefix should be treated now that clause 5's "no assumption can be made" case applies to it. Not blocking to any shipped phase — every phase's own `pname` opt-in reads correctly regardless.
2. **Graceful degradation. RESOLVED by [ADR-152](adr/ADR-152-j2534-2-foundational-decisions.md) Decision 1.** Advertising stays static (`pname` `"J2534-2:"` opt-in only), never gated by Discovery; device capability is enforced at `ConnectComLogicalLink` time instead, refined by the Discovery cache once Phase 1 exists.
3. **`DeviceID`- vs `ChannelID`-scoped IOCTLs. RESOLVED by [ADR-152](adr/ADR-152-j2534-2-foundational-decisions.md) Decision 2.** Device-scoped J2534-2 commands (`GET_DEVICE_CONFIG`/`SET_DEVICE_CONFIG`, etc.) ride the existing `IoCtl` RPC as module-scoped commands, no new RPC; `GET_DEVICE_INFO`/`GET_PROTOCOL_INFO` stay internal-only (kept by [ADR-153](adr/ADR-153-j2534-2-discovery-mechanism-phase1.md) Decision 3, rather than exposed as a new client-visible IOCTL pair).
4. **D-PDU-side mapping was an open unknown at plan time — resolved per-phase, not by one central answer.** ADR-069's resource-ID table and the ComParam surface are shaped by ISO 22900-2, not raw J2534, and whether ISO 22900-2 already defines a resource-ID/ComParam equivalent for a given J2534-2 protocol varies case by case — this plan deliberately deferred that research to each protocol phase's own ADR (§5 step 4) rather than doing one upfront survey across both ISO 22900-2 editions. That per-phase research is now complete for every shipped phase, and landed in one of three distinct outcomes depending on what ISO 22900-2 actually offered: ADR-164 (SWCAN) and ADR-179 (J1939) found ISO 22900-2 equivalents and extended the resource/ComParam tables directly; ADR-188 (TP2.0) found none and added a standalone `ChannelProtocol` identity instead (the same outcome UART Echo Byte, Honda DIAG-H, J1708, GM UART, Ethernet_NDIS, and Analog Inputs each reached independently); and ADR-158/159 (CAN FD family) found neither a resource nor a reason to add a new identity — clause 21/22 define no unqualified base `ProtocolID`, so FD-ness is inferred purely from staged Working ComParams at `ConnectComLogicalLink` time by substituting `LogicalLinkState::hw_protocol_id`/`base_hw_protocol_override` on the *existing* `CAN`/`ISO15765` identity, with no new resource-table row or `ChannelProtocol` variant at all. No phase remains that still needs this research done.
5. **Conformance claims. RESOLVED by [ADR-152](adr/ADR-152-j2534-2-foundational-decisions.md).** Conformance is claimed only per implemented feature area, never a blanket "J2534-2 compliant" claim, further bounded by the attached device's own capabilities.
6. **Mock fidelity. RESOLVED by [ADR-152](adr/ADR-152-j2534-2-foundational-decisions.md).** Confirmed phase-by-phase, not an upfront rewrite; the mock's rejection of not-yet-implemented J2534-2 IDs is deliberate and spec-shaped (`ERR_INVALID_IOCTL_ID`/`ERR_INVALID_PROTOCOL_ID`).

## 5. Per-phase execution checklist (applies to every phase in §6)

1. Confirm that no partial/duplicate implementation already exists for the phase's area.
2. Header/binding constants: added once, up front, in Phase 0 (see rationale in §6, Phase 0) — later phases reference existing constants rather than re-touching `j2534-0404-sys`, unless a phase's structs require it (flagged where relevant).
3. **Only if the phase's protocol needs its own distinct D-PDU protocol identity** — either because ISO 22900-2 already defines one to map onto directly, or because design question 4's per-phase research (step 4 below) finds no equivalent and a standalone identity is the design-approved resolution (the outcome TP2.0, UART Echo Byte, Honda DIAG-H, J1708, GM UART, Ethernet_NDIS, and Analog Inputs each independently reached — see §4 item 4) — excludes Phase 1 Discovery, Phase 12 Repeat Messaging, Phase 13 Programming/Pin Voltage, and Phase 14 Device Configuration (those four add IOCTLs/behavior against existing channels or `DeviceID`, not a new protocol), **and excludes Phase 2** (Pin Selection/Additional Channels: `_PS`/`_CHx` are hardware/connector-selection concerns, not distinct D-PDU application protocols — see Phase 2's own roadmap entry in §6 for why this doesn't automatically mean a new `ChannelProtocol` per variant; the qualifier-representation mechanism itself was resolved by ADR-156's arithmetic `_CHx` mapping, later re-expressed by ADR-178's interface freeze as direct `ResourceData.protocol_id` naming with a compound-name grammar for SAE J2610 SCI — see §7's "Interface freeze retrofit" entry): extend `ChannelProtocol` + `j2534_protocol_id()` (ADR-023).
4. **Same condition as step 3:** extend the D-PDU resource-ID table (ADR-069) — **only after** resolving design question §4.4 for this protocol family; if no ISO 22900-2 equivalent is documented, settle the spec interpretation in an ADR before inventing a table row.
5. **Only if the phase adds a genuine channel/protocol-scoped `SCONFIG` (`GET_CONFIG`/`SET_CONFIG`) parameter with a D-PDU ComParam equivalent:** extend the ComParam ID space and per-protocol support table (ADR-027/ADR-028); update `comparam-protocol-support.md`. This is narrower than step 3's exception list: Phase 13's programming/pin-voltage work is `PassThruSetProgrammingVoltage`/IOCTL data, not `SCONFIG`, and Phase 14's `NON_VOLATILE_STORE_*` values ride the separate, device-scoped `GET_DEVICE_CONFIG`/`SET_DEVICE_CONFIG` IOCTL pair (§2.3's item 13) — `ComParamId`/ADR-028 exist specifically to translate D-PDU ComParams onto channel/protocol-scoped `SCONFIG`, so neither belongs in that table; both instead go through step 6's IOCTL work on their own path — the existing `IoCtl` RPC, module-scoped, per design question §4.3's resolution (ADR-152).
6. **Only if the phase adds a new IOCTL** (per §2.3's "New IOCTL(s)" column — Phase 2, Phase 3's three feature areas, Phase 6, Phases 9–11, and Phase 15 add none): resolve the D-PDU-side mapping first (same prerequisite as steps 4–5, tracked under design question §4.4) before implementing anything. `PDU_IOCTL_*` is a curated, adapter-private D-PDU command namespace (`service_params.rs`'s `PDU_IOCTL_BASE` block — 17 values at plan time, 28 as of Phase 16/ADR-194; check that file directly for the current count and next-free offset before minting a new one, rather than trusting either number here) that only aliases 4 legacy raw J2534 IOCTLs — it is not a passthrough for arbitrary new J2534-2 IOCTL IDs, so a new raw IOCTL like `SW_CAN_HS` or `PROTECT_J1939_ADDR` does not automatically become a new `rpc_misc.rs` handler with a client-visible `PDU_IOCTL_*` name; it may instead need to be invoked internally (e.g. behind a ComParam or an implicit protocol operation), depending on how ISO 22900-2 actually models that capability. When a capability does need a new client-visible D-PDU command, it rides the existing `IoCtl` RPC as a module- or CLL-scoped command per design question §4.3's resolution (ADR-152) — never a new RPC. A phase with no new IOCTL implements its behavior entirely through `PassThruConnect`/`SET_CONFIG`/message-construction changes instead (steps 3–5 and the wrapper/message-handling code directly).
7. **Never grows `vci-service-interface/src/proto/service.proto`.** Per [ADR-178](adr/ADR-178-freeze-j2534-2-dpdu-interface.md), a new protocol capability is represented entirely through mechanisms that already existed in the proto file at commit `8a76116` — no new `.proto` message or field, ever, even where step 5 or step 6 above would otherwise reach for one: a scalar or a native id/value-pair-list-shaped (`SCONFIG_LIST`-shaped) capability is represented as a ComParam (per step 5, minting a fresh id when genuinely native-only, following ADR-178's naming/id-range convention); a heterogeneous or byte-blob-shaped native structure is represented via the existing `DataItem.bytearray_data` (`IOBytearray`) carrier, with a documented internal byte-layout table added to `docs/rpc-api-guide.md`. A phase whose capability doesn't fit either shape is settled by a design decision (ADR) per ADR-178's own Consequences note rather than adding proto surface as a default — TP2.0's connection-oriented lifecycle (Phase 7) was the case this note anticipated needing genuinely new RPC-level semantics, but resolved without any: `REQUEST_CONNECTION`/`TEARDOWN_CONNECTION` are invoked internally from the existing `PDU_COPT_STARTCOMM`/`PDU_COPT_STOPCOMM` verbs (see Phase 7 Stage 7a's own §7 entry).
8. Extend `j2534-0404-mock` to simulate the new protocol/IOCTL behavior for tests.
9. Add integration tests (mock-backed, per existing `j2534-0404-service` test conventions).
10. Update the affected documents in the same change.
11. Review edge cases explicitly, since every phase touches FFI/protocol semantics or spans multiple crates.
12. Write a phase-specific ADR for any non-obvious decision beyond what the superseding ADR already settled (J1939 address-claiming and TP2.0 connection lifecycle are expected to need their own ADRs; simpler phases may not).


## 6. Phased roadmap

Phasing rationale: Phase 0 (constants) is a prerequisite for every later phase. Phase 1 (capability discovery) is a prerequisite for every phase except Repeat Messaging (12), Programming/Pin Voltage (13), and Analog Inputs (15) — those three phases' "Depends on" entries below list only Phase 0, so they can start without waiting on Discovery. Phase 2 (Pin Selection / Additional Channels) is a prerequisite for every subsequent protocol phase whose `ProtocolID`s are defined as `_PS` variants — which, per the feature table in §2.3, is every new protocol **except** Analog Inputs (`ANALOG_IN_1`..`32`, enumerated directly rather than pin-selected or `_CHx`-extended) and Ethernet_NDIS (bound to an NDIS adapter, not a pinned physical connector); those two phases' "Depends on" entries below reflect that exception. Phases 3+ are ordered by (a) how much they reuse infrastructure this subsystem already has (CAN-family work reuses ADR-046/047's dual-channel/software-ISO-TP machinery) and (b) real-world diagnostic value for a UDS-oriented gateway. This ordering is a recommendation, not a hard commitment — re-sequencing later phases (e.g. pulling Repeat Messaging earlier, since it has no protocol dependency) is fine as priorities become clearer.

## 8. Open risks (not blocking the plan, but should inform sequencing)

- **D-PDU mapping was the single biggest unknown affecting every protocol phase's resource-table work** (§4.4) — resolved per-phase as anticipated, not up front; every shipped phase completed its own instance of this research (see §4.4 and each phase's §7 entry for its specific finding). No longer an open risk for any of the 20 shipped feature areas; the same per-phase research step would apply again to any future new phase (e.g. a v05.00 addendum).
- **v04.04 vs v05.00 error-code drift** (§2, caveat under "New error codes") — re-verify if/when a v05.00 spec copy becomes available.
- **Real hardware availability** — SWCAN, GM UART, Honda DIAG-H, TP2.0, and J1939 are vendor/OEM-specific; without physical test hardware, correctness rests on mock fidelity (§5, step 7) and careful re-reading of the spec, not live-hardware validation. Flag this explicitly in each phase's `implementation-notes.md` update.
