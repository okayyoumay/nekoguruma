# ADR-220: `vci-service-manager` Conforms to the `endpoints`-Based `get_status` Contract (Fixes the Always-Fails Real-Instance Startup Bug)

**Date:** 2026-09-08
**Status:** Accepted (Decision item 5's `proxy_to_instance` mechanism removed by ADR-221 — the manager no longer proxies gRPC traffic at all; clients connect directly to `grpc_endpoint`. Items 1-4/6-8, the `endpoints`-selection contract itself, remain in force.)
**Affects:** `vci-service-manager` main (`ManagedInstance`/`InstanceStatus`/`wait_until_running`/`read_instance_status`/`proxy_to_instance`), `vci-service-manager/docs/implementation-notes.md`, `iso22900-service/docs/grpc-instance-spec.md`, `docs/adr/INDEX.md`

## Context

`vci-service-manager` spawns each of `iso22900-service`/`j2534-0404-service`/`j2534-0500-service` as a child process and speaks a small JSON-RPC-over-stdio protocol to it (`ping`/`get_status`/`stop`), implemented identically by all three via the shared `vci_service_launcher::start_service`/`JsonRpcHandler` (`vci-service-launcher/src/vci_server.rs`). Once a spawned instance reports itself running, `vci-service-manager` proxies gRPC/gRPC-Web HTTP traffic to it.

ADR-052 (loopback bind family fallback) changed `get_status`'s success response from a fixed IPv4+IPv6 pair to a non-empty `endpoints: Vec<SocketAddr>` list — a dual-stack host gets both families sharing one port, an IPv4-only or IPv6-only host gets a single entry for whichever family is actually available. ADR-052's own Consequences are explicit that this makes endpoint selection the CLIENT's responsibility: "Clients must treat it as a non-empty list and pick an address they can reach, rather than indexing a fixed `[v4, v6]` layout." `j2534-0404-service/docs/startup-spec.md` was updated to document this `endpoints` contract accordingly.

`vci-service-manager` was never updated to follow it. Its `wait_until_running` (`main.rs`) still reads a top-level `result.get("port")` field from the `get_status` response — a field that has not existed since ADR-052 replaced it with `endpoints`. The real response, built by `vci-service-launcher/src/jsonrpc/dispatch.rs` from `VciServerContext::get_status`, is `{"running": true, "library_name": ..., "endpoints": [...]}` with no top-level `port` at all. So for every service that initializes successfully and is genuinely listening, `result.get("port")` is always `None`, the function's `.ok_or_else(...)` always fires, and `wait_until_running` always returns `Err("service reported running without a valid port")` — the success path that would set `instance.grpc_port` and return `Ok(())` is unreachable. Confirmed directly against the current source (not merely inferred from a report): `vci-service-launcher/src/vci_server.rs`'s `JsonRpcHandler::get_status` impl returns only `{"endpoints": self.endpoints}`, and `dispatch.rs` wraps that as shown above, with no `port` key anywhere in the chain.

Net effect: **every attempt to start a real service instance through `vci-service-manager` fails with an internal error today**, even when the underlying service initializes and binds correctly — a bug this severe went uncaught because no test exercises the real JSON-RPC handshake end to end (`vci-service-manager`'s own `main_test.rs` is never wired into the crate via any `mod` declaration, so nothing in it runs under `cargo test`; a stale `iso22900-service/docs/grpc-instance-spec.md:55` — never updated for ADR-052, unlike `startup-spec.md` — still documents the old `port` shape, which is almost certainly what `vci-service-manager` was originally written against).

A narrower fix that only extracts a bare `u16` port from `endpoints` would trade one loud, obvious bug for a quieter, worse one: `proxy_to_instance` (`main.rs`) hardcodes its proxy target as `http://127.0.0.1:{grpc_port}/...`, unconditionally assuming IPv4. `vci_server.rs`'s own `bind_loopback_listeners` genuinely produces an IPv6-only `endpoints` list on an IPv6-only host (confirmed by reading it directly: the IPv4 bind attempt is skipped when the family is unavailable, falling through to only the IPv6 listener). On such a host, a port-only fix would report `running: true` with a "valid" `grpc_port` while `proxy_to_instance` keeps trying to reach `127.0.0.1`, which is not where the service is listening — silently unreachable despite reporting healthy, strictly worse than today's honest failure.

## Decision

`vci-service-manager` is brought into conformance with the *already-ratified* `endpoints` contract; `vci-service-launcher`'s JSON-RPC response shape is left unchanged. This is a client-side bug fix, not a producer-side contract change — ADR-052 already assigns endpoint selection to the client, and a launcher-side "primary endpoint" field would still be a `SocketAddr` string the manager has to parse, so it would not actually simplify anything while adding a policy the producer (which does not know which address family a given consumer can reach) has no basis to decide on the consumer's behalf. It also keeps the blast radius to one crate instead of touching the shared launcher plus three service binaries' own doc/test surfaces for no behavioral gain.

Concretely:

1. `ManagedInstance`'s `grpc_port: u16` field is replaced with `grpc_endpoint: Option<SocketAddr>` — `None` immediately after spawn (mirroring the existing sentinel-`0` shape it replaces), set to `Some(...)` only once `wait_until_running` resolves a real endpoint.
2. A new `select_grpc_endpoint(result: &Value) -> Result<SocketAddr, String>` helper parses the response's `endpoints` array (each entry a `SocketAddr`-formatted string, e.g. `"127.0.0.1:54321"` / `"[::1]:54321"`) and picks one: **the first `SocketAddr` whose `is_ipv4()` is true, else the first entry regardless of family.** This is a determinism tie-breaker only, not a reachability decision — the manager and the child it just spawned always share a host, so any address family the child bound to is reachable from the manager; IPv4-first simply matches the manager's own existing `127.0.0.1:8080` default bind and today's pre-bug intended behavior on the common dual-stack case, and avoids depending on `bind_loopback_listeners`' own v4-then-v6 push order (an implementation detail of a different crate, not part of the documented contract) the way a bare `.first()` would.
3. `select_grpc_endpoint` treats a missing `endpoints` key, a `null` value (a real, code-reachable shape: `dispatch.rs`'s own `.unwrap_or(Value::Null)` substitutes `Null` if a handler ever omits the key), an empty array, or any entry that fails to parse as a `SocketAddr` as a hard error including the offending value — `endpoints` being "never empty" per `vci_server.rs`'s own doc comment is a producer-side intent, not a compiler-enforced invariant the consumer may assume without a defensive check.
4. `InstanceStatus` gains `grpc_endpoint: Option<SocketAddr>` (serialized via `SocketAddr`'s own `Display`-based `Serialize` impl, e.g. `"127.0.0.1:54321"`/`"[::1]:54321"`) and keeps `grpc_port: Option<u16>` as a value derived from it (`.map(|e| e.port())`) for backward-compatible REST JSON shape, even though a repo-wide grep found no in-repo consumer of the field today — it is this manager's own public HTTP surface, not an internal implementation detail, so removing it outright is a separate, unrelated compatibility decision this fix does not make.
5. `proxy_to_instance` builds its proxy target from the stored `grpc_endpoint` directly (`format!("http://{endpoint}/")`, relying on `SocketAddr`'s `Display` to already produce the bracketed `[::1]:port` form a URI parser accepts) instead of `format!("http://127.0.0.1:{grpc_port}/...")`, fixing the IPv6-only-host reachability gap described above as part of the same change, not as a follow-up. **Superseded by ADR-221:** `proxy_to_instance` (and the manager's gRPC proxying role entirely) was later removed outright — turned out to be fundamentally unfixable as a proxy (path-based instance selection is incompatible with how generated gRPC clients connect; see that ADR's Context). Clients now connect directly to `grpc_endpoint`, the exact value this item taught `ManagedInstance`/`InstanceStatus` to track — that part of this Decision (items 1-4/6-8) remains in force and is what ADR-221 builds on.
6. `read_instance_status`'s existing three-arm shape (no instance / process exited / running) is preserved exactly; only the running arm's `grpc_port: Some(...)` construction changes to also populate `grpc_endpoint`.
7. `iso22900-service/docs/grpc-instance-spec.md`'s stale `get_status` `Result` line is corrected to the `endpoints` shape, matching `startup-spec.md`'s already-correct wording — closing the doc drift that is the most likely reason this bug was introduced in the first place.
8. New unit tests (in `main.rs`'s own inline `#[cfg(test)] mod tests`, not the dead, unwired `main_test.rs`) pin `select_grpc_endpoint` against response fixtures shaped exactly like `dispatch.rs`'s real output: dual-stack (IPv4 first and, separately, IPv6 first — proving the tie-break is order-independent), IPv4-only, IPv6-only, `null`, `[]`, and one malformed entry.

## Consequences

- Starting a real service instance through `vci-service-manager` works again on dual-stack, IPv4-only, and IPv6-only hosts — today it cannot succeed at all, on any host, for any of the three service binaries.
- Endpoint-selection policy stays owned by consumers, per ADR-052's own Decision; this ADR does not add a producer-side "primary endpoint" field to `vci-service-launcher`, and a future proposal to add one should be weighed against the fact that it would not have simplified this fix.
- A future change to `vci-service-launcher`'s `get_status` response shape will now fail `vci-service-manager`'s own unit test (`select_grpc_endpoint`'s fixtures) rather than silently reintroducing this same class of bug undetected, the way this one went unnoticed for the entire time ADR-052 has been in force.
- **Accepted residual, not fixed here:** `iso22900-service/tests/stdio_startup.rs`'s and `j2534-0404-service/tests/stdio_startup.rs`'s own `get_status` assertions pick the response's first `endpoints` entry (`arr.first()`) rather than preferring IPv4 the way this ADR's `select_grpc_endpoint` does — both would silently start asserting against an IPv6 address instead of IPv4 if `bind_loopback_listeners`' internal push order (v4-then-v6 today) ever changed, since neither test's own intent depends on which family it happens to observe. Out of scope for this fix (a different crate's test suite, unrelated to `vci-service-manager`'s own bug); worth a follow-up if `bind_loopback_listeners`' ordering is ever revisited.
- **Accepted residual, not fixed here:** `vci-service-manager/src/main_test.rs` remains an unwired, dead duplicate of the inline tests already in `main.rs`'s own `#[cfg(test)] mod tests` — confirmed to never run under `cargo test` (no `mod main_test;` declaration anywhere in the crate). Deleting it is a one-line, purely mechanical cleanup with no relation to this fix's own scope; left for a future pass touching this file rather than folded in here.
