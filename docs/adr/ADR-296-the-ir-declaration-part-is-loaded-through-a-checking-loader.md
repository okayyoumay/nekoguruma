# ADR-296: The IR Declaration Part Is Loaded Through a Checking Loader

**Date:** 2026-10-14
**Status:** Accepted
**Affects:** `diag-ir` (`src/declaration.rs`, `src/generated/`, `schema/README.md`), design 8.2.6

## Context

The IR's declaration part (design 8.2.2) is defined by the FlatBuffers schema
`crates/diag-ir/schema/ir.fbs`, but the schema had never been compiled: nothing could write or
read a document. The response decoder, the CSV converter (ADR-295) and the fuzz target for
malformed IR all need a way to read one.

A document reaches the agent from a signed manifest (8.2.6). Past that check, nothing but the
reader stands between a malformed document and the decoder. FlatBuffers' verifier makes a buffer
safe to read, but it does not make it sensible:

- With its default limits, a small buffer can unpack into a very large object tree: many offsets
  may point at the same vector, and the verifier counts the apparent size only against a fixed
  2 GiB cap. A 1 MB buffer whose flash segments share one checksum unpacked into about 1.9 GB.
- It checks only the size of an enum field, so an out-of-range value reads as a value of the enum
  type that no variant names.
- It skips the value of a union whose tag it does not know, so the accessors return `None` and the
  object API turns the union into `NONE`: a field with an unknown conversion would decode as if
  it had none.
- No field of the schema is `required`, so a document without its variant verifies.

## Decision

1. **The generated bindings are committed.** `flatc` output for `ir.fbs` lives in
   `crates/diag-ir/src/generated/ir_generated.rs`, generated by the `flatc` release whose version
   equals the `flatbuffers` crate's version in the workspace `Cargo.toml`, since the generated
   code calls that runtime. The build does not need `flatc`. A schema change regenerates the file
   in the same commit and bumps `IR_SCHEMA_VERSION`; a `flatbuffers` upgrade regenerates it with
   the matching `flatc`. The file is never edited by hand (CLAUDE.md, "Generated code").
2. **One loader.** `diag_ir::declaration::load_ecu_document` is the only way a buffer is read. In
   order, it rejects a buffer shorter than the root offset and file identifier, a file identifier
   other than `DIR1`, a buffer the verifier rejects, a schema version other than
   `IR_SCHEMA_VERSION`, and finally what the value checks (item 4) find.
3. **Verifier limits grow with the buffer.** The apparent size, everything following every offset
   may read, is at most eight times the buffer's length, and the number of tables at most one per
   four bytes. An honest document shares only vtables, and one with thousands of fields measured
   under twice its length, so the factor leaves room while bounding what `unpack` allocates to a
   small multiple of what was received. The depth limit stays at 64; the only recursion the schema
   allows is a `Repeat` marker that is itself a shaped `Field`.
4. **Values are checked after verification.** The loader walks the document and rejects an enum
   value outside its type (placement, length kind, data kind, byte order, termination, repeat
   count, flash step), a conversion or shape tag the schema does not define, a document without
   its variant, source format or source digest, and layouts whose ids do not strictly increase
   (ADR-242 keeps them sorted so that they can be found by id).
5. **No other schema version is read.** The loader accepts exactly `IR_SCHEMA_VERSION`, as
   ADR-281 item 4 allows until the first release; a compatibility window would be a later
   decision.

## Consequences

- Every reader of a declaration part goes through the same checks, and the fuzz target has one
  entry point to feed.
- The generated file adds about 7,700 lines and some 200 `unsafe` blocks to `diag-ir`, a crate
  with no FFI role. The review instructions list the generated bindings among the places where
  `unsafe` is expected, and flag a hand edit of the file or a schema change without regenerated
  bindings.
- The value checks cover what the schema states. Rules that `ir.fbs` gives only in comments (field
  order, which shapes may appear where, length kinds per type) are left to the frontends that
  write documents and to the decoder that reads them.
- The object-API structs are `#[non_exhaustive]`, so a frontend in another crate builds a
  document from `Default::default()` and assigns its fields.
- The `flatbuffers` runtime is built into the agent and the server, which depend on `diag-ir`; the
  worker binaries do not link it (`j2534-0404-service` uses `diag-ir` only in its tests). The
  apparent-size limit saturates rather than overflowing on a 32-bit build.
