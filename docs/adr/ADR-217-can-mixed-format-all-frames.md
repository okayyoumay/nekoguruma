## Context

ADR-160 (Phase 3 Stage 3c) implemented SAE J2534-2 clause 8 "Mixed Format Frames on a CAN Network" as a new `CanChannelMode::NativeMixed` deployer-configured mode, but scoped it to `CAN_MIXED_FORMAT_ON` (value 1) only. `CAN_MIXED_FORMAT_ALL_FRAMES` (value 2) was deliberately left unimplemented — `rpc_link.rs`'s `CAN_MIXED_FORMAT_ON`/`_OFF` constants are followed by a comment stating the `_ALL_FRAMES` value is "deliberately not defined here," citing ADR-160's own Context: "no D-PDU consumer for a parallel raw echo of USDT traffic — a client wanting raw bus monitoring already gets that from an ordinary raw-CAN CLL."

Re-investigating this backlog entry confirmed that reasoning still holds — no client demand for `_ALL_FRAMES` as a standalone raw-monitoring feature has emerged, and a separate raw-CAN CLL on the same physical bus still gives a client that exact capability today. The decision to implement `_ALL_FRAMES` anyway was made explicitly for spec completeness, not because a gap in raw-monitoring capability was found.

**What changed the picture, and is this ADR's actual motivating finding:** `_ALL_FRAMES` is not purely additive capability with no other effect. ADR-162 (native-mixed mode's own first follow-up round) added a `UniqueRespIdTable` collision check that rejects any CLL from staging a `CP_CanRespUUDTId` whose native filter key overlaps a flow-control-eligible `CP_CanRespUSDTId` key on the same native-mixed channel — because under `CAN_MIXED_FORMAT_ON`'s clause 8 Figure 1 either/or semantics, an overlapping frame always routes to `FLOW_CONTROL_FILTER`/ISO15765 reassembly and the UUDT interpretation is unreachable (a silent misrouting/corruption hazard, not a merely-suboptimal path — ADR-162 Context). ADR-162's own Consequences section states directly: "The only future path to serving such a table as configured is the already-deferred `CAN_MIXED_FORMAT_ALL_FRAMES`... this ADR does not implement it, and cross-references it here so a future `_ALL_FRAMES` implementer knows this is the collision case it would need to resolve." So implementing `_ALL_FRAMES` is not simply "turn on a third config option" — it changes what ADR-162's collision check must reject.

**The mechanics, confirmed directly against the spec text** (`vehicle-comm-specs/j2534-2-0404/J2534-2_202012 - Optional Pass-Thru Features.md`, clause 8.2.1, Figure 1 vs. Figure 2): under `CAN_MIXED_FORMAT_ON`, a received frame is evaluated against `FLOW_CONTROL_FILTER`s first, and only a non-matching frame is then evaluated against `PASS_FILTER`/`BLOCK_FILTER` — the two outcomes are mutually exclusive per frame. Under `CAN_MIXED_FORMAT_ALL_FRAMES`, the same frame is evaluated against both filter families *independently and in parallel* — a frame matching both can be delivered to the client twice: once reassembled as an ISO15765 message (`FLOW_CONTROL_FILTER` match), once as a raw CAN frame (`PASS_FILTER` match, not blocked). This is a device-side duplication: the device pushes up to two separate native `PASSTHRU_MSG` reads for the one physical frame, each with its own distinct `ProtocolID`.

This service's RX dispatch already processes native messages one at a time, keyed on each message's own `ProtocolID` (`events.rs`'s `process_frame_for_entry`, the `RxEntryKind::Hardware { native_mixed }` branch, ADR-160 Decision 4) — it does not assume a 1:1 mapping between physical frames and delivered messages, nor does it need to know whether the device is in `ON` or `ALL_FRAMES` to route a given native message correctly, so genuine dual *routing* needs no RX-side change.

**A Codex review of this PR found that the RX-side header/footer *split* was not equally unaffected.** `events.rs`'s `header_footer_len` widens an ISO15765 delivery's header by one byte when the frame's CAN ID uses extended addressing, consulting a per-CLL `can_addressing_by_id: Vec<(u32, Addressing)>` table (`events_rx_routing.rs`'s `build_cll_rx_entries`) built by chaining BOTH a table row's `CP_CanRespUSDTId` entry and its `CP_CanRespUUDTId` entry into one flat, role-blind vector, then asking whether ANY entry for the frame's CAN ID is `Addressing::Extended`. Before this ADR, a colliding row (USDT id == UUDT id) was always rejected under `NativeMixed` by ADR-162, so the two entries could coexist in the flat table but a genuine raw delivery for that CAN ID under a *rejected* configuration never happened; the same over-broad `.any()` was separately, silently latent under `DualChannel` and `SoftwareIsoTp` (neither is gated by ADR-162's `NativeMixed`-only check), where a colliding row with different USDT/UUDT `Addressing` was always accepted but never previously exercised by this repo's own test suite. `ALL_FRAMES` is what makes this ADR's own new configuration — and, incidentally, the two pre-existing ones — reachable with a real corrupted delivery: whichever role's entry is NOT the one that matched still answers the `.any()` check, so a normal-addressed UUDT delivery gets its first payload byte wrongly stripped as an Address Extension byte (or, symmetrically, a normal-addressed USDT delivery does) whenever the other role's entry for the same CAN ID happens to be extended-addressed. See Decision item 5 (replacing the retracted "no RX dispatch change" claim above) and Consequences.

## Decision

1. **A new sibling `CanChannelMode` variant, `NativeMixedAllFrames`**, added the same way `Auto` and `NativeMixed` were each added before it — parsed from new config-string aliases (`"native-mixed-all-frames"` / `"native-mixed-all"` / `"mixed-format-all"` / `"mixed-all"`, matching the existing alias-set style), every prior variant byte-for-byte unchanged. Not a payload-carrying variant on `NativeMixed` (e.g. `NativeMixed { all_frames: bool }`) or a second config key: `CanChannelMode::parse`/`find_can_channel_mode` are a flat string→variant contract every existing mode fits, and the two sub-modes need genuinely different branch behavior at more than one call site (Decision 3 below) that two named variants make self-documenting at each `match`, where a boolean flag would hide it.

2. **A new `CanChannelMode::is_native_mixed_family(&self) -> bool` helper**, `matches!(self, Self::NativeMixed | Self::NativeMixedAllFrames)`, for call sites where `ON` and `ALL_FRAMES` behave identically (Decision 3's family-wide sites). `can_mode.rs` gains no knowledge of native `SET_CONFIG` wire values (`0`/`1`/`2`) — that mapping stays local to `rpc_link.rs`, mirroring ADR-160 Decision 2's own reasoning for keeping it out of `can_mode.rs`.

3. **Existing native-mixed call sites split into two groups, not a uniform widen:**

   - **Family-wide (`is_native_mixed_family()`) — behavior is identical under `ON` and `ALL_FRAMES`:**
     - `install_point_to_point_fc_filters`'s `native_mixed` gate (`rpc_link.rs`, ADR-160 Decision 3's per-UUDT-id `PASS_FILTER` installer) — the installed filter type doesn't depend on which native-mixed sub-mode is active, only on whether one is.
     - `events.rs`/`events_rx_routing.rs`'s `mode_is_native_mixed`/`RxEntryKind::Hardware { native_mixed }` — these only gate whether the per-frame `ProtocolID` branch exists on a channel at all (Context above); unchanged in shape, but the boolean that feeds them is now computed from the family check.
     - The root "does native-mixed apply to this connect" computation in `rpc_connect_com_logical_link` (`rpc_link.rs`, formerly a single `native_mixed_format: bool` local) — needed to decide whether to issue the connect-time `SET_CONFIG` at all, and which value.

   - **`ON`-only (stays a literal `== CanChannelMode::NativeMixed`, never widened) — the ADR-162 collision-rejection mechanism:**
     - The fail-fast self-collision check in `rpc_connect_com_logical_link` (`rpc_link.rs`, ADR-162 Decision 2).
     - The cross-CLL collision check threaded into `finalize_connected_link` (`rpc_link.rs`, ADR-162 Decision 2).
     - `promote_unique_resp_id_table`'s own `native_mixed_mode` gate (`rpc_link.rs`, ADR-162 Decision 2's post-connect `SetUniqueRespIdTable`/`CoptUpdateparam` path) — confirmed to already compute this independently (not sharing a variable with any family-wide site), so it needs **no code change at all**; it is already correctly scoped to `NativeMixed` alone.

   This is the ADR-162 cross-reference resolving itself: under `ON`, an overlapping `CP_CanRespUUDTId`/`CP_CanRespUSDTId` pair is a genuine hazard (the UUDT interpretation is unreachable, ADR-162 Context) and stays rejected. Under `ALL_FRAMES`, the same overlap is no longer ambiguous — the device delivers both interpretations as two independently-tagged messages, and this service's existing per-message RX dispatch (Context above) already routes each correctly — so the configuration that `ON` must reject is exactly the configuration `ALL_FRAMES` exists to serve. Not widening the collision check to the new variant is what lets a client actually use `ALL_FRAMES` for the one case ADR-162 named as its future justification; widening it would make the new mode strictly less capable than doing nothing, since it would inherit `ON`'s rejection without ever reaching `ALL_FRAMES`'s payoff.

4. **`NewPhysicalChannelParams`'s `native_mixed_format` field changes from `bool` to `Option<u32>`**, mirroring the existing `fd_data_phase_rate: Option<u32>` field's own shape in the same struct (ADR-158) — `None` for every connect where native-mixed doesn't apply (unchanged trigger conditions: ISO15765-family, not FD-substituted, not pin-selected/`_CHx`-qualified), `Some(CAN_MIXED_FORMAT_ON)` or `Some(CAN_MIXED_FORMAT_ALL_FRAMES)` depending on which variant `effective_can_channel_mode()` resolved to. `connect_new_physical_channel`'s connect-time `SET_CONFIG` step changes from `if native_mixed_format { ...ON }` to `if let Some(value) = native_mixed_format { ...value }` — the rollback-on-`ERR_NOT_SUPPORTED` failure path (mirroring `fd_data_phase_rate`'s own shape) is unchanged and applies identically regardless of which value was sent. `CAN_MIXED_FORMAT_ALL_FRAMES: u32 = 2` is defined next to the existing `_OFF`/`_ON` constants, replacing the "deliberately not defined" comment.

5. **RX *routing* is unchanged (Context above); the RX *header-split addressing lookup* is fixed, per a Codex review finding on this PR.** `CllRxEntry`'s single `can_addressing_by_id: Vec<(u32, Addressing)>` field is split into two role-specific fields, `usdt_addressing_by_id` and `uudt_addressing_by_id` (`events.rs`, populated by `events_rx_routing.rs`'s `build_cll_rx_entries`, one `filter_map` over `active_unique_resp_id_table` per role instead of one `flat_map` chaining both). A new `CllRxEntry::rx_addressing_table(&self, uudt_routed: bool) -> &[(u32, Addressing)]` method selects between them. `poll_rx_inner`'s header-split call site (the `for (delivery_data, unique_resp_identifier, raw, uudt_routed) in deliveries` loop) now calls `header_footer_len(entry.header_protocol, entry.rx_addressing_table(uudt_routed), ...)` instead of always passing the old flat table — `uudt_routed` (`process_frame_for_entry`'s own per-delivery return value, ADR-184) is already computed at this call site for delivery attribution, and reliably identifies which role a given delivery matched (`UniqueRespIdKey::matched`'s USDT-before-UUDT precedence makes `route_frame_matched_uudt`'s `MatchKind::Uudt` check, and `route_frame_uudt_only`'s unconditional `true`, both correct role indicators). `header_footer_len`'s own signature and internal `.any()` lookup are unchanged — it remains role-agnostic; the caller now hands it the correct table. The K-line fast-init call site (`events.rs`, `run_protocol_init`) is unaffected: it always passes an empty slice literal, not a `CllRxEntry` field, since ISO15765 addressing is structurally unreachable there.

   This was unreachable before this ADR: ADR-162 always rejected a colliding USDT/UUDT row under `NativeMixed`, so the flat table's role-blindness never manifested with an actual dual-role delivery on that path. It was, however, ALREADY latently reachable under `DualChannel` and `SoftwareIsoTp` — neither is gated by ADR-162's `NativeMixed`-only collision check, so a colliding row with differing `Addressing` per role was always accepted there, just never exercised by a test with differing addressing before now. This fix corrects that pre-existing exposure too, not only the new `ALL_FRAMES` case; see Consequences.

6. **No mock behavior change beyond accepting the value.** `j2534-0404-mock`'s `can_mixed_format: u32` storage, its `ERR_NOT_SUPPORTED`/ISO15765-family gate, and its Table-5 queue/filter-clearing side effects on a `SET_CONFIG` value change are all already generic over the stored value — none special-case `1` vs. checking only "present"/"changed." A test simulating `ALL_FRAMES` dual delivery calls the existing `inject_rx`/`__mock_inject_rx_msg` test helper twice for the same logical frame — once tagged `CAN`, once tagged `ISO15765` — exactly matching what a real `ALL_FRAMES` device delivers per Figure 2; no new `__mock_*` export is added (mirrors this codebase's own precedent of declining to widen `__mock_inject_rx_msg`'s signature for a narrow convenience, instead keeping a distinct export for a genuinely different shape).

7. **Nothing else on ADR-160's own "Deferred, not implemented" list is dragged in.** TX-side per-message `ProtocolID` selection, `"auto"`-mode extension/detection, discovery-cache wiring, and the `FD_ISO15765_PS` exclusion are all independent of which native-mixed sub-mode is active — `_ALL_FRAMES` is RX-only per clause 8.2.1/Figure 2, and the `!is_fd_protocol_id(...)` connect-time exclusion applies identically to both variants (a `FD_ISO15765_PS` link stays on ADR-159's fallback regardless of which native-mixed variant a deployer configures).

8. **RX *routing* is NOT unchanged after all, correcting Decision 5's own claim -- a second Codex review round found a real cross-CLL misdelivery Decision 5 alone did not fix.** `process_frame_for_entry`'s ISO-tagged `RxEntryKind::Hardware` arm (the one Decision 5 already touches) calls the role-agnostic `route_frame`/`route_frame_matched_uudt` pairing, which matches EITHER a `CP_CanRespUSDTId` OR a `CP_CanRespUUDTId` entry for the frame's CAN ID -- correct for the pre-existing ADR-041 single-channel workaround (a `CP_CanRespUUDTId` entry with no genuine `PASS_FILTER` gets an ADR-041 `FLOW_CONTROL_FILTER` instead, so its ONLY delivery path is exactly this ISO-tagged arm), but wrong for a native-mixed entry: under either native-mixed sub-mode, a `CP_CanRespUUDTId` entry gets a genuine `PASS_FILTER` and is ONLY ever legitimately delivered via the raw-CAN-tagged FIRST arm (`route_frame_uudt_only`) above. Before this fix, the cross-CLL collision Decision 3/Consequences already documents as newly-servable under `ALL_FRAMES` (CLL A's `CP_CanRespUUDTId` == CLL B's `CP_CanRespUSDTId`, same physical channel) let the ISO-tagged native message representing B's own USDT interpretation ALSO match A's UUDT entry via `route_frame`'s role-agnostic search, since `process_frame_for_entry` fans every received native message out to every CLL entry on the shared channel (`poll_rx_inner`'s `for entry in &mut cll_entries` loop) -- misattributing B's own delivery to A as well, under A's own `unique_resp_identifier`.

   Fixed by threading a `uudt_eligible: bool` tier gate into `UniqueRespIdKey::matched` (`events_rx_routing.rs`, same shape as the pre-existing `is_tx_side` gate on the TP2.0 tiers): `false` skips the UUDT tier entirely for that key (falling through to lower-precedence tiers, or `None`), never affecting USDT/J1939SA/TP20. The uid and `uudt_routed` role are now resolved by a SINGLE combined search, `route_frame_with_role(...) -> Option<(u32, bool)>` -- collapsing what were previously two independently-computed answers (`route_frame`'s own uid search plus `route_frame_matched_uudt`'s separate, unaware `MatchKind::Uudt` search) into one, so they cannot disagree. `route_frame`/`route_frame_matched_uudt` become thin wrappers hardcoded to `uudt_eligible: true` (a provable no-op for every pre-existing caller -- both keep their exact original signatures, zero test-call-site churn), while `process_frame_for_entry`'s ISO-tagged arm calls `route_frame_with_role` directly with `uudt_eligible = !native_mixed`. Applied to the WHOLE native-mixed family (`ON` and `ALL_FRAMES`), not `ALL_FRAMES` alone -- under `ON` this is a provable no-op, since ADR-162's collision check already rejects every table shape (self-row, cross-row, cross-CLL) that could ever let an ISO-tagged frame's CAN ID equal a native-mixed entry's own UUDT id in the first place; `RxEntryKind::Hardware`'s `native_mixed` field doesn't distinguish sub-modes anyway, so a sub-mode-specific gate would add a field with no observable effect.

   **A companion gap, closed in the same fix:** `build_cll_rx_entries`'s own `native_mixed` computation (`events_rx_routing.rs`) was missing the `!qualified` (no pin selection, no `_CHx` index) term every one of `rpc_link.rs`'s native-mixed call sites already has. Harmless before this round (a qualified link's frames are always ISO15765-tagged, and the only pre-existing reader of `native_mixed` that cared, the raw-CAN-tagged first arm, never fires for a qualified link regardless), but this round's new `uudt_eligible`-gated second arm makes the field load-bearing: without `!qualified`, a qualified link on a native-mixed-family module would wrongly get `native_mixed: true` and have its own legitimate ADR-041-style UUDT delivery dropped by the new gate, even though `rpc_link.rs` never actually clause-8-`SET_CONFIG`s or `PASS_FILTER`s a qualified link at connect time. Added `l.pin_select.is_none() && l.channel_index.is_none()` to the computation, mirroring `rpc_link.rs`'s own term exactly.

## Consequences

- **The ADR-162 collision case is now servable, but only under `NativeMixedAllFrames` specifically — not under `NativeMixed`.** A deployer wanting to stage an overlapping `CP_CanRespUUDTId`/`CP_CanRespUSDTId` pair on one native-mixed channel must configure `"native-mixed-all-frames"`, not `"native-mixed"`; the same table stays rejected under `"native-mixed"` exactly as ADR-162 established. This is a deliberate, not incidental, difference between the two config values — documented here so a future reader does not mistake the unwidened `== NativeMixed` collision checks for an oversight.
- **A client on an `ALL_FRAMES` channel that stages an overlapping table now has the device deliver BOTH interpretations of a matching frame** (an assembled ISO15765 message and a raw UUDT-routed CAN frame, as two independent native messages) rather than a rejection — this is clause 8's own defined behavior (Figure 2), not a new invented semantic. Whether a *client COP* actually observes both is a separate question, governed by this service's existing `NumReceiveCycles` registrant-matching rules (ADR-100/ADR-182), unrelated to native-mixed mode: an unbounded receive style (`NumReceiveCycles == -1`/`-2`, IS-CYCLIC/IS-MULTIPLE) accumulates every matching delivery and observes both, exactly as this ADR's own dual-delivery test exercises. An ordinary bounded `CoptSendrecv` (a finite `NumReceiveCycles`, e.g. the common single-request/single-response shape) only accepts matches up to its own target count (`bind_registrant`'s `matches_got < matches_needed` gate, `events.rs`) — with a target of `1`, whichever of the two native messages is processed first satisfies the registrant, and the second is silently unbound (no error, no hang, but only one interpretation is actually delivered to that COP, non-deterministically UUDT-raw or USDT-reassembled depending on delivery order). A client relying on always observing both interpretations of an overlapping frame must use an unbounded receive style; a bounded one sees at most one, matching how this same mechanism already behaves for any other frame with more matches than a bounded COP requested.
- **`ALL_FRAMES`'s only implemented consumer benefit is this collision case.** The standalone "single client, dual-format monitoring on one CLL" value proposition ADR-160's Context questioned remains unconfirmed by any concrete client request — this ADR does not change that; it implements `_ALL_FRAMES` because doing so resolves ADR-162's own forward-reference, not because new raw-monitoring demand was found.
- **`NativeMixed` (`ON`) is unaffected in every OBSERVABLE respect** — same `SET_CONFIG` value, same `PASS_FILTER` installation, same ADR-162 collision rejection, same RX routing OUTCOME. Decision 8's `uudt_eligible` gate does run for `ON` too (it is a family-wide fix, not `ALL_FRAMES`-only), but is a provable no-op there — ADR-162's collision check already rejects every table shape (self-row, cross-row, cross-CLL) that could ever make an ISO-tagged frame's CAN ID equal a native-mixed entry's own UUDT id under `ON`, so the gate never has a real table to act on. `NativeMixedAllFrames` is a genuinely new, opt-in fourth-plus-one config value, not a relaxation of the existing one.
- **Discovery-cache wiring for clause-8 `_ALL_FRAMES` support remains deferred**, matching `NativeMixed`'s own identical deferral (ADR-160 Consequences, ADR-153 precedent) — an unsupporting device's connect-time `SET_CONFIG` still fails `ERR_NOT_SUPPORTED` and rolls back the connect, just not pre-emptively at discovery time.
- **The RX header-split addressing-table role-split (Decision 5) also fixes a pre-existing, previously-untested exposure under `DualChannel` and `SoftwareIsoTp`**, not just this ADR's own `ALL_FRAMES` case — see Decision 5's own explanation of why the old flat table was never actually reachable with a real dual-role delivery under `NativeMixed`/ADR-162, but always was under those two other modes.
- **Decision 8's routing fix resolves the cross-ROW role-attribution ambiguity described below, but ONLY for a native-mixed-family entry — `SingleChannel`/`DualChannel` primary entries keep the exact same ambiguity, now the sole remaining accepted residual.** Consider two DIFFERENT rows in one CLL's `active_unique_resp_id_table` — row A with `CP_CanRespUSDTId = X` (normal-addressed), row B with `CP_CanRespUUDTId = X` (extended-addressed), same CAN ID X, no single row colliding against itself. An ISO15765-tagged native message for CAN ID X is routed by `route_frame_with_role` (`events_rx_routing.rs`), which returns the FIRST row (iteration order) whose own `UniqueRespIdKey::matched` succeeds — if row B is iterated first and `uudt_eligible` is `true` (a `DualChannel`/`SingleChannel` primary entry, where `RxEntryKind::Hardware` cannot tell "primary channel of a dual-channel module" apart from any other non-native-mixed entry today), this delivery is still attributed `MatchKind::Uudt` (`uudt_routed = true`) even though it arrived exactly like an ordinary USDT delivery — `uudt_addressing_by_id`'s lookup for X (row B's own extended entry) is CONSISTENT with that choice; the ambiguity is in which row wins the routing/attribution decision, not in which addressing table Decision 5 then consults for whichever role won. For a native-mixed entry, `uudt_eligible = false` on this arm means row B's UUDT tier can never win here regardless of iteration order — Decision 8 resolves the cross-row case there as a side effect of resolving the cross-CLL case it actually targeted. `DualChannel`'s primary channel could in principle take the identical `uudt_eligible: false` treatment (its own UUDT ids also get no ADR-041 `FLOW_CONTROL_FILTER`, served by the companion channel instead — `rpc_link.rs`), but extending it is deliberately out of scope for this ADR: `RxEntryKind::Hardware` has no field distinguishing a dual-channel primary from an ordinary single-channel entry today, and widening the gate's own trigger condition is a separate change with its own verification burden. Same class of accepted residual as ADR-197 Decision 2's own table-vs-RxStatus-bit precedence note — recorded here, not fixed, since Codex's own finding did not report this narrower case and it predates this ADR. **Closed for `DualChannel` by [ADR-222](ADR-222-uniquerespid-can-width-disambiguation.md)'s `uudt_on_companion` field**, added to `RxEntryKind::Hardware` for an unrelated reason (CAN-ID-width contention correctness) but which gives `RxEntryKind::Hardware` exactly the "distinguish a dual-channel primary" capability this bullet said was missing, and whose `uudt_eligible = !native_mixed && !uudt_on_companion` gate is precisely the widening this bullet described as out of scope. `SingleChannel`'s own share of this residual is NOT closed — `SingleChannel` has no companion channel at all (`uudt_on_companion` is always `false` there), so its genuine same-CAN-ID cross-role ambiguity (unlike `DualChannel`'s, which was never a real ambiguity to begin with — `DualChannel`'s primary simply never receives UUDT traffic) remains open.
