# ADR-212: SAE J2534-2 Clause 7 Additional Channels (`_CHx`) — Extend to Single Wire CAN

**Date:** 2026-09-02
**Status:** Accepted
**Affects:** `j2534-0404`, `j2534-0404-service` resources/names/rpc_link/comparam_id/events/rpc_primitive/rpc_misc, `j2534-0404-mock`, docs, `tests/grpc_mock/sw_can.rs`

## Context

ADR-211 closed Fault-Tolerant CAN as the pathfinder round for the shared CAN-collapse-family `_CHx` infrastructure fix, and its own Decision item 1 designated Single Wire CAN (SWCAN/GMLAN, clause 9, `PROTOCOL_SW_CAN_PS`/`PROTOCOL_SW_ISO15765_PS`) as Round 2. This round inherits the shared infrastructure fix already proven a no-op for every already-shipped family (`base_protocol_id`'s recursive fallback, `resolve_channel_selection`'s three normalized-base routes, `chx_device_info_supported_parameter`'s raw-id-keyed two-tier contract) — none of that needs to change again here. What this round adds is SW-CAN's own family-specific wiring, verified directly against the current tree (not assumed from ADR-211's own generic estimate) rather than repeated from FT-CAN's site list unchanged, since ADR-211 itself flagged two reasons this round's surface differs:

1. **A larger surface than FT-CAN.** FT-CAN had no family-specific ComParams, IOCTLs, or RxStatus handling of its own (ADR-168 Decision 5). SW-CAN does (ADR-164 Decision 2): three of the five `CP_ChangeSpeed*` ComParams translate to native `CONFIG_SW_CAN_HS_DATA_RATE`/`CONFIG_SW_CAN_SPEEDCHANGE_ENABLE`/`CONFIG_SW_CAN_RES_SWITCH` (`comparam_id.rs`), `PDU_IOCTL_SW_CAN_HS`/`PDU_IOCTL_SW_CAN_NS` are SW-CAN-specific IOCTLs (service-side pass-through, and mock-side simulated with their own protocol-identity check), and `SW_CAN_HS_RX`/`SW_CAN_NS_RX` RxStatus bits are withheld entirely before content parsing (ADR-172, `events.rs`). Confirmed by direct reading: all three of these currently key off the narrow, two-value `resources::is_sw_protocol_id`/the mock's own `is_sw_protocol`, which match only the bare `_PS` ids — a `_CHx`-connected SW-CAN link's raw hardware id is in the new `_CH1..128` range instead, so all three would silently misbehave for such a link today (ComParam translation drops the mapping, the mock's IOCTL handler wrongly returns `ERR_NOT_SUPPORTED`, and RxStatus withholding never fires, leaking a speed-transition-confirmation frame as if it were genuine content).

2. **A confirmed vendor-header naming inconsistency.** SW-CAN's own `_CHx` blocks are `PROTOCOL_SW_CAN_CAN_CH1` (`0x9300`)–`_CH128` (`0x937F`) and `PROTOCOL_SW_CAN_ISO15765_CH1` (`0x9380`)–`_CH128` (`0x93FF`) — both prefixed `SW_CAN_`, matching SAE J2534-2's own clause 24 table naming rather than the `SW_CAN_CH1`/`SW_ISO15765_CH1` naming every other family's own `_CHx` block uses relative to its own `_PS` id's prefix (verified directly against `j2534-0404-sys/src/bindings/j2534_v0404.h`). This is purely a naming fact to encode correctly in `chx_block_base`'s reverse-lookup table (the key is still each `_PS` id, `PROTOCOL_SW_CAN_PS`/`PROTOCOL_SW_ISO15765_PS`; only the block constant names on the value side differ from the `SW_CAN_PS => SW_CAN_CH1`-shaped pattern every other family follows) — not a design question, and the two ranges are contiguous and non-overlapping with every other family's own block (0x9300–0x93FF, versus e.g. FT-CAN's 0x9480–0x957F).

Three items found during this round's own investigation, beyond ADR-211's own generic framing:

- **`resolve_pin_selection`'s SW-CAN arm has the identical masking gap ADR-211 Context item 2 described for FT-CAN pre-fix**, confirmed by direct reading (`names.rs`): the arm gates on the narrow `is_sw_protocol_id(raw_hw_protocol_id)` with no `requested_index.is_some()` bypass before its own `!j2534_2_opted_in`/mutual-exclusion logic — every already-`_CHx`-enabled family's own arm has this bypass (added incrementally, one family's round at a time, starting with the FT-CAN round for FT's own arm). Without it, a compound `_CHx`-suffixed SW-CAN name reaches this arm (its `raw_hw_protocol_id` is still the bare `_PS` id; the index rides separately in `requested_index`) and is processed as an ordinary, non-`_CHx` pin-selection request, which `resolve_channel_selection`'s later mutual-exclusion check then rejects as "pin_selection and channel_index both set" instead of resolving correctly — the same shape ADR-211 already fixed for every other family in its own round, applied here to SW-CAN specifically.
- **`apply_fd_mode`'s SW-vs-FD-mode rejection guard is duplicated at two sites** (the `CAN`-branch and `ISO15765`-branch arms of the connect-time FD-mode state machine, `rpc_link.rs`), both still keyed on `is_sw_protocol_id` — ADR-211 re-keyed only the analogous FT-CAN guards (its own two sites) to `is_ft_family_protocol_id`; the SW-CAN guards were untouched, since SW-CAN wasn't in scope for that round.
- **`resources::chx_device_info_supported_parameter` has no SW-CAN arms**, the same historical gap FT-CAN had before its own Codex-review-round-2 fix — this round adds them from the start (applying the lesson learned, not waiting for a review round to find it again), and proactively gives the mock its own independent SW-CAN capacity override (mirroring the mock-infrastructure fix FT-CAN's round needed only after a final-sweep `edge-case-hunter` finding) so the round's own regression test is discriminating on the first attempt.

One item found only during this round's own implementation/verification pass, not by the up-front investigation: **`CP_SwCan_HighVoltage`'s `TX_FLAG_SW_CAN_HV_TX` composition, at THREE call sites, not the two ComParam-translation/RxStatus-withholding classes Context item 1 above already names.** `rpc_primitive::apply_resolved_tx_flags` (the shared TX-flags composition an ordinary `CoptSendrecv` funnels through), `rpc_misc.rs`'s own, independent Repeat-Message TX-flags composition, and `events.rs`'s `sw_can_hv_rx` binding (the RX-side counterpart that tags a received frame's own `RxFlag` with the ISO 22900-2 Table D.5 byte 1 bit 0 high-voltage-wakeup indication, `RX_SW_CAN_HV_RX`/bit 16 — distinct from the `SW_CAN_HS_RX`/`SW_CAN_NS_RX` withholding gate a few lines above it in the same function, which Decision item 4 below already covers) all independently gated this bit on the narrow `is_sw_protocol_id`. The first two were found and fixed by direct code review immediately after the implementer's own dispatch closed; the third — `events.rs`'s RX-side binding specifically — was missed even then and was only caught by a full-diff `edge-case-hunter` pass (reproduced with a temporary failing test before being fixed for real). All three are the identical bug shape as every other re-keying in this round, just on a ComParam/RxStatus mechanism Context item 1's own up-front survey did not enumerate.

## Decision

1. **`resources.rs`:**
   - New `is_sw_family_protocol_id` predicate (`_PS` OR either `_CH1..=_CH128` range), mirroring `is_ft_family_protocol_id`'s exact shape. `is_sw_protocol_id` itself stays untouched and narrow — it remains correct for `resolve_pin_selection`'s own arm-gate purpose and the mock's `pins_assigned` initialization gate, the same "narrow predicate stays narrow, a new family-wide predicate added alongside it" precedent every prior family's round established.
   - `chx_block_base`/`chx_base_protocol_id`'s `BLOCKS` array (currently 15 entries) gains two: `PROTOCOL_SW_CAN_PS => PROTOCOL_SW_CAN_CAN_CH1`, `PROTOCOL_SW_ISO15765_PS => PROTOCOL_SW_CAN_ISO15765_CH1` — the key is each `_PS` id (matching every other family's convention); only the block constant names on the value side reflect the vendor-naming quirk from Context item 2.
   - `connect_discovery_check`: widen SW-CAN's existing bare `PROTOCOL_SW_CAN_PS | PROTOCOL_SW_ISO15765_PS` match into two range-inclusive guard arms (mirroring FT-CAN's own widening in ADR-211), each still returning its own distinct `DeviceFlag` parameter (`DEVICE_INFO_SW_CAN_SUPPORTED`/`DEVICE_INFO_SW_ISO15765_SUPPORTED`) so a `_CHx`-qualified SW-CAN connect gets the same fail-fast Discovery gate the `_PS` connect already does.
   - `chx_device_info_supported_parameter`: add two guard arms for SW-CAN, keyed on the raw id exactly like the FT-CAN arms this same function already has (Codex review round-2 correction, ADR-211) — `DEVICE_INFO_SW_CAN_SUPPORTED`/`DEVICE_INFO_SW_ISO15765_SUPPORTED`, checked before the generic per-family fallback.
   - `bustype_default_name_for_hw_protocol_id`: re-key SW-CAN's arm from `is_sw_protocol_id` to `is_sw_family_protocol_id`.

2. **`rpc_link.rs`:**
   - `rpc_get_resource_status`'s raw-candidate-matching site and its own `matches_status_hw_id` closure (both currently `is_sw_protocol_id(id) || is_ft_family_protocol_id(id)`): re-key the SW-CAN half to `is_sw_family_protocol_id` so a `_CHx`-connected SW-CAN link can be found by a raw-id resource-status query the same way a `_PS`-connected one already can.
   - `apply_fd_mode`'s two SW-vs-FD-mode rejection guards (the `CAN`-branch and `ISO15765`-branch arms, currently both `is_sw_protocol_id`): re-key both to `is_sw_family_protocol_id`, so a `_CHx`-connected SW-CAN link that reaches this function (a client staging FD ComParams on it) is still recognized and rejected as SW-CAN, not silently treated as plain CAN/ISO15765 and promoted to `FD_CAN_PS`/`FD_ISO15765_PS`.

3. **`comparam_id.rs`:** `to_j2534_config_id`'s SW-CAN arm (the `CP_ChangeSpeedRate`/`CP_ChangeSpeedCtrl`/`CP_ChangeSpeedResCtrl` → `CONFIG_SW_CAN_HS_DATA_RATE`/`CONFIG_SW_CAN_SPEEDCHANGE_ENABLE`/`CONFIG_SW_CAN_RES_SWITCH` translation, checked against the raw `hw_protocol_id` with no `base_protocol_id` normalization step, per that arm's own existing doc comment): re-key from `is_sw_protocol_id` to `is_sw_family_protocol_id`, so these three ComParams still translate to native `SET_CONFIG` calls on a `_CHx`-connected SW-CAN link.

4. **`events.rs`:** the `SW_CAN_HS_RX`/`SW_CAN_NS_RX` RxStatus withholding gate (ADR-172, checked against the frame's own native protocol id, raw and pre-`RX_STATUS_FLAGS_MASK`): re-key from `is_sw_protocol_id` to `is_sw_family_protocol_id`, so this withholding still fires for a `_CHx`-connected SW-CAN link's frames (whose native protocol id is the connected `_CH<N>` id, not the bare `_PS` id) instead of leaking a speed-transition confirmation as ordinary content. The `sw_can_hv_rx` binding a few lines below this same gate (the RX-side `RX_SW_CAN_HV_RX`/bit-16 `RxFlag` tag, ADR-191, distinct from the withholding gate above it) needs the identical re-key — found late, by a full-diff `edge-case-hunter` pass rather than up front (Context above).

5. **`rpc_primitive.rs`/`rpc_misc.rs`:** `CP_SwCan_HighVoltage`'s `TX_FLAG_SW_CAN_HV_TX` composition, at TWO independent call sites (`rpc_primitive::apply_resolved_tx_flags`, the shared TX-flags composition every ordinary `CoptSendrecv` funnels through; and `rpc_misc.rs`'s own separate Repeat-Message TX-flags composition): re-key both from `is_sw_protocol_id` to `is_sw_family_protocol_id`, so this bit still reaches the wire on a `_CHx`-connected SW-CAN link's own sends. Found during this round's own implementation, not the up-front investigation (Context above).

6. **`names.rs`:** `resolve_pin_selection`'s SW-CAN arm gains the standard `requested_index.is_some()` bypass every other `_CHx`-enabled family's arm has, placed before the arm's own `!j2534_2_opted_in`/pin-validation logic — closing the masking gap Context above describes. `resolve_channel_selection`'s own three routes need no further change: ADR-211's fix there was general, not family-specific, so SW-CAN already gets correctly-normalized bases through all three routes once this arm stops masking the compound-name route specifically.

7. **`j2534-0404/src/lib.rs`:** re-export `PROTOCOL_SW_CAN_CAN_CH1`/`PROTOCOL_SW_CAN_CAN_CH128`/`PROTOCOL_SW_CAN_ISO15765_CH1`/`PROTOCOL_SW_CAN_ISO15765_CH128`.

8. **`j2534-0404-mock/src/lib.rs`:**
   - `CHX_BLOCK_BASE_IDS`/`BASE_PROTOCOL_IDS` (currently `[u32; 15]`) each gain two entries for SW-CAN, positionally aligned exactly like the `resources.rs` `BLOCKS` array in Decision item 1.
   - New `is_sw_family_protocol` predicate, mirroring `is_sw_family_protocol_id`. Unlike FT-CAN's own mock-side family-wide predicate (which had no genuine call site and stayed `#[allow(dead_code)]`), this one has a real, confirmed call site: `IOCTL_SW_CAN_HS`/`IOCTL_SW_CAN_NS`'s handler currently rejects with `ERR_NOT_SUPPORTED` unless the connected channel's protocol id passes the narrow `is_sw_protocol` — re-key that check to `is_sw_family_protocol` so these two IOCTLs still work on a `_CHx`-connected SW-CAN channel. `ChannelState::new`'s `pins_assigned` gate stays on the narrow `is_sw_protocol`, unchanged, matching every other family's identical mock-side convention (a `_CHx` id has no J1962 pin concept, the same reason `is_ps_protocol`/`is_fd_protocol`/every other family-narrow predicate is excluded there too).
   - `DEVICE_INFO_SW_CAN_SUPPORTED`/`DEVICE_INFO_SW_ISO15765_SUPPORTED`'s `GET_DEVICE_INFO` arm: move from the mock's flat, always-`0x0000_0001` capability group into the `chx_capacity`-packed group every other capacity-governed family uses — applying FT-CAN round's own final-sweep fix proactively this time, rather than shipping the same silent-no-op-then-Codex-catches-it gap again. New, INDEPENDENT capacity override for SW-CAN's two flags (mirroring `ft_can_chx_capacity_override`/`__mock_set_ft_can_chx_capacity` exactly, added to close FT-CAN's own final-sweep coverage gap) — this lets this round's own regression test genuinely discriminate "consulted the SW-CAN-specific flag" from "consulted the generic CAN/ISO15765 flag" on the first attempt, without needing a follow-up fix the way FT-CAN's round did.

9. **New regression tests** (`tests/grpc_mock/sw_can.rs`, extending the existing `_PS`-level suite): raw-`_CH1`-id connect (both CAN and ISO15765 sub-variants) with a baud-rate-default assertion (mirroring FT-CAN's own Codex-round-1 regression test shape, applied proactively here since `bustype_default_name_for_hw_protocol_id`'s widening is part of this round from the start), compound-name connect asserting the actual native connected id, `connect_discovery_check`/`chx_device_info_supported_parameter` `_CHx` coverage as `resources.rs` unit tests (matching every prior family's own convention for this kind of check), a `GetResourceStatus` query-match test for a `_CHx`-connected link, an `apply_fd_mode` SW-vs-FD rejection test for a `_CHx`-connected SW-CAN link, a `CP_ChangeSpeed*` ComParam round-trip test on a `_CHx`-connected link asserting the native `SET_CONFIG` actually fires, an `IOCTL_SW_CAN_HS`/`_NS` test on a `_CHx`-connected link, the capacity-discrimination test described in Decision item 8 (generic capacity set high, SW-CAN's own set low, connect an index within the former but above the latter, assert synchronous rejection with zero native connect attempts), and two tests for `CP_SwCan_HighVoltage`'s TX/RX bits on a `_CHx`-connected link (Decision items 4-5's own findings), each verified genuinely discriminating by hand-reverting its fix and confirming exactly that one test fails.

## Consequences

- `_CHx` Additional Channels now covers 17 of the 18 protocol families once this round ships (the 15 ADR-211 already closed, plus SW-CAN's two). Only CAN FD/ISO15765-on-CAN-FD remain out of scope, needing their own future round per ADR-211's own Decision item 5 (the `apply_fd_mode` state-machine design question).
  **Update:** that future round shipped as [ADR-213](ADR-213-can-fd-additional-channels.md) — `_CHx` Additional Channels now covers all 18 protocol families.
- The shared infrastructure fix (ADR-211's own Decision items 2-3) needed zero further changes for this round — confirmed by direct tracing, not assumed — validating design-advisor's original three-round sequencing choice (land the shared fix on the smallest family first, then prove it generalizes).
- SW-CAN's own family-specific surface (ComParam translation, RxStatus withholding, the mock's IOCTL handler) is `_CHx`-aware in this round's own final state — the mock's own capacity-override infrastructure was built discriminating from the start, applying FT-CAN round's own final-sweep lesson directly rather than repeating that gap. `CP_SwCan_HighVoltage`'s own TX/RX bit, specifically, was NOT caught up front despite that same discipline (Context above, Decision items 4-5) — found only during this round's own implementation and a later full-diff `edge-case-hunter` pass, the identical "keep looking after the up-front investigation" pattern this series has hit before (ADR-211's own third `resolve_channel_selection` route, found the same way).
- CAN FD/ISO15765-on-CAN-FD's own future round still inherits the infrastructure fix and must resolve the `apply_fd_mode` design question (ADR-211 Decision item 5) as its own first step — unaffected by this round.
- **Accepted residual, out of scope for this round:** `chx_device_info_supported_parameter` still has no arms for GM UART, SAE J1939, UART Echo Byte, Honda DIAG-H, SAE J1708, or TP2.0 (ADR-211's own Consequences already recorded this as a residual after the FT-CAN round; SW-CAN's own two arms close two of those eight originally-missing slots, leaving six). Tracked in `j2534-0404-service/docs/implementation-notes.md`'s Prioritized Backlog.
  **Update:** a later, mechanical extension of this same guard-arm pattern (no new design decision, so no new ADR) closed the residual for five of those six families (SAE J1939, UART Echo Byte, Honda DIAG-H, SAE J1708, TP2.0); only GM UART's own already-separately-accepted residual (ADR-189 Decision 5) remains. See `j2534-0404-service/docs/implementation-notes.md`'s Prioritized Backlog for current status.
