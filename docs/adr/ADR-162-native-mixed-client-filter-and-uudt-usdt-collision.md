# ADR-162: Native-Mixed Mode Follow-Ups — Client PASS/BLOCK Filter Scope and UUDT/USDT Match-Key Collision

**Date:** 2026-08-06
**Status:** Accepted (Consequences' collision-case forward-reference to `CAN_MIXED_FORMAT_ALL_FRAMES` fulfilled by ADR-217 — Decision item 2's collision check itself is unchanged and stays scoped to `NativeMixed`/`CAN_MIXED_FORMAT_ON` only)
**Affects:**
- `j2534-0404-service/src/service/rpc_misc.rs` (`ioctl_start_msg_filter` doc comments and error text, no behavior change)
- `j2534-0404-service/src/service/rpc_link.rs` (`install_client_message_filters` invariant note; a fail-fast self-collision check in `rpc_connect_com_logical_link`; an authoritative cross-CLL collision check inside `finalize_connected_link`'s existing rollback critical section; `promote_unique_resp_id_table`, which becomes fallible)
- `j2534-0404-service/src/service/events.rs` (`handle_update_param`'s `promote_unique_resp_id_table` call site emits `PduErrEvtProtErr` on a collision rejection; the COP still finishes normally)
- `j2534-0404-service/tests/grpc_mock/mixed_format_can.rs` (new collision-rejection coverage)

## Context

ADR-160 (Phase 3 Stage 3c) left two follow-ups open, both flagged by Codex review on PR #33 as pre-existing gaps in the native-mixed CAN mode it introduced, and both recorded in `j2534-0404-service/docs/implementation-notes.md`'s backlog. This ADR resolves both.

**1. Client `PASS_FILTER`/`BLOCK_FILTER` and the paired raw-CAN `ProtocolID` (clause 8.2.2.4).** SAE J2534-2 clause 8.2.2.4 (paraphrase, not quoted per this repo's copyright policy) requires a `PASS_FILTER`/`BLOCK_FILTER` installed on a `CAN_MIXED_FORMAT`-enabled channel to carry the raw-CAN-family `ProtocolID` paired with the channel's ISO15765-family id (clause 8.1's association rule; `resources::mixed_format_can_protocol_id` already implements this pairing for the UUDT filter this service installs internally, ADR-160 Decision 3). The backlog's original framing was that `install_client_message_filters` (`rpc_link.rs:162-260`) mistags a client-staged filter with the plain ISO15765 `hw_protocol_id` instead, risking `ERR_MSG_PROTOCOL_ID` on a conforming adapter.

Direct investigation of the current code shows that scenario is unreachable, not live: `rpc_misc.rs`'s `ioctl_start_msg_filter` (the sole D-PDU entry point for client `PASS_FILTER`/`BLOCK_FILTER`) rejects the whole request outright, before the not-yet-connected/already-connected branch split and before `pending_client_filters` is ever populated, whenever `base_hw_protocol_id() == ISO15765` (the pre-existing ADR-038 guard, predating native-mixed mode). `base_hw_protocol_id()` normalizes `ISO15765_PS`, `FD_ISO15765_PS`, and every `ISO15765_CHx` variant to `ISO15765` (`resources.rs`), and `hw_protocol_id`'s only post-create mutations (FD/pin-select substitution) never move a link into the ISO15765 family from outside it — so every reachable CLL state is covered, and `install_client_message_filters` can never actually run with an ISO15765-family `hw_protocol_id`. The mistagging bug the backlog described does not exist in the current code.

That leaves a real but different gap: ADR-038's rejection rationale ("only `FLOW_CONTROL_FILTER` is valid on an ISO15765 channel") is now incomplete. Under native-mixed mode specifically, clause 8.2.2.4 makes a correctly-tagged client `PASS_FILTER`/`BLOCK_FILTER` a spec-legitimate operation this service still refuses unconditionally.

**2. UUDT/USDT hardware-filter overlap.** `install_point_to_point_fc_filters` (`rpc_link.rs` ~3044-3235) installs, per `UniqueRespIdTable` entry on the same physical channel: a `FLOW_CONTROL_FILTER` tagged with the ISO15765 `hw_protocol_id` for a `CP_CanRespUSDTId` with flow control enabled (~3126), and, under native-mixed mode, a `PASS_FILTER` tagged with the paired raw-CAN `ProtocolID` for `CP_CanRespUUDTId` (~3193-3224, ADR-160 Decision 3). The native filter message these two installers build (`can_filter_message`, this file) is a 4-byte mask/pattern (CAN ID only, matching any data content) for a normal-addressed key, or 5 bytes (ID plus an exact `ext_addr` data-byte match) for an extended-addressed one — so two keys' installed filters can match the SAME physical frame (overlap) not only when their CAN address, width, and extended-addressing byte are all literally equal, but also whenever either side is normal-addressed at the same ID: its 4-byte filter matches any data content, so it always subsumes an extended-addressed filter at that ID regardless of the extension byte's value. When a `CP_CanRespUUDTId` key's filter overlaps a flow-control-eligible `CP_CanRespUSDTId` key's already-installed `FLOW_CONTROL_FILTER` on the same channel this way — including the common case where one entry sets both to the same value — clause 8's `CAN_MIXED_FORMAT_ON` Figure 1 algorithm (already documented in ADR-160's Decision 4, "a received frame is either/or") evaluates `FLOW_CONTROL_FILTER` matches first: a match is delivered as an assembled ISO15765 message, and only a frame matching no `FLOW_CONTROL_FILTER` is evaluated against `PASS_FILTER`/`BLOCK_FILTER`. An overlapping UUDT frame therefore always reaches the device's ISO15765 reassembly path and never the raw-CAN `PASS_FILTER` this service installed for it — a UUDT frame is not ISO-TP-segmented, so being processed as one is a silent misrouting/corruption hazard, not a merely-suboptimal delivery path.

This is a deterministic consequence of `CAN_MIXED_FORMAT_ON`'s own defined behavior, not a hardware race. `CAN_MIXED_FORMAT_ALL_FRAMES` (clause 8's mode 2, which would deliver both interpretations in parallel) is already out of scope per ADR-160 Decision/Consequences — no D-PDU consumer need was identified for a parallel raw echo of USDT traffic, and implementing it here would only relocate the ambiguity to service-side routing (which interpretation to forward), not resolve it.

## Decision

### 1. Client `PASS_FILTER`/`BLOCK_FILTER` on an ISO15765-family link stays rejected — rationale corrected, not relaxed

`ioctl_start_msg_filter`'s ADR-038 rejection (`rpc_misc.rs` ~1317-1331, ~1497-1506) and the ADR-079 pass-all-baseline rejection (~1414-1423) are kept exactly as they behave today — no change to `install_client_message_filters`'s callers, no new `effective_can_channel_mode()` computation at this call site. Their doc comments and client-facing error text are corrected to state the accurate reason: under native-mixed mode, clause 8.2.2.4 makes a correctly-tagged client filter spec-legitimate, but this service defers supporting it, rather than claiming (as ADR-038's original text does, correctly for every mode except native-mixed) that no such filter type is ever valid on an ISO15765 channel.

Relaxing the guard to actually admit native-mixed client filters is deliberately not done here: the ADR-079 amendment already rejects `PDU_FLT_PASS`/`_PASS_UUDT` unconditionally regardless of protocol (a pass-all hardware baseline makes a narrower client PASS_FILTER a no-op), so relaxation would only ever admit `PDU_FLT_BLOCK`/`_BLOCK_UUDT`; and admitting even that buys little without matching work in `poll_rx_inner`'s native-mixed RX branch (ADR-160 Decision 4), which currently delivers a CAN-tagged frame only when it matches a `CP_CanRespUUDTId` table entry — a client `BLOCK_FILTER`'s hardware-level effect would need new delivery-routing logic to be observable, not just a translated `PassThruMessage::new` call. The cost (an async `effective_can_channel_mode()` read at the IOCTL call site, which per the existing AB-BA-deadlock discipline in `rpc_link.rs` must run before any `api`/`device_id` lock — safest computed before `ioctl_start_msg_filter`'s own `shared_channels` acquisition; a `filter_protocol_id` translation parameter threaded through `install_client_message_filters`, which is exactly the kind of missed-translation site the original backlog item worried about, except now genuinely reachable; and new FD/`_CHx` boundary handling) is disproportionate to a client capability nothing in this service can yet deliver end-to-end. Deferred, recorded in the backlog below.

`install_client_message_filters` (`rpc_link.rs`) gains an invariant comment (and a `debug_assert!` on the normalized `base_protocol_id(hw_protocol_id) != ISO15765`) recording that this function is never reachable with an ISO15765-family id today, and that a future relaxation of the guard above must add `mixed_format_can_protocol_id` translation here before removing that assumption.

### 2. UUDT/USDT hardware-filter overlap is rejected under native-mixed mode, at both points a `UniqueRespIdTable` is established

A new shared helper (`can_filter_keys_overlap`) determines whether two `CanAddress` keys' native filters can match the same physical frame — id and 11-/29-bit width must match exactly (a genuinely different frame either way), but the extended-addressing byte need not: since `can_filter_message` only appends it (narrowing the match to one specific data byte) when the key is extended-addressed, a normal-addressed key's 4-byte, any-data-content filter always overlaps an extended-addressed key at the same id regardless of the extension byte's value, and two extended-addressed keys only overlap when their extension bytes also match. (An earlier draft of this mechanism compared match keys for plain equality — id + width + extended-addressing byte — which is not the same relation: it both missed the normal-vs-extended overlap just described and required an irrelevant `flow_control_enabled` bit to match; both gaps were caught by Codex review on the implementation PR and are why the mechanism is described as an overlap check, not an equality check, here.) A candidate `UniqueRespIdTable` is checked this way against the keys (via the existing `CanAddress`/`CanIdFormat` construction) of every `CP_CanRespUUDTId` and every flow-control-eligible `CP_CanRespUSDTId` (present, `CP_CanRespUSDTFormat`'s flow-control bit set, `CP_CanPhysReqId` present — mirroring the exact predicate `install_point_to_point_fc_filters` already uses to decide whether it installs a `FLOW_CONTROL_FILTER` at ~3108-3151) across **every** `UniqueRespIdTable` entry on the same physical `channel_id` — including entries belonging to a sibling CLL sharing that channel (native-mixed channels are joinable, ADR-160 Decision 1), in both directions (a new UUDT id against existing USDT keys, and a new USDT key against existing UUDT ids). An overlap fails the operation under native-mixed mode only; the identical table is unaffected off native-mixed, since without a native-mixed `PASS_FILTER` install there is nothing for the overlap to break.

Enforced at the two points a `UniqueRespIdTable` becomes active. Both points need the check and the in-memory commit to share one `logical_links` critical section — `promote_unique_resp_id_table` never takes `shared_channels`, so `logical_links` is the only lock that actually serializes a connecting CLL against a concurrent sibling's `CoptUpdateparam`; a check that runs in a separate critical section from the commit it gates leaves a real TOCTOU window (the promote side can equally fail to see an unpublished joiner mid-connect).

- **`rpc_connect_com_logical_link`**, in two parts:
  - **Fail-fast self-check** (no rollback needed): once `native_mixed_format` is known and before `ensure_open_device` runs, and only when the connecting link is unqualified (no pin-select/`_CHx` — mirrors `install_point_to_point_fc_filters`'s own `!qualified` gate, since a qualified link never gets the native-mixed `PASS_FILTER` in the first place), this CLL's own already-promoted `active_unique_resp_id_table` is checked against itself. Nothing native has happened yet at this point, so a self-collision returns `PDU_ERR_FCT_FAILED` (`state_guard_status`, matching the precedent at `rpc_misc.rs`'s own shared-channel filter-scoping rejection) with zero rollback. This alone fully covers the new-physical-channel case (a fresh channel has no sibling to collide with).
  - **Authoritative cross-CLL check inside `finalize_connected_link`**: within its existing `logical_links` critical section, before that section mutates anything, an immutable scan compares this CLL's candidate table against every sibling CLL already showing this `channel_id` (published cross-CLL state is only ever visible there, since a sibling's own `finalize_connected_link` call is what publishes it). A collision reuses `finalize_connected_link`'s existing concurrent-destroy rollback path verbatim (originally ADR-012: compare-and-restore the `occupancy_epoch` via `restore_occupancy_epoch_on_rollback`, decrement `ref_count`, remove and disconnect the `SharedChannel` if it drops to zero) — only the returned error differs (`PDU_ERR_FCT_FAILED` instead of the concurrent-destroy `not_found`). This is what actually excludes the join-vs-sibling race the self-check alone cannot see.
- **`promote_unique_resp_id_table`** (`rpc_link.rs` ~3278), on a post-connect `SetUniqueRespIdTable`/`CoptUpdateparam`: the native-mixed gate (`effective_can_channel_mode()`) is read *before* `logical_links` is acquired (a new AB-BA rule alongside the existing `api`/`device_id` one — `probe_can_channel_mode` holds `resolved_can_channel_mode` while awaiting `logical_links` via `ensure_uudt_companion_channel`). The check, the sibling scan, and the `active_unique_resp_id_table` commit then happen in one `logical_links` critical section (moved earlier than today's separate commit step) — a collision returns an error with nothing touched (no filter removed, old table and filters untouched), satisfying "checked before `remove_point_to_point_fc_filters`" by construction. `promote_unique_resp_id_table` changes its return type from `()` to `Result<(), NativeMixedTableCollision>`. `handle_update_param` (`events.rs` ~10236) does *not* fail the COP on this error — `PduComPrimitiveStatus` has no failed variant (only Idle/Executing/Finished/Cancelled/Waiting) — it emits `PduErrorEvent::PduErrEvtProtErr` via `send_error_event` (mirroring the existing `PDU_ERR_EVT_RSC_LOCKED` precedent at ~10425-10434: an error event for the part that couldn't be applied, while the COP still finishes normally) and falls through to the unconditional `PduCopstFinished`, since the rest of that `CoptUpdateparam`'s ComParam promotion already landed and is not undone by the table rejection. The `PDU_IOCTL_CLEAR_MSG_FILTERS`/`RESET` reinstall path needs no new check: it only ever rebuilds filters from an Active table that already passed this check when it was promoted.

The collision check is pure in-memory comparison over already-locked `logical_links` state; it never acquires `api`.

## Consequences

- **Client `PASS_FILTER`/`BLOCK_FILTER` support on a native-mixed link remains a deferred capability**, not implemented here — recorded in `j2534-0404-service/docs/implementation-notes.md`'s backlog as a P2/P3 follow-up (RX delivery-routing work plus the translation/lock-ordering cost above), reclassified from the P1 "live bug" the backlog previously described.
- **A colliding `UniqueRespIdTable` under native-mixed mode has no accepted configuration** other than avoiding the collision (distinct UUDT/USDT addresses) or using a non-native-mixed `CanChannelMode`. The only future path to serving such a table as configured is the already-deferred `CAN_MIXED_FORMAT_ALL_FRAMES` (ADR-160 Consequences) — this ADR does not implement it, and cross-references it here so a future `_ALL_FRAMES` implementer knows this is the collision case it would need to resolve.
- `promote_unique_resp_id_table` becoming fallible is a narrow, additive signature change confined to its one caller; no other caller exists.
- The cross-CLL, cross-entry, both-directions scope of the collision check means a `SetUniqueRespIdTable` on one CLL can now fail because of another CLL's table on the same shared native-mixed channel — an intentional consequence of the collision being a property of the shared physical channel, not of any single CLL's table in isolation.
- A rejected `CoptUpdateparam`'s `PduErrEvtProtErr` event does not stop the rest of that call's ComParam promotion (bustype/tester-present/etc.) from applying, nor does it change the COP's terminal status — matching ISO 22900-2's existing partial-apply model for a config element a handler cannot accept (the same shape as the pre-existing `PDU_ERR_EVT_RSC_LOCKED` case). A client distinguishes "table rejected, rest applied" from "everything applied" only via the error event, not via `GetStatus(cop)`.
- `native-mixed` is deployment-config-fixed, never `Auto`-resolved (ADR-160: "`Auto` never resolves to `NativeMixed`"), so `effective_can_channel_mode() == NativeMixed` is invariant for the service's lifetime once configured — the promote-side gate has no re-resolution race to guard against.
