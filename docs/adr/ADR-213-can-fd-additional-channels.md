# ADR-213: SAE J2534-2 Clause 7 Additional Channels (`_CHx`) — Extend to CAN FD / ISO15765-on-CAN-FD

**Date:** 2026-09-03
**Status:** Accepted (partial supersession: ADR-158 Decision item 1's `channel_index.is_some()` rejection, and ADR-159 Decision item 5's identical rejection and its "stay out" framing, are both superseded by this ADR; ADR-159 Decision item 7's Discovery deferral is fulfilled for the `_CHx` capacity dimension by this ADR; ADR-211's own Decision item 5 deferral is fulfilled by this ADR)
**Affects:** `j2534-0404`, `j2534-0404-service` resources/names/rpc_link, `j2534-0404-mock`, docs

## Context

ADR-211 (Fault-Tolerant CAN) and ADR-212 (Single Wire CAN) closed the first two rounds of a three-round plan `design-advisor` set for the CAN-collapse-family `_CHx` series, leaving CAN FD (`FD_CAN_PS`, ADR-158/Phase 3a) and ISO15765-on-CAN-FD (`FD_ISO15765_PS`, ADR-159/Phase 3b) as the final two of the eighteen SAE J2534-2 clause-7 protocol families. ADR-211's own Decision item 5 explicitly deferred this round and demanded its own investigation independently confirm the spec reading before trusting ADR-211's paraphrase, rather than assuming its shape.

**This round's investigation found a genuine error in that paraphrase.** ADR-211 claimed no direct-naming route exists for FD-on-a-specific-Additional-Channel, favoring an index-aware promotion/reversion shape as the only option. Directly re-reading the SAE J2534-2 DEC2020 edition's own clause 21.3.2.1.4 (Table 89) and clause 22.3.2.2.1 (Table 96) shows both `FD_CAN_PS`/`FD_CAN_CHx` and `FD_ISO15765_PS`/`FD_ISO15765_CHx` are listed as directly-nameable `<ProtocolID>` values for `PassThruConnect`, the same shape every other family's `_PS`/`_CHx` pair has — confirmed further by the vendor header, which defines `PROTOCOL_FD_CAN_CH1..128` (`0x9880`-`0x98FF`) and `PROTOCOL_FD_ISO15765_CH1..128` (`0x9900`-`0x997F`) as real native constants, contiguous and non-overlapping with every other family's own `_CHx` block. So a direct-naming route genuinely exists at the raw J2534 native-API layer.

This does not, however, undermine ADR-158/159's own already-shipped decision that this adapter's D-PDU-facing resource model reaches FD only via post-connect ComParam-staged substitution, never via direct naming. That decision rests on two separate, still-valid grounds: (1) ISO 22900-2 (both the 2009(E) and 2022 editions) has no distinct CAN-FD bus type or resource of its own — FD is expressed purely as ComParams staged on the ordinary CAN/ISO15765 D-PDU resource, so this service's own resource table has zero rows for `FD_CAN_PS`/`FD_ISO15765_PS` and never will; and (2) `apply_fd_mode` recomputes FD-ness fresh from staged Working ComParams on every single connect (ADR-158 Decision item 1), and `CoptUpdateparam`'s own guard (`rpc_primitive.rs`) enforces that the staged ComParams and the link's actual `hw_protocol_id` never disagree — a directly-named FD id with no FD ComParams staged would simply be reverted at connect, and one with them staged would be redundant with the substitution path. Two sources of truth for FD-ness cannot coexist with that already-shipped invariant, so substitution-only reachability is this adapter's own deliberate design choice, not a limitation this round should revisit for `_PS`. ADR-158 Decision item 3's phrasing that no legitimate direct-naming route exists "at all" is loosely worded in light of the Table 89/96 finding above — worth a clarifying note, not a supersession, since its substance (this adapter's own D-PDU contract) still holds.

Clause 21.3.2.5.1 and clause 22.3.2.6.1 describe distinct connect-time behavior for the `_CHx` variants specifically: for the `_PS` id, the data-phase-rate configuration parameter must be set before pin selection (or, in a single batched call, ordered ahead of it) or the call fails. For the `_CHx` ids, there is no pin-selection step at all — each `_CHx` channel is already tied to its own vendor-assigned pins and stays electrically inert until the data-phase-rate parameter is set, at which point it attaches; read/write/periodic-message/filter calls are rejected until that attachment happens. This service already issues the data-phase-rate `SET_CONFIG` at connect time (`rpc_link.rs`, derived from the staged `CP_CANFDBaudrate`/`CP_Baudrate`), so a `_CHx`-connected link's `channel_index` plus its staged FD ComParams already expresses everything clause 21/22 need for an FD `_CHx` connect — nothing about the family's own connect semantics is lost by keeping direct FD naming rejected while allowing the substitution path to become index-aware instead.

A structurally different precedent already exists in this codebase for a family where clause-7 Additional Channels genuinely does not apply: Analog Inputs (clause 10) was decided out of `_CHx` scope entirely, because clause 10 enumerates its 32 channels directly with no base/`_CHx` relationship for the mechanism to model at all. CAN FD is not in that situation — it has a real `_PS`/`_CHx` split with its own connect semantics, confirmed above — so that precedent does not transfer here.

## Decision

1. **`apply_fd_mode`'s substitution becomes index-aware**, mirroring the existing SAE J1850 VPW/PWM autodetect rewrite's three-way revert shape (already precedent in this same file): promoting a link with `channel_index = Some(n)` staging FD ComParams now writes `hw_protocol_id` to the corresponding `FD_CAN_CH<n>`/`FD_ISO15765_CH<n>` id instead of rejecting outright; reverting a link whose ComParams no longer signal FD restores `CAN_CH<n>`/`ISO15765_CH<n>` (not bare `CAN`/`ISO15765`) when a `channel_index` is present, `ps_protocol_id`'s own pin-selected id when a `pin_select` is present, or the bare base otherwise. The `channel_index.is_some()` rejection arms in both the `CAN` and `ISO15765` branches (ADR-158 Decision item 1, ADR-159 Decision item 5) are removed; the `base_hw_protocol_override` half of both revert branches already accounted for `channel_index.is_some()` when this was written (unreachable dead code until now) and needs no change — only the `hw_protocol_id` half was missing its `_CHx` case.

2. **`resources.rs` wires FD into the shared `_CHx` infrastructure the same way FT-CAN and SW-CAN were**: `chx_block_base`'s BLOCKS array gains `PROTOCOL_FD_CAN_PS => PROTOCOL_FD_CAN_CH1` and `PROTOCOL_FD_ISO15765_PS => PROTOCOL_FD_ISO15765_CH1` (17 entries becomes 19); `chx_device_info_supported_parameter` and `connect_discovery_check` each gain two FD arms in the same shape FT-CAN's/SW-CAN's own arms already use, keyed to (newly re-exported) `DEVICE_INFO_FD_CAN_SUPPORTED`/`DEVICE_INFO_FD_ISO15765_SUPPORTED` — this also fulfills ADR-159 Decision item 7's Discovery deferral for the `_CHx`-capacity dimension specifically (clause-5 opt-in enforcement at `apply_fd_mode` itself remains unchanged, still out of this ADR's scope, matching every other family's own precedent of leaving the pname-opt-in check where it already is).

   `fd_protocol_id` stays `_PS`-only — it is the family's qualifying key into `chx_block_base`, the same role every other collapse family's own `_PS`-keyed function plays. A new `fd_protocol_id_for_link(base, channel_index)` helper composes `fd_protocol_id` with `chx_protocol_id` when an index is present, giving `apply_fd_mode` one call for both the `_PS` and `_CHx` promotion cases.

   `is_fd_protocol_id` is **widened in place** to recognize both `_PS` ids and both `_CH1..=_CH128` ranges — a deliberate departure from ADR-211 Decision item 4's "narrow predicate stays narrow, add a family-wide predicate alongside it" convention, made because FD has no `resolve_pin_selection` arm of its own to keep the narrow form for (unlike SW-CAN/FT-CAN), and of this predicate's roughly dozen non-test call sites, none needs the narrow, `_PS`-only form — every one of them (ComParam-support gating, RX/TX flag handling, `CoptUpdateparam`'s ComParam-consistency guard, the connect-time data-phase-rate/pin-synthesis snapshot) needs to treat an FD `_CHx` link exactly like an FD `_PS` link. Widening in place, rather than adding a second `is_fd_family_protocol_id`, avoids a class of silent-miss bug this series has hit before (a call site left keyed on the narrow form after a family gains `_CHx` support) at every one of those call sites at once.

3. **The connect-time snapshot's default-pin synthesis is gated off for `_CHx` FD links.** `rpc_link.rs`'s connect snapshot currently synthesizes a default J1962 pin selection for any FD link lacking an explicit `pin_select`, since clause 21/22's `_PS` variant has no pin-preassigned default the way Classic CAN does. Left unchanged, once `is_fd_protocol_id` recognizes `_CHx` ids too, this would incorrectly issue `SET_CONFIG(CONFIG_J1962_PINS)` on an already vendor-pin-preassigned `_CHx` channel — a clause-7/21.3.2.5.1 violation this round's own investigation found by tracing the snapshot code directly, not something the up-front spec reading alone would have surfaced. The synthesis step is additionally gated on `link.channel_index.is_none()`; the data-phase-rate `SET_CONFIG` step stays unconditional on `is_fd_protocol_id` alone, since that is the step that attaches a `_CHx` channel per clause 21.3.2.5.1/22.3.2.6.1.

4. **`names.rs`'s existing direct-FD-naming rejection is left as the single guard it already is**, not duplicated: because it already gates on `is_fd_protocol_id` (widened by Decision item 2 above), it automatically extends to reject a directly-named `FD_CAN_CHx`/`FD_ISO15765_CHx` id the same way it already rejects a directly-named `FD_CAN_PS`/`FD_ISO15765_PS` id, with no separate edit needed — only its message text gains a `_CHx` mention for clarity.

5. **The mock (`j2534-0404-mock`) gets FD `_CHx` handling it never had at all before this round** — unlike every other family's own round, the mock has zero existing `DEVICE_INFO_FD_CAN_*`/`DEVICE_INFO_FD_ISO15765_*` handling to extend (ADR-158/159 Decision item 7's own deferral left this entirely unwired). This round adds both flags to the shared `chx_capacity`-packed `IOCTL_GET_DEVICE_INFO` arm, and implements clause 21.3.2.5.1/22.3.2.6.1's own `_CHx` attach-on-rate behavior: a `_CHx` FD channel rejects `PassThruReadMsgs`/`PassThruWriteMsgs`/`PassThruStartPeriodicMsg`/`PassThruStartMsgFilter` with `ERR_PIN_INVALID` until the data-phase-rate `SET_CONFIG` has been issued on it. The mock's own narrow `is_fd_protocol` predicate (unlike the service's own `is_fd_protocol_id`, ADR-211 Decision item 4's split convention DOES apply here) stays narrow for the `pins_assigned` gate specifically — a `_CHx` FD channel must keep reporting `pins_assigned = true` so a client's own `CONFIG_J1962_PINS` attempt on it is correctly rejected `ERR_CHANNEL_IN_USE`, the same way every other `_CHx` channel's pins are already treated as fixed. A new family-wide predicate is added alongside it for the `BIT_SAMPLE_POINT`/`SYNC_JUMP_WIDTH` read-only-parameter rule, which does need to apply uniformly across `_PS` and `_CHx`.

## Consequences

- `_CHx` Additional Channels now covers all 18 protocol families (19 native `_CHx` blocks, once FT-CAN's, SW-CAN's, and CAN FD's own two-blocks-per-family shape are all accounted for) — the three-round `design-advisor` plan ADR-211 set is complete.
- `resources.rs`'s `is_chx_protocol_id`/`chx_protocol_id` doc comments' stale "18 protocol families (19 native blocks, `SW_CAN` split across two)" wording — already flagged as an undercount by a prior round's backlog entry once FT-CAN's own split was accounted for — is corrected in the same PR: three families (FT-CAN, SW-CAN, CAN FD) each contribute two native blocks to the 19-block total, not one.
- Reconnecting a `_CHx` FD link after its ComParams stop signaling FD must land back on the same `CAN_CH<n>`/`ISO15765_CH<n>` id it started from, not the bare base — verified with a dedicated regression test, mirroring the same class of gap ADR-211's own final-diff `edge-case-hunter` sweep found and fixed for FT-CAN's mock capacity wiring.
- **Accepted residual, carried forward unchanged from ADR-158/159, now also applying to `_CHx`:** a link that alternates between Classic and FD mode across reconnects opens two distinct physical channels on what a real adapter would treat as one vendor channel resource (Classic `CAN_CH5` and FD `FD_CAN_CH5` have different `ChannelKey`s) — a real adapter's own clause-7 resource accounting would answer `ERR_RESOURCE_IN_USE` for the second; this service's own mock does not model that cross-mode contention. Not a new gap this round introduces, only a wider surface for an already-accepted one.
- **Accepted residual:** `_CHx`-capacity enforcement is keyed to the FD family's own `DEVICE_INFO_FD_CAN_SUPPORTED`/`DEVICE_INFO_FD_ISO15765_SUPPORTED` flags (Decision item 2) but a link that reconnects from Classic `CAN_CH5` (within the generic CAN family's own cached capacity) to FD `FD_CAN_CH5` (potentially a smaller FD-specific capacity) is judged against the FD cap only at the FD reconnect itself, not proactively — the same "cap is enforced at the connect that actually needs it, not speculatively" model every other family's own capacity check already uses.
