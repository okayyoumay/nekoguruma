## `iso22900-mock`

### Prioritized Backlog

- **P2**: `iso22900-mock`'s `PDUIoCtl` (`crates/iso22900-mock/src/lib.rs`) takes the IOCTL command ID as `T_PDU_IT`, while the header `crates/iso22900-sys/src/bindings/d_pdu_api_func.h` and the bindings' `DPduApiSys::PDUIoCtl` declare `UNUM32`. Both are 32-bit integers, so calls work, but `crates/iso22900-mock/tests/abi_parity.rs` has to check `PDUIoCtl` by layout instead of by signature. Done when: the mock's parameter is `UNUM32` (converted to `T_PDU_IT` inside where it is compared), `PDUIoCtl` is in that test's signature list and its layout-only test is removed.
- **P2**: Pull-request CI never compiles `crates/iso22900-mock/tests/abi_parity.rs` for a target where the mock's `exported_fn!` picks `extern "stdcall"` (Windows x86): `core-windows` is x86_64 and `worker-check` in `.github/workflows/ci.yml` runs `cargo check` on `sim-vci`, `j2534-0404-service` and `iso22900-service` without their tests, so a calling-convention drift between the mock and the `iso22900-sys` bindings there (the event callback type `CALLBACKFNC` included) would merge unnoticed. Done when: `worker-check` (or another pull-request job) runs `cargo check -p iso22900-mock --tests --target i686-pc-windows-gnullvm`.
- **P2**: `crates/iso22900-mock/docs/testing-guide.md` says the mock is a process-global singleton and every test calls `__mock_reset` first, but not how tests that share it may run in parallel. Done when: the guide has a section stating that tests loading the mock in one process need `#[serial]`, that nextest runs each test in its own process (`.config/nextest.toml`) while `cargo test` does not, and when to call `__mock_reset`.

## `iso22900-service`

### Prioritized Backlog

- **P2**: `iso22900-mock`'s `PDUGetEventItem` (`crates/iso22900-mock/src/lib.rs`) only synthesizes `PDU_IT_RESULT` items, never `PDU_IT_STATUS`, so the terminal-status branch of `to_proto_event_item` in `crates/iso22900-service/src/service/events.rs` (it drops a COP's `cop_tags` entry on `PDU_COPST_FINISHED` or `PDU_COPST_CANCELLED`, ADR-204) is unreachable through the mock and has no test. A black-box test cannot see the eviction: the terminal item is built before the entry is removed, no later event follows for that COP, and `rpc_start_com_primitive` reconciles the entry on its own when a handle is reused. Done when: the mock can emit a COP status event (for example through a new `__mock_` back door), and a crate-internal test (a `#[cfg(test)]` module next to `events.rs`, or equivalent test-only access to `CopTagMap`) asserts that the `cop_tags` entry is present before `to_proto_event_item` handles a terminal status item and gone after it, so the test fails if the removal is deleted.
- **P2**: `rpc_subscribe_event` (`crates/iso22900-service/src/service/rpc_primitive.rs`) inserts the new sender into `self.subscriptions` (which can evict and cancel an earlier subscriber for the same `(module, cll)` key) before it takes `self.api` again and calls `register_event_callback`. If the gRPC request is dropped while waiting on that lock, the slot holds a subscription with no native callback, so the link gets no events. This mirrors the ordering hazard ADR-204 fixed in `rpc_start_com_primitive`. Registering first does not close the window by itself: a drop while waiting for the map lock would then leave a registered callback (possibly replacing the one of an existing subscriber for the same key) with no subscription behind it, and a failing `register_event_callback` already leaves the new entry in the map today. Done when: the map update and the native registration either both take effect or neither does (both locks taken before either effect, in the service's lock order, so no `.await` lies between them, or the first effect rolled back when the second does not happen), and a test drops the request future while `self.api` is held and asserts that neither a map entry without a callback nor a callback without a map entry is left behind.
- **P2**: The finalizer task that `rpc_subscribe_event` (`crates/iso22900-service/src/service/rpc_primitive.rs`) spawns for each `SubscribeEvent` stream calls `unregister_event_callback` when the stream's sender closes, but never removes that sender's entry from `self.subscriptions`. A closed sender therefore stays in the map until a later subscription for the same `(module, cll)` replaces it or a `terminate_subscription*` helper in `crates/iso22900-service/src/service/rpc.rs` removes it. The finalizer also checks ownership under the map lock but releases it before unregistering, so a newer subscriber for the same key can register in between and then lose its callback. Done when: the finalizer removes the entry it owns (and only that one, not a newer subscriber's under the same key) and unregisters the callback without such a window, and a test closes a stream normally and asserts the entry is gone.
- **P2**: The ADR-204 cancellation-window fix in `rpc_start_com_primitive` (`crates/iso22900-service/src/service/rpc_primitive.rs` takes the `cop_tags` lock before the native call, so no `.await` remains between the native side effect and the tag update) has no test of its own; the `cop_tag` tests in `crates/iso22900-service/tests/grpc_mock.rs` (`start_com_primitive_accepts_max_length_cop_tag`, `start_com_primitive_rejects_oversized_cop_tag`, `subscribe_event_echoes_cop_tag_racing_start_response`) cover size checks and event/response ordering only. Done when: a crate-internal test with access to the service's `cop_tags` map holds that lock from another task, drops the `rpc_start_com_primitive` future while it waits for the lock, and asserts that the native call never ran (`__mock_get_start_com_primitive_count` unchanged) and the map is unchanged, so the test fails if the lock is moved back after the native call, where the drop would leave a started COP whose tag was never reconciled.
- **P2**: No test in `crates/iso22900-service/tests/grpc_mock.rs` shows that when the native library reuses a `(module, cll, cop)` handle, events for the new COP do not echo the previous occupant's `cop_tag` (`cop_tags` in `crates/iso22900-service/src/service/rpc_primitive.rs`, ADR-204). Done when: a test starts a COP with a tag, lets the mock hand out the same handle to a second COP started without a tag (or with another one), and asserts the second COP's events carry its own tag.
- **P2**: No test observes the terminal status of a live `iso22900-service` `SubscribeEvent` stream when the service shuts down because stdin closes: `process_exits_when_stdin_is_closed_with_live_subscribe_event_stream` in `crates/iso22900-service/tests/stdio_startup.rs` keeps the stream unpolled (`_event_stream`), only closes stdin and asserts only that the process exits, so a regression in delivering the `cancelled` status (`crates/iso22900-service/docs/subscribe-event-shutdown.md`) would go unnoticed. Done when: that test (or a new one in the same file) polls the stream after stdin closes and asserts the status it ends with.
- **P2**: No test observes the terminal status of a live `iso22900-service` `SubscribeEvent` stream when the service is stopped through the `stop` JSON-RPC method; the stdio tests in `crates/iso22900-service/tests/stdio_startup.rs` that send `stop` open no event stream. Done when: a test in that file opens a stream, sends `stop`, polls the stream and asserts the status it ends with (`crates/iso22900-service/docs/subscribe-event-shutdown.md`).
- **P2**: `crates/iso22900-service/tests/stdio_startup.rs` covers `get_status`, `stop` and process exit, but no test sends the JSON-RPC `ping` method (`crates/vci-service-launcher/src/jsonrpc/dispatch.rs`) to the `iso22900-service` binary; `crates/j2534-0404-service/tests/stdio_startup.rs` does it for the J2534 service. Done when: an `iso22900-service` stdio test sends `ping` and checks the response.
- **P2**: The "Error Mapping" table in `crates/iso22900-service/docs/architecture.md` is out of date: it maps `DPduApiError::PduStatus` codes to several gRPC statuses, but that variant no longer exists, and `runtime_error_parts` in `crates/iso22900-service/src/error.rs` maps every native `DPduApiError::PduError` to `INTERNAL`, with the raw code in `ErrorDetail.pdu_error` (ADR-105). Done when: the section describes what `crates/iso22900-service/src/error.rs` does today (runtime, construct and registry errors, and the sanitized messages of ADR-089), or points to "Rich Error Detail" in `docs/rpc-api-guide.md` for the runtime part.
- **P2**: `iso22900-mock` (`crates/iso22900-mock/src/lib.rs`) has no error-injection back door for `PDUUnlockResource` (only `PDULockResource` and `PDUGetLastError` have one: `__mock_set_lock_resource_error`, `__mock_set_last_error`), so the failure path of `rpc_unlock_resource` in `crates/iso22900-service/src/service/rpc_link.rs`, which goes through `with_api_for_link`, is untested. Done when: the mock has an override that makes `PDUUnlockResource` fail, and a test in `crates/iso22900-service/tests/grpc_mock.rs` drives that failure and checks the returned status and `ErrorDetail`, as `link_scoped_failure_carries_error_event_data_from_last_error` does for `PDULockResource`.
- **P2**: `iso22900-mock` (`crates/iso22900-mock/src/lib.rs`) has no error-injection back door for `PDUGetComParam` (only `PDULockResource` and `PDUGetLastError` have one: `__mock_set_lock_resource_error`, `__mock_set_last_error`), so the failure path of `rpc_get_com_param` in `crates/iso22900-service/src/service/rpc_link.rs`, which maps the error with `map_runtime_error_for_link`, is untested. Done when: the mock has an override that makes `PDUGetComParam` fail, and a test in `crates/iso22900-service/tests/grpc_mock.rs` drives that failure and checks the returned status and `ErrorDetail`, as `link_scoped_failure_carries_error_event_data_from_last_error` does for `PDULockResource`.
- **P2**: `iso22900-mock` (`crates/iso22900-mock/src/lib.rs`) has no error-injection back door for `PDUSetComParam` (only `PDULockResource` and `PDUGetLastError` have one: `__mock_set_lock_resource_error`, `__mock_set_last_error`), so the failure path of `rpc_set_com_param` in `crates/iso22900-service/src/service/rpc_link.rs`, which maps the error with `map_runtime_error_for_link`, is untested. Done when: the mock has an override that makes `PDUSetComParam` fail, and a test in `crates/iso22900-service/tests/grpc_mock.rs` drives that failure and checks the returned status and `ErrorDetail`, as `link_scoped_failure_carries_error_event_data_from_last_error` does for `PDULockResource`.

## `j2534-0404-service`

### Known Flaky Tests

Load-sensitive tests that can fail spuriously when the full suite runs under
parallel system load. A failure here is **not** a regression unless it also
reproduces in isolation (`cargo test -p j2534-0404-service <test name>`,
several consecutive runs). `cargo-runner` consults this list before
reporting a failure as a regression (see `.claude/agents/cargo-runner.md`);
add a new entry only after confirming the same failure reproduces on a
commit that predates your change.

New timing-sensitive tests should follow the write-time guideline in
`tests/grpc_mock/harness.rs`'s module doc (ADR-149) to avoid adding to
this list in the first place.

Triage note: if widening a suspected timing margin makes a test fail
*more* often (or deterministically) rather than less, that disproves the
margin theory — stop widening and instrument instead (see
`receive_only_cyclic_reap_gated_by_exhaustive_drain_not_just_a_poll_running`
in the "Test-suite reliability: past flaky-test root causes" section of
`crates/j2534-0404-service/docs/implementation-notes.md` for a worked example).

- **`tests/grpc_mock/j1939.rs`: four tests that failed intermittently in full-module runs, cause not found.** Repeated full-module runs
  (`cargo test -p j2534-0404-service --test grpc_mock -- j1939::`) used to fail a different test about 1 run in 3 (observed:
  `optional_startcomm_message_sends_with_the_claimed_source_address`,

  `cancelling_the_optional_startcomm_message_after_a_successful_claim_stops_its_own_repeat_slots`,

  before ADR-195 made the test config path per-process. On the current tree (79 tests) 18 consecutive runs passed on Linux, 12 of
