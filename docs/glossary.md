# Glossary

This glossary defines terms used by the worker crates (`worker-crates.md`) and their ADRs. Standard abbreviations follow ISO 22900-2:2022 and SAE J2534-1 (DEC2004) unless noted otherwise.

---

## A–C

**Access Timing Parameter service** (ISO 14230-2 SID 0x83/0xC3)  
A KWP2000 service, specific to ISO 14230 (not ISO 9141, which has no equivalent), letting a tester read or set an ECU's P2/P3/P4 timing via a sub-function byte (TPI): 0 = read limits, 1 = set defaults, 2 = read active values, 3 = set given values. `j2534-0404-service` never originates this request itself — it passively observes a client-issued exchange riding the normal `CoptSendrecv` message path, and when **`CP_ModifyTiming`** is enabled, derives `CP_P2Min`/`CP_P2Max`/`CP_P2Star`/`CP_P3Min`/`CP_P4Min` from the observed TPI=2/3 values and records what the ECU reported into `CP_AccessTiming_Ecu`. Combination applies at two different levels with two different rules (ADR-146 amended, round 4): *within* one registrant's own functionally-addressed exchange, multiple ECU responses combine per field toward whichever direction is more conservative for the tester (min for P2Min, max for the rest); *across* different registrants qualifying on the same CLL in one pass — always independent SID 0x83 exchanges, never multiple ECUs answering one broadcast — the later exchange's result simply supersedes the earlier one (arrival-order / last-exchange-wins), not a worst-case combination. `CP_ModifyTiming`'s CAN/UDS sibling mechanism (ISO 15765-3/14229-3 SID 0x10/0x50 DiagnosticSessionControl on ISO15765, deriving `CP_P2Max`/`CP_P2Star` and recording what the ECU reported into `CP_SessionTiming_Ecu`, optionally redirected by the read-only `CP_SessionTimingOverride`) reuses this same pairing/storage machinery under ADR-150 — see that ADR for the UDS-specific differences (no P2Min-analog direction, so functional addressing folds both derived values toward the maximum; the session-type echo check instead of a TPI echo check). See **TimingSet**, **RxStatus / RxFlag**'s `ECU_TIMING_CHANGE` bit, ADR-146, and ADR-150.

**Additional Channels** (SAE J2534-2 clause 7)  
A SAE J2534-2 (DEC2020) mechanism letting a caller select one of up to 128 same-protocol channels on a vendor-specific connector, for a scoped set of protocols (the same seven **Pin Selection** covers). `j2534-0404-service` resolves it at `CreateComLogicalLink` (`names.rs::resolve_channel_selection`) via two routes: a directly-named **`_CHx` protocol variant** (six of the seven families; Phase 2b originally also exposed a separate `ResourceData.channel_index` field resolving identically, removed by ADR-178), decomposing back to `(base, index)` via `resources.rs::chx_base_protocol_id`; or, for SAE J2610 SCI specifically (whose four native variants all collapse onto one `_CHx` numeric block, making the direct route ambiguous), a compound-name grammar (`"<name>_CH<n>"`) in the existing `resource_name`/`protocol_name` string fields, added by a Codex-review fix to the same ADR-178 revert — see **channel_index**. No `SET_CONFIG` step is needed at `ConnectComLogicalLink`, unlike Pin Selection, since clause 7 channels are vendor-connector-based, not DLC-pin-based (ADR-156 Decision 3). Requires the connecting module to have opted into J2534-2 (clause 5). Mutually exclusive with Pin Selection: either route combined with non-default `dlc_pin_data` is rejected `INVALID_ARGUMENT`. See **channel_index**, **`_CHx` protocol variant**.

**Analog Inputs** (SAE J2534-2 clause 10)  
32 independent, read-only native ProtocolIDs (`PROTOCOL_ANALOG_IN_1`..`PROTOCOL_ANALOG_IN_32`), each connecting independently and delivering device-queued 4-byte signed little-endian millivolt readings via `PassThruReadMsgs` only — write, periodic messages, and filters are all rejected `PDU_ERR_ID_NOT_SUPPORTED`. `j2534-0404-service` models all 32 as static resource-table rows (`0x023D`-`0x025C`, ADR-069) sharing one `ChannelProtocol::ANALOG_IN` identity, each row overriding onto its own native id via `hw_protocol_override` — the same shape **SAE J2610 SCI** uses, not the `_PS`-id-is-the-identity shape UART Echo Byte/Honda DIAG-H/SAE J1708 use. Has no pin concept at all (unlike every other resource family) and no ISO 22900-2 anchor whatsoever, the first D-PDU resource family this service defines with none. The native clause 10.3.3.2.2 `SAMPLE_RATE` acquisition parameter is exposed as the project-minted **`CP_AnalogSampleRate`** ComParam (id `0x80C4`, ADR-178 — no ISO 22900-2 source), staged via `SetComParam` and resolved at `ConnectComLogicalLink` time; required staged nonzero to connect. It used to be a top-level `CreateComLogicalLinkRequest.analog_sample_rate` field (ADR-177; and before that a `ResourceData`-scoped field a Codex review finding, PR #66, found unreachable via the normal discovery flow) — both prior shapes are gone. The protocol's ComParam allowlist accepts `CP_AnalogSampleRate` plus, as of ADR-216, the clause 10.3.3.2 family's other seven parameters: four more writable ones (`CP_AnalogActiveChannels`/`CP_AnalogSamplesPerReading`/`CP_AnalogReadingsPerMsg`/`CP_AnalogAveragingMethod`) and three genuinely read-only ones (`CP_AnalogSampleResolution`/`CP_AnalogInputRangeLow`/`CP_AnalogInputRangeHigh` — this service's first read-only ComParams, populated only by a one-time connect-time `GET_CONFIG` readback, reading `0` before that; the two range params report SIGNED via the proto's `Snum32` oneof arm, this service's first signed-value-reporting ComParam). A second CLL joining an already-open `ANALOG_IN_x` channel is checked against the rate actually APPLIED to that channel (recorded on `SharedChannel`), not any CLL's live Working state, since a staged ComParam is re-stageable post-connect, and also receives the same connect-time readback the opening CLL does. See ADR-177/ADR-178/ADR-216.

**Bearer Token** (`vci1.` prefix)  
A short-lived HMAC-SHA256-signed token, presented by the gRPC client as the `authorization: Bearer <token>` metadata header on every RPC against a running worker's **`grpc_endpoint`**. It is signed with the per-instance key the agent (`worker-host`) hands the worker over its stdio control channel, and verified by the worker's own listener (a shared interceptor in `vci-service-launcher`). The key is held only by the agent and that worker: it never travels over the gRPC socket and is never handed to a separate client process. The agent mints its own tokens per call (ADR-221, ADR-231). Format: `vci-service-interface/src/token.rs`.

**Bus type ID**  
`j2534-0404-service`'s opaque `0x0301`-`0x0309` namespace identifying an ISO 22900-2 BUSTYPE row in the static resource table (`resources.rs`, ADR-069) — e.g. `0x0301` = `ISO_11898_2_DWCAN`. Distinct from the legacy `GetObjectId(OBJT_BUSTYPE, ...)`/`map_bustype_name()` mapping, which resolves straight to a J2534 protocol ID and remains a fallback for `GetResourceIds`'s `bus_type_name` selector when no table row matches. See **Resource ID**.

**CAN**  
Controller Area Network. The most common automotive serial bus (ISO 11898-2). Used at baud rates of 125 kbps, 250 kbps, 500 kbps, or 1 Mbps.

**CAN channel mode** (`can_channel_mode`)  
A per-library `config.toml` key selecting how `j2534-0404-service` maps CAN-family CLLs onto J2534 physical channels: `"single-channel"` (default — one channel per CLL), `"dual-channel"` (ISO15765 channel plus an on-demand companion CAN channel for UUDT reception), `"software-isotp"` (raw CAN channel with USDT segmentation/reassembly performed by the service, supporting both normal and extended addressing), `"auto"` (probes whether the device can hold an ISO15765 channel and a companion CAN channel open at once, then behaves as `"dual-channel"` or `"single-channel"` accordingly), or `"native-mixed"`/`"native-mixed-all-frames"` (SAE J2534-2 clause 8 "Mixed Format Frames on a CAN Network": the ISO15765 channel itself is put into `CAN_MIXED_FORMAT_ON` or `CAN_MIXED_FORMAT_ALL_FRAMES` via `SET_CONFIG`, and its UUDT response id rides a genuine `PASS_FILTER` on that same channel instead of a companion channel or the ADR-041 `FLOW_CONTROL_FILTER` workaround — requires a device that actually implements clause 8. The two sub-modes differ in one respect: under `"native-mixed"` (`ON`), a `UniqueRespIdTable` whose UUDT and USDT match keys would overlap on the same channel is rejected outright, since clause 8's either/or filter evaluation would always route the overlap to ISO15765 reassembly (ADR-162); under `"native-mixed-all-frames"` (`ALL_FRAMES`), the same table is servable instead — clause 8's filter evaluation runs in parallel per frame, so both interpretations are independently delivered (ADR-217)). See ADR-046, ADR-047, ADR-160, ADR-162, and ADR-217.

**CAN FD** — CAN with Flexible Data-Rate (SAE J2534-2 clause 21, ISO 11898-1:2015)  
A CAN bus extension supporting a higher-speed data phase and payloads up to 64 bytes (vs. Classic CAN's 8), addressed via the `PROTOCOL_FD_CAN_PS` `_PS`-only protocol ID — clause 21's Table 89 defines no unqualified base CAN FD id at all, unlike every other **`_PS` protocol variant** family. ISO 22900-2 has no separate CAN-FD resource either; a D-PDU client stages **`CP_CANFDTxMaxDataLength`**/`CP_CANFDBaudrate` on the ordinary `CAN` resource instead, and `j2534-0404-service` infers FD mode from those Working ComParams at `ConnectComLogicalLink` time (`rpc_link::J2534Service::apply_fd_mode`), substituting `PROTOCOL_FD_CAN_PS` for plain `CAN` — never accepting a directly-named `PROTOCOL_FD_CAN_PS`/`PROTOCOL_FD_CAN_CHx` protocol ID, which is rejected outright (ADR-158; `_CHx` too, ADR-213). See **data phase rate**, **TX_DL**, ADR-158.

**CAN FD Additional Channels (ADR-213):** `FD_CAN_CH1..128` participates in the existing clause-7 arithmetic mapping, keyed by its own `_PS` id like **Fault-Tolerant CAN (FTCAN)**'s/**Single Wire CAN (SWCAN/GMLAN)**'s own blocks, and named consistently with its `_PS` id (no vendor-header naming quirk, unlike SWCAN's). CAN FD is a CAN-collapse family like FTCAN/SWCAN — `base_protocol_id` normalizes `FD_CAN_PS` onto the true `CAN` base rather than self-identifying — so this round (the third and final of the `design-advisor` three-round plan ADR-211 set) inherited ADR-211's shared infrastructure fix unchanged. Unlike direct naming (still rejected outright, unchanged by this round), a `_CHx`-connected classic `CAN_CHx` link staging FD ComParams now PROMOTES to `FD_CAN_CHx` at `ConnectComLogicalLink` time (`apply_fd_mode`, index-aware via `resources::fd_protocol_id_for_link`), superseding ADR-158's own `channel_index.is_some()` rejection; clearing the FD ComParams on a later reconnect reverts symmetrically back to `CAN_CHx` (not bare `CAN`). A `_CHx` FD channel is already vendor-pin-preassigned (clause 21.3.2.5.1), so its connect does not synthesize a `CONFIG_J1962_PINS` call the way an unqualified `_PS` FD connect does — only the data-phase-rate `SET_CONFIG` fires, which is also the step that attaches the channel; the mock rejects I/O on a `_CHx` FD channel with `ERR_PIN_INVALID` until that rate is set. `is_fd_protocol_id()` is widened in place to recognize both `_PS` and `_CHx` ids (a deliberate departure from FTCAN's/SWCAN's own narrow/family-wide predicate split, since CAN FD has no `resolve_pin_selection` arm to keep the narrow form for). See **Fault-Tolerant CAN (FTCAN)**, **Single Wire CAN (SWCAN/GMLAN)**, **`_PS` protocol variant**, **`_CHx` protocol variant**, ADR-158, ADR-211, ADR-213.

**`_CHx` protocol variant**  
A SAE J2534-2 protocol ID (e.g. `PROTOCOL_CAN_CH5`) representing a base protocol (e.g. `CAN`) connected on vendor-connector index 5 of up to 128 (**Additional Channels**, clause 7). A caller names a `_CHx` ID directly (e.g. `protocol_id = PROTOCOL_CAN_CH5` — the field-based `channel_index` route, ADR-156 Decision 3, was removed by ADR-178), which `names.rs::resolve_channel_selection` decomposes to `(base, index)` via `resources::chx_base_protocol_id` (the inverse of `resources.rs::chx_protocol_id`'s `chx_base(base) + index - 1` arithmetic — each family is a contiguous 128-value block, so no per-index lookup table is needed) — accepted and self-describing, unlike a bare **`_PS` protocol variant**, for six of the seven in-scope families. For SAE J2610 SCI, the four native variants share one `_CHx` block, so this decomposition always yields the `SCI_A_ENGINE` representative regardless of which variant was actually named — the **compound-name grammar** exists specifically to let a caller still pick the exact variant for this one family. Unlike `_PS`, no `_CHx` index canonicalizes to the base id (clause 7 defines no base-equivalent index), so every distinct `_CHx` id keeps its own physical channel. Scoped, for now, to the same seven protocols **`_PS` protocol variant** is (ADR-156 Decision 3).

**channel_index**  
The resolved `1..=128` index value for one of up to 128 same-protocol **Additional Channels**, now computed by decomposing a directly-named **`_CHx` protocol variant**, or (SAE J2610 SCI only) by parsing a **compound-name grammar** suffix (the field-based `ResourceData.channel_index` input route was removed by ADR-178; this is no longer a proto field, only the internal `LogicalLinkState.channel_index`'s resolved value). Mutually exclusive with **pin_select**/`dlc_pin_data` (Pin Selection). See `resources.rs::chx_protocol_id`/`chx_base_protocol_id`, ADR-156 Decision 3, ADR-178.

**compound-name grammar**  
`names.rs`'s `"<resolvable-name>_CH<n>"` string form (case-insensitive, `n` a decimal `1..=128`), accepted only in `CreateComLogicalLinkRequest.ResourceName` and `RscData.protocol_name` — never in the numeric `ResourceId`/`protocol_id` routes. Tried only after whole-string resolution against the existing table/alias/numeric routes fails, so a plain canonical name is unaffected. Added by ADR-178's Codex-review fix specifically to let SAE J2610 SCI's four native variants (which otherwise all collapse onto one shared `_CHx` numeric block) still be individually selectable on an **Additional Channel** — the head resolves through the same name lookup a plain name uses, preserving the exact variant, while the suffix supplies the requested index. See **Additional Channels**, **channel_index**, ADR-178.

**CLL** — ComLogicalLink  
A logical view of a physical bus channel in the D-PDU API model. Multiple CLLs may share one physical channel when they resolve to the same hardware protocol, baud rate, and **pin_select** (`0` for every non-`_PS` link, so this reproduces "same protocol and baud rate" sharing for every protocol without SAE J2534-2 Pin Selection — ADR-156). A `_CHx`-qualified CLL needs no equivalent third-tuple-element widening: its hardware protocol id already differs per **channel_index**, so distinct indices naturally get distinct physical channels under the existing key (ADR-156 Decision 3). Maps to a J2534 `Channel` in the adapter layer.

**CLL handle** (`ComLogicalLinkHandle`)  
An opaque integer pair `(module_handle, cll_handle)` that uniquely identifies a CLL within a service instance.

**ComParam** — Communication Parameter  
A named parameter that controls protocol timing, addressing, and behavior. Identified by a numeric ID (e.g., `CP_BAUDRATE`) and data type (UNUM32, SNUM8, ByteField, StructField). `GetComParam`/`SetComParam`/`SetUniqueRespIdTable` accept either the numeric id or the shortname directly (`ParamItem`'s `oneof id`), resolved server-side; name-to-id resolution is CLL-independent — the same name always resolves to the same id regardless of protocol (ADR-103, ADR-104). Managed per-CLL; applied to hardware by `COPT_UPDATEPARAM`.

**Connect flags**  
The `Flags` argument of J2534 `PassThruConnect`, fixed for the channel's lifetime (bit 8 `CAN_29BIT_ID`, bit 9 `ISO9141_NO_CHECKSUM`, bit 11 `CAN_ID_BOTH`, bit 12 `ISO9141_K_LINE_ONLY`). Set by `j2534-0404-service` per protocol: raw `CAN` channels always get `CAN_ID_BOTH`; `ISO15765` and `ISO9141`/`ISO14230` flags are derived from the creator CLL's Working ComParams and UniqueRespIdTable (ADR-065). Bit 9 (`ISO9141_NO_CHECKSUM`) is the one exception to the "ComParams/UniqueRespIdTable" derivation: it comes from the creator CLL's `CllCreateFlag` RawMode/ChecksumMode combination instead (`raw_mode && !checksum_mode`, ADR-198 Phase 2) — see `docs/rpc-api-guide.md`'s `CllCreateFlag` section.

**COP** — ComPrimitive  
A single communication operation on a CLL (send a message, wait for a response, start/stop communication, etc.). Maps to a `PassThruWriteMsgs` / `PassThruReadMsgs` sequence in J2534.

**COP handle** (`ComPrimitiveHandle`)  
An opaque triple `(module_handle, cll_handle, cop_handle)` that identifies a running or completed COP.

**cop_tag** (`StartComPrimitiveRequest.cop_tag`/`EventItem.cop_tag`, ADR-204)  
An optional, opaque `bytes` value a client chooses at `StartComPrimitive` and reads back verbatim off `EventItem.cop_tag`, for correlating an event to the call that started its COP without depending on `cop_handle` alone or any client-side event-buffering discipline (a genuine ordering hazard this workspace's async poll-task architecture, ADR-021, can expose — a live event can arrive before the client has even finished consuming the matching `StartComPrimitiveResponse`). Echoed only while `cop_handle` is also present on the event; absent when no tag was supplied. Enforces a documented maximum size (`MAX_COP_TAG_LEN`, 64 bytes) at `StartComPrimitive`, rejected `INVALID_ARGUMENT` if exceeded, since the tag is echoed on every event a cyclic/periodic COP produces over its whole lifetime. Both `iso22900-service` and `j2534-0404-service` echo it uniformly on every `EventItem` variant carrying a `cop_handle` (`result_data`/`cop_status`/`error_data`). Superseded the removed `CreateComLogicalLinkRequest.cll_tag` (a complete no-op no client could ever observe, deleted outright rather than wired up — see ADR-204). See **COP handle**, ADR-204.

**COPT** — ComPrimitive Type  
The type of a COP operation:
- `COPT_STARTCOMM` (0x8001) — start communication (tester present)
- `COPT_STOPCOMM` (0x8002) — stop communication
- `COPT_UPDATEPARAM` (0x8003) — apply working-set ComParams to hardware
- `COPT_SENDRECV` (0x8004) — send a request and wait for a response
- `COPT_DELAY` (0x8005) — wait for a time interval
- `COPT_RESTORE_PARAM` (0x8006) — restore ComParams from active set

## D–F

**D-PDU API** — Diagnostic Protocol Data Unit API  
ISO 22900-2 standardized API for vehicle communication interfaces. Exposes a module/CLL/COP object model. Implemented in this project as a gRPC service (`iso22900-service`).

**data phase rate** (SAE J2534-2 clause 21, `CONFIG_FD_CAN_DATA_PHASE_RATE`)  
The CAN FD-specific bit rate used during a frame's data phase (the portion of an FD frame transmitted faster than the arbitration phase's baud rate). `j2534-0404-service` computes it as `CP_CANFDBaudrate` when nonzero, else falling back to `CP_Baudrate`, and issues it via `PassThruIoctl(SET_CONFIG, CONFIG_FD_CAN_DATA_PHASE_RATE)` — mandatorily *before* `CONFIG_J1962_PINS` on the same channel (clause 21.3.2.5.1; a native connect fails `ERR_FAILED` if this ordering is violated). See **CAN FD**, ADR-158.

**Device Configuration** — SAE J2534-2 clause 18  
A mechanism letting a caller read/write ten 4-byte non-volatile storage slots (`NON_VOLATILE_STORE_1`..`_10`) on the pass-thru device itself — persisting across power loss and firmware updates for at least 6 months per write, per clause 18.4's own notes. The first J2534-2 feature with no `ProtocolID`, pin space, or ComParam at all, and the first `DeviceID`-scoped (not `ChannelID`/CLL-scoped) IOCTL pair `j2534-0404-service` implements: `PDU_IOCTL_GET_DEVICE_CONFIG`/`PDU_IOCTL_SET_DEVICE_CONFIG` resolve `module_handle → device_id → PassThruIoctl(GET_DEVICE_CONFIG/SET_DEVICE_CONFIG)`, module-scoped like `PDU_IOCTL_READ_J1962PIN_VOLTAGE`, gated on the connecting module's J2534-2 opt-in (clause 5). Both carry a hand-packed little-endian byte payload inside the pre-existing `bytearray_data` (`IOBytearray`) `DataItem` variant — `u32 entry_count`, then `entry_count` × `{u32 parameter_id, u32 value}` (mirroring native `SCONFIG_LIST`/`SCONFIG` directly; ADR-176's original design used a dedicated `IODeviceConfigList`/`IODeviceConfigEntry` proto message pair instead, reverted by ADR-178) — the first `DataItem`-carried shape holding more than one native parameter/value pair per call, letting a client batch multiple slot reads/writes in one round trip, per clause 18.4's own guidance to conserve non-volatile write cycles this way. `GET_DEVICE_CONFIG`'s entries carry only `parameter_id` as meaningful input; `SET_DEVICE_CONFIG`'s carry both fields. A malformed payload (shorter than 4 bytes, or whose length doesn't match `entry_count`) is rejected `INVALID_ARGUMENT`. Unlike `SET_CONFIG`/`GET_CONFIG`'s ComParam-backed parameters, these ten slots have no ISO 22900-2 ComParam equivalent at all, so `parameter_id` range validation lives entirely in the native/mock layer (mirroring `PDU_IOCTL_READ_J1962PIN_VOLTAGE`'s own no-service-side-allowlist convention), not a service-side allowlist. `j2534-0404-mock` models the store as process-global state surviving `PassThruClose`/`PassThruOpen` (mirroring real non-volatile persistence), wiped only by the `__mock_reset` test backdoor. See **Repeat Messaging**, **IOCTL**, ADR-176, ADR-178.

**DLC** — Data Link Connector  
The OBD-II connector in a vehicle (SAE J1962). Has 16 pins; specific pins carry different bus signals.

**DLL** — Dynamic Link Library  
A vendor-supplied shared library (`.dll` on Windows, `.so` on Linux) that implements either the D-PDU API or J2534 PassThru API for a specific hardware device.

**DoIP** — Diagnostics over Internet Protocol  
Ethernet-based diagnostic transport (ISO 13400). Supported by D-PDU API but not by J2534 v04.04.

## E–G

**ECU** — Electronic Control Unit  
An embedded computer in a vehicle that controls one or more vehicle systems (engine, transmission, ABS, etc.).

**EnvFilter**  
A `tracing-subscriber` filter directive string that controls log verbosity. Example: `"j2534_0404_service=debug,info"`.

**Ethernet_NDIS** — SAE J2534-2 clause 24  
Binds a J2534 channel to an OS-visible NDIS/RNDIS network adapter rather than to a serial/CAN-style bus — the seventh standalone, non-CAN-family-variant J2534-2 protocol this service ships (after **UART Echo Byte Protocol**, **Honda DIAG-H Protocol**, **SAE J1708 Protocol**, **SAE J1939 Protocol**, **TP2.0 Protocol**, and **GM UART Protocol**), adding a genuinely new `ChannelProtocol::ETHERNET_NDIS` (self-mapping, `hw_protocol_override: None`) the same way. Clause 24's own scope is narrow: connect/disconnect plus one info IOCTL only — actual payload traffic is routed entirely outside the J2534 API, onto the OS network stack, so `j2534-0404-service` rejects every `ComOperationType` unconditionally (`PDU_ERR_ID_NOT_SUPPORTED`), including the receive-only exemption **Analog Inputs** grants and independent of `comm_started` state, and skips its usual pass-all `PassThruStartMsgFilter` install at connect (no COP-level API surface exists to filter for) while still leaving the channel's poll task alive, gated off only for its RX pass (`rx_supported: false`) rather than torn down. One new resource-table row (`0x0261`, `ETHERNET_NDIS`) on a standalone bus type, `IEEE_802_3` (`0x0312`) — unlike every earlier standalone protocol's own editorially-picked bus-type name, this is the first one with a real ISO 22900-2:2022 Table B.2 anchor: that table already names `IEEE_802_3` as DoIP's own physical-layer bus-type short name. Pin data follows clause 24 Table 103's own J1962 pin set (the pin numbers themselves are not editorial); only the pin *typing* is editorial, mirroring **SAE J1708 Protocol**'s own precedent for an unconstrained pin-type default. A new ComParam, `CP_NdisPinOption`, resolves into `CONNECT_FLAG_NDIS_PINS_OPTION1`/`OPTION2` at `ConnectComLogicalLink` time; a native `ERR_NO_CONNECTION_ESTABLISHED` at connect maps to `PDU_ERR_NO_CABLE_DETECTED`. The one surviving IOCTL, `PDU_IOCTL_GET_NDIS_ADAPTER_INFO`, hand-packs the native `NDIS_ADAPTER_INFORMATION` struct (adapter ID/name, link status, MAC/IPv4/IPv6 addresses, pin config) into an `IOBytearray` DataItem (ADR-178 convention). See **CAN FD**, **TP2.0 Protocol**, **GM UART Protocol**, **`_PS` protocol variant**, ADR-194.

**Extended addressing** (ISO 15765-2)  
An ISO-TP addressing mode that prepends a one-byte Address Extension (AE) to every frame (SF/FF/CF/FC), reducing each frame's payload capacity by 1 byte. Selected per UniqueRespIdTable entry via `CP_Can*Format` Table B.13 bit 3, with the AE value in the paired `CP_Can*ExtAddr` ComParam. Supported by both the hardware `FLOW_CONTROL_FILTER` path (`rpc_link.rs`) and the software ISO-TP engine (`isotp::Addressing::Extended`, ADR-047).

**ExtraDataIndex**  
A field on the native `PASSTHRU_MSG` struct (SAE J2534-1 §8.2/§8.5) marking the offset within `Data` at which trailing In-Frame Response (IFR) bytes begin — everything from `ExtraDataIndex` to `DataSize` is IFR, not core protocol data. A conforming device reports `ExtraDataIndex == DataSize` (no trailing bytes) for every received message except a J1850 PWM frame genuinely carrying IFR bytes; J1850 VPW has no IFR mechanism at all. `j2534-0404-service` reads this via `PassThruMessage::extra_data_index()` and threads it into `header_footer_len`'s J1850 PWM RX-footer computation only (defensively clamped, since it crosses the FFI boundary from an untrusted vendor DLL), replacing a prior fixed-1-byte-CRC assumption that turned out to have no basis in the spec; the VPW arm ignores it unconditionally, since VPW has no IFR mechanism to consult it for. `j2534-0404-mock` models it via `StoredMessage::extra_data_index`. See ADR-171.

**Fault-Tolerant CAN (FTCAN)** — SAE J2534-2 clause 20, ISO 11898-3  
A low-speed, fault-tolerant CAN physical layer defined by ISO 11898-3, used on either of two J1962 pin-pairs (1/9 or 3/11) instead of dual-wire CAN's 6/14. Clause 20's own text is short: it treats `FT_CAN_PS`/`FT_CAN_CHx` as the same as `CAN_PS`/`CAN_CHx` apart from the differences it names explicitly, and likewise `FT_ISO15765_PS`/`_CHx` vs. `ISO15765_PS`/`_CHx` — no unqualified base id exists, the same shape **Single Wire CAN (SWCAN/GMLAN)** has, and ISO 22900-2 similarly models `ISO_11898_3_DWFTCAN` as its own independently client-selectable bus type, not a ComParam-inferred substitution. `j2534-0404-service` gives it ten dedicated resource-table rows (`0x0230`-`0x0239`, ADR-069) on a new `ISO_11898_3_DWFTCAN` bus type (`0x030A`), reusing each dual-wire-CAN sibling row's `ChannelProtocol` but with its own `protocol_name` (`_FTCAN` suffix) — unlike SWCAN's single default pin, FTCAN's rows carry a genuine two-pin default (pin 1/HI, pin 9/LOW, clause 20.2.1's first-listed pin-pair), since FTCAN is a differential pair like DWCAN, not single-wire. Connect always issues an explicit `SET_CONFIG(CONFIG_J1962_PINS)`, mirroring SWCAN's own mandatory pin-assignment requirement. `is_ft_protocol_id()`/`base_protocol_id()` arms let the rest of the service treat an FT link as its base `CAN`/`ISO15765` family for free, the same funnel ADR-157 established for every other `_PS`/`_CHx` id. No new ComParam translations or IOCTLs (unlike SWCAN's `CP_ChangeSpeed*`/`SW_CAN_HS`/`_NS`). **FT Additional Channels (ADR-211):** `FT_CAN_CH1..128`/`FT_ISO15765_CH1..128` participate in the existing clause-7 arithmetic mapping, keyed by their own `_PS` id (like SWCAN's own later ADR-212 extension) rather than a native base id. Unlike every other family this series closed (ADR-206 through ADR-210), FT-CAN is a CAN-collapse family — `base_protocol_id` normalizes `FT_CAN_PS`/`FT_ISO15765_PS` onto the true `CAN`/`ISO15765` base rather than self-identifying — so wiring `_CHx` support required a shared infrastructure fix first: `base_protocol_id`'s generic `_CHx`-normalization fallback now recurses once more (so a `_CHx` id resolves all the way to the true base, not just to the family's own `_PS` id), and `names.rs::resolve_channel_selection`'s compound-name route now computes the `_CHx` id from the raw, un-normalized row id rather than the normalized base. Both fixes are a no-op for every already-shipped family. The narrow, exact-match `is_ft_protocol_id()` predicate stays as-is for `names.rs`'s own arm-gate purpose and the mock's `pins_assigned` gate; every other family-wide call site (`connect_discovery_check`, `bustype_default_name_for_hw_protocol_id`, `apply_fd_mode`'s FT-vs-FD rejection guards, `GetResourceStatus`/`GetConflictingResources` query matching) now uses the new range-inclusive `is_ft_family_protocol_id()` instead. `LINK_FAULT` (RxStatus bit 17) forwarding into **RxStatus / RxFlag** was decided against outright by ADR-191 — the message is genuine, already-delivered content (Table 86), so only the fault annotation itself is missing, recorded as a closed accepted residual rather than an open item. See **Single Wire CAN (SWCAN/GMLAN)**, **`_PS` protocol variant**, **`_CHx` protocol variant**, ADR-168, ADR-191, ADR-211.

**FD_ISO15765_PS** — ISO15765-on-CAN-FD (SAE J2534-2 clause 22)  
A SAE J2534-2 protocol ID for running ISO 15765-2:2016 diagnostic transport over a CAN FD physical link — clause 22's Table 96 defines only `_PS`/`_CHx` variants, no unqualified base id, the same shape **CAN FD** has for clause 21. ISO 22900-2 again has no clause-22-specific resource, but unlike clause 21 it already owns every tuning concept clause 22 exposes as a native `SET_CONFIG` parameter: `CP_CANFDTxMaxDataLength`, `CP_Cr`, and `CP_CanFillerByte` gain their first non-identity native mappings (`CONFIG_FD_ISO15765_TX_DATA_LENGTH`, `CONFIG_N_CR_MAX`, `CONFIG_ISO15765_PAD_VALUE`) on this protocol specifically. `j2534-0404-service` infers FD mode the same way it does for **CAN FD** — `rpc_link::J2534Service::apply_fd_mode`'s ISO15765 branch substitutes `FD_ISO15765_PS` for plain `ISO15765` when the same `TX_DL > 8 || CP_CANFDBaudrate != 0` trigger fires on an ISO15765-connected CLL — never accepting a directly-named `FD_ISO15765_PS`/`FD_ISO15765_CHx` id, both rejected outright. Unlike raw CAN FD (where this service constructs every frame itself), the native adapter runs the real ISO15765 segmentation/flow-control state machine on this link, so TX message-size validation uses a constant `4..=4128`/`5..=4128` range (Table 98) with no service-side padding. See **CAN FD**, **TX_DL**, **data phase rate**, ADR-159.

**ISO15765-on-CAN-FD Additional Channels (ADR-213):** `FD_ISO15765_CH1..128` participates in the existing clause-7 arithmetic mapping, the exact ISO15765 analog of **CAN FD**'s own `FD_CAN_CHx` support — see that entry's "CAN FD Additional Channels" section for the full mechanism (index-aware promotion/reversion via `apply_fd_mode`, no `CONFIG_J1962_PINS` synthesis, the mock's attach-on-rate `ERR_PIN_INVALID` gate). Direct naming of `FD_ISO15765_CHx` stays rejected outright, unchanged by this round. See ADR-159, ADR-213.

**Generic OBD**  
The emissions-related diagnostic data that vehicles under an OBD mandate (depending on jurisdiction, vehicle class and model year) must report to any scan tool, with standardized requests and identifiers: SAE J1979 / ISO 15031-5 (on ISO 15765-4, and on ISO 9141-2, ISO 14230-4 or SAE J1850 in older vehicles), SAE J1979-2 ("OBD on UDS") and WWH-OBD (ISO 27145). The system provides it as a standard vehicle-knowledge package, independent of maker ODX data (ADR-237).

**GM UART Protocol** — SAE J2534-2 clause 11 (GM UART, SAE J2740)  
GM's master/slave UART bus: the tester must be granted bus mastership (a poll-message/poll-response handshake, or an immediate grant on vehicles with no bus master) before diagnostic communication can begin — the seventh standalone, non-CAN-family-variant J2534-2 protocol this service ships (after **UART Echo Byte Protocol**, **Honda DIAG-H Protocol**, **SAE J1708 Protocol**, **SAE J1939 Protocol**, and **TP2.0 Protocol**), adding a genuinely new `ChannelProtocol::GM_UART_PS` (`0x00008009`, self-mapping, `hw_protocol_override: None`) the same way. Clause 11's own text makes the mastership *negotiation logic* (when to listen, retry/backoff, deciding a poll was missed) the client application's responsibility, not this service's — the device/driver's job is limited to two new thin, synchronous `PassThruIoctl` sub-functions, `SET_POLL_RESPONSE` (defines the poll-response message bytes to transmit) and `BECOME_MASTER` (waits up to ~2s for a matching poll message, or grants immediately if `Poll_ID` is zero, then transmits the poll response), each forwarded via the existing `IoCtl` RPC as new `L`-scoped ADR-079 commands, no service-owned state machine involved. One new resource-table row (`0x0260`, `GM_UART`, ADR-069) on a minted standalone bus type, `GM_UART_UART` (`0x0311`) — clause 11 has no ISO 22900-2 preset at all, the **Analog Inputs**/**TP2.0 Protocol** minting precedent. Clause 11.2.2 documents exactly two valid single pins (J1962 pin 9 primary, pin 1 secondary) with no spec-mandated default — the same closed-two-single-pin shape **Honda DIAG-H Protocol** already established, mirrored exactly (only the pin numbers and default, 9 not 14, differ). **The first standalone protocol to also support Additional Channels (`_CHx`):** `GM_UART_CH1..CH128` participate in the existing arithmetic `_CHx` mapping unchanged, keyed by `GM_UART_PS` itself rather than a native base id, since clause 11 defines no unqualified base id to key by instead. Unlike every other standalone protocol shipped so far, clause 11 defines no ComParam concept at all (no baud rate, no timing parameters) — the bustype default seeds no non-zero values, and no protocol-specific ComParam allowlist branch was added (an open question left for a future pass). See **CAN FD**, **Single Wire CAN (SWCAN/GMLAN)**, **Honda DIAG-H Protocol**, **TP2.0 Protocol**, **`_PS` protocol variant**, **`_CHx` protocol variant**, ADR-189.

**gRPC**  
Google Remote Procedure Call framework. Used to expose VCI service APIs. Messages are serialized with Protocol Buffers. The service uses gRPC HTTP/2 transport; gRPC-Web support for browser clients is provided directly by each worker's own listener (`vci-service-launcher`, via `tonic-web`); nothing proxies gRPC traffic (ADR-221). See **`grpc_endpoint`**, **Bearer Token**.

**`grpc_endpoint`**  
The `SocketAddr` (e.g. `127.0.0.1:54321`, or `[::1]:54321` on an IPv6-only host — see ADR-052, ADR-220) a running service instance is actually listening on, reported by the worker's `get_status` reply on the stdio control channel. The agent connects here **directly**, presenting a **Bearer Token** signed with that worker's key.

## H–J

**Handle**  
An opaque numeric identifier for an API object. In this project, handles are newtype-wrapped `u32` values.

**Honda DIAG-H Protocol** — SAE J2534-2 clause 13  
Honda's proprietary "92 Hm/2" diagnostic message format over "DIAG-H," a single-wire, half-duplex, UART-based physical layer at a fixed 9600bps — architecturally the second standalone, non-CAN-family J2534-2 protocol this service ships (after **UART Echo Byte Protocol**), adding a genuinely new `ChannelProtocol::HONDA_DIAGH_PS` (self-mapping, `hw_protocol_override: None`) the same way. One new resource-table row (`0x023B`, ADR-069); default pin 14 — the pin Honda's own diagnostic application always targets per clause 13.2.4, including through the adapter cables 3-pin/5-pin-DLC vehicles use — always issuing an explicit `SET_CONFIG(CONFIG_J1962_PINS)` on connect. Unlike UART Echo Byte (no documented closed pin set) or **Single Wire CAN (SWCAN/GMLAN)** (one valid pin), clause 13.2.4 documents exactly two valid single pins (1 and 14) — a closed-set check in `resolve_pin_selection` accepts either and rejects every other single pin. Its ComParam surface (`LOOPBACK`/`P1_MAX`/`P3_MIN`/`P4_MIN`, clause 13.3.3.1's closed list) deliberately excludes `DATA_RATE` from `SetComParam`/`GetComParam` reach — the first J2534-2 phase to do so, since clause 13's baud rate is fixed, not `SetComParam`-configurable — reusing ISO9141's own K-line timing defaults (`P1_MAX`/`P3_MIN`/`P4_MIN`) per clause 13.3.1's explicit reuse. `DATA_RATE` is nonetheless seeded internally at 9600bps in `comparam_defaults.rs`'s `honda_diagh_uart()`, purely so `PassThruConnect`'s native baud-rate argument (via `ComParamSet::baud_rate()`) is populated correctly — a client-facing exclusion, not an absence of the value (Codex review finding, PR #63). `CoptStartcomm`'s `cop_data` is treated as a genuine optional message (like CAN/J1850/SCI), not an init address like UART Echo Byte's mandatory 5-baud byte — clause 13 defines no initialization process at all, so this protocol is deliberately excluded from the service's `is_kline` init-eligibility classification (design-advisor decision, ADR-174), the opposite classification from UART Echo Byte despite both sharing a K-line-like single-wire UART physical layer. **Repeat Messaging** needs no protocol-specific rejection (clause 13 has no exclusion equivalent to UART Echo Byte's clause 12.3.3.1). Additional Channels and Discovery-cache connect-time wiring are out of scope this phase. See **CAN FD**, **Single Wire CAN (SWCAN/GMLAN)**, **UART Echo Byte Protocol**, **SAE J1708 Protocol**, **`_PS` protocol variant**, ADR-174.

**ISO 15765-2** (ISO-TP)  
Transport protocol that provides segmentation and reassembly of large diagnostic messages over CAN. Used by most modern OBD-II and UDS diagnostics.

**ISO 22900-2**  
The standard defining the D-PDU API. This project implements it as a gRPC service.

**IOCTL** — Input/Output Control  
A generic mechanism in both D-PDU API and J2534 for hardware-specific commands (voltage measurement, filter management, DoIP entity setup, etc.). `j2534-0404-service` implements the 25 D-PDU `PDU_IOCTL_*` commands (`PDU_IOCTL_RESET`, `PDU_IOCTL_SUSPEND_TX_QUEUE`, `PDU_IOCTL_SET_EVENT_QUEUE_PROPERTIES`, etc., ADR-079; plus `PDU_IOCTL_SW_CAN_HS`/`PDU_IOCTL_SW_CAN_NS`, ADR-164; plus `PDU_IOCTL_START_REPEAT_MESSAGE`/`_QUERY_REPEAT_MESSAGE`/`_STOP_REPEAT_MESSAGE`, ADR-165 — see **Repeat Messaging**; plus `PDU_IOCTL_READ_J1962PIN_VOLTAGE`, Phase 13; plus `PDU_IOCTL_GET_DEVICE_CONFIG`/`PDU_IOCTL_SET_DEVICE_CONFIG`, ADR-176 — see **Device Configuration**), resolved by name via `GetObjectId(OBJT_IO_CTRL, ...)`. A native J2534 `IoctlID` in SAE J2534-1's tool-manufacturer-reserved range (`0x10000`-`0xFFFFFFFF`) is instead forwarded raw to native `PassThruIoctl` via a vendor passthrough (`rpc_misc.rs::rpc_io_ctl_vendor`), selecting raw-pointer vs. `SBYTE_ARRAY` payload shape via a client-supplied flags header. As amended (a Codex review round, PR #133): since the client's flag bit can request either shape regardless of what a given `cmd_id`'s real native contract expects, and a bare fixed capacity cap is itself an invented, unsafe bound, a per-library `vendor_ioctls` config table (`config.apis.j2534-0404.libs."<lib>".vendor_ioctls."0x<cmd_id>"`, `VendorIoctlConfigEntry{shape,input_bytes,output_bytes}`, see `vci-service-config`'s `find_vendor_ioctls`) is the sole source of each vendor command's shape and (for raw mode) exact buffer sizes, loaded and fail-fast validated once at startup; a `cmd_id` carrying a non-NULL buffer with no configured entry fails `FAILED_PRECONDITION`, and a client-selected shape not matching the configured one fails `INVALID_ARGUMENT`. See ADR-219.

**IS-CYCLIC**  
`ComPrimitiveCtrlData.NumReceiveCycles == -1`: the COP's receive phase waits inline for the first matching response only, with the normal `CP_P2Max` window (ADR-053). On the first positive match, a `COPT_SENDRECV` COP detaches into the **Receive Only** tier and returns, freeing its CLL/channel for other COPs to execute while it keeps matching responses indefinitely in the background (ADR-100 Decision §2/§3, S5) — this is the ISO 22900-2 §9.2.6.3.4-compliant replacement for the pre-ADR-100 behavior of blocking the poll task until `CancelComPrimitive`. The detached COP still reports `PDU_COPST_EXECUTING` via `GetStatus` and ends via `CancelComPrimitive`, a hard channel error, generation-staleness (reconnect), or — if configured — `CP_CyclicRespTimeout` (ADR-100 Decision §4, S6; scope widened to also cover a created-receive-only COP with a positive `NumReceiveCycles` by ADR-182; see **NumReceiveCycles**' `-1` row). Rejected synchronously (`INVALID_ARGUMENT`) on `COPT_STOPCOMM`'s optional final-message receive phase, since that COP must terminate to return the CLL to `PDU_CLLST_ONLINE` (ADR-087). See **IS-MULTIPLE**, **NumReceiveCycles**, **Receive Only**.

**IS-MULTIPLE**  
`ComPrimitiveCtrlData.NumReceiveCycles == -2`: the COP's receive phase collects every matching response from one or more ECUs until the `CP_P2Max` window (restarted after each accepted response) closes — the normal shape for a functionally-addressed request answered by several ECUs (ADR-053). Valid on both `COPT_SENDRECV` and `COPT_STOPCOMM`'s optional final-message receive phase; on `COPT_STOPCOMM` specifically, an additional absolute ceiling (`max(16 × CP_P2Max, 2000ms)`) bounds the total wait against a chatty ECU, since that receive phase is non-cancellable (ADR-087). See **IS-CYCLIC**, **NumReceiveCycles**.

**J2534**  
SAE J2534 ("PassThru") standard for vehicle interface adapters. The worker supports v04.04 (DEC2004), implemented as a gRPC adapter (`j2534-0404-service`). v05.00 is not supported.

## M–O

**Module** (D-PDU API)  
A logical representation of one VCI hardware device. Maps to a J2534 `Device`. Identified by a `ModuleHandle`.

**Module** (J2534)  
The hardware device opened by `PassThruOpen`. Has one `DeviceId`. In `j2534-0404-service`, one module exists per configured **Module config entry** (or a single default module when none are configured); the service opens at most one device at a time regardless of how many modules are configured (ADR-107).

**Module config entry** (`modules`, `pname`)  
A `j2534-0404-service` `config.toml` entry under `config.apis.j2534-0404.libs."<lib>".modules` (a TOML array-of-tables) pre-declaring one selectable physical device: a human-readable `label` (surfaced as `ModuleData.vendor_module_name`) and a `pname` connection-target string passed verbatim as `PassThruOpen`'s `pName` argument. J2534-1 v04.04 has no in-spec device-selection mechanism (`pName` must be NULL per spec §7.2.1); passing a configured non-NULL `pname` is an out-of-spec vendor extension some J2534 DLLs support (ADR-107). `module_handle` is the entry's 1-based position in the configured array. When `modules` is omitted, the service synthesizes a single default entry (`pname = None`, i.e. `PassThruOpen(NULL, ...)`) matching pre-ADR-107 behavior.

**MsgId** — SAE J2534-2 clause 14 (**Repeat Messaging**)  
The interface-assigned identifier a `PDU_IOCTL_START_REPEAT_MESSAGE` call returns for the repeat slot it just created, used by a later `PDU_IOCTL_QUERY_REPEAT_MESSAGE`/`PDU_IOCTL_STOP_REPEAT_MESSAGE` call to poll or cancel that same slot. `j2534-0404-service` never allocates a `MsgId` itself — it is a device-side value forwarded verbatim — but tracks each one against the `ComLogicalLink` that started it (`LogicalLinkState::repeat_message_ids`, ADR-165 Decision 4): a `QUERY`/`STOP` naming a `MsgId` this CLL never started, including one started by a sibling CLL sharing the same physical channel (the device itself has no notion of CLL identity on a shared channel), is rejected `PDU_ERR_INVALID_MSG_ID` before ever reaching the native call. See **Repeat Messaging**.

**MVCI** — Modular Vehicle Communication Interface  
The physical hardware device that connects a PC to a vehicle bus. Also called VCI or J2534 adapter.

**NRC** — Negative Response Code  
A UDS/ISO 14229 status byte returned in a negative response message. Key NRCs handled by this project:
- `0x78` — requestCorrectlyReceived-ResponsePending (triggers auto-wait, see ADR-018)
- `0x21` — busyRepeatRequest
- `0x23` — uploadDownloadNotAccepted

**N_WFTmax** — Wait Frame Transmissions maximum  
The ISO 15765-2 (ISO-TP) network-layer parameter bounding how many consecutive FlowControl `FS_WAIT` frames a network layer entity may itself TRANSMIT while acting as the *receiver* of a segmented message (i.e. when generating its own FlowControl replies), not how many it tolerates receiving as the *sender*. `ISO15765_WFT_MAX` is the J2534 `SET_CONFIG` parameter carrying this value to native hardware; ISO 22900-2's equivalent, `CP_CanMaxNumWaitFrames`, expresses the same limit as a `PDU_PT_UNUM32` (range `[0, 1027]`). `j2534-0404-service`'s `software-isotp` mode (ADR-046) never sends `FS_WAIT` on its RX/reassembly path (always `FS_CONTINUE_TO_SEND`), so this comparam is currently satisfied trivially by this implementation; it is still forwarded to native hardware unchanged. The TX driver's own defense against a WAIT flood from a peer is a separate, internal-only bound (ADR-124, superseding ADR-121's earlier — incorrect-direction — attempt to enforce this comparam on the TX/sender side).

**NumReceiveCycles** (`ComPrimitiveCtrlData.NumReceiveCycles`)  
Governs a COP's receive phase: `0` = no response required at all — the cycle completes immediately after the write, regardless of `expected_response_array` (ADR-058); `n > 0` = exactly `n` matching responses — the `CP_P2Max` window restarting after each for a `NumSendCycles != 0` (SEND-AND-RECEIVE) COP, but for a created-receive-only (`NumSendCycles == 0`, ADR-059) COP, `CP_CyclicRespTimeout` governs it exclusively instead (ADR-182, see **Receive Only**); `-1` = **IS-CYCLIC**; `-2` = **IS-MULTIPLE**; values below `-2` are rejected (`INVALID_ARGUMENT`). See ADR-053 for `COPT_SENDRECV`'s original cycle semantics and ADR-087 for `COPT_STOPCOMM`'s optional final-message receive phase, which reuses the same field with `-1` additionally rejected.

## P–R

**PassThru** — J2534 PassThru API  
The function interface exported by a J2534 DLL: `PassThruOpen`, `PassThruConnect`, `PassThruReadMsgs`, `PassThruWriteMsgs`, `PassThruIoctl`, etc.

**PDU** — Protocol Data Unit  
A unit of data at a given protocol layer. In D-PDU API context, a PDU is a framed diagnostic message.

**PDU_EVT_DATA_LOST** (async event)  
ISO 22900-2 §9.5.16's event for a CLL event queue reaching a full state (per D.1.8, the event data itself is not stored in the queue) — it is a callback-only, information-only signal, never a queue item. `j2534-0404-service` emits it (ADR-115) via `SubscribeEvent`'s `LostEventItemNotification` only. The CLL event queue has single-consumer semantics: a live subscriber opportunistically drains it (any pre-existing backlog streams out live, FIFO, on the very next push), but the queue's `event_queue_cap`/`event_queue_mode` policy is still enforced on every item regardless of subscriber state — matching the native D-PDU model, where a registered callback doesn't grant unlimited queue capacity. A healthy, keeping-up subscriber almost never sees `Lost` in practice (the queue empties every cycle), but a backlog that built up before the subscriber attached can still cross the cap on the next push, firing exactly one `Lost` even to an actively-succeeding live subscriber. `Lost` fires once per drop: a `Limited`-mode CLL sends it instead of the discarded item's own notification; a `Circular`-mode CLL sends it alongside the newly-inserted item's notification, marking the evicted older item's loss from the queue. A poll-only client (`GetEventItem`, no live subscription) never observes this event — the shared proto's `EventItem` has no `Lost` variant, mirroring a native D-PDU client with no registered callback.

**PDU_ERR_EVT_RSC_LOCKED** (async error event)  
ISO 22900-2 §9.4.16 d)'s error event for a non-owning CLL's `CoptUpdateparam` attempting to modify a `PDU_PC_BUSTYPE`-class ComParam another CLL holds `LOCK_PHYSICAL_COM_PARAMS` on. Distinct from the synchronous status codes `PDU_ERR_RSC_LOCKED`/`PDU_ERR_RSC_LOCKED_BY_OTHER_CLL` (still used elsewhere, e.g. `LockResource`/`UnlockResource`, `ConnectComLogicalLink`, `SetUniqueRespIdTable`): per the spec, a lock conflict on `CoptUpdateparam` never rejects the call — the COP is created, every non-conflicting ComParam still applies, at most one `PDU_ERR_EVT_RSC_LOCKED` fires for the conflicting `PDU_PC_BUSTYPE`-class ones, and the COP still finishes normally (`PDU_COPST_FINISHED`) (ADR-110, superseding ADR-044's synchronous rejection).

**PDU_PC_BUSTYPE** (ComParam class)  
The ISO 22900-2 ComParam class covering physical-layer/bus-configuration parameters (`CP_Baudrate`, CAN bit timing/sample point, UART config, termination, network line selection — see `j2534-0404-service/docs/comparam-protocol-support.md`'s "Physical Layer ComParams (BUSTYPE class)" table). Distinct from `PDU_PC_UNIQUE_ID` (per-ECU addressing, managed via `SetUniqueRespIdTable`, ADR-042). `j2534-0404-service` rejects `temp_param_update` calls that would stage a `PDU_PC_BUSTYPE` difference between Working and Active (ADR-067).

**Pin Selection** (SAE J2534-2 clause 6)  
A SAE J2534-2 (DEC2020) mechanism letting a caller request DLC pins other than a protocol's default wiring, for a scoped set of protocols. `j2534-0404-service` resolves it at `CreateComLogicalLink` (`names.rs::resolve_pin_selection`/`compute_pin_select`) from `ResourceData.dlc_pin_data`, then binds the chosen pins at `ConnectComLogicalLink` via `CONFIG_J1962_PINS`, inside the same rollback-protected connect sequence (ADR-156). Requires the connecting module to have opted into J2534-2 (its `pname` carrying the `"J2534-2:"` prefix); applies only when the resource resolves via `protocol_id` or a generic `protocol_name` alias, not a canonical resource name matching a resource-table row (ADR-156's Corrections). See **`_PS` protocol variant**, **pin_select**.

**pin_select**  
The `0x0000PPSS`-packed `u32` bitmask `j2534-0404-service` computes from a caller's `dlc_pin_data` for **Pin Selection** (`names.rs::compute_pin_select`) and applies to a `_PS` channel via `PassThruIoctl(SET_CONFIG, CONFIG_J1962_PINS)` — `PP` the primary (HI/K/TX/PLUS) pin number, `SS` the secondary (LOW/L/RX/MINUS) pin number, `SS = 0` for a single-wire protocol. Also the third element of the `ChannelKey` (ADR-156, widened again to a fourth element by ADR-158 for the CAN FD data-phase rate): two `_PS` links selecting different pins never share a physical channel, even at the same hardware protocol and baud rate.

**Pin type ID**  
`j2534-0404-service`'s stable logical ID (2000-range: `HI`=2000, `LOW`=2001, `K`=2002, `L`=2003, `TX`=2004, `RX`=2005, `PLUS`=2006, `MINUS`=2007, `SINGLE`=2008, `IGN`=2009, `PROGV`=2010) for an ISO 22900-2 PINTYPE short name (`names.rs::map_pintype_name`), independent of any specific DLC connector pin number. Each **Resource ID** row's typed `dlc_pins` pair a pin number with one of these IDs (e.g. `(6, 2000)` for a CAN `HI` pin); `GetResourceIds`'s pin selectors and `CreateComLogicalLink`'s pin-driven configuration narrowing (e.g. disambiguating `SAE_J2610_on_SAE_J2610_SCI`'s four SCI wirings) both match against these typed pairs.

**`_PS` protocol variant**  
A SAE J2534-2 protocol ID (e.g. `PROTOCOL_CAN_PS`) representing a base protocol (e.g. `CAN`) connected with caller-selected DLC pins that are left unassigned at connect time until a **pin_select** `CONFIG_J1962_PINS` `SET_CONFIG` call binds them. `j2534-0404-service` resolves to a `_PS` variant automatically when **Pin Selection** applies (`resources.rs::ps_protocol_id`) — the common case. A caller may also name a `_PS` ID directly (e.g. `protocol_id = PROTOCOL_CAN_PS`), which `names.rs::resolve_pin_selection` normalizes back to its base id via `resources::base_protocol_id` before resolution; such a request always requires `dlc_pin_data` to assign the pins with, since a `_PS` ID has none by default (rejected `INVALID_ARGUMENT` otherwise). Scoped, for now, to the seven protocols SAE J2534-2 clause 6.3.1 Table 1 lists (ADR-156).

**Proto** — Protocol Buffers  
Serialization format used for gRPC messages. Schema lives in `vci-service-interface/src/proto/service.proto`.

## R–S

**RDF** — Root Description File  
An XML file that lists installed D-PDU API libraries with their short names and DLL paths. Read by `iso22900-registry`. Located via the Windows registry (`HKLM\SOFTWARE\D-PDU API\Root File`) or, on non-Windows, the hardcoded path `/etc/pdu_api_root.xml`; there is no environment-variable override. `iso22900-service` consults a `library_path` config override (see **Library Path Override**) before falling back to RDF-based lookup, so a library name can be resolved without an RDF file at all.

**RC-Pending** — Response-Code Pending  
Informal shorthand for NRC 0x78 (`requestCorrectlyReceived-ResponsePending`). The ECU sends this to indicate it received the request but needs more time to compute the response.

**Receive Only** (registrant tier)  
ISO 22900-2 §9.2.6.3.4's "Receive Only list" — the second of `j2534-0404-service`'s two per-CLL COP-attribution tiers (ADR-100 Decision §2, alongside **active Send/Receive**), scanned only after both an active-Send/Receive claim and tester-present's own signature check have failed to bind a frame. Populated by (a) a COP created with `NumSendCycles == 0` (ADR-059), and (b) an **IS-CYCLIC** COP that migrated in place after its first positive response (ADR-100 Decision §2/§3, S5). Tier-2 registrants are plain-match only — ISO 22900-2 §9.2.6.3.4's 7F clause excludes receive-only ComPrimitives from negative-response auto-handling entirely — so pending-RC (0x7F/0x21/0x23/0x78) detection never runs for them, unlike tier-1. A vacuous (empty mask/pattern) `ExpectedResponseStructure` is this tier's spec-sanctioned use case (broad bus monitoring) and is the documented migration path for a client that relied on the pre-ADR-100 unsolicited-delivery-of-everything behavior (see **Unbound Frame**). A created-receive-only registrant with `NumReceiveCycles == -1` OR a positive `n` additionally supports `CP_CyclicRespTimeout` as its SOLE completion-timing mechanism (ADR-100 Decision §4, S6, scope widened from `-1`-only to also cover positive `n` by ADR-182 — `CP_P2Max` never governs either subtype): a nonzero value finishes the COP if no match arrives within the timeout, restarted on each accepted match; `0` (default, every protocol preset) disables it, so the COP runs until its target count is reached (positive `n` only) or `CancelComPrimitive`/a hard channel error/reconnect-driven generation-staleness ends it. For the positive-`n` subtype, an expiry with the target count still unmet additionally raises a receive-timeout error before finishing; reaching the target count itself always finishes the COP with no error, taking priority over a concurrently-running deadline, with up to one internal maintenance-tick's latency (not immediate). Both subtypes are tier-2 from the instant they are registered — unlike a migrated IS-CYCLIC registrant, neither has an active-Send/Receive phase to migrate out of — so each frees its physical channel's poll task immediately rather than waiting for its own first accepted match (or, for the positive-`n` subtype, its full count); more than one such monitor may be live on CLLs sharing one physical channel with neither blocking the other or any other queued COP. A created-receive-only `NumReceiveCycles == -2` (**IS-MULTIPLE**) registrant is unaffected by this ADR-182 widening: it is tier-2 from creation too (round-9 Finding-1), but keeps running inline/blocking, `CP_P2Max`-governed, exactly as before.

**Registry** (Windows)  
Windows registry keys used to discover installed VCI libraries:
- D-PDU API: `HKLM\SOFTWARE\D-PDU API\Root File`
- J2534 v04.04: `HKLM\SOFTWARE\PassThruSupport.04.04\<device-name>\FunctionLibrary`
- J2534 v05.00: `HKLM\SOFTWARE\PassThruSupport.05.00\<device-name>\FunctionLibrary`

**Repeat Messaging** — SAE J2534-2 clause 14  
A mechanism letting a caller hand the interface a message, a retransmit interval, and a stop-**`MsgId`**-condition (`Condition`); the interface then autonomously retransmits it on the interval timer and evaluates every incoming frame against a caller-supplied mask/pattern itself, entirely device-side (no software timer or RX evaluation on the API-caller side) — regardless of which `Condition` is selected, per clause 14.2.1. `Condition == 0` (`REPEAT_MESSAGE_UNTIL_MATCH`) retransmits through silence and stops only on a matching received frame; `Condition == 1` (`REPEAT_MESSAGE_WHILE_MATCH`) retransmits only while every received frame matches, and stops on the first non-matching frame *or* on a silent interval — two independent stop triggers (ADR-173, correcting an inversion of this pairing in ADR-165's original design). `j2534-0404-service` is a thin forwarder for this feature (ADR-165), the same position it already occupies for **Single Wire CAN**'s `SW_CAN_HS`/`SW_CAN_NS` **IOCTL**s: `PDU_IOCTL_START_REPEAT_MESSAGE`/`_QUERY_REPEAT_MESSAGE`/`_STOP_REPEAT_MESSAGE` resolve `cll_handle → channel_id → PassThruIoctl(*_REPEAT_MESSAGE)` directly, gated on the connecting module's J2534-2 opt-in (clause 5). `QUERY_REPEAT_MESSAGE` reports 1 for a still-live slot and 0 for one that has self-terminated but not yet been explicitly stopped — the `MsgId` remains valid, and the slot remains tracked, until an explicit `STOP_REPEAT_MESSAGE` (clause 14.2.2.3/Table 53, ADR-173 Decision 3). The repeat message's D-PDU payload (`repeat_msg_data`, payload-only per ADR-051 — carried, along with `time_interval`/`condition`/`mask_data`/`pattern_data`/`tx_flag_bits`, as a hand-packed byte payload inside `DataItem.bytearray_data` since ADR-178 removed the dedicated `IORepeatMessageSetup` proto message this used) is composed into a full native frame the same way an ordinary `CoptSendrecv` TX is; the client's mask/pattern is widened with this CLL's own expected-response header/ID bytes prepended before being forwarded, keeping the mask/pattern surface payload-scoped like every other D-PDU-facing mechanism in this service. See **MsgId**, ADR-165, ADR-173, ADR-178.

**Resource** (D-PDU API)  
A physical bus instance described by protocol, bus type, and pin assignments. Used to create a CLL. In `j2534-0404-service`, resources are enumerated via `GetResourceIds` and identified by a **Resource ID** (below), not a raw protocol ID (ADR-069).

**Resource ID**  
`j2534-0404-service`'s opaque `0x0201`-`0x022F` namespace identifying one row of the static resource table (`resources.rs`, ADR-069) — each row binds a `ChannelProtocol`, a **Bus type ID**, typed DLC pins (see **Pin type ID**), and an optional hardware-protocol override (`ResourceDef::hw_protocol_override`, used only where the row's actual connect protocol diverges from its `ChannelProtocol`'s own, e.g. the four `SAE_J2610_on_SAE_J2610_SCI` rows). Not a J2534/`ChannelProtocol` value; a client discovers resource IDs via `GetResourceIds` and passes them back to `CreateComLogicalLink`/`GetResourceStatus`/`GetConflictingResources` verbatim. `CreateComLogicalLink` and `GetResourceStatus` resolve a resource ID through the table first, falling back to the legacy raw/extended `ChannelProtocol` interpretation for a value not in it. `GetConflictingResources` (ADR-106) resolves through the table only — a resource ID with no table row yields an empty conflict list rather than a legacy-`ChannelProtocol` fallback match, since a raw protocol value carries no pin/controller metadata to compute a static conflict from. `GetResourceIds`'s own `protocol_id` *selector*, by contrast, takes a `ChannelProtocol`/J2534 protocol value, never a resource ID — the two numeric namespaces are disjoint by construction, and there is no "look up by resource ID" filter on `GetResourceIds`. Some rows are alias rows sharing one `ChannelProtocol` under a distinct resource ID (e.g. `ISO_OBD_on_K_Line`); `SAE_J2610_SCI` and `SAE_J2610_on_SAE_J2610_SCI` each expand to four resource IDs, one per SCI configuration. `CreateComLogicalLink` still accepts a legacy raw (`1..=0x0B`) or extended (`0x0100+`) `ChannelProtocol` value directly as a fallback for resource IDs not present in the table.

**Response concatenation** (`CP_EnableConcatenation`)  
The D-PDU ComParam (`PARAM_ENABLE_CONCATENATION`, id `0x807B`) that instructs `j2534-0404-service` to detect an ECU answering a single request with more than one complete message and merge them into one delivered response, waiting for a receive timeout before finalizing (ISO 22900-2 Table B.20, ADR-148). A continuation is recognized by a three-component key, `(unique_resp_identifier, source_id, SID)` — not the SID/`unique_resp_identifier` pair alone — where `source_id` is the frame's own split-header source-address byte. `source_id` was added (ADR-148 Amendment 3) after a P1 bug: a no-`UniqueRespIdTable` KWP/J1850 CLL (the only working RX mode for these protocols today) delivers `unique_resp_identifier == 0` for every frame, so keying on SID/`unique_resp_identifier` alone let two distinct ECUs answering the same broadcast/functional request with the same SID collide into one corrupted buffer. Distinct from **ISO 15765-2** transport-layer multi-frame reassembly, which already produces one complete message per frame sequence beneath this layer before concatenation logic ever runs. Per ISO 22900-2:2022 Table B.11, supported only on the KWP family (ISO 9141-2, ISO 14230-2/-4) and SAE J1850 VPW/PWM — not CAN/ISO15765 or SCI (the 2009(E) edition's protocol list differed; ADR-148 documents following the 2022 edition). Implemented as a `CopRegistrant`-level `ConcatBuf` accumulator (`events.rs`), scoped to tier-1-at-creation registrants and excluding **IS-CYCLIC** and **Receive Only**-created registrants; reuses the existing `CP_P2Max`-derived deadline rather than a new timing mechanism.

**Rich error model** (`ErrorDetail`)  
The mechanism by which a failing RPC attaches structured error information to its gRPC `Status`, replacing the removed `GetLastError` RPC (ADR-105). A `google.rpc.Status` message (carrying `code`/`message`/`details: repeated google.protobuf.Any`) is encoded into the standard `grpc-status-details-bin` trailer, with this project's own `ErrorDetail` (`pdu_error`, optional `error_event_data`, optional `detail_text`) packed as the `Any` payload. `vci-service-interface/src/rich_error.rs` hand-writes minimal `google.rpc.Status`/`google.protobuf.Any` prost messages rather than vendoring a second `.proto` file, since both are fixed, tiny, external schemas. Not every failure carries an `ErrorDetail` — only ones the underlying protocol (ISO 22900-2 / J2534) actually defines a return code for; pure request-shape/transport validation failures do not.

**RxStatus / RxFlag**  
J2534's `PASSTHRU_MSG.RxStatus` (SAE J2534-2) is a standardized 32-bit word (`CAN_29BIT_ID`, `ISO15765_ADDR_TYPE`, `ISO15765_PADDING_ERROR`, `TX_INDICATION`, `RX_BREAK`, `START_OF_MESSAGE`, `TX_MSG_TYPE`). ISO 22900-2's `PDU_RESULT_DATA.RxFlag` (`ResultData.rx_flag` in the gRPC proto) defines a bit-compatible 4-byte layout under big-endian serialization (byte 2 bit 0 ↔ `RxStatus` bit 8; byte 3 bits 0-7 ↔ `RxStatus` bits 0-7) — contrary to ADR-061's original premise that `RxFlag` had no bit-position standard at all. `j2534-0404-service` forwards the 5 low bits unconditionally (`RxFlag` byte 3 bits 0-4: `TX_MSG_TYPE`, `START_OF_MESSAGE`, `RX_BREAK`, `TX_INDICATION`, `ISO15765_PADDING_ERROR`), bit-copied as `[0, 0, 0, RxStatus & 0x1F]` whenever any of those 5 bits is set and `Vec::new()` (no flags asserted) when all 5 are clear (a Normal Message); the other `RxFlag` bits ISO 22900-2 defines remain unreported/zero (ADR-098, extending ADR-097's original `START_OF_MESSAGE`-only forwarding; ADR-097 itself superseded ADR-061), EXCEPT two `RxFlag` byte 1 bits this service computes/forwards itself rather than folding into the ADR-098 low-bit mechanism (bundled together into one `events::RxFlagExtras` struct, ADR-191): `ECU_TIMING_CHANGE` (byte 1 bit 1) — the first such bit, set only on the specific bound `0xC3` **Access Timing Parameter service** response frame(s) whose `CP_ModifyTiming` ComParam modification the same poll pass's hardware push and Active store actually landed (ADR-146; delivery of any such frame is buffered until that pass's store outcome is known, so the flag always asserts "derived timing WAS stored into Active," never merely "a qualifying response was observed"). The flag is tied to Active only: as of the `WorkingTimingSnapshot` first-wins guard (ADR-146, Codex round-7, PR #17), that same pass's Working write for a given key is skipped whenever a concurrent `SetComParam`/ADR-067 Temp-writeback already changed it, so the flag does not guarantee a subsequent `GetComParam` (which reads only `link.working`) reflects the exchange. And `SW_CAN_HV_RX` (byte 1 bit 0, ADR-191) — a direct, standardized mapping (ISO Annex D.2.2 Table D.5 and SAE J2534-2 Table 12 bit 16 describe the same signal near-identically): `true` only for a genuine **Single Wire CAN (SWCAN/GMLAN)**-family frame whose native `RxStatus` carries bit 16, gated on `resources::is_sw_protocol_id`; the frame stays exactly as content-eligible as ADR-172 Decision 3 already established (bit 16 was never withheld) — this only adds the missing annotation on top of already-correct delivery. A frame is excluded from `ExpectedResponse`/pending-RC matching only when one of the 4 indication-type bits — `TX_MSG_TYPE`/Loopback, `START_OF_MESSAGE`, `RX_BREAK`, or `TX_INDICATION`/TxDone — is set (`rx_status_flags & !ISO15765_PADDING_ERROR == 0` is the eligibility test), since such a frame's payload is often empty or short after header/footer splitting and would otherwise vacuously match — or, for a Loopback echo of a request whose first byte happens to equal a pending-NRC value, be misread as a genuine pending-RC response — during a pending `CoptSendrecv` wait. `ISO15765_PADDING_ERROR` alone does *not* exclude a frame: unlike the other 4 bits it tags a genuine, fully reassembled ISO15765 response (final CAN frame with fewer than 8 data bytes), not a header-only indication — notably every `7F SS 78` response-pending NRC from an ECU that does not pad its CAN frames. ADR-098 originally (2026-07-17) shipped a blanket `rx_status_flags == 0` guard that also excluded `ISO15765_PADDING_ERROR`, which broke both real-response completion and `CP_RC78Handling` pending-RC detection for such ECUs; corrected the same day (see ADR-098's Correction section). A separate, earlier withhold check (ADR-172) runs ahead of this 4-bit gate for **Single Wire CAN (SWCAN/GMLAN)** links specifically: `RxStatus` bits 17/18 (speed-transition confirmations, undefined data) are checked against the frame's own native protocol id and dropped entirely before `is_content_frame` ever sees them — these bits don't fit `RxFlag` byte 3's 5-low-bit scope and bit 17 means something unrelated (`LINK_FAULT`) on Fault-Tolerant CAN, so this could not simply be added to `RX_STATUS_FLAGS_MASK`.

**SAE J1708 Protocol** — SAE J2534-2 clause 17  
A heavy-duty-truck serial bus (9600bps, device-computed checksum unless disabled) — the third standalone, non-CAN-family J2534-2 protocol this service ships (after **UART Echo Byte Protocol** and **Honda DIAG-H Protocol**), adding a genuinely new `ChannelProtocol::J1708_PS` (self-mapping, `hw_protocol_override: None`) the same way. One new resource-table row (`0x023C`, ADR-069); default J1962 pins 3/11, typed as a differential pair (`PIN_PLUS`/`PIN_MINUS`) like J1850 — unlike Honda DIAG-H's/UART Echo Byte's own single-pin defaults, this pair has **no textual basis in clause 17 or clause 6** for the J1962 connector specifically (an editorial convenience default only, the least spec-grounded default this codebase has picked so far), always issuing an explicit `SET_CONFIG(CONFIG_J1962_PINS)` on connect. Unlike every prior closed-set pin case (**Single Wire CAN (SWCAN/GMLAN)**, **Fault-Tolerant CAN (FTCAN)**, **Honda DIAG-H Protocol**), clause 17 documents no valid-pin table on the J1962 connector at all, so `resolve_pin_selection`'s new arm accepts any well-formed 1-or-2-pin selection with no closed-set rejection. Its ComParam surface (`DATA_RATE`/`LOOPBACK`/`PARAM_MESSAGE_PRIORITY`, clause 17.3.2.2.1's closed list) is a *superset* of the universal default, unlike Honda DIAG-H's narrower one — J1708's baud rate genuinely is `SetComParam`-configurable (clause 17.2.2 gives a minimum-support default, not a fixed value). This phase also gives `CP_MessagePriority` (`PARAM_MESSAGE_PRIORITY`, already registered but never natively wired) its first real translation: a new TxFlags mechanism, `MSG_PRIORITY_VALUE` (clause 17.4.5, bits 16-19), clamping to `1..=8` with absent/out-of-range values mapping to `8`. The `CHECKSUM_DISABLED` connect flag needed no new code — bit-identical to the existing `CONNECT_FLAG_ISO9141_NO_CHECKSUM` macro, already covered by `rpc_link.rs`'s existing checksum-never-generated policy. **Multi-connector pin space, deferred:** clause 6.3.3.2 defines three separate pin-numbering spaces (`J1962_PINS`/`J1939_PINS`/the dedicated SAE J1708 connector's own `J1708_PINS`) and requires only "at least one" per protocol; this phase scopes to J1962 only, leaving the other two connectors open for a future phase (needs a **`pin_select`**/`PinData` connector-discriminator design pass, ADR-156's own unresolved deferral). **Repeat Messaging** needs no protocol-specific rejection (clause 17 has no exclusion equivalent to UART Echo Byte's clause 12.3.3.1). Additional Channels and Discovery-cache connect-time wiring are out of scope this phase. See **CAN FD**, **Single Wire CAN (SWCAN/GMLAN)**, **UART Echo Byte Protocol**, **Honda DIAG-H Protocol**, **`_PS` protocol variant**, ADR-175.

**SAE J1939 Protocol** — SAE J2534-2 clause 16  
A heavy-duty-vehicle CAN-based protocol with a 250kbps default rate (client-configurable via the universal `DATA_RATE` ComParam like any other CAN-family link, `comparam_support.rs::is_j1939_param` permits it — this service's own preset seeds 250kbps, ADR-179, but does not hard-fix it) and 29-bit (extended) CAN identifiers only — the fifth phase of J2534-2 protocol support this service ships, and the first requiring a device-driven negotiation handshake rather than a fixed address. `ChannelProtocol::J1939_PS` gets two resource-table rows (`0x025D`/`0x025E`, ADR-069) on a new `SAE_J1939_11_DWCAN` bus type, both with an EMPTY default pin list — unlike every other J2534-2 protocol phase, a J1939 CLL must always stage explicit `dlc_pin_data` at connect time; there is no row-default fallback at all (ADR-179 Decision 2). Clause 16.3's SAE J1939-81 address-claim/defend negotiation is the protocol's own centerpiece: a CLL stages a candidate address list (`CP_J1939PreferredAddress`) and its 8-byte identity (`CP_J1939Name`, the **NAME**), and `CoptStartcomm` drives a retry-over-the-candidate-list state machine (native `PROTECT_J1939_ADDR`) until one candidate is claimed and defended or the list is exhausted (`CP_J1939AddrClaimTimeout` bounds each attempt, 1.25s default). `CP_J1939AddressNegotiationRule`'s bit 1 opts a CLL out of negotiation entirely, in which case `CP_TesterSourceAddress`/`NODE_ADDRESS` are client-managed instead, the same posture every non-negotiated protocol already uses. A **PGN** (Parameter Group Number) — the addressing unit clause 16.4 frames define on top of the 29-bit CAN ID — is composed from `CP_J1939PDUFormat`/`CP_J1939PDUSpecific`/`CP_J1939DataPage`; `CP_J1939TargetAddress` selects the responding ECU (or the `0xFF` broadcast/BAM form). `SharedChannel::j1939_claims` tracks which CLL owns each currently-claimed address (and, since ADR-180 Decision 23, the NAME it claimed it under) on a physical channel shared by sibling CLLs, so a NAME/address a torn-down CLL failed to natively relinquish is reconciled (`leaked_j1939_claims`) before a fresh claim, a repeat-message start, or a negotiation opt-out can proceed — closing the class of "two claimants defend one identity" bug this negotiation model uniquely exposes among this service's protocols. See ADR-179 (Phase 5 core: connect mechanics, ComParam mapping, framing) and ADR-180 (claim-registration atomicity, cancellation, and the many concurrency/state-machine corrections layered onto it across a long Codex review loop) for the full design history. See **CAN FD**, **Single Wire CAN (SWCAN/GMLAN)**, **SAE J1708 Protocol**, **`_PS` protocol variant**, ADR-179, ADR-180.

**SERMI** — Security-Related Vehicle Repair and Maintenance Information  
The EU scheme (under Regulation (EU) 2018/858 as amended by 2021/1244) that controls access to theft-protection functions such as key programming: accredited conformity assessment bodies approve repair businesses and authorise their employees. The authorised employee presents their credential to the maker's portal. The system handles the step through the OEM authentication provider and never holds the credential (ADR-237).

**Signal** (time series)  
One decoded value recorded over time during monitoring or acquisition, such as engine speed or coolant temperature. Signals are not stored directly: the stored original is the *record*, one response received from the vehicle with its monotonic timestamp and source, and signals are decoded from records with the IR's decode plans (design 4.3, 8.2.2; ADR-236). Not to be confused with a J2534 channel (a communication path opened with `PassThruConnect`).

**Single Wire CAN (SWCAN/GMLAN)** — SAE J2534-2 clause 9  
A single-wire, reduced-speed CAN physical layer (GM's GMLAN, per GM specification GMW3110) used on pin 1 of the J1962 connector instead of dual-wire CAN's pins 6/14. Clause 9 defines only two `_PS`-qualified protocol ids, `SW_CAN_PS`/`SW_ISO15765_PS` — no unqualified base id exists, the same shape **CAN FD** has — but unlike CAN FD, ISO 22900-2 Annex G models SWCAN as its own independently client-selectable resource, not a ComParam-inferred substitution. `j2534-0404-service` gives it ten dedicated resource-table rows (`0x0226`-`0x022F`, ADR-069) on a new `SAE_J2411_SWCAN` bus type (`0x0309`), reusing each dual-wire-CAN sibling row's `ChannelProtocol` but with its own `protocol_name` (`_SWCAN` suffix, to avoid making the ten pre-existing dual-wire names ambiguous) and a single default pin (`(1, PIN_HI)`, clause 9.2.1 — pin 1 only). Connect always issues an explicit `SET_CONFIG(CONFIG_J1962_PINS)`, mirroring **Pin Selection**'s pin-binding step, since the physical layer stays unassigned until then regardless of caller-supplied pins. `is_sw_protocol_id()` lets the rest of the service treat an SW link as its base `CAN`/`ISO15765` family (the narrow, arm-gate-only form; family-wide call sites use `is_sw_family_protocol_id()`, ADR-212). Three of the five `CP_ChangeSpeed*` ComParams ADR-017 originally rejected (`CP_ChangeSpeedRate`/`Ctrl`/`ResCtrl`) now translate to native `CONFIG_SW_CAN_HS_DATA_RATE`/`_SPEEDCHANGE_ENABLE`/`_RES_SWITCH` on an SW link — the GMW3110 speed-change handshake itself (a fixed byte-sequence the adapter watches for) is not directly configurable, so `CP_ChangeSpeedMessage`/`CP_ChangeSpeedTxDelay` are accepted but stored-only; `CP_SwCan_HighVoltage` is wired as a per-message `TX_FLAG_SW_CAN_HV_TX` TxFlags bit instead of a `SET_CONFIG` param. `SW_CAN_HS`/`SW_CAN_NS` (mode-switch **IOCTL**s) ride the existing `IoCtl` RPC as two new per-CLL commands, rejected on a non-SW link and a no-op on a shared physical channel. FD-on-SW substitution is out of scope. Of the RxStatus SW-mode-transition bits: bits 17/18 (speed-transition confirmations) are withheld from content processing rather than mishandled as content (ADR-172, see **RxStatus / RxFlag**) and remain unforwarded into `RxFlag`, pending a deferred, unconfirmed `SPD_CHG_EVENT` equivalence (ADR-191); bit 16 (`SW_CAN_HV_RX`) stays content-eligible (unchanged, ADR-172 Decision 3) and is now forwarded into `RxFlag` byte 1 bit 0 (ADR-191). **SW Additional Channels (ADR-212):** `SW_CAN_CAN_CH1..128`/`SW_CAN_ISO15765_CH1..128` participate in the existing clause-7 arithmetic mapping, keyed by their own `_PS` id like **Fault-Tolerant CAN (FTCAN)**'s own blocks — but SWCAN has its own confirmed vendor-header naming inconsistency unlike FTCAN: both block constant names are prefixed `SW_CAN_` regardless of which `_PS` id (`SW_CAN_PS`/`SW_ISO15765_PS`) they extend, rather than the `SW_CAN_CHx`/`SW_ISO15765_CHx` naming every other family's own block uses relative to its own `_PS` id's prefix. SWCAN is a CAN-collapse family like FTCAN — `base_protocol_id` normalizes `SW_CAN_PS`/`SW_ISO15765_PS` onto the true `CAN`/`ISO15765` base rather than self-identifying — so this round inherited ADR-211's shared infrastructure fix unchanged and added its own family-specific wiring: `chx_device_info_supported_parameter`'s own SW-CAN guard arms (built alongside a new, independent mock capacity override from the start, unlike FTCAN's own follow-up fix), and re-keying every family-wide call site (`connect_discovery_check`, `bustype_default_name_for_hw_protocol_id`, `apply_fd_mode`'s SW-vs-FD rejection guards, `GetResourceStatus` query matching, `comparam_id.rs`'s `CP_ChangeSpeed*` translation, `events.rs`'s `SW_CAN_HS_RX`/`_NS_RX` withholding gate and `SW_CAN_HV_RX`'s own `RxFlag` tag) from `is_sw_protocol_id()` to the new `is_sw_family_protocol_id()`. `CP_SwCan_HighVoltage`'s own `TX_FLAG_SW_CAN_HV_TX` bit needed the identical re-key at three more sites (`rpc_primitive::apply_resolved_tx_flags`, `rpc_misc.rs`'s Repeat-Message TX-flags composition, and the `SW_CAN_HV_RX` `RxFlag` tag just mentioned) — found only during this round's own implementation and a later `edge-case-hunter` pass, not the up-front investigation. See **CAN FD**, **Fault-Tolerant CAN (FTCAN)**, **`_PS` protocol variant**, **`_CHx` protocol variant**, ADR-164, ADR-172, ADR-191, ADR-212.

**STmin** — Separation Time minimum  
The ISO 15765-2 (ISO-TP) flow-control parameter that tells the sender the minimum gap to leave between consecutive frames. Encoded as a single byte: `0x00`-`0x7F` for 0-127 ms (1 ms resolution), `0xF1`-`0xF9` for 100-900 us (100 us resolution). `STMIN_TX` is the J2534 `SET_CONFIG` parameter that overrides the tester's own STmin on transmit; ISO 22900-2's equivalent, `CP_StMinOverride`, expresses the same override as a plain microsecond value (1 us resolution, `0xFFFFFFFF` = "use the vehicle-reported value") and is converted to the `STMIN_TX` byte encoding at the hardware-forwarding boundary in `j2534-0404-service` (see ADR-037).

**STRUCTFIELD** (`PDU_PT_STRUCTFIELD`, ISO 22900-2 §B.3.3.2)  
A ComParam data type whose value is an array of same-sized struct entries, the layout selected by a `ComParamStructType` discriminant (`T_PDU_CPST`). Three struct types are ISO 22900-2 standard (`PDU_CPST_SESSION_TIMING`/`PDU_CPST_ACCESS_TIMING`/`PDU_CPST_TLS_VERSION_AND_CIPHER`, values `0x1`-`0x3`); any other value is vendor/tool-specific, with no spec-defined layout. `iso22900-service` maps the three standard types 1:1 onto the gRPC proto's typed `ParamStructfield` list variants (`session_timing`/`access_timing`/`tls_version_and_cipher`), using `size_of` of the corresponding native struct as the entry size. A vendor struct type instead uses `ParamStructfield.vendor_specific` (`ParamVendorSpecificStruct`): `type_url` carries the `ComParamStructType` discriminant as `"pdu-cpst:0x<8 lowercase hex digits>"`, and `value` is the vendor's native struct-array bytes verbatim, since the D-PDU API gives `iso22900-service` no metadata to reinterpret them. Because a native `PDUGetComParam` call for a vendor struct type returns only an entry count, not the entry byte-size, `GetComParam`/`GetUniqueRespIdTable` resolve `size_of_entry` from a per-library `vendor_struct_types` table in `config.toml` alone (see `vci-service-config`'s `find_vendor_struct_type_size`), failing `FAILED_PRECONDITION` if unconfigured — an unconfigured vendor struct type's read fails loudly by design, never fabricating a size. `SetComParam`/`SetUniqueRespIdTable` consult the identical config for a non-empty vendor STRUCTFIELD write, requiring the declared `size_of_entry` to match exactly (`INVALID_ARGUMENT` otherwise); config is the sole source for both directions, since a successful native write never validates the caller's declared size against the connected library's real layout, so an earlier process-lifetime write cache was removed (Codex-review-found local heap-disclosure fix, ADR-218 amendment). See ADR-218.

## T–U

**Tonic**  
Rust gRPC framework used in all service crates. Built on Hyper and Tokio.

**temp_param_update** (`ComPrimitiveCtrlData` field, ISO 22900-2 §9.4.3)  
Set on a single `COPT_SENDRECV`/`COPT_STARTCOMM`/`COPT_STOPCOMM` call to stage a one-off override: the Working set (bound at call time) drives that COP's transaction instead of Active, and — for `COPT_SENDRECV`/`COPT_STARTCOMM` — is pushed to hardware for the duration of the transaction, then reverted to the Active snapshot bound at that same call time. Two effects flow from this: (1) after a successful call, Working is written back from Active (`j2534-0404-service`, ADR-067) — the override is consumed, not a permanent fork of Working from Active; (2) a `PDU_PC_BUSTYPE`-class ComParam difference between Working and Active makes the whole call fail synchronously with `PDU_ERR_TEMPPARAM_NOT_ALLOWED` (ADR-067) — `temp_param_update` may stage per-COP values, never a bus-physical reconfiguration.

**TimingSet** (`PDU_PARAM_STRUCT_ACCESS_TIMING.TimingSet`, ISO 22900-2 §B.3.3.2.3)  
A discriminator field distinguishing which of several coexisting timing entries a **Access Timing Parameter service** structfield entry (`CP_AccessTiming_Ecu`/`CP_AccessTimingOverride`) represents: `1` = the ECU's own default set (also what a TPI=1/2 exchange reports), `2` = override values the tester supplied for the ECU to use instead of its own reported TPI=2 values, `3` = override values the tester set via a TPI=3 exchange, `4` = normal post-initialization values, `0xFF` = extended timing after a keyword-initialization handshake. `j2534-0404-service` (ADR-146) only ever writes/reads `TimingSet` 1, 2, and 3 for the live-exchange mechanism; 4 and `0xFF` are accepted as client-set data but never derived by this service.

**TX_DL** — Transmit Data Length (SAE J2534-2 clause 21, D-PDU `CP_CANFDTxMaxDataLength`)  
The maximum CAN FD frame payload length in bytes a CLL will transmit, one of the DLC-encoded values `{0, 8, 12, 16, 20, 24, 32, 48, 64}` (Table 90/97; `0` = unset, `8` = Classic CAN's own max payload). Together with `CP_CANFDBaudrate`, `TX_DL` drives `j2534-0404-service`'s **CAN FD**/**FD_ISO15765_PS** mode-inference trigger: `TX_DL > 8 || CP_CANFDBaudrate != 0` — `TX_DL == 8` alone is ambiguous (indistinguishable from Classic CAN), but a nonzero `CP_CANFDBaudrate` is decisive by itself. On a raw `FD_CAN_PS` link (ADR-158), the live staged `TX_DL` drives a service-computed TX message-size range with DLC-rounding padding, since this service builds every frame itself; on an `FD_ISO15765_PS` link (ADR-159), `TX_DL` instead forwards natively to `CONFIG_FD_ISO15765_TX_DATA_LENGTH` (floored at `8` when unset) and the TX message-size range is a constant `4..=4128`/`5..=4128` (Table 98) with no service-side padding, since the native adapter's ISO15765 state machine segments and pads on its own. See **CAN FD**, **FD_ISO15765_PS**, **data phase rate**, ADR-158, ADR-159.

**TxFlag**  
A bitmask in `PDU_COP_CTRL_DATA` controlling per-message transmission options (suppress positive response, raw mode, CAN ID width, etc.).

**TP2.0 Protocol** — SAE J2534-2 clause 19 (VW/Audi, SAE J2819)  
A connection-oriented transport protocol multiplexing up to four simultaneous logical connections over one native `PassThruConnect(TP2_0_PS)` channel, each addressed on the wire by a 4-byte CAN-ID prefix (clause 19.4.4) — architecturally the sixth standalone, non-CAN-family-variant J2534-2 protocol this service ships (after **UART Echo Byte Protocol**, **Honda DIAG-H Protocol**, **SAE J1708 Protocol**, and **SAE J1939 Protocol**), adding a genuinely new `ChannelProtocol::TP2_0_PS` (self-mapping, `hw_protocol_override: None`) the same way, even though it physically rides a CAN transceiver. **One D-PDU CLL models one TP2.0 connection** — the central design decision (ADR-188): `IOCTL_REQUEST_CONNECTION`/`_TEARDOWN_CONNECTION` are invoked internally from `CoptStartcomm`/`CoptStopcomm` (and CLL teardown), never exposed as new client-visible `PDU_IOCTL_*` commands, resolving the ADR-178 "genuinely new RPC-level semantics" question this phase was flagged as possibly needing. Multiple CLLs share one physical channel through the existing `ChannelKey`/**SharedChannel** machinery unchanged. One new resource-table row (`0x025F`, `SAE_J2819_TP2_0`) on a minted standalone bus type, `TP2_0_DWCAN` (`0x0310`) — TP2.0 has no ISO 22900-2 preset at all, the **Analog Inputs** minting precedent, not a spec-sanctioned dual-wire-CAN variant. Clause 19.2.2 documents exactly one valid pin pair (J1962 pins 6/14, packed `0x0000_060E`) — unlike **Fault-Tolerant CAN (FTCAN)**'s two documented pairs, `resolve_pin_selection`'s new arm accepts only that one pair. Five minted ComParams (`CP_TP20ChannelSetupCanId`/`_DestinationAddress`/`_TxIdProposal`/`_RxIdProposal`/`_ApplicationType`, ids `0x80C9`-`0x80CD`, the **`CP_AnalogSampleRate`** naming/id-range convention) carry the Table 78 connection-request fields `CoptStartcomm` packs into the 11-byte `IOCTL_REQUEST_CONNECTION` request; on `CONNECTION_ESTABLISHED` the assigned TX-ID is recorded on `LogicalLinkState::tp20_connection`, which `tx_header.rs`'s message composer takes as an explicit parameter rather than reading it back through `CP_TP20TxIdProposal` (an earlier version wrote the assigned TX-ID back into that same client-settable ComParam, mirroring **SAE J1939 Protocol**'s own `CP_TesterSourceAddress` write-back — closed as a Codex review fix, PR #97, once staging a bogus value on that ComParam before any connection existed was found to let it substitute for a real established connection). RX-ID-matched delivery across sibling CLLs reuses ADR-184's `UniqueRespIdKey`/`route_frame` machinery directly: a synthetic per-CLL entry sourced from the connection's own RX-ID when established, or a deliberately unmatchable sentinel otherwise (also PR #97 — an earlier version omitted the entry entirely for a non-established CLL, wildcard-delivering a sibling's own traffic to it). **Passive connections (ADR-190, Phase 7 Stage 7b):** clause 19.3.1 also requires the interface to support exactly one inbound-accepting connection, individually enabled via two more minted ComParams, `CP_TP20PassiveIdentifier`/`CP_TP20PassiveRxId` (`0x80CE`-`0x80CF`), applied directly via native `SET_CONFIG` rather than the generic ComParam-translation pipeline (so ordinary ComParam application can never arm/re-arm the listener outside this mechanism's own arm/disarm lifecycle). **Arm-and-complete** is the central design decision: a CLL arms the slot via its own `CoptStartcomm`, completing immediately once armed rather than waiting for the first inbound connection — this codebase's single poll-task-per-physical-channel architecture forces this, since an unbounded wait would starve every sibling CLL's own sends/`CoptStartcomm`s on the same physical channel. Establishment/loss then arrives through the same `CONNECTION_ESTABLISHED`/`_LOST` indication path active connections already use; a `Lost` outcome re-enters a new `Tp20ConnectionPhase::Listening` (not a terminal `Lost`), since the device keeps auto-accepting the next inbound connection while the `SET_CONFIG` values stay valid, and the connection's own persistent routing entry (unlike an active connection's, removed once resolved) is what lets that next indication route correctly. New `SharedChannel::tp20_passive: Option<Tp20PassiveSlot>` exclusivity token — deliberately an `Option`, not an `Arc<AtomicBool>` reservation flag like **GM UART Protocol**'s `become_master_in_flight`: that pattern guards a bounded in-flight native call and rejects a sibling's channel-join, while the passive slot's exclusive state is held for the listener's entire armed (unbounded) lifetime, and clause 19.3.1 requires active connections and the passive slot to coexist rather than choose between them. **Broadcast frames and periodic re-trigger (ADR-192, Phase 7 Stage 7c):** clause 19.3.2.2/19.3.2.3's broadcast-send capability, via a new per-send-scoped ComParam, `CP_TP20BroadcastAddress` (`0x80D0`, staged through the existing `temp_param_update` mechanism rather than a link-invariant setting), which composes `[address] ++ payload` and ORs the native `TX_FLAG_TP2_0_BROADCAST_MSG` bit into the send — the device then produces the spec-mandated 5-frame `0xAA`/`0x55`-alternating burst on its own. A cyclic `CoptSendrecv` (`num_send_cycles == -1`) instead maps to a real native `PassThruStartPeriodicMsg`/`PassThruStopPeriodicMsg` pair, tracked against the owning COP/CLL the same way `PassThruStartMsgFilter` state is (reintroducing, deliberately and narrowly, the periodic-message call ADR-093 otherwise retired for **tester-present** — no other native primitive reproduces a burst-then-periodic wire shape). A cyclic broadcast periodic start rejects synchronously (`FailedPrecondition`) rather than queuing while this CLL's TX dispatch is suspended, since a native periodic-message start has no `tx_held`-shaped deferred-dispatch representation to fall back on. A second minted ComParam, `CP_TP20BroadcastInterval` (`0x80D1`), wires `TP2_0_T_BR_INT` (`0x8044`) — the one exception to Table 77's still-deferred nine other timing/count ComParams (native defaults only). Also still deferred: `_CHx` Additional Channels. See **CAN FD**, **Single Wire CAN (SWCAN/GMLAN)**, **Fault-Tolerant CAN (FTCAN)**, **SAE J1939 Protocol**, **GM UART Protocol**, **`_PS` protocol variant**, ADR-188, ADR-190, ADR-192.

**UART Echo Byte Protocol** — SAE J2534-2 clause 12  
A K-line UART protocol used for Honda ABS/VSA (per SAE J2809) or KWP1281 (per SAE J2818), distinguished by a per-byte echo/complement handshake between tester and ECU that the vendor DLL handles internally — this service is a thin forwarder for it, the same position it already occupies for **Repeat Messaging**. New `ProtocolID`s `UART_ECHO_BYTE_PS`/`_CHx` — architecturally unlike **CAN FD**/**Single Wire CAN (SWCAN/GMLAN)**/**Fault-Tolerant CAN (FTCAN)**, which each reuse the existing `ChannelProtocol::CAN`/`ISO15765` identity via a resource row's `hw_protocol_override` since their own spec clauses frame them as CAN-family equivalents, clause 12 has no such relationship to any protocol this service already models, so `j2534-0404-service` gives it a genuinely new, standalone `ChannelProtocol::UART_ECHO_BYTE_PS` (self-mapping, `hw_protocol_override: None`) — the same category `ISO9141`/`J1850PWM` occupy. One new resource-table row (`0x023A`, ADR-069), not ten like SWCAN/FTCAN, since no OBD-family composite spec exists for this protocol; default pin 7 (the VW/Audi convention), always issuing an explicit `SET_CONFIG(CONFIG_J1962_PINS)` on connect. Its ComParam surface was originally narrow by design: `DATA_RATE`/`LOOPBACK` (clause 12.3.4.1's closed parameter list, which also makes `CP_TesterPresentSendType` and `CP_InitializationSettings` permanently unreachable for this protocol), plus, as of ADR-216, the ten native-only `CP_UebT0Min`-`CP_UebT9Min` timing ComParams clause 12 defines — project-minted, no ISO 22900-2 source, native whole-millisecond values (not the ISO µs convention every other timing ComParam in this service uses), staged/read the same as any other writable ComParam. (Previously an accepted residual: Codex review + design-advisor consult, PR #57, found this service had no generic native `SET_CONFIG`/`GET_CONFIG` passthrough for these ten, so they ran at the native adapter's own spec-mandated Table 36 defaults with no client override path — closed by ADR-216 applying ADR-178's own project-minted-ComParam mechanism.) **Repeat Messaging** is explicitly rejected for this protocol. `CoptStartcomm`'s `cop_data` must be exactly one byte (the 5-baud init address) — clause 12 defines only an enhanced `FIVE_BAUD_INIT`, never a fast-init or an init-less start, unlike ISO9141/ISO14230. Additional Channels (`_CHx`) were later closed by ADR-207; Discovery-cache connect-time wiring is also now wired (ADR-185 Stage 1). See **CAN FD**, **Single Wire CAN (SWCAN/GMLAN)**, **Fault-Tolerant CAN (FTCAN)**, **Honda DIAG-H Protocol**, **SAE J1708 Protocol**, **`_PS` protocol variant**, ADR-170, ADR-207, ADR-216.

**UDS** — Unified Diagnostic Services  
ISO 14229-1. The standard diagnostic protocol used in modern vehicles. Runs over ISO-TP (ISO 15765-2) on CAN.

**USDT** — Unacknowledged Segmented Data Transfer  
ISO 15765-2 segmented messaging over CAN: payloads longer than one CAN frame are split into FirstFrame/ConsecutiveFrames and paced by FlowControl frames. This is what a J2534 `ISO15765` channel implements in hardware — or what `j2534-0404-service` implements itself in `software-isotp` mode (ADR-046). Addressed per ECU via `CP_CanRespUSDTId` / `CP_CanPhysReqId`.

**UUDT** — Unacknowledged Unsegmented Data Transfer  
Single-CAN-frame messaging with no transport-layer segmentation or flow control (e.g. periodic measurement responses). Addressed per ECU via `CP_CanRespUUDTId`. On J2534 hardware, UUDT frames are only visible on a raw `CAN` channel or via the UUDT `FLOW_CONTROL_FILTER` workaround on an `ISO15765` channel (ADR-041); the `dual-channel` CAN channel mode receives them on a companion CAN channel instead (ADR-046), and the `native-mixed` mode receives them via a genuine `PASS_FILTER` on the same ISO15765 channel instead (ADR-160).

**Unbound Frame**  
A content frame (i.e. not an indication frame — see **RxStatus / RxFlag**'s eligibility test) that, after passing UniqueRespIdTable routing (ADR-007), matches no active-Send/Receive registrant, no **Receive Only** registrant, and no armed tester-present discard window — ISO 22900-2 §9.2.6.3.4's full attribution scan (`bind_frame`) falls through every tier. As of ADR-100 Decision §5 (S8), such a frame is discarded outright: not buffered, not delivered as unsolicited `ResultData`. Before ADR-100, every unbound frame was instead delivered to the client unsolicited (`cop_handle: None`) — a deliberate, client-visible behavior change; a client relying on the old blanket delivery (e.g. bus monitoring) should register a `NumSendCycles == 0` **Receive Only** COP with a broad/vacuous `ExpectedResponseStructure` instead, which already receives exactly this class of frame. An indication frame reaching the same fallthrough is unaffected by this flip — it keeps its pre-existing `ResultData` delivery path per ADR-098 (ADR-100 Decision §3 step 1's carve-out).

**UniqueRespIdTable**  
A per-CLL table that maps `unique_resp_identifier` values to per-ECU ComParam sets. Used to route received frames to the correct COP when multiple ECUs are addressed on the same channel. Like ComParams, it has a Working/Active split (`SetUniqueRespIdTable` stages Working; promotion to Active happens at this CLL's own `ConnectComLogicalLink` or at `COPT_UPDATEPARAM`) — but a COP always resolves addressing against Active, unconditionally, even under `temp_param_update` (see Working-set / Active-set below, ADR-068). See ADR-007, ADR-014.

**VCI** — Vehicle Communication Interface  
A hardware adapter that connects a PC to vehicle diagnostic buses (CAN, K-Line, Ethernet, etc.). Synonymous with J2534 adapter or MVCI.

**vci-service-config**  
Shared Rust crate that loads and parses `config.toml`, independent of any gRPC/JSON-RPC bootstrap. Exposes `find_logging_config`, `find_library_path`, `list_configured_libraries`, and `list_configured_library_paths` (name-plus-path variant, ADR-036). `vci-service-launcher` re-exports it as `vci_service_launcher::config` for logging (ADR-033); `iso22900-registry` and `j2534-0404-registry` each wrap `find_library_path`/`list_configured_libraries` with their own API name fixed, and each build `enumerate_libraries()` on top of `list_configured_library_paths`, which is how `vci-service-manager` reaches this crate's data without depending on it directly (ADR-034, ADR-036).

**vci-service-launcher**  
Shared Rust crate that provides the startup template for all gRPC services. Handles DLL loading, gRPC server lifecycle, JSON-RPC stdio control channel, and logging initialization.

**Working-set / Active-set** (ComParam)  
D-PDU API distinguishes between the *working set* (parameters staged for the next update) and the *active set* (parameters currently in effect on hardware). `COPT_UPDATEPARAM` copies the working set to the active set and applies it to hardware. A ComPrimitive (`COPT_SENDRECV`/`COPT_STARTCOMM`) binds whichever set applies (Active normally, or Working when `temp_param_update` is set) once, synchronously, at `StartComPrimitive` call time — not live, at whatever moment the poll task later gets around to executing it (ADR-067; see `temp_param_update` below). The `UniqueRespIdTable` gets the same Working/Active split, promoted at the same two points (`ConnectComLogicalLink`, `COPT_UPDATEPARAM`) — but with one asymmetry: a ComPrimitive always resolves the table from Active, never Working, even under `temp_param_update` (ADR-068; see `UniqueRespIdTable` above).

**Write-job journal** (agent)  
The agent's durable record of a write job, one append-only file per job and ownership generation (`crates/agent/src/journal.rs`). It holds the completed steps, the last confirmed block, the ECU hardware part number and pre-erase software version, the per-stage resume counts with the attempt key, and the transfer-start and RequestTransferExit intent markers, each committed before the request it guards. Read back, it gives the facts an interrupted transfer restarts from and the checkpoint summary a handover carries (ADR-229, ADR-244).
