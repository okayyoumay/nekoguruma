# ADR-216: Native-Only ComParam Exposure — Analog Inputs and UART Echo Byte Remaining Parameters

**Date:** 2026-09-03
**Status:** Accepted
**Affects:** `j2534-0404-service/src/service/service_params.rs`, `comparam_id.rs`, `comparam_support.rs`, `comparam_defaults.rs`, `names.rs`, `rpc_link.rs`, `rpc_primitive.rs`, `events.rs`, `vci-service-interface/src/proto/service.proto` (no field added, `Snum32` reporting reuses the existing `sint32 snum32` oneof arm), `j2534-0404-mock`, `docs/rpc-api-guide.md`, `j2534-0404-service/docs/comparam-protocol-support.md`, `docs/glossary.md`, `docs/j2534-0404-architecture.md`, `j2534-0404-service/docs/implementation-notes.md`

## Context

ADR-170 (UART Echo Byte, Phase 9) and ADR-177 (Analog Inputs, Phase 15) each deferred exposing a set of native-only SAE J2534-2 `SET_CONFIG`/`GET_CONFIG` parameters with no ISO 22900-2 D-PDU ComParam equivalent at all, pending a "first mint" decision on whether this codebase should invent client-facing vocabulary for a concept ISO 22900-2 never defined. Ten parameters remain from UART Echo Byte (clause 12.3.4.1's `UEB_T0_MIN`, `UEB_T1_MAX`, `UEB_T2_MAX`, `UEB_T3_MAX`, `UEB_T4_MIN`, `UEB_T5_MAX`, `UEB_T6_MAX`, `UEB_T7_MIN`, `UEB_T7_MAX`, `UEB_T9_MIN` — all `0x0`-`0xFFFF` millisecond values, native ids `CONFIG_UEB_T0_MIN`=`0x8028` through `CONFIG_UEB_T9_MIN`=`0x8031`); seven remain from Analog Inputs (clause 10.3.3.2's `ACTIVE_CHANNELS`, `SAMPLES_PER_READING`, `READINGS_PER_MSG`, `AVERAGING_METHOD`, plus the read-only `SAMPLE_RESOLUTION`/`INPUT_RANGE_LOW`/`INPUT_RANGE_HIGH`; native ids `CONFIG_ACTIVE_CHANNELS`=`0x8020` through `CONFIG_INPUT_RANGE_HIGH`=`0x8027`). Analog Inputs' eighth clause-10.3.3.2 parameter, `SAMPLE_RATE`, is already exposed — not this ADR's subject.

ADR-178 has since resolved the "first mint" question this pair of ADRs deferred, in the course of re-expressing `SAMPLE_RATE` itself as `CP_AnalogSampleRate` (a ComParam with a freshly minted `0x80C4` id and no ISO 22900-2 source). Its own Consequences section states this explicitly establishes the codebase's precedent for minting a genuinely native-only, no-ISO-source ComParam, and its Decision records a forward-looking rule for every future phase: a scalar or native id/value-pair-list-shaped capability is represented as a ComParam, minting a fresh id when genuinely native-only, following that ADR's own id-range convention. `CP_TP20*` (`0x80C9`-`0x80D1`) and `CP_NdisPinOption` (`0x80D2`) already ship under this same rule. So the mechanism this ADR needs is not a novel invention — it already exists and is governed; what remains is applying it to these 17 parameters specifically, plus resolving three properties none of the prior mints needed to handle: a genuinely read-only ComParam (the three capability parameters), a signed-value ComParam (the two millivolt range parameters), and a connect-time ordering interaction with the already-shipped `CP_AnalogSampleRate`.

`implementation-notes.md`'s own backlog entry recording this deferral (ADR-170's own, predating ADR-178) also speculated GM UART's clause 11 parameters were a likely second consumer of whatever mechanism eventually got built. Checked directly against SAE J2534-2 clause 11.3.3 and against `j2534-0404-sys/src/bindings/j2534_v0404.h`: this is incorrect. Clause 11 defines no native `CONFIG_*` numeric parameter at all — its own native-only concepts (`SET_POLL_RESPONSE`, `BECOME_MASTER`) are action commands, already shipped by ADR-189 as two dedicated `PDU_IOCTL_*` commands, not ComParams. This is consistent with, not contrary to, the shape decided below: a command is IOCTL-shaped in this codebase (ADR-152 Decision 2, ADR-189 Decision 4); persistent numeric configuration is ComParam-shaped.

A connect-ordering interaction, not present in any prior phase, needs resolving as part of this change: `connect_new_physical_channel` (`rpc_link.rs`) issues `SET_CONFIG(CONFIG_SAMPLE_RATE)` immediately after `PassThruConnect`, before the generic per-protocol ComParam batch (`apply_j2534_params`) runs later in the same function. SAE J2534-2 clause 10.3.3.2.3/.2.4 require the device to reject `SAMPLES_PER_READING`/`READINGS_PER_MSG` with `ERR_NOT_SUPPORTED` whenever the sample rate is already nonzero — and `CP_AnalogSampleRate` is required-nonzero on every analog link (ADR-177/ADR-178). Left unordered, staging either of these two new ComParams together with the sample rate ADR-178 already requires would make every such connect fail, the moment either is added to the generic batch.

## Decision

1. **Seventeen new `PDU_PC`-classed Unum32 ComParams**, minted at the next free `0x8000`-range ids after `CP_NdisPinOption`'s `0x80D2` (ADR-178's own id-range convention): `0x80D3` `CP_AnalogActiveChannels`, `0x80D4` `CP_AnalogSamplesPerReading`, `0x80D5` `CP_AnalogReadingsPerMsg`, `0x80D6` `CP_AnalogAveragingMethod`, `0x80D7` `CP_AnalogSampleResolution` (read-only), `0x80D8` `CP_AnalogInputRangeLow` (read-only, signed), `0x80D9` `CP_AnalogInputRangeHigh` (read-only, signed); `0x80DA`-`0x80E3` `CP_UebT0Min`, `CP_UebT1Max`, `CP_UebT2Max`, `CP_UebT3Max`, `CP_UebT4Min`, `CP_UebT5Max`, `CP_UebT6Max`, `CP_UebT7Min`, `CP_UebT7Max`, `CP_UebT9Min`, matching this codebase's existing `CP_<Family><NativeName>` naming shape for a project-minted, no-ISO-source ComParam. All 17 are documented as project-invented with no ISO 22900-2 source, following `CP_AnalogSampleRate`'s own precedent.

2. **Units are native-verbatim, not converted to an ISO-style unit.** UEB values stay in whole milliseconds (matching `CONFIG_UEB_T*`'s own native encoding directly, mirroring `CP_TP20BroadcastInterval`'s identical native-millisecond precedent) rather than the microsecond convention ISO 22900-2's own `CP_*` timing ComParams use — this ComParam family has no ISO timing convention to match in the first place, so inventing one would be a false consistency. Documented explicitly in `docs/rpc-api-guide.md` so a client does not assume the ISO µs convention applies here.

3. **`comparam_support.rs` allowlist**: the four writable Analog Inputs ComParams (`CP_AnalogActiveChannels`/`SamplesPerReading`/`ReadingsPerMsg`/`AveragingMethod`) join the existing, currently-single-entry `ANALOG_IN` family allowlist alongside `CP_AnalogSampleRate`; the three read-only capability ComParams are allowed for `GetComParam` reach (see item 6) but rejected outright by `SetComParam` (item 5), so they need no allowlist entry for the write path at all. The ten UEB ComParams join `UART_ECHO_BYTE_PS`'s existing allowlist (currently `is_universal_param` only, ADR-170 Decision 3) as a new `is_ueb_timing_param(param_id)` check alongside it.

4. **`comparam_id.rs`'s `to_j2534_config_id` gains two new non-identity translation arms**, checked against the raw `hw_protocol_id` before `base_protocol_id` normalization, mirroring the FD/SW/Honda-DIAG-H/J1939 arms already in this function: an Analog Inputs arm (keyed on `resources::is_analog_in_protocol_id`) mapping the four writable ComParams 1:1 onto `CONFIG_ACTIVE_CHANNELS`/`CONFIG_SAMPLES_PER_READING`/`CONFIG_READINGS_PER_MSG`/`CONFIG_AVERAGING_METHOD`; a UEB arm keyed on the existing family-wide `resources::is_uart_echo_byte_family_protocol_id` predicate (not the narrower `_PS`-only check — ADR-213's own Round 3 fix already established that a translation arm keyed on a bare `_PS` id silently loses its translation for a `_CHx`-connected link of the same family, and UEB has shipped `_CHx` support since ADR-207) mapping the ten UEB ComParams 1:1 onto their `CONFIG_UEB_*` ids. The three read-only Analog Inputs ComParams are deliberately left untranslated (fall through to `None`) — they are never staged into a `SET_CONFIG` batch in the first place (item 5), so no forwarding mapping is needed or wanted for them.

5. **`SetComParam` validation** (`rpc_link.rs`, mirroring the existing `CP_BlockSizeOverride`-style early-rejection precedent — reject a value the device would reject anyway before it can poison a batched `SET_CONFIG` call that also carries other, otherwise-valid staged params): the ten UEB ComParams are range-checked to `0..=0xFFFF` (SAE J2534-2's own declared range for all ten); `CP_AnalogReadingsPerMsg` to `1..=0x408` (1-1032, Table 16's own range); `CP_AnalogSamplesPerReading` to `>= 1` (Table 16's range floor; clause 10.3.3.2.3/.2.4's own zero-value special case (a zero setting for either parameter disarms the analog subsystem entirely) is intentionally not offered through these two ComParams — `CP_AnalogSampleRate` remains the sole arming/disarming knob, per ADR-178's own established contract for that ComParam). `CP_AnalogActiveChannels`/`CP_AnalogAveragingMethod` get no service-side range check (a hardware-dependent channel bitmask and an open, vendor-extensible enum respectively) — an invalid value is rejected by the native device's own `ERR_INVALID_IOCTL_VALUE`, forwarded through the same error-mapping path Analog Inputs' Write/periodic/filter rejections already use. The three read-only ComParams reject any `SetComParam` attempt outright with `PDU_ERR_COMPARAM_NOT_SUPPORTED` — SAE J2534-2 clause 10.3.3.2.6-.2.8 each require the device itself to return an equivalent native rejection (`ERR_INVALID_IOCTL_PARAM_ID`) for a `SET_CONFIG` on any of these three, so rejecting synchronously in this service, before ever reaching the native call, is a direct application of the same constraint, not an invented restriction.

6. **The three read-only ComParams are populated by a one-time connect-time `GET_CONFIG` readback**, not by any live `GetComParam`-time hardware read. `GetComParam` (`rpc_link.rs`) never touches `self.api`/hardware today for any ComParam — it reads exclusively from a CLL's already-staged `working`/`active` `ComParamSet`, and this stays true for these three; the only two existing precedents for a hardware-sourced ComParam value in this codebase (the post-5-baud-init `CP_Baudrate` write-back, and ADR-192's channel-wide capture) both work by writing a `GET_CONFIG` result into the CLL's own Working/Active state at the moment it becomes known, not by making `GetComParam` itself reach into hardware — this ADR follows the identical shape. On every analog `ConnectComLogicalLink` (both a genuinely new physical channel and a join onto an already-open one — a joiner never pushes its own Working values today, so it needs the same readback a fresh connect gets), one `GET_CONFIG` batch reads `ACTIVE_CHANNELS`/`SAMPLE_RESOLUTION`/`INPUT_RANGE_LOW`/`INPUT_RANGE_HIGH`/`AVERAGING_METHOD` and writes the result into that CLL's Working **and** Active `ComParamSet` alike (writing only one would desync `bustype_params_differ`'s existing equality check for the BUSTYPE-classed `CP_AnalogActiveChannels`/`CP_AnalogAveragingMethod`, item 7); a read failure is best-effort logged (`warn!`), matching the existing `CP_Baudrate` write-back's own failure handling, never fails the connect itself. `CP_AnalogActiveChannels` and `CP_AnalogAveragingMethod` are included in this same readback deliberately, alongside the three genuinely-read-only ones: clause 10.3.3.2.1's own default for `CP_AnalogActiveChannels` is device-dependent (every channel the hardware actually has, active by default), so without a readback a freshly-connected link would report a stale/zero value for a parameter that is, in fact, live and meaningful on the device from the moment of connect; `CP_AnalogAveragingMethod` is included so a joining CLL adopts the channel's live value at connect time rather than its own seeded Working default (`comparam_defaults.rs`'s `analog_in()`), which would otherwise let that joiner's later blanket `CoptUpdateparam` forward (item 10; `apply_params_to_hardware_locked` carries no rate-gate on this param, unlike SamplesPerReading/ReadingsPerMsg) silently clobber the channel's actual hardware value. Before `ConnectComLogicalLink`, all five read `0` (not yet known) — documented as an explicit Consequence, not silently left ambiguous.

    The two batching ComParams, `CP_AnalogSamplesPerReading`/`CP_AnalogReadingsPerMsg`, are ALSO synced at this same connect-time point (fresh connect and join alike), but via a different mechanism than the five params above: rather than a live `GET_CONFIG`, they are copied from the channel's own already-recorded `SharedChannel::applied_analog_samples_per_reading`/`applied_analog_readings_per_msg` (item 10) into the connecting CLL's Working **and** Active `ComParamSet`. Every connect, fresh and join, adopts the channel's applied acquisition configuration for these two params too — a joiner never keeps its own seeded default. Sourcing from `applied_*` rather than a fresh hardware read is safe (and cheaper): a failed connect-time batch already fails the whole connect (item 9), so `applied` already equals the hardware value for any conforming device, and these two are exactly what the `CoptUpdateparam` guard (item 10) itself compares against — sourcing the join-time sync from the identical field is what makes that guard's own value-comparison hold for a joiner, not just for the CLL that opened the channel.

    **Amendment (Codex review, PR #130, Finding 1):** this connect-time analog sync — both the `GET_CONFIG` capability readback and the batching-values copy — now runs **inside** `finalize_connected_link`'s own connected-publishing critical section (the same `logical_links` critical section item 6's Working/Active write always described, not a separate call running after it), rather than as two separate calls issued after `finalize_connected_link` had already published `connected = true`/`channel_key` and released `logical_links`. The capability `GET_CONFIG` read itself (a real hardware `.await`) still runs beforehand, outside any lock beyond what it takes internally — only the write into the CLL's Working/Active `ComParamSet` moved inside the critical section, threaded in as a parameter. This closes a same-handle race a client could otherwise trigger: a client that already holds `cll_handle` (returned by the earlier `CreateComLogicalLink`) and pipelines `ConnectComLogicalLink` immediately followed by `StartComPrimitive(CoptUpdateparam)` on the same handle, without waiting for the connect response (gRPC gives no ordering guarantee between the two independent RPC calls), could have its own `CoptUpdateparam` promote this CLL's Active to a newer value, only for the still-in-flight capability readback's stale `GET_CONFIG` snapshot (read earlier, before the race) to then overwrite BOTH Working and Active back to the stale value — clobbering the client's own just-issued intent even though hardware already reflected the newer value. Running the write inside the same critical section that publishes `connected`/`channel_key` means a pipelined `CoptUpdateparam` on this handle can never observe the connect as complete before this write has also completed.

7. **The four writable Analog Inputs ComParams join the existing `BUSTYPE_UNUM32` classification**, alongside `CP_AnalogSampleRate` (`service_params.rs`) — same rationale already established for that ComParam: they are channel-wide, not per-CLL, so a `CoptUpdateparam` temp-update attempt must be refused the same way (`bustype_params_differ`/the physical-ComParam lock), and `strip_bustype_keys` keeps them correctly excluded from an unrelated CLL's own bracket-revert. The ten UEB ComParams and the three read-only Analog Inputs ComParams stay default (per-CLL, non-BUSTYPE) classed — the UEB ones mirror every other native K-line timing ComParam's own existing per-CLL-forwarded shape (`W1`-`W4`/`TIDLE`/`TINIL`/`TWUP`, etc.), and the read-only ones are never staged/forwarded at all, so BUSTYPE classification is moot for them.

8. **Two values `CP_AnalogInputRangeLow`/`CP_AnalogInputRangeHigh` report signed** at the `GetComParam` boundary specifically — stored internally in `working.unum32`/`active.unum32` in their native two's-complement 32-bit encoding (Table 16's own encoding, e.g. `0xFFFFB1E0` = -20.00V), but surfaced to the client via the proto's existing, currently-unused `ParamData::Snum32(i32)` oneof arm (`service.proto`'s pre-existing `sint32 snum32 = 4` field — no proto change needed) rather than the `Unum32` arm every other numeric ComParam in this service currently uses. `SetComParam` gains a dedicated `Snum32` oneof arm (`rpc_link.rs`) purely to reject a write in this shape with the same `PDU_ERR_COMPARAM_NOT_SUPPORTED` item 5 already gives the `Unum32` arm — not because either param has a write direction (both stay read-only), but because a client that round-trips a `GetComParam` response straight back through `SetComParam` naturally sends `Snum32`, not `Unum32`, and would otherwise fall through to a generic, differently-shaped `unimplemented` rejection instead (edge-case-hunter finding, round 2 correction). Every other `param_id` sent via this arm — there being no writable Snum32-shaped ComParam in this codebase at all — falls through to that same generic rejection.

9. **`connect_new_physical_channel`'s existing generic ComParam batch (`apply_j2534_params`) is applied before the existing `SET_CONFIG(CONFIG_SAMPLE_RATE)` step**, reordered from today's rate-then-batch sequence.** This closes the ordering hazard in Context: clause 10.3.3.2.3/.2.4's own semantics treat `SAMPLES_PER_READING`/`READINGS_PER_MSG` as configuration of an as-yet-unarmed subsystem, only armed once `SAMPLE_RATE` goes nonzero — applying the generic batch first, then arming the rate, matches that intent directly, rather than fighting it with an artificial exception. `CP_AnalogActiveChannels` and `CP_AnalogAveragingMethod` carry no such ordering constraint (clause 10.3.3.2.1/.2.5) and are unaffected by the reorder either way.

10. **`CoptUpdateparam` on an already-connected analog link rejects a genuine re-stage** of `CP_AnalogSamplesPerReading`/`CP_AnalogReadingsPerMsg` away from the value actually applied at connect time — extending the existing ADR-178 guard that already rejects a `CP_AnalogSampleRate` re-stage on a connected link the identical way, via the identical value-comparison shape: two new `SharedChannel` fields, `applied_analog_samples_per_reading`/`applied_analog_readings_per_msg`, record what was actually applied to hardware at connect time (mirroring `applied_analog_sample_rate` end to end), and the `CoptUpdateparam` guard rejects the whole update only when the staged value for either ID genuinely differs from its recorded applied value. A same-value re-stage, or an update that never touches either ID at all, is not rejected by this guard. Separately, `apply_params_to_hardware_locked` (`events.rs`) now permanently excludes `CONFIG_SAMPLES_PER_READING`/`CONFIG_READINGS_PER_MSG` from its post-connect `SET_CONFIG` forwarding, alongside its existing `DATA_RATE` exclusion — this is necessary because that function forwards every `unum32` Working param present with a translation as one blanket batch, not a delta of what changed, and `comparam_defaults.rs`'s `analog_in()` unconditionally seeds both ids into every analog CLL's Working set at creation; without this exclusion, even an update touching only `CP_AnalogAveragingMethod` would re-forward both ids to hardware, which SAE J2534-2 clause 10.3.3.2.3/.2.4 requires the device to reject with `ERR_NOT_SUPPORTED` whenever `CP_AnalogSampleRate` is already nonzero on that channel (true for every already-connected analog link, per ADR-178) — regardless of whether the forwarded value matches what is already applied. Together, the two changes mean a same-value re-stage or an unrelated update never attempts to re-push these two ids to hardware at all, and only a genuine attempted change is pre-emptively rejected before reaching hardware. `CP_AnalogAveragingMethod` also carries no re-stage restriction, but is no longer "unchanged" in the same sense: item 6's readback now also adopts it at connect time (fresh and join alike), so a joiner's later blanket `CoptUpdateparam` re-forward carries the channel's live value forward instead of clobbering it back to the joiner's own stale seeded default.

    **Amendment (Codex review, PR #130, Finding 2) — change-only forward for `CP_AnalogActiveChannels`/`CP_AnalogAveragingMethod`:** these two remain live-changeable via `CoptUpdateparam` exactly as originally decided — this amendment does not exclude them from forwarding the way the two batching ComParams above are excluded, and does not generalize the fix to any other `BUSTYPE_UNUM32` member (tracked separately, see the new backlog entry this amendment adds to `j2534-0404-service/docs/implementation-notes.md`). But a CLL's own currently-*unchanged* copy of either param is never re-forwarded to hardware on an unrelated `CoptUpdateparam`: `apply_params_to_hardware_locked`/`handle_update_param`'s blanket-forward pushes every `unum32` key present in a CLL's own staged set on ANY `CoptUpdateparam` that CLL issues, not a delta of what that specific update actually changed. Combined with item 6's now-mandatory connect-time sync of these two params onto every CLL sharing a channel (including joiners), this means: if CLL A changes `CP_AnalogAveragingMethod` live (`SetComParam` + `CoptUpdateparam`) after CLL B already joined and synced its own now-stale copy of the pre-change value, B's own Working/Active still holds that stale copy — nothing re-syncs a *live* post-connect change across sibling CLLs the way item 6's readback syncs the value once, at B's own connect time. When B later issues ANY `CoptUpdateparam` for an unrelated ComParam, the blanket-forward would re-send B's own stale copy of `CONFIG_AVERAGING_METHOD`/`CONFIG_ACTIVE_CHANNELS`, silently reverting A's live change on hardware — while A's own `GetComParam` still (now wrongly) reports the newer value. A new helper, `comparam_support::strip_unchanged_analog_channel_wide_keys`, is called in `handle_update_param` (`events.rs`) on `hw_set` after `apply_bustype_lock` and before the hardware push: for each of the two params, if the calling CLL's own staged effective value (`comparam_support::effective_unum32`, the same "changed" definition ADR-133/`bustype_params_differ` already use) equals that same CLL's own current effective Active value, the key is stripped from `hw_set` (never from `active`/`promote_set`, which are unaffected) — so only a value this CLL is genuinely changing right now is ever forwarded. This also closes a second, more serious variant: if the connect-time readback (item 6) ever failed, `CP_AnalogActiveChannels` would be absent (effective `0`) in every CLL's Working/Active, and the unfixed blanket-forward would push `CONFIG_ACTIVE_CHANNELS = 0` on the next unrelated update — clause 10.3.3.2.1's own bitmask semantics read that as deactivating every analog channel on the device, not merely a stale-value staleness. `CP_AnalogActiveChannels` no longer "goes through the ordinary `CoptUpdateparam` path unchanged" as originally stated — it goes through the ordinary path with this one change-only-forward guard applied, identically to `CP_AnalogAveragingMethod`.

    This connect-time sync of the two batching ComParams from `SharedChannel::applied_*` (item 6) is what makes this guard's own contract actually hold for a JOINING CLL, not just for the CLL that opened the physical channel: without it, a joiner's own Working set keeps `comparam_defaults.rs`'s seeded default (`1`/`1`) regardless of what the channel's owner actually staged, and this guard — which compares the joiner's own staged value against `sc.applied_*` — would then reject even an update that never touches either ID, the moment the owner staged a non-default value at its own connect. The sync closes that gap by construction: a joiner's Working set is made to already equal `sc.applied_*` before any `CoptUpdateparam` runs, so the guard's value-comparison passes for an unrelated update on a joiner exactly as it already did for the opening CLL.

## Consequences

- Closes both `implementation-notes.md` backlog entries this residual was tracked under (ADR-170's general-mechanism entry and ADR-177's own "remaining parameters" entry) in one PR, since the mechanism ADR-178 already established makes the marginal cost of covering both consumers together — one allowlist arm, one translation arm, names, defaults, and tests per family — small relative to designing the mechanism itself. `ADR-170`'s and `ADR-177`'s own Status lines are annotated (their shared accepted residual is closed by this ADR).
- The stale "GM UART's clause 11 parameters are a likely second consumer" claim in the now-deleted backlog entry is not carried forward; GM UART's own native-only concepts are already fully shipped (ADR-189) via IOCTLs, not ComParams — the two are different shapes for different concept classes (commands vs. persistent configuration), not two candidates for the same mechanism.
- First read-only ComParams and first signed-value-reporting ComParam in this codebase. `PDU_ERR_COMPARAM_NOT_SUPPORTED` on a `SetComParam` attempt against one of the three read-only Analog Inputs ComParams is this service's existing rejection code for a disallowed param, reused rather than inventing a new one.
- `CP_AnalogActiveChannels`/`CP_AnalogSampleResolution`/`CP_AnalogInputRangeLow`/`CP_AnalogInputRangeHigh` read `0` before the owning CLL's first successful `ConnectComLogicalLink` — a client reading them pre-connect gets an explicitly-not-yet-known value, not a hardware-accurate one; documented in `docs/rpc-api-guide.md` rather than left as a surprise.
- Changing `CP_AnalogSamplesPerReading`/`CP_AnalogReadingsPerMsg` on an already-connected analog link requires a disconnect/reconnect cycle, mirroring `CP_AnalogSampleRate`'s own already-accepted identical constraint (ADR-178) — not a new limitation this ADR introduces, but an extension of one already accepted for the sibling ComParam in the same subsystem.
- A join onto an already-open `ANALOG_IN_x` channel now also receives the same connect-time sync a fresh connect gets, which can overwrite a joiner's own already-staged Working value with the channel's actual applied/live one — a deliberate consequence (the same "live value wins" precedent the existing `CP_Baudrate` write-back and the join-time sample-rate check both already establish for this subsystem), not an oversight. This now covers all four writable Analog Inputs ComParams a joiner might have staged a different value for, not `CP_AnalogActiveChannels` alone as originally established by the ADR-177/ADR-178 precedent: `CP_AnalogAveragingMethod` is overwritten by the same `GET_CONFIG` readback as `CP_AnalogActiveChannels` (item 6), and `CP_AnalogSamplesPerReading`/`CP_AnalogReadingsPerMsg` are overwritten by the connect-time sync from `SharedChannel::applied_*` (item 6/item 10). SAE J2534-2 clause 10.3.3.2's own framing treats this configuration as belonging to the analog acquisition subsystem as a whole, not to any one CLL, so a joiner's own staged value never having a claim on the physical channel's actual state is a direct reading of that framing, not an invented restriction. The rate itself, `CP_AnalogSampleRate`, is the deliberate exception to this "live value wins" pattern (ADR-178): it is mandatory-to-stage before connecting, and a re-stage attempt that would change it on an already-connected link is rejected outright rather than silently overwritten — the acquisition subsystem's one parameter whose value a client must get right up front, not one it can leave to the channel's own state to resolve.
- UEB timing ComParams' native-millisecond unit (vs. the µs convention every ISO-sourced `CP_*` timing ComParam in this service otherwise uses) is a real, documented inconsistency a client must be aware of — an intentional accepted cost of exposing a native concept verbatim rather than inventing a false ISO-style conversion for a ComParam family with no ISO precedent to be consistent with in the first place.
- Accepted residual, not fixed by this ADR: `CP_TesterPresentSendType`/`LOOPBACK`-adjacent scope aside, `LOOPBACK` remains allowed on a UART Echo Byte link via the existing `is_universal_param` check (ADR-170 Decision 3) even though clause 12.3.4.1's own Table 36 closing text names only `DATA_RATE`/`J1962_PINS` among the standard J2534-1 parameters as supported for this protocol — a pre-existing allowlist looseness this ADR's own UEB timing-parameter addition sits beside but does not itself introduce or widen; tracked as a new backlog item rather than fixed here, since correcting it is a narrower, independent allowlist question outside this ADR's own scope.
- Accepted residual (Codex review, PR #130, Finding 2 amendment, item 10): even with the change-only-forward fix, a sibling CLL's own `GetComParam(CP_AnalogActiveChannels)`/`GetComParam(CP_AnalogAveragingMethod)` can still report a stale value for a time after another CLL changes either live — the fix stops the sibling's own stale copy from being re-forwarded to *hardware*, it does not push the new value into the sibling's own Working/Active bookkeeping. This is the exact same per-CLL Working/Active staleness ADR-110 already accepts generally (`LogicalLinkState::active` is per-CLL bookkeeping with no cross-CLL synchronization, and can go stale relative to the real, shared hardware value with no local signal of that) — not a new gap this amendment introduces.
- Accepted residual (Codex review, PR #130, Finding 2 amendment, item 10): re-staging a value equal to a CLL's own current copy of `CP_AnalogActiveChannels`/`CP_AnalogAveragingMethod` is a hardware no-op under the change-only-forward fix — the `SetComParam`/`CoptUpdateparam` call itself still succeeds (these two params carry no rejection), but the redundant `SET_CONFIG` is silently skipped rather than actually re-issued to the device. This matches ADR-133's own effective-value definition of "change" (`comparam_support::effective_unum32`) — a re-stage that produces no effective difference was never a "change" that definition would recognize in the first place.
