# ADR-131: `ModuleConnect` Does Not Recover a `PDU_MODST_NOT_AVAIL` Module — `ModuleDisconnect` Then `ModuleConnect` Is the Only Recovery Path

**Date:** 2026-07-24
**Status:** Accepted (amends ADR-107 Decision (d); extended by ADR-134)
**Affects:** `j2534-0404-service/src/service/rpc_module.rs`, `j2534-0404-service/src/service/rpc_link.rs`, `j2534-0404-service/src/service.rs`, `j2534-0404-service/docs/iso22900-2-conformance-audit.md`

## Context

Conformance-audit finding A2-8 (`iso22900-2-conformance-audit.md`) added `J2534Service::require_connected_device_for`, which the module-scoped `PDU_IOCTL_*` commands use to reject with `PDU_ERR_MODULE_NOT_CONNECTED` unless a device is open for the requested handle. Two consecutive Codex review rounds on the same PR (#143) then found — and this ADR resolves — a real gap in how that check interacts with `events::handle_channel_hard_error` (`events.rs`): when the RX poll task's `PassThruReadMsgs` fails for a channel, this function tears the affected CLLs down and sets `module_state.status` to `PduModstNotAvail`, but deliberately leaves `device_id` open (ISO 22900-2 §9.4.29.2 (e): the module handle, and its event queue, stay valid after a comm loss specifically so a client can still retrieve queued event/error items — see also NOTE 2, quoted below).

**Round 1** (fixed, commit `b616d50`): `require_connected_device_for` originally checked only whether `device_id` was open; a module marked `NotAvail` by a hard error, with `device_id` still `Some`, incorrectly passed the check. Fixed by additionally requiring `module_state.status == PduModstReady`.

**Round 2** (the gap this ADR closes): once round 1 landed, a `NotAvail` module had no way back to `Ready` short of an undocumented `ModuleDisconnect`, even though `rpc_module_connect`'s already-open no-op branch (`ensure_open_device_for` -> `ensure_open_device_inner`, `service.rs`) reported ordinary success. My first attempt at closing this (commit `0fe51d0`) made `rpc_module_connect` unconditionally reset `module_state` to `ModuleState::default()` (status `PduModstReady`, `last_error` cleared) after every successful `ensure_open_device_for` call, including the already-open no-op branch. Codex's next review round correctly identified this as a *new* defect: the already-open branch performs no native call whatsoever, so declaring the module `READY` again was a blind assertion with nothing behind it — a client would get `ModuleConnect` success and then have every module IOCTL hand it a `DeviceId` that may still be genuinely unreachable.

Two independent review rounds landing P1 findings on the same mechanism (module recovery after a hard error) is this repository's own trigger, per `.claude/README.md`'s `design-advisor` escalation gate, for routing to a top-tier design pass rather than a third ad-hoc patch. That pass is what produced this decision.

**What the spec actually says.** ISO 22900-2:2009(E) §9.4.29.2 Behaviour, read in full rather than just clause (d) in isolation, lays out `PDUModuleConnect` as a short sequence: first confirm the module is actually reachable (returning `PDU_ERR_FCT_FAILED` if it is not, from state `PDU_MODST_AVAIL`), and only after that check and the steps between succeed does the last clause move the module to `PDU_MODST_READY` (that particular transition fires no event callback).

Clause (d) only fires after (a)–(c) succeed — it is not an unconditional postcondition of every `PDUModuleConnect` call, contrary to how my round-2 fix read it. The use-case table in the same section defines exactly one path into `PDU_MODST_READY`: `PDU_MODST_AVAIL -> PDU_MODST_READY`, reached specifically via a successful `PDUModuleConnect` call. There is no `PDU_MODST_NOT_AVAIL -> PDU_MODST_READY` transition anywhere in the spec's state machine — a `NotAvail` module is not, per the state machine, eligible to become `Ready` via `ModuleConnect` at all.

NOTE 2 (same section) is explicit about what a client should do instead: when the D-PDU API notices that contact with a connected MVCI protocol module has been lost, the module's status becomes `PDU_MODST_NOT_AVAIL`; the spec's advice to the client is to first drain whatever is left in that module's event queue and then call `PDUModuleDisconnect`.

And §9.4.30 (`PDUModuleDisconnect`) confirms the handle is deliberately kept alive across this transition specifically so that recovery sequence works: a module handle remains valid for a subsequent `PDUModuleConnect` call after `PDUModuleDisconnect` has run on it.

J2534 v04.04 (the native layer this adapter wraps) has no health-check/ping primitive at all — the only call that meaningfully proves a device is reachable is `PassThruOpen` itself, which only runs on a genuine fresh open.

## Decision

`PDU_MODST_NOT_AVAIL` is sticky until an explicit `ModuleDisconnect`. Specifically:

- `rpc_module_connect` (`rpc_module.rs`), after `ensure_open_device_for` succeeds, reads `module_state.status` while still holding the `device_id` guard `ensure_open_device_for` returned (closing the TOCTOU window a concurrent `ModuleDisconnect` would otherwise open between the two checks — `device_id` -> `module_state` is the pre-existing nested-lock order, ADR-107 addendum). If `status != PduModstReady`, it rejects with `PDU_ERR_FCT_FAILED` (`Code::FailedPrecondition`), a message directing the client to call `ModuleDisconnect` then `ModuleConnect`, and the tracked `last_error` (carrying `PDU_ERR_EVT_LOST_COMM_TO_VCI`) in the `ErrorDetail` — `PDU_ERR_FCT_FAILED` is a legal `PDUModuleConnect` return (Table 38); `PDU_ERR_MODULE_NOT_CONNECTED` is not.
- The unconditional `*self.module_state.lock().await = ModuleState::default();` my round-2 fix added to `rpc_module_connect` is removed entirely. `module_state` is now written to `Ready` in exactly one place: `ensure_open_device_inner`'s fresh-`PassThruOpen` branch (unchanged, pre-existing) — a genuine native open is what revalidates the device, not a client's mere repeat of `ModuleConnect`.
- `rpc_module_disconnect` is unchanged by this ADR: it does not itself touch `module_state.status` (pre-existing behavior), so a `NotAvail` module's status is whatever it was until the *next* `ModuleConnect` runs `ensure_open_device_inner`'s fresh-open path (since `device_id` is now `None` after disconnect) and resets it to `Ready` there.
- This scopes ADR-107 Decision (d)'s "already-open handle -> no-op" description to modules still `PduModstReady` — the no-op remains exactly as ADR-107 described for the ordinary repeat-`ModuleConnect`-on-a-healthy-module case; it is only the already-open-but-`NotAvail` case that now rejects instead of silently succeeding.

## Alternatives Considered

1. **Force a real `PassThruClose` + fresh `PassThruOpen` cycle inside `rpc_module_connect` when `status != Ready`.** Rejected: `handle_channel_hard_error` is scoped per-channel, not per-device (`events.rs`) — sibling channels' CLLs and poll tasks can still be live when one channel hard-errors. Closing the device out from under them would require replicating `ModuleDisconnect`'s entire teardown sequence (CoP cancellation ordering, `terminal_cops.purge_many`, subscription termination) inside `ModuleConnect`, which has no such teardown today and is not the function the spec assigns that job to. It is also unsupported by the spec's own state machine regardless — nothing licenses a `NotAvail -> Ready` transition via `ModuleConnect`, forced reopen or not.
2. **Probe the device with a cheap native call (e.g. `PassThruReadVersion`) and reset to `Ready` only if it succeeds, else fail.** Rejected: J2534 v04.04 has no dedicated health-check primitive, and `PassThruReadVersion` succeeding would prove nothing about whether the actual communication channels a hard error tore down are usable again — it queries the adapter DLL/firmware, not the vehicle bus. Even a passing probe would leave the client with "module READY" but every CLL already destroyed, which still needs a full reconnect regardless. `j2534-0404-mock` also has no error-injection hook for `PassThruReadVersion`'s failure path today, so this option's negative case could not even be tested without new mock infrastructure.
3. **Keep the round-2 blind-reset behavior (`ModuleConnect` always succeeds and clears `NotAvail`).** Rejected: this is the defect Codex's round-2 review found — a false success that hands the client a possibly-dead `DeviceId`, and it silently discarded `last_error`, breaking ADR-105's `error_event_data` reporting for a client that had not yet retrieved the loss-of-comm event.

## Consequences

- A client that loses communication to the VCI must call `ModuleDisconnect` before a subsequent `ModuleConnect` can succeed again — a bare repeat `ModuleConnect` on a `NotAvail` module now fails fast with `PDU_ERR_FCT_FAILED` instead of either wedging forever (round 1's gap) or lying about success (round 2's gap). This matches NOTE 2's own advisory recovery sequence exactly, rather than inventing adapter-specific semantics for a situation the spec already addresses.
- `last_error`/`PDU_ERR_EVT_LOST_COMM_TO_VCI` survives a rejected `ModuleConnect` call (previously silently cleared by the round-2 fix), so a client that calls `ModuleConnect` before draining the event queue can still retrieve it via `GetStatus`/the `ErrorDetail` on the rejection itself.
- **Closed by ADR-134:** `GetVersion` used to call `ensure_open_device_for` directly (not `require_connected_device_for`) without checking `module_state.status` at all — a `NotAvail` module's already-open device could lazily "succeed" through the no-op branch, returning stale version info rather than a clean `PDU_ERR_MODULE_NOT_CONNECTED`. ADR-134 added the same scoped `module_state.status` check `CreateComLogicalLink` already had.
- Spec-edition caveat (per this repository's standing policy): the §9.4.29.2/§9.4.30 clauses cited above are ISO 22900-2:2009(E). `docs/j2534-0404-architecture.md` targets the 2022 edition; a 2022 revision of Behaviour (a) or the `NOT_AVAIL` use-case table is possible and has not been checked against this decision.

## Amendment (Codex review, PR #143, round 3 on the same mechanism): `CreateComLogicalLink` + a fresh channel connect could silently clear `NotAvail`, bypassing `ModuleConnect`'s own rejection entirely

The Decision above closed the recovery gap for `ModuleConnect` itself, but a third Codex review round on the same PR found a second, more serious path to the identical defect the Decision rejects: `rpc_create_com_logical_link` (`rpc_link.rs`) never checked `module_state.status` at all (the residual noted above, before this Amendment), and `spawn_new_shared_channel` (also `rpc_link.rs`, invoked by `ConnectComLogicalLink` when a CLL's first physical channel is opened) unconditionally reset `module_state` to `PduModstReady` on the reasoning that "a new physical channel means the VCI adapter responded." A client on a `NotAvail` module could therefore: create a fresh CLL (never gated), connect it (opening a genuinely new physical channel, since a hard channel error only tears down the CLLs on the channel that actually failed — `device_id` and any of a module's OTHER channels stay live), and have that success silently clear `NotAvail` back to `Ready` — with no `ModuleDisconnect` ever having run. A subsequent `ModuleConnect` would then see `Ready` and succeed normally, completely bypassing this ADR's Decision.

**Fix:**
- `rpc_create_com_logical_link` now performs the same check `rpc_module_connect` does, immediately after `ensure_open_device_for` succeeds and while still holding its `device_id` guard (closing the same TOCTOU window): if `module_state.status != PduModstReady`, it rejects with `PDU_ERR_MODULE_NOT_CONNECTED` (`Self::module_not_avail_status`) rather than `PDU_ERR_FCT_FAILED` — ISO 22900-2 Table 9 (§9.4.9, `PDUCreateComLogicalLink`) lists `PDU_ERR_MODULE_NOT_CONNECTED`, unlike `PDUModuleConnect`'s own Table 38, hence the different error code between the two call sites.
- `spawn_new_shared_channel`'s reset-to-`Ready` is removed entirely, not merely guarded — it was always redundant in the ordinary (non-`NotAvail`) flow (`module_state` is already `Ready` there, either by default or via `ensure_open_device_inner`'s own reset, which `CreateComLogicalLink`'s `ensure_open_device_for` call already ran before this point) and, per this ADR's own Decision, no code path other than a fresh `PassThruOpen` is licensed to write `PduModstReady` at all.
- **Closed by ADR-134:** `ConnectComLogicalLink` itself used to not be gated on `module_state.status` at all. A CLL created while the module was `Ready`, left unconnected, and only connected AFTER the module went `NotAvail` used to still successfully open a physical channel and communicate — `rpc_connect_com_logical_link` operates on an existing `cll_handle`, not a fresh `module_handle`-scoped request, and closing this meant auditing every code path that can reach `spawn_new_shared_channel`/an existing-shared-channel join for the same TOCTOU discipline this Decision and its sibling fix both required. ADR-134 did that audit — it found a THIRD path (`CoptUpdateparam` -> `promote_unique_resp_id_table` -> `ensure_uudt_companion_channel`, entirely independent of `ConnectComLogicalLink`) beyond the one this paragraph originally named — and closed all three with gates on `rpc_connect_com_logical_link` and on `ensure_uudt_companion_channel` (the single choke point for every companion-channel open/join). See ADR-134 for the full account.

Regression coverage: `j2534-0404-service/src/service/rpc_link.rs::tests::create_com_logical_link_rejects_when_module_marked_not_avail`, `::connecting_an_already_created_cll_does_not_clear_not_avail_status` (the latter proves `ConnectComLogicalLink` still succeeds on a pre-existing CLL — the residual above — while pinning that `module_state` is no longer silently reset by that success).

## Correction (Codex review, PR #143, round 4 on the same mechanism): the rejection message told a `NotAvail` client to do the one thing that would leave them stuck

`require_connected_device_for` and `rpc_create_com_logical_link`'s `NotAvail` rejections both reused `module_not_connected_status`'s pre-existing message ("has not been connected -- call ModuleConnect first"), inherited unchanged from before this ADR. That instruction is correct for the genuinely-never-opened case (`device_id` is `None`) but actively wrong for the case this ADR's own Decision and Amendment cover: a device that IS open under a module a hard error marked `NotAvail`. Following that instruction would call `ModuleConnect`, which this same ADR's Decision made reject that exact state with `PDU_ERR_FCT_FAILED` — a client that trusted the error message would be stuck in a loop with no path forward. A separate ADR-107 sentence (Decision (d), corrected in the same commit) still described the intermediate round-2 blind-reset behavior this ADR's Decision replaced, left unstated as superseded.

**Fix:** a new `module_not_avail_status(requested, last_error)` helper (`service.rs`), carrying the message "lost communication with the VCI -- call ModuleDisconnect, then ModuleConnect to reconnect," replaces `module_not_connected_status` at both `NotAvail`-but-open call sites (`require_connected_device_for`, `rpc_create_com_logical_link`); `module_not_connected_status` itself is now reserved for the genuinely-nothing-open case and documents that split in its own doc comment. ADR-107 Decision (d)'s bullet is corrected to describe the current (reject) behavior instead of the superseded intermediate (blind-reset) one, with a pointer to this ADR for why it changed twice.
