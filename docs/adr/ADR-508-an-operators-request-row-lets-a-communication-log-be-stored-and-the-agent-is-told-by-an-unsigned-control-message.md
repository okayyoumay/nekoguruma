# ADR-508: An Operator's Request Row Is What Lets a Communication Log Be Stored, and the Agent Is Told by an Unsigned Control Message

**Date:** 2026-11-25
**Status:** Accepted
**Affects:** design 4.3, 8.11, 13.4, 14.3; `crates/server` (`uploads.rs` begin, a migration for `comm_log_requests`, the hub's delivery, the Web API), `crates/agent` (the handling of the command and the log's path), `db/README.md`, `api/openapi.yaml`, `docs/glossary.md`; details ADR-455; amends ADR-493's judgement of begin and two of its Consequences

## Context

ADR-455 fixes the rule: a job's communication log reaches the server only by an operator's explicit action, with the scope shown, and the agent then sends it over the data channel. ADR-493 built the channel and left open how an operator's action reaches the agent, and how a source that later runs append to is handled (its Consequences). Three facts follow from the code as it stands:

- Begin (ADR-493 item 3) accepts any `commLog` for a job of the calling agent and generation, so an agent could store a log nobody asked for, which design 16.2 does not allow.
- Nothing tells the agent that an operator asked: the agent's uploader sends what its ledger holds, and the ledger is filled by a debug-only command.
- Nothing deletes or ages a job's stored objects, so a log's retention has no mechanism to attach to.

## Decision

After step 4 the table, the Web API that writes a request (items 1 and 2), item 3's refusal, item 6's rule that a stored log is not replaced, the agent's side of items 4 and 5 (the two control messages and the handling of a command) and the server's side of item 4 (the sending of the command, the expiry and the application of the answers) exist.

1. **A request row per job and generation.** An operator's request is a row of `comm_log_requests` keyed by tenant, job and ownership generation, with the agent the job belongs to, the operator who asked, a state (`requested`, `accepted`, `refused` or `expired`) and, for `refused`, the agent's reason (`unknownJob`, `noLog`, `busy`, `tooLarge`). "Stored" is not a state: a stored log is the job's `job_objects` row of kind `commLog` that is `finished`. The row is written by a Web API operation that is bound to a scope the operator was shown: `GET /v1/comm-log-uploads/scope` lists 1 to 32 jobs, the period and a digest of what it shows, and `POST /v1/comm-log-uploads` names the jobs and the digest, so a request is made only for a scope that is still the one displayed. Both read the scope with one statement and judge each job by one rule; the GET lists a job the POST would refuse, with `requestable` false, so that a client can see which job stops the request. The digest is `ngr-comm-log-scope-v1`, a SHA-256 over the jobs in ascending ID order, each with its ID, the ownership generation of its stored instruction, agent, kind, VIN, creation time and end time. It holds neither the log's state nor the request's: the request itself moves them within seconds, so a repeat of a request whose answer was lost would otherwise be refused. The log's state the GET shows is that of the job's `commLog` object at the generation (`none`, `failed`, or the live object's state), beside the request's state. The call is one transaction, all or nothing, answers 202, and writes one audit row per job newly requested or renewed, with the generation alone in its detail (the VIN and the digest are never in it). A request for a job and generation whose row is `refused` or `expired` renews it by an update in place: the state returns to `requested`, `refusal`, `sent_at` and `answered_at` are cleared, and `requested_by` and `requested_at` become the new request's; a row in state `requested` or `accepted` is left as it is, and so is the job whose log is stored (a `finished` `commLog` object), whatever its row says, since a stored log is not replaced (item 6). The table keeps one row per job and generation, so a renewal cannot add a second. The agent's job is the row's: its `agent_id` is tied to the job's by a composite foreign key.
2. **Who may ask.** An operator with the `worker` permission, for a job the operator created, whose agent is not revoked and still lists the operator among its allowed operators (the check job creation makes), whose job has been delivered and has ended. Delivered means the agent acknowledged the job, ended means the job has an end time; neither is judged by the name of its state. The POST judges in this order: 403 without the permission, 404 for a job that is not the caller's or does not exist (one answer for both), 500 for a stored instruction that does not decode, 403 (the same document, no code) for a revoked agent or an operator off the allow-list, 422 `JOB_NOT_DELIVERED`, then 422 `JOB_NOT_ENDED`, and 409 `SCOPE_CHANGED` for a digest that is not the scope's; over several jobs the answer is the first class any of them has. The agents' rows are held `FOR SHARE` until the commit, so a revocation cannot commit mid-request. The GET lists a job it would refuse with `requestable` false.
3. **Begin refuses a log nobody asked for.** For kind `commLog` only, begin requires that a live `job_objects` row exists, or that a request row exists for the caller's agent, the job and the declared generation in state `requested`, `accepted` or `expired`. Otherwise it answers 404, the answer for an unknown job, and begins nothing in the store. `accepted` admits begin because the agent may begin before the server has applied its answer. `expired` admits it because expiry only stops the server's delivery: an agent that queued the log just before the expiry, or whose answer was lost, must still be able to send it. A `refused` row admits no begin: the agent said it has no log to send (or cannot send it now), so a begin is not what it answered, and a later request renews the row (item 1). A repeated begin of an upload that exists is answered from that row whatever the request's state has become. Kind `result` is not affected.
4. **The agent is told by a control message, sent at least once.** The server sends `logUploadCommand` (job, generation) on the control channel to the agent's connected session, every 10 seconds for each `requested` row of a connected agent that has not been sent within the lease and whose job has no live `commLog` object, and again after a lease of 90 seconds until the agent answers `logUploadAnswer` (`queued`, `unknownJob`, `noLog`, `busy`, `tooLarge`) or the request is 24 hours old, when its state becomes `expired`, which stops the delivery and nothing else. A pass sends at most as many rows of one agent as its outbound queue holds, in order, and leaves an agent whose queue is full alone for the rest of the pass, so one agent's backlog does not delay another's; a revoked agent is sent nothing and its answers are not applied. The server also remembers in memory which connection it sent a row on, so an agent that reconnects inside the lease is sent the command again at the next pass; after a restart of the server that memory is empty and the lease alone applies. The row is stamped `sent_at` only once the session's outbound queue has taken the frame, and an answer is applied by one statement that changes the sender's own row for that job and generation only while its state is `requested` and the row has been stamped `sent_at`, so a late `queued` for an `expired` row changes nothing, and neither does an answer to a command sent before the row was renewed (the renewal clears the stamp, and the command and the answer carry no request identity); an answer that arrives after the renewed row's next stamp is applied, and the operator asks again. With several server instances, another instance's expiry can land between this instance's read and its stamp: the same accepted window (the begin gate admits that agent's upload by item 3 all the same). The command is not signed: it only asks the agent to send what the agent holds for a job it has already accepted, to the server that issued the job, over the data channel where the server's own checks apply; a forged command can make the agent send a log early, not send it elsewhere or send other bytes. An early or forged command can make a run that resumes start without its log (the run finds the writer lock held and goes on without a log, ADR-347) only while a read holds the lock, which is the time to hash the log. The standard profile revisits that (below).
5. **The agent acts only for a job it holds, in a fixed order.** It reads only its own file for the job, `{job}.g{generation}.commlog.jsonl` in the journal directory of its mode, never a path the server names. (a) The job ID must be a canonical UUID and the received-jobs ledger's highest generation for the job must be the one asked for, else `unknownJob` (an earlier or later generation is as unknown as a job never taken). (b) An entry already pending in the upload ledger for the log answers `queued`, without reading the file and before the writer lock is tried, so a redelivered command for a queued log never answers `busy`. (c) A missing file answers `noLog` before the lock is touched, so no lock file is made for a job without a log. (d) The log's writer lock is tried once; `busy` if another writer holds it. (e) A file with no complete line answers `noLog`, and one whose complete lines are over the object limit answers `tooLarge`. (f) Otherwise the bytes up to the last line end are hashed under the lock, enqueued, and the answer is `queued`, sent once the enqueue is durable. A failure sends no answer, so the server asks again until the request expires: this covers a journal directory or a log that cannot be read, a ledger that is full or refuses the source, and a read cut off because the connection it came on ended (the read stops at its next chunk and frees the lock, so the command that the next connection carries does not meet `busy`).
6. **The log is the job's `commLog` object, beside its `result`.** It has no retention period and no column for one: whatever later removes a job's result removes both, with the request rows. One log is stored per job and generation, and a stored log is not replaced.
7. **Built in five steps.** (1) This decision, the table and begin's refusal. (2) The two control messages and the agent's handling. (3) The server's delivery and its application of the answers (a task of the hub's set, `comm_log_requests.rs`). (4) The Web API, whose second call renews refused and expired rows as item 1 says. (5) An end-to-end test with the real agent, server and object store. After step 1 the table exists, nothing writes it outside tests, and begin refuses every log of the upload route without a row; after step 4 the Web API writes it.

Rejected:

- **A signed command.** A signature protects nothing the data channel's checks do not, in M3's local profile; it would add a purpose and a payload form for a message that only asks.
- **The agent polling for requests.** The control channel already reaches a connected agent, and a poll would add a route, a timer and a load on the server for an event that is rare.
- **A stored proposal the agent fetches.** It needs a route of its own and a state to expire, for the same rare event.
- **A retention column on the job's objects now.** The period depends on the tenant and record kind of design 4.3, which are not built; a column written now would be a second place for the rule.
- **Replacing a stored log.** A later run appends to the log, so the stored object would silently differ from the one an operator was shown, and a replacement would need the object's old key kept or removed in step with the row.

## Consequences

- One stored log per job and generation. A run that appends after the log was stored is not sent again.
- A log that turns `finished` while a request's statement waits on a row lock is not seen by that statement's check of the stored log (the statement keeps its snapshot), so the request may still be written for it; the delivery then never sends it, since a live object stops the command.
- A request for a job that the server expired while its delivery's acknowledgement was in flight is refused as not delivered, though the agent may hold a log for it; and a row `accepted` whose upload never arrives is not asked again.
- Nothing deletes stored logs or request rows yet. This is acceptable in the local profile only, and a pass over a job's objects and request rows, with VIN deletion, is needed before any deployment that is not local.
- The runner's intake must write every job's log at the path of item 5 and enqueue the result for the uploader, or a requested log answers `noLog`.
- On the standard profile the command's authentication is revisited with the profile where the server's answer proof is not required (ADR-504 item 6).
- ADR-493 item 3's judgement of begin gains item 3 above, and its Consequences on the source that changes and on how an operator's upload reaches the agent are answered by items 4 to 6.
