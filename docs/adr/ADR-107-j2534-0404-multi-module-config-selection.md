# ADR-107: Config-Declared Multi-Module Device Selection for J2534 v04.04

**Date:** 2026-07-21
**Status:** Accepted
**Affects:** `vci-service-config`, `j2534-0404`, `j2534-0404-service` service, config, rpc_module, rpc_link, error

## Context

`j2534-0404-service` has always supported exactly one module: `DEFAULT_MODULE_HANDLE = 1` is a fixed constant, `GetModuleIds` hardcodes a single `ModuleData` row (`vendor_module_name = "j2534-0404"`), and the device is opened lazily via `PassThruOpen(NULL, ...)` the first time it's needed.

Deployments increasingly need to address more than one physical VCI device behind the same vendor DLL from a single service instance — e.g. a bench with two identical adapters, distinguished only by which USB port or serial number they're plugged into. SAE J2534-1 v04.04 §7.2.1 reserves `PassThruOpen`'s `pName` parameter and requires it be `NULL`; the spec defines no device enumeration or selection mechanism at all. There is therefore no in-spec way to open a *specific* one of several connected devices through the v04.04 API.

## Decision

### (a) Spec deviation: non-NULL `pName` as a vendor-extension device selector

Each pre-declared module entry in `config.toml` (`config.apis.j2534-0404.libs."<lib>".modules`, a TOML array-of-tables) carries a `pname` connection-target string. `j2534-0404-service` passes that string verbatim as `PassThruOpen`'s non-NULL `pName` argument when opening that module's device. This is explicitly out-of-spec — real J2534 v04.04 conformance requires `pName == NULL` — but is a vendor-extension behavior some real J2534 DLLs support in practice (a serial number, port identifier, or other opaque connection-target string), and is the only mechanism `PassThruOpen`'s own signature offers for this purpose. The user explicitly approved this deviation given the alternative below.

**Rejected alternative:** select among multiple *registered* vendor DLLs (distinct `library_name`s / registry entries) instead of passing a device-selection argument to a single DLL's `PassThruOpen`. This is spec-compliant (each DLL enumerates and opens whatever device it's paired with, with `pName` staying `NULL`), but does not solve the actual deployment shape this ADR targets — two or more identical, or vendor-identical, physical devices behind the *same* DLL, distinguished only by a connection-target argument the DLL itself defines. Registering the same DLL multiple times under different service instances/`library_name`s does not let one service instance address more than one such device, and doesn't help when the DLL itself is what needs the extra selector. Not chosen; `j2534-0404-registry`'s existing device-name/library discovery is unrelated and untouched by this change.

### (b) Single-open-device, not simultaneous multi-device

Configuring multiple modules does **not** mean the service can talk to multiple physical devices at once. `J2534Service`'s state model — `device_id`, `ModuleState`, `shared_channels`, event subscriptions (`SubscriptionKey = (module_handle, cll_handle)`, keyed loosely but never actually populated for more than one module concurrently) — is single-module by design (ADR-020's module-level state tracking, ADR-001's `ModuleDisconnect` force-cleanup semantics). Extending every one of those to a per-module partition (separate CLL/channel/subscription namespaces per open device, concurrent poll tasks, etc.) is a materially larger change than "let the deployer choose *which* module to open" and is explicitly out of scope here. `device_id` becomes `Arc<Mutex<Option<(module_handle, DeviceId)>>>` — a single slot tagged with which module currently owns it, not a per-module map.

### (c) `module_handle` = 1-based config array position, no explicit/stable IDs

`GetModuleIds` returns one `ModuleData` row per `modules` entry, in config-file order, with `module_handle` equal to the entry's 1-based position in that array. When `modules` is absent entirely, the service synthesizes exactly one entry (`label = "j2534-0404"`, no `pname`) at handle 1 — byte-for-byte the pre-ADR-107 behavior. There is no separate persistent/stable module ID scheme.

**Operational tradeoff, accepted:** if a deployer reorders or edits the `modules` array between restarts, `module_handle` values silently point at different physical devices than before. A client that persists a `ModuleHandle` across a service restart (unusual for this protocol, but not forbidden by it) can end up connecting to the wrong device, or get a "not configured" rejection if the array shrank. Deployers are responsible for keeping the array order stable; this is a config-authoring discipline, not something the service can validate.

### (d) Reject-on-switch: at most one module open, no automatic disconnect-and-reswitch

`ModuleConnect(h)`:
- No device open yet → opens `h`'s configured entry (`PassThruOpen` with that entry's `pname`, or `NULL` for the synthetic default entry).
- A device is already open under `h` AND `module_state.status == PduModstReady` → no-op with respect to the device itself (no `PassThruClose`/`PassThruOpen`), matching pre-ADR-107 idempotent-reconnect behavior. If instead `module_state.status != PduModstReady` (a hard channel error marked it `PduModstNotAvail` without closing `device_id`), this rejects with `PDU_ERR_FCT_FAILED` rather than succeeding — `NotAvail` is sticky until an explicit `ModuleDisconnect` (ADR-131, amending this bullet: an earlier intermediate fix on the same PR briefly had `rpc_module_connect` unconditionally reset `module_state` to `PduModstReady` here, which ADR-131 found to be a false-success defect and replaced with this rejection).
- A device is already open under a **different** handle → rejected with `PDU_ERR_RESOURCE_BUSY`, surfaced as gRPC `Code::FailedPrecondition` via the existing ADR-105 rich-error path (`state_guard_status`). `PassThruOpen` is **not** called. The client must call `ModuleDisconnect` first to release the currently-open module before connecting a different one.

`PDU_ERR_RESOURCE_BUSY` ("resource already in use") is the correct ISO 22900-2 semantic match for this rejection — a second module is not construct-scoped in the way `PDU_ERR_SHARING_VIOLATION` is defined (that code is about a construct, e.g. a CLL/channel, already claimed within one open module — see ADR-105 `error.rs:64`'s distinct, unrelated `ERR_DEVICE_IN_USE → PduErrSharingViolation` mapping, which is about a *native*, cross-process device conflict at `PassThruOpen` time and is unchanged by this ADR).

`require_module_handle` (the RPC-layer's single module-handle range-validation choke point, used by `rpc_module.rs`/`rpc_link.rs`/`rpc_primitive.rs`/`rpc_misc.rs`, plus `rpc_link.rs`'s own `GetResourceIds` `PDU_HANDLE_UNDEF`-accepting variant) generalizes from a fixed `== DEFAULT_MODULE_HANDLE` equality check to a `1..=module_count` range check, where `module_count` is the number of configured `modules` entries (or 1, when absent). `PDU_HANDLE_UNDEF` continues to mean "the current/default module" and continues resolving to handle 1 everywhere it already did (module-level event/subscription keys, `GetResourceIds`'s response echo) — this ADR does not change per-CLL or per-event module-handle attribution to track which module is actually open; those call sites still assume/report module 1. See Accepted Residuals.

### (e) `device_id` is the strict outermost lock; check-then-act call sites hold the guard for the whole operation

`ModuleDisconnect`/`PDU_IOCTL_RESET` racing with `ModuleConnect` was the third recurrence of the same underlying bug class this ADR keeps closing: "acted on whatever module was open, not the one requested." The first two (Decision (d), Residual 3) were plain check-then-open gaps, fixed by routing every module-scoped RPC through `ensure_open_device_for`/a reject-on-mismatch check. The third was a TOCTOU race in the reject-only helper itself (`reject_if_open_under_different_handle`, added by Residual 3's follow-up fix): it locked `device_id`, checked, and dropped the lock before returning `Ok(())`, leaving a window — between that check and the caller's own later teardown (`ModuleDisconnect`'s link/channel/device cleanup) or reset (`PDU_IOCTL_RESET`'s in-memory state reset) work, both of which cross `.await` points — in which a concurrent `ModuleConnect`/`ModuleDisconnect` could open or close a *different* device, so the guarded operation could still end up acting on the wrong module despite the check having passed.

**Decision:** `device_id` is the strict outermost lock in this service. Any call site that needs to check-then-act on it obtains it via `lock_device_for(requested)` (`service.rs`, renamed from `reject_if_open_under_different_handle`), which returns the held `tokio::sync::MutexGuard` itself rather than dropping it — the caller holds the returned guard for the ENTIRE guarded operation, not just the initial check. `rpc_module_disconnect` binds it once and reuses it at the later teardown point instead of re-locking; `ioctl_reset` binds it as a named guard that lives to the end of the function. No code path may acquire `device_id` while already holding any other service lock (`logical_links`, `shared_channels`, `primitives`, `subscriptions`, `module_state`, `api`) — verified safe because none of the (now five, including `lock_device_for`'s own) `device_id` acquisition sites in this service currently do so, and every event sender in this service is an `mpsc::UnboundedSender`, so sends performed while holding the `device_id` guard cannot block and cannot deadlock against it.

**Consequences:** module-scoped RPCs that touch `device_id` (`ModuleConnect`, `ModuleDisconnect`, `PDU_IOCTL_RESET`, and the `ensure_open_device_for`-routed RPCs) now serialize on it for their full duration rather than just the initial check — acceptable under the single-open-device model (Decision (b)), since this service never has more than one device open concurrently regardless. Any future code that acquires `device_id` while holding another service lock is a deadlock risk and is forbidden by this invariant (documented on the `device_id` field itself and on `lock_device_for`). Residual: `rpc_module_connect`'s `was_open` snapshot (a separate `device_id.lock().await.is_some()` read, ahead of `ensure_open_device_inner`'s own lock acquisition) can still race two concurrent `ModuleConnect` calls into both observing `was_open == false`, causing a duplicate or suppressed `ModuleListChg` event. This is benign — an extra/missing event, not a correctness bug on `device_id` itself — and is backlogged, not fixed, by this decision (`j2534-0404-service/docs/implementation-notes.md`'s Prioritized Backlog).

The invariant also applies to read-only handlers, not just check-then-act mutation paths: any handler that gates its interpretation of `logical_links` (or other per-module state) on the open-module identity — e.g. `GetResourceStatus`, which only scans `logical_links` for a queried module when that module is the one currently open — must hold `device_id` across the whole check-and-read, not just peek and release it before the read. A plain peek-and-release remains acceptable only when nothing later in the same call is interpreted through the peeked value.

### (f) Addendum: `device_id` is outermost only among the *nested* lock set — two device-derived probe caches sit ABOVE it, and reset on device-lifecycle boundaries

Decision (e)'s claim that "no code path may acquire `device_id` while already holding any other service lock … verified" is factually incomplete: it does not account for `j1850_bus_flavor` (ADR-070's SAE J1850 VPW/PWM auto-detect cache) and `resolved_can_channel_mode` (ADR-046 addendum's CAN dual/single-channel auto-detect cache). Both are, in pre-existing code that predates this addendum, already held across a transient `device_id` acquisition: `autodetect_sae_j1850_flavor` (`rpc_link.rs`) holds `j1850_bus_flavor` while calling into `probe_sae_j1850_flavor` → `ensure_open_device` → `device_id`, and `probe_can_channel_mode` (`rpc_link.rs`) holds `resolved_can_channel_mode` while calling `ensure_uudt_companion_channel` → `ensure_open_device` → `device_id`. So they sit ABOVE `device_id` in the lock hierarchy, not nested under it the way `module_state`/`logical_links`/`shared_channels`/`primitives`/`subscriptions`/`api` are.

This was surfaced by a Codex-review P1 finding on PR #110's multi-module support: because neither cache was ever reset, a `ModuleDisconnect` (module 1) followed by `ModuleConnect` (module 2) let module 2 silently reuse module 1's stale probe conclusions (auto-detected J1850 flavor, auto-detected CAN channel mode) instead of re-probing the newly-opened physical device.

**Decision:** a two-level lock hierarchy, and a reset policy tied to each state's own level:

- Probe-cache locks (`j1850_bus_flavor`, `resolved_can_channel_mode`) may be held across a transient `device_id` acquisition. `device_id` holders must never acquire either of them — the inverse ordering would deadlock against the existing pre-ADR-107 code above.
- All three device-derived states now reset on device-lifecycle boundaries, each at its own level: `module_state` resets at fresh device-open time (`ensure_open_device_inner`, nested under `device_id` at its established level — this preserves post-mortem `last_error` queryability in the window between a disconnect and the next reconnect, rather than resetting at disconnect time). ~~The two probe caches reset at `ModuleDisconnect`, explicitly AFTER the `device_id` guard (`slot`) is released~~ **superseded by addendum (h): `ModuleDisconnect` no longer resets either probe cache at all — see (h) for why the clear-on-disconnect approach below was replaced.**
- `probe_can_channel_mode` never writes `resolved_can_channel_mode` for a CLL handle that no longer exists in `logical_links` by the time its probe call returns — a disconnect that raced the probe is not a real "single channel only" conclusion about the hardware and must not poison the cache for the next module, mirroring `autodetect_sae_j1850_flavor`'s existing "only cache a conclusive result" discipline. **Addendum (h) extends this liveness gate to also require a device still be open (not just the CLL handle live), and applies it to `autodetect_sae_j1850_flavor`'s write-back too.**

**Consequences:** a probe racing a concurrent disconnect costs at most one redundant re-probe on the next module's first relevant CLL — benign, not a correctness issue. Decision (e)'s enumerated "locks nested under `device_id`" list gains `module_state`'s reset-at-open behavior as a documented detail, but its membership is unchanged. The two probe caches are explicitly NOT part of that nested set and must never be acquired while `device_id` is held; any future code that does so is a lock-order-inversion deadlock risk and is forbidden by this addendum, the same way Decision (e) forbids the reverse acquisition order for the nested set. Regression coverage: `j2534-0404-service/tests/grpc_mock/modules.rs::module_switch_reprobes_j1850_flavor_instead_of_reusing_stale_cache`, `::module_switch_reprobes_can_channel_mode_instead_of_reusing_stale_cache`, and `j2534-0404-service/src/service/rpc_link.rs::tests::probe_can_channel_mode_does_not_cache_for_a_dead_handle` (the dead-handle hardening, a unit test since it needs direct access to the `pub(super)` `probe_can_channel_mode`).

### (g) Addendum: the non-selecting `ensure_open_device` re-validates its `cll_handle` against `logical_links` atomically with `device_id`, closing the mid-disconnect reopen race

**Context:** Decision (f) established that `ModuleDisconnect` must release `device_id` (`drop(slot)`) *before* resetting the two probe caches (`j1850_bus_flavor`, `resolved_can_channel_mode`), since those caches sit ABOVE `device_id` in the lock hierarchy and acquiring `device_id` while holding them would invert it. That ordering, by itself, opened a window: a CLL-scoped probe (`autodetect_sae_j1850_flavor` → `probe_sae_j1850_flavor`, or `probe_can_channel_mode` → `ensure_uudt_companion_channel`) blocked waiting for `device_id` could acquire it right after `ModuleDisconnect`'s `drop(slot)` and, under the non-selecting `ensure_open_device`'s old no-guard-holding, handle-agnostic logic, either reuse or reopen a device — including, if a concurrent `ModuleConnect` for a *different* module had already raced in, incorrectly probing that other module's freshly-opened device using a stale CLL's context. This is the race the P3 entry in `j2534-0404-service/docs/implementation-notes.md`'s Prioritized Backlog flagged as out of scope for Decision (f).

**Decision:** the non-selecting `ensure_open_device` is now CLL-scoped by signature — it takes the caller's `cll_handle` and, via `ensure_open_device_inner`'s new `cll_liveness: Option<u32>` parameter, re-validates that the CLL still exists in `logical_links` immediately after acquiring `device_id` and before doing anything else. This check runs first, ahead of both the "already open, return it" branch and the "nothing open, open a new one" branch, so it covers a probe resuming into either state. It refuses with an unknown-handle error (`unknown_handle_status`, `NotFound`/`PDU_ERR_INVALID_HANDLE`) rather than acting for a CLL a concurrent disconnect already tore down. This is race-free, not merely narrowed: `rpc_module_disconnect` clears `logical_links` (`rpc_module.rs`) while still holding `device_id`, and only calls `drop(slot)` afterward, so any probe that acquires `device_id` after that release deterministically finds its CLL already gone. The strict, module-selecting `ensure_open_device_for` is unaffected (passes `cll_liveness = None`) — it is already handle-safe via `reject_on_mismatch`.

**Consequences:** no epoch/flag state was needed — the fix reuses the same `device_id` critical section and the pre-existing `logical_links` clear-before-release ordering in `rpc_module_disconnect`. `ConnectComLogicalLink` (and the other two CLL-scoped callers, `ensure_uudt_companion_channel`, `probe_sae_j1850_flavor`) racing a disconnect now correctly fails with an unknown-handle error instead of silently reopening a device or probing the wrong module's device. One accepted residual: a probe that already obtained the device *before* the disconnect locked `device_id` runs its actual hardware I/O against the now-closing device, serialized against `ModuleDisconnect`'s own teardown by the `api` mutex; any resulting probe conclusion is discarded because it is never conclusive by the pre-existing only-cache-conclusive discipline (Decision (f)'s third bullet, and `autodetect_sae_j1850_flavor`'s mirrored behavior) — benign, not fixed further here. The P3 backlog entry this addendum closes has been removed from `j2534-0404-service/docs/implementation-notes.md`'s Prioritized Backlog. Regression coverage: `j2534-0404-service/src/service/rpc_link.rs::tests::ensure_open_device_rejects_a_dead_cll_handle_with_nothing_open` and `::ensure_open_device_rejects_a_dead_cll_handle_with_a_device_already_open` (unit tests, mirroring `probe_can_channel_mode_does_not_cache_for_a_dead_handle`'s approach of reproducing the "CLL already torn down" state directly rather than timing the actual race, since the existing `grpc_mock` harness has no delay-injection hook).

### (h) Addendum: epoch-tagged self-validating probe caches replace clear-on-disconnect, plus two more lock-family fixes

**Context:** addenda (f) and (g), across four rounds of point-fixes, kept the two device-derived probe caches (`j1850_bus_flavor`, `resolved_can_channel_mode`) correct by having `rpc_module_disconnect` clear them, ordered *after* `device_id`'s guard (`slot`) was released — required because those caches sit ABOVE `device_id` in the lock hierarchy (f) and so cannot be cleared while `slot` is held. That ordering itself created the exact race (g) closed on the callee side (the non-selecting `ensure_open_device`'s `cll_liveness` re-check). A full holistic audit after those five review rounds concluded the clear-on-disconnect approach is structurally unfixable by reordering alone: `device_id` is released before the caches are cleared (an unavoidable consequence of the lock hierarchy), so there is always a window in which a concurrent request can reconnect a *different* module and run a probe that reads the still-stale cache before `ModuleDisconnect` gets around to clearing it — applying the old module's stale probe result to the new module's CLL. No ordering of "release `device_id`, then clear caches" can close this window; only self-validation on read can.

**Decision:** replace clear-on-disconnect with an epoch-tagged self-validating cache scheme.

- A new `device_epoch: Arc<AtomicU64>` field, mutated only while holding `device_id`'s lock, read lock-free. Bumped on every successful device OPEN (`ensure_open_device_inner`, immediately after `*slot = Some(...)`) and on every device CLOSE, attempted or successful (`rpc_module_disconnect`, immediately after `slot.take()` — even a failed `PassThruClose` still bumps it, so a failed close still invalidates the caches).
  - **Amendment (2026-07-22, Codex review on PR #113):** the epoch is `u64` via `portable_atomic::AtomicU64`, not `std`'s — `std::sync::atomic::AtomicU64` does not exist on `armv5te-unknown-linux-gnueabi` (the ISA predates the LDREXD/STREXD instructions it needs). `portable-atomic` provides a genuine lock-free `AtomicU64` there via the Linux kernel's `kuser_cmpxchg64` helper (already a de-facto requirement of any glibc armv5 userland, so this adds no new platform assumption; a kernel built with `CONFIG_KUSER_HELPERS=n` cannot run this target's libc either), and forwards to the native atomic at zero cost on every other supported target. Narrowing the epoch to `u32` was considered and rejected: two bumps per open/close cycle wrap a `u32` after 2^31 cycles, letting a stale cache entry's epoch collide with the live value and pass the equality check — reintroducing the exact cross-device ABA this scheme exists to prevent. A `Mutex<u64>` was also rejected: the "read lock-free" property above is exactly what keeps the epoch outside the `cache-lock → device_id → logical_links` hierarchy this addendum's own Decision documents — a mutex-wrapped epoch would need a new, carefully-ordered lock acquisition at every read site enumerated above, in a lock family that has already produced one real AB-BA deadlock (the first bullet under "Two more real bugs" below).
- Both probe caches change from `Option<T>` to `Option<(u64, T)>`, the `u64` being the epoch the value was probed under. A read is a cache hit only if the stored epoch equals the current `device_epoch`; otherwise it is treated as a miss and re-probed — a stale-epoch entry is harmless and simply triggers a re-probe, needing no active invalidation.
- Write-backs stamp the CURRENT epoch while transiently holding `device_id` (read the epoch while still holding that lock, guaranteeing it is the epoch the currently-open device is actually running under, since the epoch is only ever mutated under `device_id`'s lock), gated on BOTH a device still being open (`slot.is_some()`) AND the probing CLL still existing in `logical_links` — extending `probe_can_channel_mode`'s pre-existing CLL-liveness-only gate (f) to also cover device-openness, and to gate the `DualChannel` conclusion the same way it already gated `SingleChannel`. `autodetect_sae_j1850_flavor`'s write-back gets the identical gate (previously ungated beyond "only cache a conclusive result"). Lock order for a write-back: the cache lock (already held from the read), then `device_id`, then `logical_links` — unchanged from (f)'s hierarchy.
- `effective_can_channel_mode` (ADR-046) applies the same epoch check: a stale-epoch cached mode is never used, falling back to `SingleChannel` exactly as a cold cache would.
- `ModuleDisconnect` no longer touches either probe cache at all. The large comment blocks in `rpc_module.rs` explaining the old drop-then-clear ordering are collapsed into a short note pointing at this addendum.
- Two more real bugs the same audit found, in the same lock family, fixed in the same commit:
  - **AB-BA deadlock:** `install_point_to_point_fc_filters` held `api` and, later in the same scope, awaited `effective_can_channel_mode()` (which locks `resolved_can_channel_mode`), while `probe_can_channel_mode` holds `resolved_can_channel_mode` and awaits `api` (via `ensure_uudt_companion_channel`) — a genuine AB-BA deadlock between two concurrent calls. Fixed by hoisting the `effective_can_channel_mode()` call to before `api` is locked. General rule, now documented on `effective_can_channel_mode` itself: never call it while holding `api` or `device_id`.
  - **Orphan-CLL race:** `rpc_create_com_logical_link` called `ensure_open_device_for(requested_handle)` and then, separately, inserted the new CLL into `logical_links`, with `device_id` released in between. A concurrent `ModuleDisconnect` completing in that gap could leave a CLL recorded for a device already closed (or a different one). Fixed by re-acquiring `device_id` via `lock_device_for(requested_handle)` and holding it across the `logical_links` insert; if nothing is open under `requested_handle` by then, the call now fails with `FailedPrecondition`/`PDU_ERR_RESOURCE_BUSY` ("ModuleDisconnect raced CreateComLogicalLink") instead of recording an orphaned CLL.

**Consequences:** no clear-ordering rules to maintain for either probe cache — `ModuleDisconnect` is now a pure teardown with respect to them. Same-module reconnect-to-different-hardware still correctly re-probes, since a close+reopen always bumps `device_epoch` even when `module_handle` is unchanged (an improvement over (f)/(g), which only distinguished by module identity, not device instance). A stale-epoch entry lingers harmlessly in memory until overwritten by the next successful probe. Accepted residuals (tracked in `j2534-0404-service/docs/implementation-notes.md`'s backlog):
  - `GetVersion` and the `READ_VBATT`/`SET_PROG_VOLTAGE`/`READ_PROG_VOLTAGE` IOCTLs release `device_id` before their `api` call; a disconnect+reconnect racing in that exact window could act on the wrong module if the native library reuses numeric device IDs. **Closed by addendum (i).**
  - The pre-existing `was_open`-event-duplication race noted in Decision (e)'s Consequences remains benign and unfixed.

Regression coverage: `j2534-0404-service/src/service/rpc_link.rs::tests::probe_can_channel_mode_reprobes_and_overwrites_an_epoch_mismatched_entry`, `::probe_can_channel_mode_does_not_cache_a_dual_conclusion_with_no_device_open`, `::effective_can_channel_mode_ignores_a_stale_epoch_entry`. The AB-BA deadlock and orphan-CLL fixes have no dedicated regression test: reproducing either race deterministically needs delay/synchronization-point injection machinery this harness does not have (both fixes were verified by code inspection plus the full existing suite showing no regression); noted as a testing gap rather than silently skipped.

### (i) Addendum: `ensure_open_device`/`ensure_open_device_for` return the held guard, closing the "resolve then release" gap at all seven call sites

**Context:** addendum (h)'s first accepted residual: `GetVersion` and the `READ_VBATT`/`SET_PROG_VOLTAGE`/`READ_PROG_VOLTAGE` IOCTLs resolved their `DeviceId` via `ensure_open_device_for`, which released `device_id` before the caller made its own `self.api` call using that id. A concurrent `ModuleDisconnect`+reconnect landing in that window could close/reopen the device, leaving the caller to either fail on a stale `DeviceId` or, if the native library reuses `DeviceId` values across a close/open pair (nothing in the J2534 spec guarantees otherwise), silently act on the wrong module's device. The same "resolve then release" shape existed at four more call sites: `rpc_create_com_logical_link` (worked around it with a second `lock_device_for` re-acquisition, addendum (h)'s orphan-CLL fix), `rpc_connect_com_logical_link`, `ensure_uudt_companion_channel`, and `probe_sae_j1850_flavor`.

**Decision:** `ensure_open_device`/`ensure_open_device_for` (and the shared `ensure_open_device_inner` both forward to) now return the held `tokio::sync::MutexGuard<'_, Option<(u32, DeviceId)>>` alongside the `DeviceId`, instead of dropping it before returning — the same guard-holding shape `lock_device_for` already used (Decision (e)). Every caller that makes a follow-up native `self.api` call using the returned `DeviceId` now holds the returned guard across that call:

- `rpc_get_version` (`rpc_module.rs`) and the three voltage IOCTLs, `ioctl_read_vbatt`/`ioctl_set_prog_voltage`/`ioctl_read_prog_voltage` (`rpc_misc.rs`), hold the guard across their single native call — `rpc_get_version` drops it explicitly right after; the three IOCTLs let it live to the natural end of the function (which also covers the error-path `last_error` read and, for `ioctl_set_prog_voltage`, the `prog_voltage` mirror write).
- `rpc_create_com_logical_link` (`rpc_link.rs`) now holds the single guard `ensure_open_device_for` returns across the `logical_links` insert directly — this makes addendum (h)'s two-step fix (a second `lock_device_for` re-acquisition, with an explicit "ModuleDisconnect raced CreateComLogicalLink" rejection for the gap between the two acquisitions) obsolete: with one continuously-held guard there is no gap left to detect, so that re-acquisition and its rejection branch are deleted outright, not merely superseded.
- `rpc_connect_com_logical_link` and `ensure_uudt_companion_channel` (`rpc_link.rs`) each hold the guard across their native `connect`/channel-setup work, then drop it explicitly once `device_id` is no longer needed for the rest of the function — critically, *before* reaching any later call in the same function that itself acquires `device_id` (`probe_can_channel_mode`, `ensure_uudt_companion_channel` itself, both reachable later in `rpc_connect_com_logical_link`'s control flow): `tokio::sync::Mutex` is non-reentrant, so still holding the guard into either would self-deadlock.
- `probe_sae_j1850_flavor` (`rpc_link.rs`) lets the guard live to the end of the function, covering the entire candidate-probing loop's real `connect`/write/read/disconnect calls.

No new lock-ordering rule: `device_id` was already the outermost lock (Decision (e)); this addendum only changes how long each caller holds a guard it already implicitly depended on being valid for, not what may be acquired while holding it.

**Consequences:** all seven call sites this residual and (h)'s orphan-CLL fix covered now hold `device_id` continuously from resolution through their native call, closing the gap for good. Reconfirmed by manual review (not merely by the test suite passing) that no site newly holds the returned guard into a call that itself locks `device_id`, `lock_device_for`, or another `ensure_open_device`/`ensure_open_device_for` — the two sites where this was a live risk (`rpc_connect_com_logical_link`, `ensure_uudt_companion_channel`) both drop their guard before reaching the reentrant call. The P3 backlog entry this addendum closes has been removed from `j2534-0404-service/docs/implementation-notes.md`'s Prioritized Backlog. Found by Codex review on PR #110 (design-advisor-directed fix). No dedicated regression test: reproducing the underlying race deterministically needs delay/synchronization-point injection machinery this harness does not have (same limitation as (g)'s and (h)'s untested races) — verified instead by the full existing suite showing no regression and by the manual guard-lifetime review above.

**Accepted latency tradeoff (edge-case-hunter finding on this addendum):** `probe_sae_j1850_flavor` now holds `device_id` for its entire candidate-probing loop (up to two candidates × `j1850_autodetect_window_ms`, default 500 ms each, so up to ~2 s), not just for the initial device resolution. Before this addendum, the guard was released before the loop, so only the loop's own `self.api` hold (already the same duration) contended with a concurrent `ModuleDisconnect`; now `ModuleDisconnect`'s *entire* teardown sequence — not just its final `PassThruClose` — can be delayed behind an in-flight probe, since `rpc_module_disconnect` acquires `device_id` as its first statement. This is a real, bounded, narrow-scenario latency increase, not a correctness bug, and is the direct cost of closing this addendum's TOCTOU: `device_id` must stay held across the probe's native calls for the fix to mean anything. Not considered worth decoupling `ModuleDisconnect`'s client-visible notifications from the `device_id` hold, given the probe window is already bounded and this only matters when a disconnect races an autodetect probe on the *same* physical device.

### (j) Addendum: `find_modules` becomes fallible so a malformed config document fails startup instead of silently disappearing into "not configured"

**Context:** `vci-service-config::load_toml_config()` has always been deliberately lenient, crate-wide: any read or parse failure of `config.toml` is logged to stderr and treated as `TomlConfig::default()` (an empty document), so every lookup built on it (`find_logging_config`, `find_library_path`, `find_can_channel_mode`, `find_modules`, `list_configured_libraries`, `list_configured_library_paths`, `manager_config`) silently falls back to "nothing configured for this key" rather than failing. That leniency is intentional and appropriate for typo-tolerant settings like logging levels or a `library_path` override. But `label`/`pname` are the only *required* fields anywhere in this crate's whole config schema, and `find_modules` is not typo-tolerant the same way: a `[[...modules]]` entry missing `pname` (or any other TOML syntax error anywhere in the document) failed the entire document's `toml::from_str` parse, which `load_toml_config()` then swallowed into `TomlConfig::default()` — indistinguishable, from `find_modules`'s `Option::None` return, from "this deployer never configured `modules` at all." `j2534-0404-service` therefore synthesized the default single module and called `PassThruOpen(NULL, ...)` against whatever device happened to be available, defeating the entire point of module selection (Decision (a)) and its own `modules = []`/non-ASCII-`pname` startup-error guarantees (Decision/Consequences above) — a config author who *intended* to pin down a specific device could end up silently talking to an arbitrary one instead. Found as a Codex-review P1 finding on PR #110.

**Decision:** `find_modules` alone becomes fallible. A new `try_load_toml_config() -> Result<TomlConfig, ConfigFileError>` (`vci-service-config/src/lib.rs`) does the read/parse work without swallowing errors; `NotFound` still resolves to `Ok(TomlConfig::default())` (no file at all remains a legitimate "nothing configured" state, distinct from "file exists but is broken"). `load_toml_config()` becomes a thin lenient wrapper around it (`unwrap_or_else` with the same `eprintln!` warning as before) and every existing caller keeps calling that lenient wrapper unchanged — this crate is also used by `iso22900-service`/`vci-service-manager`/`iso22900-registry`/`j2534-0404-registry`, and their lenient fallback for logging/library-path/manager-setting typos is intentional and must not change. `find_modules` switches to calling `try_load_toml_config()` directly and returns `Result<Option<Vec<ModuleConfigEntry>>, ConfigFileError>` (`ConfigFileError` distinguishing `Read` from `Parse`, both carrying the file path and source error, with `Display`/`Error` impls). `j2534-0404-service::config::resolve_modules` maps `Err` to a startup error (`invalid_input`, the same `io::Error` shape its other validation failures already use) rather than falling through to `build_module_entries(None)`'s default-module synthesis.

**Consequences:** a `j2534-0404-service` deployment with a `modules` config now fails startup on ANY parse error anywhere in the config document, not just within `modules` itself — since an unparseable document makes the real "is `modules` configured" answer unknowable, this is intended, not accidental: a malformed config file must never silently select a default device. Every other lookup in this shared crate (`find_logging_config`, `find_library_path`, `find_can_channel_mode`, `list_configured_libraries`, `list_configured_library_paths`, `manager_config`) keeps its pre-existing lenient fallback unchanged — an accepted residual, not an oversight, since this crate's other consumers rely on that leniency for non-critical settings. Regression coverage: `vci-service-config/src/lib.rs::tests::malformed_modules_entry_is_an_error_not_none`, `::unreadable_or_unparseable_document_is_an_error_for_find_modules`.

## Consequences

- New `vci-service-config` API: `ModuleConfigEntry { label, pname }` and `find_modules(api, arch, lib) -> Result<Option<Vec<ModuleConfigEntry>>, ConfigFileError>` (fallible as of addendum (j); originally `Option<Vec<ModuleConfigEntry>>`), mirroring `find_library_path`'s two-level (arch+lib, api+lib) priority with no api-level default (a device list only makes sense tied to one specific library).
- New `j2534-0404` wrapper API: `J2534Api0404::open(&self, name: Option<&CStr>) -> Result<DeviceId, Error>`, replacing the old zero-argument `open()`. `j2534-0500`'s unrelated `open()` is untouched.
- `j2534-0404-service::config::resolve_modules` converts each configured `pname` `String` to an owned `CString` once at startup — an embedded-NUL or non-ASCII `pname` fails startup immediately (`CString::new` for the NUL check; ASCII checked explicitly, since Windows J2534 DLLs read `pName` as an ANSI narrow string) rather than failing unpredictably on some later `PassThruOpen`/`ModuleConnect` call. `modules = []` (present but empty) is also a startup error, as is `find_modules` returning `Err` (addendum (j)) — neither falls back to the default single module.
- `J2534Service::ensure_open_device` (used by call sites that have no `module_handle` of their own to select with — the small set of CLL-scoped internal helpers reached only after `CreateComLogicalLink` already pinned a module down, per the follow-up fix described in Accepted Residual #3 below) stays a non-selecting convenience: it returns whatever device is already open, regardless of handle, and only opens a fresh one (the default module) when nothing is open yet. `ensure_open_device_for(module_handle)` is the strict, module-selecting variant Decision (d) describes; every RPC that itself receives and validates a `module_handle` AND is allowed to lazily open a device — `ModuleConnect`, `GetVersion`, `CreateComLogicalLink` — uses it. As of the A2-8 conformance fix (Accepted Residual #5 below), the module-scoped `PDU_IOCTL_RESET`/`READ_VBATT`/`SET_PROG_VOLTAGE`/`READ_PROG_VOLTAGE` IOCTLs no longer do — they use the stricter `require_connected_device_for`, which never opens a device itself. The 3 module-scoped-but-unsupported IOCTLs (`GENERIC`/`GET_CABLE_ID`/`READ_IGNITION_SENSE_STATE`), which never called `ensure_open_device_for` in the first place, now call `require_connected_device_for` too, so a pre-connect caller sees `PDU_ERR_MODULE_NOT_CONNECTED` instead of their usual unsupported-command error.
- No `.proto` changes: `ModuleConnectRequest` (already just `module_handle`) and `ModuleData` (already has `vendor_module_name`/`vendor_additional_info`) are sufficient to express N configured modules.

### Accepted Residuals

1. ~~**`module_status` reports `PDU_MODST_READY` for every configured row, including ones not currently open.**~~ **Closed by ADR-132 (conformance-audit A2-25).** `GetModuleIds` now reports the real tracked `self.module_state.status` (the same value `GetStatus`'s `ModuleHandle` branch reads) for the row matching whichever handle is currently open, and `PDU_MODST_AVAIL` — the spec's detected-but-not-connected initial state — for every other row, instead of hardcoding `READY` everywhere. The "no J2534 enumeration API to probe a closed device's real health" limitation this residual described is still true and remains an accepted gap (see ADR-132's own Consequences), but the part this residual explicitly left open — "a future ADR could track 'is this the currently-open handle'" — is now done.
2. **A vendor DLL may reject a non-NULL `pName` outright** (spec-defined `ERR_NULL_PARAMETER`, since `pName` is documented as reserved/must-be-NULL). This surfaces as an ordinary `PassThruOpen` failure through the existing native-error-to-`PduError` mapping (`error.rs::map_native_error_for_link`) — no special-casing was added, and none is needed: a deployer who configures `modules` for a DLL that doesn't support this extension will simply see every `ModuleConnect` fail with whatever `PduError` `ERR_NULL_PARAMETER` maps to.
3. ~~**CLL-scoped and IOCTL RPCs do not thread their own selected `module_handle` through to device opening.**~~ **Closed in a same-cycle follow-up fix.** This residual was identified during edge-case review shortly after the ADR-107 change above landed, and reproduced: `CreateComLogicalLink(module_handle=2, ...)` on a multi-module config, with no prior `ModuleConnect`, silently opened module 1's device instead of module 2's — `require_module_handle` checked handle 2's *validity*, but the plain (non-selecting) `ensure_open_device` that followed ignored it and opened whatever was already open or defaulted to `DEFAULT_MODULE_HANDLE`. The fix: every RPC that itself receives and validates a `module_handle` — `rpc_get_version`, `rpc_create_com_logical_link`, and the module-scoped `READ_VBATT`/`SET_PROG_VOLTAGE`/`READ_PROG_VOLTAGE` IOCTLs (`rpc_module_connect` already did this) — now calls `ensure_open_device_for(module_handle)` instead, so a handle-2 request either opens module 2 or is rejected with `PDU_ERR_RESOURCE_BUSY` if a different module is already open, matching `ModuleConnect`'s existing semantics. `ensure_open_device` remains, narrowed to its three genuinely handle-less callers: `rpc_connect_com_logical_link`, `ensure_uudt_companion_channel`, and `probe_sae_j1850_flavor`, which take only a `cll_handle` whose owning module was already pinned down at `CreateComLogicalLink` time — these were not part of the bug (their device is already open under the right handle by the time they run) and are unaffected. Regression coverage: `j2534-0404-service/tests/grpc_mock/modules.rs::create_com_logical_link_opens_the_requested_modules_device` and `::create_com_logical_link_for_a_different_open_module_is_rejected`. **A second Codex-review pass on PR #110 found two more call sites the same original sweep had missed: `rpc_module_disconnect` (`rpc_module.rs`) unconditionally tore down every logical link/channel and closed whatever device was actually open, regardless of the requested `module_handle`, and the `PDU_IOCTL_RESET` handler (`rpc_misc.rs`) discarded its validated `module_handle` entirely and always reset whichever module was open.** Both are now guarded by a shared `lock_device_for(requested)` helper (`service.rs`, alongside `ensure_open_device_inner`; originally added as `reject_if_open_under_different_handle`, which peeked `device_id` and dropped the lock before returning — see Decision (e) for the TOCTOU gap that fix itself had and the guard-holding shape that replaced it) that checks `device_id` and rejects with the same `PDU_ERR_RESOURCE_BUSY`/`FailedPrecondition` shape *without* opening or closing anything itself — `ModuleDisconnect` and `PDU_IOCTL_RESET` never open a device, so they cannot reuse `ensure_open_device_for`. Nothing-open and matching-handle both remain no-ops exactly as before. Regression coverage: `modules.rs::module_disconnect_for_a_different_open_module_is_rejected`, `::module_disconnect_for_the_open_modules_own_handle_succeeds`, `::module_disconnect_with_nothing_open_is_a_noop`, `::ioctl_reset_for_a_different_open_module_is_rejected`, `::ioctl_reset_for_the_open_modules_own_handle_succeeds`. With this fix, the reject-on-switch model now applies uniformly across every module-scoped RPC this ADR and its follow-ups describe. (Superseded in part by Residual 5: as of the A2-8 conformance fix, `READ_VBATT`/`SET_PROG_VOLTAGE`/`READ_PROG_VOLTAGE` no longer call `ensure_open_device_for`, and `PDU_IOCTL_RESET` no longer calls `lock_device_for` — all four now call `require_connected_device_for`, which adds a `PDU_ERR_MODULE_NOT_CONNECTED` rejection when nothing is open at all. The reject-on-switch behavior this residual describes is unchanged for all four.)
4. **Module-level event/subscription attribution still hardcodes `DEFAULT_MODULE_HANDLE`** (`events.rs`'s module-status broadcast key, `SubscribeEvent`'s CLL-subscription key convention). A module-status event published while module 2 is open is still filed under handle 1's subscription key. This mirrors Residual 3 and has the same accepted-gap status.
5. **"Connected" for the 7 module-scoped `PDU_IOCTL_*` commands (`RESET`/`READ_VBATT`/`SET_PROG_VOLTAGE`/`READ_PROG_VOLTAGE`/`GENERIC`/`GET_CABLE_ID`/`READ_IGNITION_SENSE_STATE`, conformance-audit A2-8, `j2534-0404-service/docs/iso22900-2-conformance-audit.md`) means "a device is open under this handle," however that device came to be open — an explicit `ModuleConnect`, or one of this ADR's own lazy-open paths (`GetVersion`, `CreateComLogicalLink`).** A2-8's `require_connected_device_for` gates all 7 IOCTLs on `device_id` (plus `module_state.status == PduModstReady`, added by a separate same-round Codex finding — a stale-open `device_id` on a module `events::handle_channel_hard_error` had already marked `PduModstNotAvail` must still reject; see the A2-8 conformance-audit entry); it does not track whether `ModuleConnect` was literally the RPC that opened the device. A Codex review on PR #143 flagged this as a possible gap: `CreateComLogicalLink`/`GetVersion` can populate `device_id` with no prior `ModuleConnect` call, so those IOCTLs succeed (or, for the 3 unsupported ones, proceed to their usual `Status::unimplemented`) afterward too. This is accepted, not a bug: ISO 22900-2 §9.4.29.2 NOTE 1 keys `PDU_ERR_MODULE_NOT_CONNECTED` to the module's *status* (`PDU_MODST_READY`), not to which specific function call produced it, and in this service the READY-equivalent state is "device open under this handle, with `module_state.status` still `PduModstReady`" — `rpc_module_connect` itself does nothing beyond `ensure_open_device_for` plus an event, and `ensure_open_device_inner` resets `module_state` to `PduModstReady` on every successful open. A separate "was `ModuleConnect` literally called" flag would invent a state ISO 22900-2's model doesn't have (a live, communicating CLL whose module nonetheless reports not-connected) and would require every one of the ~450 `grpc_mock` tests that create a CLL via lazy-open without calling `ModuleConnect` first (`tests/grpc_mock/harness.rs::create_cll`) to be rewritten — real cost for negative conformance value. Revisit only if lazy-open itself (Decision (d)) is ever revisited, or if a future ISO 22900-2:2022 conversion is found to tighten NOTE 1 toward call-history semantics (no 2022 copy is available in this workspace to check — see `CLAUDE.md`'s Spec References). Regression coverage:
   `j2534-0404-service/tests/grpc_mock/pdu_ioctl.rs::module_scoped_ioctls_succeed_after_lazy_open_via_create_cll`.

### Design Alternatives Not Chosen

- Per-module state partitioning for true simultaneous multi-device support (Decision (b)) — out of scope, would require reworking `shared_channels`, `logical_links`, subscription keys, and the poll-task model to be module-aware throughout, not just at the device-open boundary.
- Stable/explicit module IDs independent of config array order (Decision (c)) — would need either a new persisted-ID scheme or a config-supplied ID field; deferred as unnecessary complexity for the deployment shapes this ADR targets (a human editing `config.toml` directly).
