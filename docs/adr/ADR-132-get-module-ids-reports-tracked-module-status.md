# ADR-132: `GetModuleIds` Reports the Real Tracked Status for the Open Module, `PDU_MODST_AVAIL` for Every Other Row

**Date:** 2026-07-25
**Status:** Accepted (closes ADR-107 Accepted Residual #1)
**Affects:** `j2534-0404-service/src/service/rpc_module.rs`, `j2534-0404-service/src/service/rpc_primitive.rs`, `j2534-0404-service/src/service.rs`, `docs/j2534-0404-architecture.md`, `docs/rpc-api-guide.md`, `j2534-0404-service/docs/iso22900-2-conformance-audit.md`

## Context

Conformance-audit finding A2-25 (`j2534-0404-service/docs/iso22900-2-conformance-audit.md`): `rpc_get_module_ids` hardcoded `module_status: PDU_MODST_READY` for every row it returns, regardless of the real tracked `ModuleState` that `GetStatus`'s `ModuleHandle` branch (`rpc_primitive.rs::rpc_get_status`) already reads from `self.module_state.lock().await.status`. This was not an oversight so much as a documented, deliberate simplification — ADR-107's own Accepted Residual #1 states it explicitly:

> `module_status` reports `PDU_MODST_READY` for every configured row, including ones not currently open. This is a pre-existing simplification (the single-entry case already did this) extended unchanged to the multi-entry case — there is no J2534 enumeration API to probe real per-device AVAIL/READY status with, so a configured-but-never-connected entry is indistinguishable from a ready one in `GetModuleIds`'s output. A future ADR could track "is this the currently-open handle" and report a closer approximation, but that was not requested here.

That "not requested" residual is exactly what A2-25 now requests. ISO 22900-2:2009(E) §9.4.24.2.1's use-case table (spec ref below) defines a real state machine for `ModuleStatus` — `PDU_MODST_AVAIL` (detected, not yet connected) → `PDU_MODST_READY` (after `PDUModuleConnect`) → `PDU_MODST_NOT_READY` (momentary) or `PDU_MODST_NOT_AVAIL` (comm loss) → back to `PDU_MODST_AVAIL` (after `PDUModuleDisconnect`) — and the spec's own `GetModuleIds`→`ModuleConnect` example (Table 32, line 2618) shows every listed module reporting `PDU_MODST_AVAIL` *before* any of them has been connected. `docs/rpc-api-guide.md`'s existing "Typical gRPC Client Flow" line already documented this expectation (`GetModuleIds → (pick a ModuleHandle with PDU_MODST_AVAIL) → ModuleConnect`) even while the code it described always returned `READY` — the doc and the implementation disagreed with each other, not just with the spec.

Unlike the still-true part of the ADR-107 residual (there is genuinely no J2534 enumeration API to probe a *closed*, never-opened device's real health), this service already tracks real per-device state for the one device that actually matters: `self.device_id` (`Option<(u32, DeviceId)>`) records which configured `module_handle` is currently open, and `self.module_state` (`ModuleState { status, last_error }`, ADR-020/ADR-131) records that device's real status — `Ready` on a fresh open, `NotAvail` on a hard channel error (sticky until `ModuleDisconnect`, ADR-131). `PDU_MODST_NOT_READY` is spec-defined (§9.4.24.2.1 Use Case (c), a momentary post-`READY` condition) but this implementation never actually writes it anywhere — `ioctl_reset` (`rpc_misc.rs`) resets `module_state` straight back to `ModuleState::default()` (`Ready`), not through an intermediate `NotReady`, so it remains an unreachable value in this codebase today, not a state `GetModuleIds` needs to specially handle. `GetModuleIds` simply never consulted `module_state`/`device_id` at all before this change.

## Decision

`rpc_get_module_ids` (`rpc_module.rs`) now reports:

- **For the row whose `module_handle` matches `self.device_id`'s currently-open handle:** the real `self.module_state.lock().await.status` — the identical value `GetStatus`'s `ModuleHandle` branch already returns for the same handle, so the two RPCs can no longer disagree about the open module's state.
- **For every other row (no device open at all, or a different handle's device is open — at most one can be, per ADR-107's single-open-device-at-a-time model):** `PDU_MODST_AVAIL`, the spec's own "detected but not yet connected" initial state (§9.4.24.2.1 Use Case (a)), matching Table 32's example and `rpc-api-guide.md`'s pre-existing (until now aspirational) documented flow.

This closes ADR-107 Accepted Residual #1 exactly as its own text anticipated ("A future ADR could track 'is this the currently-open handle' and report a closer approximation"). It does **not** attempt to probe a closed device's real reachability — J2534 v04.04 still has no enumeration/health-check primitive for that, so an unopened, misconfigured, or physically-absent module is still reported as `PDU_MODST_AVAIL` rather than something more specific; this is a narrower, honest claim ("detected per config, not yet vouched for") than the previous `READY` ("usable for API calls right now"), not a claim that every unopened entry is confirmed present.

`self.device_id` is locked first and the guard is **held** across the `self.module_state` read that follows — the pre-existing `device_id` → `module_state` nested-lock order (ADR-107 addendum), the same pattern `rpc_module_connect` already uses for its own post-open status check. An earlier version of this change released the `device_id` guard before reading `module_state`, on the reasoning that this only matched `GetStatus`'s own unguarded read for the same `ModuleHandle` case; a Codex review on PR #145 correctly identified that as a materially worse failure mode than mere staleness: a `ModuleDisconnect(handle A)` immediately followed by a `ModuleConnect(handle B)` landing entirely inside the gap between the two released-then-reacquired locks could pair handle A's row with handle B's freshly-reset `Ready` status — not staleness, but an actively self-contradictory response (A shown `Ready`, B shown `Avail`, when the reverse was true for the whole window this call actually ran in). Holding one guard across both reads closes that window; the response now reflects a single consistent instant, same as every other module-scoped RPC's discipline in this file.

## Alternatives Considered

1. **Report `PDU_MODST_NOT_READY` or leave unopened rows at `PDU_MODST_READY`.** Rejected: neither matches the spec's state machine, which reserves `NOT_READY` for a momentary post-`READY` condition (§9.4.24.2.1 Use Case (c) — not currently produced by this implementation at all, see Context above) and `READY` for post-`ModuleConnect` — an entry that was never connected has never been in either state. `AVAIL` is the only use-case-table state that fits "detected, not connected."
2. **Try to probe every configured entry's real device reachability before returning `GetModuleIds`.** Rejected: this would mean opening (or otherwise touching) every configured module's device just to answer a status query, with observable side effects (device occupancy, vendor-DLL logging, physical bus activity) far beyond what a read-only enumeration call should have — and J2534 v04.04 has no side-effect-free probe primitive to do this with in the first place (the same gap ADR-131 hit for its own alternatives).
3. **Track a full per-module `ModuleState` array instead of one shared `module_state` plus `device_id`.** Rejected as unnecessary scope: this service only ever has one device open at a time (ADR-107 Decision (b)/(d)), so a single shared `module_state` scoped to "whichever device is open right now" is already exact for the one entry that can be non-`AVAIL` — a per-module array would track N-1 always-`AVAIL` slots for no behavioral gain.

## Consequences

- `GetModuleIds` and `GetStatus` can no longer disagree about a module's status, for any handle, open or not — both now implement the identical per-handle state machine (`PDU_MODST_AVAIL` when not the open handle, `self.module_state.status` when it is; see Amendment 3 below for how `GetStatus` itself was brought in line with this Decision).
- A client following `rpc-api-guide.md`'s documented `GetModuleIds → (pick a handle with PDU_MODST_AVAIL) → ModuleConnect` flow now gets the behavior that line always described, instead of every handle appearing indistinguishably `READY` before any connect.
- Unopened entries still cannot be distinguished from each other by real per-device health (present-but-misconfigured vs. genuinely absent) — this remains an accepted residual, unchanged from ADR-107, since it would require a J2534 enumeration primitive this adapter's native layer does not have.

## Amendment 1 (Codex review, PR #145): every lazy-open path must emit `PDU_INFO_MODULE_LIST_CHG`, not just `ModuleConnect`

Before this Decision, `GetModuleIds`'s `module_status` never actually changed as a result of a device opening or closing — it was hardcoded `READY` regardless — so there was no open/close transition for a subscriber to miss. Once `GetModuleIds` started reporting real per-handle state (this ADR's Decision above), that stopped being true: a none-to-open transition is now a real, client-visible state change, and `rpc_module_connect` was the only RPC that emitted `PDU_INFO_MODULE_LIST_CHG` on it. Two other RPCs can also perform the same none-to-open transition without ever calling `ModuleConnect` at all — `GetVersion` and `CreateComLogicalLink` both lazily open a device via `ensure_open_device_for` (ADR-107 Decision (d)) — so a subscriber that relies on `PDU_INFO_MODULE_LIST_CHG` to know when to re-poll `GetModuleIds` would see a stale `PDU_MODST_AVAIL` row after either of those two paths opened the device, even though the row had in fact become `PDU_MODST_READY`.

**Fix:** the notification moved to `ensure_open_device_inner` (`service.rs`) itself — the single choke point where `*slot = Some((requested, id))` actually performs the none-to-open transition, for every caller (`ensure_open_device_for` and the plain, non-selecting `ensure_open_device` alike). `rpc_module_connect`'s own `if !was_open { events::send_system_info(...) }` block is removed as redundant; the notification it used to send is now sent by the function it called. Emitting it while still holding the `device_id` guard (`slot`) is safe and not new: `rpc_module_connect` already awaited this same call with its own `device_id` guard held before this change simply moved the call one level down; `send_system_info` only locks `system_event_buf`/`subscriptions`, both inner to `device_id` in this service's lock order (ADR-107 addendum).

This also uniformly covers the three genuinely handle-less internal callers of the plain `ensure_open_device` (`rpc_connect_com_logical_link`, `ensure_uudt_companion_channel`, `probe_sae_j1850_flavor`) — though in the normal flow none of them can actually hit the fresh-open branch: each runs only after `CreateComLogicalLink` already pinned a module down and opened its device (ADR-107 Residual #3, closed), so they only ever observe `ensure_open_device_inner`'s already-open branch, which does not re-notify.

## Amendment 2 (Codex review, PR #145): a failed `PassThruClose` still clears `device_id`, but skipped the notification entirely

`rpc_module_disconnect` (`rpc_module.rs`) calls `slot.take()` — clearing `self.device_id` — *before* attempting the native `PassThruClose`; this is pre-existing, unrelated to this ADR (the epoch bump next to it is explicitly documented as running "before the close is even attempted", so a failed close still invalidates the epoch-tagged probe caches). The pre-existing `events::send_system_info(..., ModuleListChg)` call, however, sat *after* `close_result?` — so a `PassThruClose` failure propagated the error and returned before that notification ever ran. Before this ADR's Decision this was harmless: `GetModuleIds` never consulted `device_id` at all, so there was no client-visible module-list change to miss regardless of whether `PassThruClose` succeeded. Once `GetModuleIds` started deriving a row's status from `device_id` (this ADR's Decision), it stopped being harmless: the slot clears -- and that row silently becomes `PDU_MODST_AVAIL` -- on every disconnect attempt, close failure or not, but subscribers were only told about the success case.

**Fix:** the notification now runs unconditionally right after `drop(slot)`, before `close_result?` propagates any error, so it fires whenever the slot was actually cleared regardless of whether the subsequent `PassThruClose` succeeded — including the nothing-was-open no-op case, exactly as before (`close_result` is trivially `Ok(())` there, so the ordering change is a no-op for that path). No dedicated regression test: `j2534-0404-mock`'s `PassThruClose` has no error-injection hook (unlike e.g. `__mock_set_stop_filter_error`), so exercising the close-failure branch needs new mock infrastructure — deferred, tracked in `implementation-notes.md`'s Prioritized Backlog; the fix was verified by code inspection and by the full existing suite showing no regression on the ordinary (close-succeeds and nothing-open) paths.

## Amendment 3 (Codex review, PR #145, P1): `GetStatus`'s `ModuleHandle` branch ignored the requested handle entirely, disagreeing with `GetModuleIds` for every unopened module

Before this Decision, `rpc_get_status`'s `ModuleHandle` branch (`rpc_primitive.rs`) returning `self.module_state.status` unconditionally — for *whatever* handle the client asked about, never checking `self.device_id` at all — was harmless for the same reason as Amendment 1: `GetModuleIds` also ignored real state, so the two RPCs coincidentally "agreed" (both wrongly reported `READY` for everything). Once `GetModuleIds` started implementing a real per-handle state machine (this ADR's own Decision), that coincidence broke: `module_state`'s default and post-open value is `PduModstReady`, and `rpc_module_disconnect` deliberately does not reset it (ADR-131 Decision, third bullet) — so at startup, and after every successful disconnect, `GetStatus(module_handle=N)` kept returning `READY` (or whatever the last open module's tracked status happened to be) for a handle `GetModuleIds` now correctly reports as `AVAIL`. With more than one configured module, an unopened handle could even inherit a *different*, currently-open module's `READY`/`NotReady`/`NotAvail` status — a straightforwardly wrong answer, not just a stale one, and a **P1** severity Codex correctly assigned it (higher than Amendments 1/2's P2 notification gaps, since this is a wrong-value bug in a read RPC itself, not a missed side-channel notification).

**Fix:** `rpc_get_status`'s `ModuleHandle` branch now runs the identical per-handle check `rpc_get_module_ids` does — `self.device_id`'s currently-open handle compared against the requested handle — returning `self.module_state.status` only when they match, `PDU_MODST_AVAIL` otherwise. The `device_id` guard is held across the `module_state` read for the same TOCTOU reason the Decision section above describes for `GetModuleIds` itself: a `ModuleDisconnect`+`ModuleConnect(other handle)` racing two separately-acquired locks could otherwise attribute a freshly-opened module's status to the handle actually being queried. `GetModuleIds` and `GetStatus` now provably implement the same state machine rather than merely being expected to by convention — regression coverage: `j2534-0404-service/tests/grpc_mock/modules.rs::get_status_module_handle_matches_get_module_ids_when_nothing_is_open`, `::get_status_module_handle_matches_get_module_ids_for_the_open_handle_only` (the latter cross-checks both RPCs' responses against each other directly, not just against a hardcoded expected value, for a multi-module config with one handle open and one not).
