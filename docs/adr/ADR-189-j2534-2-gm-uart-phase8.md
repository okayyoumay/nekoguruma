# ADR-189: SAE J2534-2 GM UART Protocol (Phase 8)

**Date:** 2026-08-24
**Status:** Accepted
**Affects:** `j2534-0404-service/src/service/{resources,names,protocol,rpc_misc,rpc_link,rpc_primitive,service_params,comparam_defaults}.rs`, `j2534-0404-service/src/service.rs`, `j2534-0404-service/src/error.rs`, `j2534-0404-mock/src/lib.rs`, `j2534-0404/src/lib.rs`, `j2534-0404-service/tests/grpc_mock/{gm_uart,harness}.rs`, `docs/j2534-2-support-plan.md`, `j2534-0404-service/docs/implementation-notes.md`, `docs/adr/INDEX.md`

## Context

`docs/j2534-2-support-plan.md` §6 lists Phase 8 (GM UART, SAE J2740, clause 11) as the next unshipped phase whose full dependency chain (Phases 0-2) has already shipped, rating its own `design-advisor` need up front as "Maybe — bus-mastership handshake". Clause 11 sets up a master/slave arrangement between tester and target ECU, in which the tester must first be granted bus mastership (via a poll-message/poll-response exchange, or an immediate grant on vehicles with no bus master) before diagnostic communication can begin.

The coarse "Maybe" reflected a real risk: SAE J1939's own address-claim negotiation (Phase 5, ADR-179) needed a `design-advisor` consult specifically because *this service* had to own and drive a multi-round, asynchronous claim/defend state machine internally, coupled to `PDU_COPT_STARTCOMM`. If GM UART's bus-mastership handshake required the same kind of service-owned state machine, it would warrant the same escalation.

Investigation (this ADR) found that is not the case. Clause 11's own text is explicit that the mastership-negotiation *logic* (deciding when to listen, what poll type was seen, when to relinquish, retry/backoff) belongs to the reprogramming *application*, not the J2534 device or driver — the device/driver's job is limited to two new synchronous, thin `PassThruIoctl` sub-functions:

- `SET_POLL_RESPONSE`: define the bytes of the poll-response message the interface should transmit.
- `BECOME_MASTER`: wait for a poll message matching a given ID (or send the poll-response immediately if the ID is zero), transmit the poll response, and report success/failure — a single blocking native call with an ~2 second native-side timeout, not a state machine this service needs to drive.

This is structurally identical in shape to two already-shipped, no-escalation-needed phases: Phase 4's `SW_CAN_HS`/`SW_CAN_NS` (two new `ChannelID`-scoped IOCTLs, thin passthrough, no service-side logic) and Phase 12's Repeat Messaging (this service is "purely a thin IoCtl forwarder", ADR-165). No new asynchronous indication routing, no new per-CLL state machine, and no new concurrency hazard class is introduced.

The remaining design questions — protocol identity shape, pin selection, and how the two new IOCTLs plug into this service's existing dispatch/proto surface — all have direct, unambiguous precedent already established by prior phases (cited in Decision below). None required a fresh design call.

## Decision

1. **Protocol identity**: a new standalone `ChannelProtocol::GM_UART_PS` (`hw_protocol_override: None`), the same shape UART Echo Byte (ADR-170)/Honda DIAG-H (ADR-174)/J1708 (ADR-175) already use — clause 11 has no CAN-family relationship and no unqualified base `ProtocolID` (Table 26 defines only `GM_UART_PS`/`GM_UART_CHx`). One new resource-table row, `resource_id: 0x0260` (the next free id after TP2.0's `0x025F`), minted protocol name `GM_UART`, a new standalone bus type `BUSTYPE_GM_UART`. `resources.rs`'s `bustype_default_name_for_hw_protocol_id` (the fallback used when a raw hardware protocol id is named directly, bypassing the resource table, so `RscData.bus_type_name` is the only other source of a Working ComParam set) gained an `is_gm_uart_protocol_id` branch resolving to `"GM_UART_UART"` (`comparam_defaults::gm_uart_uart`) — round 3 correction, Codex review PR #98: without it, a directly-named `GM_UART_PS`/`GM_UART_CHx` id with no matching `bus_type_name` got an empty ComParam set, or silently inherited an unrelated bus's defaults (e.g. a CAN bus name's baud rate) if one happened to be supplied.

2. **Additional Channels**: `GM_UART_CH1`..`CH128` (already-minted constants from Phase 0) participate in the existing Phase 2b arithmetic `_CHx` mapping (`resources::chx_block_base`) — the first standalone (non-CAN-family) protocol to combine a single resource-table row with `_CHx` support, since UART Echo Byte/Honda DIAG-H/J1708 have no `_CHx` variants at all and J1939's own `_CHx` block, while already recognized by the arithmetic mapping's range, is explicitly out of scope for Phase 5. No new mechanism: `chx_block_base` gains one new match arm pointing at `PROTOCOL_GM_UART_CH1`.

3. **Pin selection**: clause 11.2.2 names exactly two valid single pins — pin 9 (primary) and pin 1 (secondary) — with no spec-mandated default, the identical closed-two-single-pin shape Honda DIAG-H's own `resolve_pin_selection` arm already established (clause 13.2.4, pins 1/14). Mirrors that arm exactly: a resource-table row access with no explicit `dlc_pin_data` gets an editorial convenience default of pin 9 (the spec's own "primary"/"typically used" pin, the same category of non-normative default this codebase already applies for UART Echo Byte's pin 7 and Honda DIAG-H's pin 14); a raw-protocol-id access bypassing the resource table with no explicit pin is rejected (matching every existing standalone protocol's identical raw-id-bypass rule); any pin other than {1, 9} is rejected regardless of access path.

   Round 3 corrections (Codex review, PR #98): (a) `names.rs`'s
   `row_needs_dynamic_pin_selection` predicate — the single source of truth
   both `find_table_row_by_name` and `parse_protocol_id_from_resource`
   consult to decide whether a matched row routes through
   `resolve_pin_selection` at all — never registered
   `resources::is_gm_uart_protocol_id`, so a name-based connect
   (`protocol_name: "GM_UART"`) skipped Pin Selection entirely, silently
   omitting the mandatory `SET_CONFIG(CONFIG_J1962_PINS)` when no explicit
   pins were supplied and rejecting an explicit, spec-valid pin 1 choice
   during fixed-row narrowing. Fixed by adding the predicate. (b) Because
   GM UART is the first standalone-row protocol this service implements
   that ALSO has in-scope `_CHx` support (Decision 2), fix (a) exposed a
   second gap: the compound `_CHx`-suffixed name grammar (e.g.
   `"GM_UART_CH1"`) resolves to the SAME row/protocol as (a)'s fix routes
   through `resolve_pin_selection`, but with `requested_index` set instead
   of empty `dlc_pin_data` — the row's mandatory pin-selection logic
   computed a default pin selection regardless, which `resolve_channel_selection`'s
   own clause-6/clause-7 mutual-exclusion check then rejected as an
   invalid combination. `resolve_pin_selection`'s `PROTOCOL_GM_UART_PS` arm
   now checks `requested_index` first: `Some` with empty `dlc_pin_data`
   bypasses pin selection entirely (`Ok(None)`, mirroring how a
   directly-named `_CHx` id already bypasses every arm in this function);
   `Some` combined with non-empty `dlc_pin_data` is rejected outright
   (edge-case-hunter verification pass, PR #98 round 3: the first version
   of this bypass silently discarded caller-supplied pins instead of
   rejecting the double-qualification, since `resolve_channel_selection`'s
   own mutual-exclusion check does not independently catch it —
   `resources::is_ps_protocol_id` was never extended to the standalone-row
   families).

4. **Two new `ChannelID`-scoped (L) D-PDU IOCTL commands**, following Phase 12/14's own "mint the next `PDU_IOCTL_BASE` offset, forward to a new native wrapper" pattern — the 26th and 27th D-PDU commands:
   - `PDU_IOCTL_SET_POLL_RESPONSE` (`PDU_IOCTL_BASE + 0x1A`): forwards to a new `j2534-0404::J2534Api0404::set_poll_response(channel_id, bytes)`, itself a thin `PassThruIoctl(IOCTL_SET_POLL_RESPONSE)` wrapper (mirroring `sw_can_hs`/`sw_can_ns`'s own shape). Input is the poll-response message bytes (Table 28's `PollResponseMsg[100]`, ≤100 bytes) via `bytearray_data`; no output.
   - `PDU_IOCTL_BECOME_MASTER` (`PDU_IOCTL_BASE + 0x1B`): forwards to a new `become_master(channel_id, poll_id)` wrapper around `PassThruIoctl(IOCTL_BECOME_MASTER)`. Input is the single `Poll_ID` byte (Table 32's `unsigned char Poll_ID`) via `unum32_value` (0..=255, rejected client-side above that range to avoid a silent truncation to `u8`) — the same shape `ioctl_read_j1962_pin_voltage`'s own single-byte pin-number parameter already uses; not `bytearray_data`, since the `DataItem` oneof has no dedicated single-byte variant; no output. This native call's own blocking wait (~2s worst case per clause 11.3.3.2) needs no service-side timeout/cancellation logic, but does need its own dispatch treatment: unlike every other native call this service issues (all near-instant, so far always awaited directly under `self.api`'s async lock), this one is issued inside `tokio::task::spawn_blocking` (acquiring `self.api` via `Mutex::blocking_lock` from within that closure, not the ordinary async guard) so a multi-second wait doesn't tie up a tokio runtime worker thread — this codebase had no prior native call slow enough to need that treatment, so no such "discipline" existed before this call (Codex review finding, PR #98, round 1; corrects this ADR's own initial, inaccurate claim that one already did). `self.api`'s own pre-existing global mutex still serializes this call against every other native call for its own ~2s duration, exactly as it already does for every native call regardless of duration — see Consequences. Native `ERR_FAILED` (the documented "no poll message within 2s" outcome) is left to `map_native_error_for_link`'s existing generic mapping — no protocol-specific error-code handling is needed, unlike Phase 13's `ERR_PIN_IN_USE`/`ERR_VOLTAGE_IN_USE`.

   Both IOCTLs are rejected (`PDU_ERR_ID_NOT_SUPPORTED`) on a non-GM-UART link, mirroring `PDU_IOCTL_SW_CAN_HS`/`_NS`'s own protocol gate. Both are also gated on `SharedChannel::ref_count == 1` (this channel's sole owner) before the native call runs — a poll-response definition or a mastership bid affects the whole physical GM UART bus, so a per-CLL call would otherwise silently affect a sibling CLL sharing the same channel, mirroring `PDU_IOCTL_SW_CAN_HS`/`_NS`'s own identical shared-physical-channel precaution (ADR-164). A channel that fails this gate is REJECTED (`PDU_ERR_RSC_LOCKED_BY_OTHER_CLL`/`ResourceExhausted`, the same shape `rpc_link.rs`'s own join-side rejections for this resource already use), not silently accepted as a no-op success — round 2 correction, Codex review PR #98: the original round-1 shape returned `Ok(())` for a shared channel, which lied to the caller about having attempted the IOCTL at all.

   Round 2 also closed a narrower race specific to `BECOME_MASTER` (Codex P2 finding, PR #98, design-advisor consult): the `ref_count == 1` gate above is checked, then `shared_channels` is released, and only then does the ~2s blocking native call run inside `spawn_blocking` — leaving a window where a sibling CLL's `ConnectComLogicalLink` could join the SAME physical channel (bumping `ref_count` under its own, separate `shared_channels` acquisition, `rpc_link.rs`, which never touches `self.api`) while the mastership bid was still outstanding, defeating the sole-owner gate's own purpose. Closed by a new `SharedChannel::become_master_in_flight: Arc<AtomicBool>` field: set under the SAME `shared_channels` critical section as the `ref_count == 1` gate itself (so the two are decided and armed atomically — no sibling join, which needs this same lock, can land in between), and cleared by an RAII guard (`BecomeMasterInFlightGuard`) constructed as the FIRST statement inside the `spawn_blocking` closure — deliberately not in the surrounding async fn — so the clear survives every exit path: normal return, a panic/unwind inside the native call, and a tonic RPC cancellation of the awaiting async future (which does not stop a blocking closure `spawn_blocking` has already started running on its own worker thread). Both existing-channel-join branches now reject a join while the flag is set, the same shape as the pre-existing `dead`-channel rejection: `rpc_connect_com_logical_link` (`rpc_link.rs`); `ensure_uudt_companion_channel` is confirmed unreachable for a GM_UART_PS channel and was deliberately left unmodified — its own `channel_key` is always `(j2534_0404::CAN, baud_rate, 0, 0)`, so it can never match a GM-UART-keyed `SharedChannel` entry. `PDU_IOCTL_SET_POLL_RESPONSE` gets no equivalent reservation flag. Accepted residual, not a verified guarantee: clause 11.3.3.1 documents `SET_POLL_RESPONSE` as a simple define-the-response-bytes call with no wait described anywhere in its own text, unlike `BECOME_MASTER`'s explicit ~2s bound (clause 11.3.3.2) — but the spec's silence on timing is not a spec-guaranteed bound, only an assumption this ADR makes based on what a conforming implementation is described as doing. A real adapter whose own native `SET_POLL_RESPONSE` implementation happens to be slow would reopen a narrower version of the same in-flight window `BECOME_MASTER`'s own fix just closed. Not fixed here — revisit if this assumption is ever found wrong against real hardware.

5. **Discovery-cache wiring**: Stage 1's `DeviceFlag` mechanism (ADR-185) gets one new `connect_discovery_check` entry for `GM_UART_PS`/`GM_UART_CHx`, keyed on `DEVICE_INFO_GM_UART_SUPPORTED` — the same shape every other Stage-1 family already uses. `GM_UART_SIMULTANEOUS`'s companion bit and `GM_UART_PS_J1962`'s per-pin validity query are deliberately left unwired this phase, folded into the two existing standing backlog items that already track the identical deferral for every other Stage-1 family (the `_SIMULTANEOUS` companion-bit item, and — new — a per-pin-query deferral matching SAE J1708's own unwired clause-6 connector-validity queries).

6. **No new proto surface.** Both new IOCTLs ride the existing generic `IoCtl`/`DataItem` RPC surface (`bytearray_data`/`ubyte_array`, both pre-existing oneof variants), consistent with the ADR-178 interface freeze — no `service.proto` change.

## Consequences

- Clause 11's own bus-mastership *negotiation* (when to listen, retry/backoff, deciding a poll was missed) is explicitly the client application's responsibility per the spec text itself — this service only ever forwards the two IOCTLs and the ordinary connect/message-framing machinery every other protocol already gets. No new indication-routing map, no new per-CLL asynchronous state, no new concurrency class — unlike SAE J1939 (Phase 5) or TP2.0 (Phase 7), this phase adds no `events_*`-style routing module.
- `GM_UART_SIMULTANEOUS` and `GM_UART_PS_J1962` (per-pin discovery) stay unwired, tracked in `j2534-0404-service/docs/implementation-notes.md`'s Prioritized Backlog alongside every other Stage-1 family's identical deferral.
- Message framing (Table 33: 3-byte header — destination ID, source ID, length — plus up to 167 data bytes, min/max Tx/Rx both `3..=170`) follows the same size-validation shape every other standalone protocol's `resolve_send_recv_tx`/message-size checks already use; no new framing mechanism.
- This is the first standalone (non-CAN-family) protocol combining a single resource-table row with `_CHx` Additional Channels support — `chx_block_base`'s match arm addition is a mechanical, one-line extension of the existing Phase 2b mechanism, not a new one.
- `BECOME_MASTER`'s ~2 second native-side wait (clause 11.3.3.2) needs no new timeout/cancellation surface — it is entirely inside the single `PassThruIoctl` call this service already forwards to every native IOCTL — but does need `spawn_blocking` dispatch, corrected after an initial round mistakenly claimed this codebase already had a blanket `spawn_blocking` discipline for every native call (it did not; grep for `spawn_blocking` across the whole workspace before this fix returns zero matches). Accepted residual: `self.api: Arc<Mutex<J2534Api0404>>`'s own pre-existing global mutex — the same one that already serializes every native call this service issues, across every protocol and channel, regardless of duration — still serializes `BECOME_MASTER` against every other concurrent native call for its own ~2s duration; only the *additional* cost this call's own dispatch shape would otherwise have added (blocking a tokio runtime worker thread, and holding `shared_channels` longer than necessary) is removed. Splitting `self.api` into a finer-grained (e.g. per-physical-channel) lock so an unrelated channel's own native calls could proceed concurrently during a `BECOME_MASTER` wait would be a cross-cutting architectural change affecting every protocol this service supports, not a GM-UART-scoped fix — out of scope for this phase.
- Accepted residual (round 2, design-advisor consult, PR #98): `become_master_in_flight` closes the in-flight bookkeeping gap — a sibling CLL being published as `connected` on this physical channel mid-mastership-bid — but cannot and does not extend to the mastership *tenure* after the IOCTL returns. Clause 11 places relinquish/renegotiation logic in the client application, with no end-of-mastership signal this service could ever observe (Context, above), so a sibling joining immediately AFTER a successful `BECOME_MASTER` call is normal, expected behavior, indistinguishable from a join after any other successful sole-owner IOCTL on this channel. During the in-flight window itself, the pre-existing global `self.api` mutex independently prevents any sibling's own native call from reaching the bus regardless of this flag; `become_master_in_flight` closes the remaining, narrower gap — a sibling getting published as `connected` mid-bid, before its own first native call would even be attempted — specifically.
- Round 4 (Codex finding, PR #98): both `ioctl_set_poll_response` and `ioctl_become_master` used to resolve a requesting CLL's `channel_key` via `require_gm_uart_link` under `logical_links` alone, release that lock, and only afterward separately acquire `shared_channels` to check `ref_count`/arm `become_master_in_flight`. In the gap between those two acquisitions, `DisconnectComLogicalLink` (which acquires `shared_channels` first per this ADR's own outermost-lock invariant, then `logical_links` nested inside it, clearing the disconnecting CLL's own `channel_key` to `None` under that held `shared_channels` guard) could run to completion for the exact CLL making the IOCTL call. If a sibling CLL remained attached to the same physical channel, the now-stale `channel_key` snapshot still resolved to a `SharedChannel` entry whose `ref_count` had just dropped to 1 — the IOCTL handler then wrongly believed it had observed sole ownership on behalf of the (now-disconnected) requesting CLL, and fired `SET_POLL_RESPONSE`/`BECOME_MASTER` on what was actually the sibling's own exclusively-owned channel. Fixed by giving `require_gm_uart_link` a proof parameter (an immutable reference to the caller's already-held `shared_channels` `MutexGuard`) that forces `channel_key` resolution to happen inside the same critical section the `ref_count`/`become_master_in_flight` gate uses, rather than a snapshot taken beforehand — one unbroken critical section, matching the `shared_channels` → `logical_links` nesting order this ADR and ADR-080 already establish. `ioctl_sw_can_mode` (pre-existing, ADR-164) shared the identical snapshot-then-relock shape and the identical latent gap; it received the identical fix (hoisting its own `shared_channels` acquisition ahead of the `logical_links` snapshot) in the same PR, without going through `require_gm_uart_link` since its gate predicate and no-op/reject semantics are its own.
- New accepted residual (round 4, PR #98): once `become_master_in_flight` is armed and `shared_channels` is dropped (so the native call can run inside `spawn_blocking`), the *requesting* CLL's own disconnect is not blocked by the flag — it can tear down the channel concurrently with its own in-flight `BECOME_MASTER` bid. This is bounded and accepted the same way the mastership-tenure residual above is: the pre-existing global `self.api` mutex, held by the `spawn_blocking` closure for the call's duration, still serializes disconnect's own native teardown call behind `become_master`'s return, so no interleaved hardware calls occur — the bid simply completes on a channel that then closes immediately after, and any mastership granted dies with the channel.
