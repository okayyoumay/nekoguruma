# ADR-175: SAE J2534-2 SAE J1708 Protocol (Phase 11)

**Date:** 2026-08-13
**Status:** Accepted (Decision item 1's `J1708_CHx` deferral fulfilled by ADR-209)
**Affects:** `j2534-0404-service/src/service/protocol.rs`, `resources.rs`,
             `names.rs`, `comparam_support.rs`, `comparam_defaults.rs`,
             `comparam_id.rs`, `rpc_link.rs`, `rpc_primitive.rs`,
             `j2534-0404/src/lib.rs`, `j2534-0404-mock`

## Context

`docs/j2534-2-support-plan.md`'s Phase 11 covers SAE J2534-2 clause 17, the
SAE J1708 protocol: a heavy-duty-truck serial bus, 9600bps, distinguished by
a device-computed checksum (unless disabled), a genuinely new per-message
`MSG_PRIORITY_VALUE` TxFlags field, and an unusually large message-size
range. New `ProtocolID`s `J1708_PS`/`J1708_CHx` — Phase 0 (ADR-152) already
added the raw constants to `j2534_v0404.h`; `j2534-0404/src/lib.rs` does not
yet re-export `PROTOCOL_J1708_PS`.

**Standalone protocol, same architectural category as UART Echo Byte
(ADR-170) and Honda DIAG-H (ADR-174).** Clause 17 defines no relationship
between J1708 and any protocol this service already models (no
`hw_protocol_override` substitution target) — `ChannelProtocol::J1708_PS`
gets a genuinely new, self-mapping identity, the same shape as its two
predecessors.

**Multi-connector pin-space discovery (this phase's central finding) —
scoped to J1962-only, not requiring `design-advisor`.** Clause 17.3.2.1
itself only says the physical layer stays disconnected until `SET_CONFIG`
selects "the desired cable and pins," without naming which pin parameter.
Clause 6.3.3.2 (Table 3) resolves this: three separate, protocol-agnostic
pin-numbering spaces/native `SET_CONFIG` parameters exist —
`J1962_PINS` (the standard 16-pin OBD-II connector, the only one this
codebase implements today, per ADR-156's own explicit Phase-2 scoping),
`J1939_PINS` (the SAE J1939-13 connector's own 9-pin numbering — J1708+/-
happen to live at its pins 6/7), and `J1708_PINS` (a dedicated SAE J1708
6-pin Deutsch connector with its own numbering — J1708+/- at pins 1/2).
ADR-156's Consequences section explicitly deferred `J1939_PINS`/
`J1708_PINS` support to whichever of Phase 5 (J1939) or this phase reached
it first, noting ISO 22900-2's `PinData` carries no connector discriminator
at all — representing "pin 3 on the J1939-13 connector" distinctly from
"pin 3 on J1962" was left genuinely unresolved, not stubbed.

A code-scout investigation into how deeply this codebase's Pin Selection
mechanism (`names.rs::validate_j1962_pin_number`, `compute_pin_select`,
`ChannelKey`'s `pin_select` encoding, `resources.rs`'s `dlc_pins` tables)
assumes J1962 specifically found the assumption runs through every layer,
not a single swappable constant — genuinely supporting a second/third
pin-space would need a `PinData` connector discriminator, a `ChannelKey`
dimension to avoid two different physical buses computing colliding
`pin_select` values, and a resource-table shape decision (duplicate rows
per connector vs. a discriminator field). That is real, `design-advisor`-scale
work.

Clause 6.3.3.2's own text resolves whether this phase needs to attempt it
now: "at least one" of the three pin parameters must be supported per `_PS`
protocol — not all three. J1962-only is spec-conformant on its own, mirrors
every prior standalone-protocol phase's own connector (SWCAN, FT-CAN, UART
Echo Byte, Honda DIAG-H all use `CONFIG_J1962_PINS` exclusively), and heavy
truck scan tools commonly do wire J1708 signals onto specific J1962 pins in
practice. Deferring `J1939_PINS`/`J1708_PINS` support is therefore a scope
decision resolvable directly, the same way Phase 4 (SWCAN, ADR-164) resolved
its own initially-structural-looking question in its own Context/Decision
sections rather than escalating — not a forced architectural change this
phase must attempt.

**A genuinely new per-message mechanism: `MSG_PRIORITY_VALUE`
(TxFlags bits 16-19).** No protocol shipped so far in this service needed a
new piece of client-supplied per-message data with no home in the ISO
22900-2 D-PDU model this service's gRPC surface is built on — every prior
TxFlags addition (`ISO15765_ADDR_TYPE`, `TX_FD_CAN_FORMAT`) was computed
server-side from protocol/addressing context already available. Clause
17.4.5 defines a 1-8 priority value (invalid/unset clamped to 8, the
lowest). Investigation found `PARAM_MESSAGE_PRIORITY`
(`service_params.rs`, D-PDU `CP_MessagePriority`, native id `0x8083`) already
exists in this codebase's ComParam registry — seeded as a J1939/SCI default
in several bustypes, and ISO 22900-2 (both the 2009(E) and 2022 editions)
explicitly documents this ComParam's semantics for SAE J1708 specifically:
message priority used to calculate required bus idle time before
transmission, default 8. This is a direct, spec-grounded ComParam-to-native
translation opportunity — the same shape ADR-037 (`CP_StMinOverride` ->
`STMIN_TX`) and ADR-072 (µs -> native-resolution ComParams) already
established, not a "mint new D-PDU vocabulary with no source" situation like
UART Echo Byte's own `UEB_T*` accepted residual (ADR-170). `CP_MessagePriority`
is already allowed on several protocol families
(`comparam_support.rs::is_can_param`/`is_kwp_param`/`is_j1850pwm_param`/
`is_j1850vpw_param`) but has never had a real native translation before —
this phase is the first to give it observable effect.

**Checksum handling — direct application of ADR-050's existing ISO9141
precedent, no new code.** Clause 17.3.2.1.1's `CHECKSUM_DISABLED` connect
flag (bit 9) is numerically identical to the existing
`CONNECT_FLAG_ISO9141_NO_CHECKSUM` macro — Phase 0's own progress notes
flagged this exact bit-aliasing as a decision point for this phase.
`rpc_link.rs::connect_flags`'s own doc comment already states this service
never generates/verifies ISO9141/14230 checksums itself and deliberately
never sets that bit (ADR-050) — checksum handling stays entirely with the
interface. Clause 17.4.3's own text describes an equivalent
interface-computed-checksum default for J1708 (bit unset = interface
generates/verifies). Applying ADR-050's identical policy to J1708 needs no
new code at all: `connect_flags`'s existing `_ => 0` fallback already
produces the correct (unset) result for any protocol without a dedicated
match arm, including `J1708_PS`.

**Pin cardinality within the J1962 connector — no closed set, unlike every
predecessor.** Unlike SWCAN (clause 9.2.1, one pin), FT-CAN (clause 20.2.1,
two documented pin-pairs), or Honda DIAG-H (clause 13.2.4, two documented
single pins), clause 17 documents no valid-pin table on the J1962 connector
at all (its own pin table, clause 6.3.3.2, describes only the
J1708-dedicated connector's numbering, which this phase does not use per
the scoping decision above). Inventing a closed-set restriction here would
have no textual basis — unlike UART Echo Byte's own single-pin restriction,
which ADR-170 grounded in clause 12's explicit absence of a second-pin role
for that specific single-wire K-line bus. J1708 is not stated to be
single-wire on the J1962 connector at all, so this phase does not import
that inference.

## Decision

1. **New `ChannelProtocol::J1708_PS` const**, value `0x0000800D` matching
   `PROTOCOL_J1708_PS` directly — self-mapping through `j2534_protocol_id()`,
   the same shape as `UART_ECHO_BYTE_PS`/`HONDA_DIAGH_PS`.
   `j2534-0404/src/lib.rs` gains the missing `PROTOCOL_J1708_PS` re-export.
   `J1708_CHx` Additional Channels are **deferred**, matching every other
   standalone/CAN-family J2534-2 protocol shipped so far — the
   `PROTOCOL_J1708_CH1`-`CH128` header macros already exist and
   `is_chx_protocol_id`'s numeric range already covers them.
2. **One new resource-table row**, not multiple — clause 17 defines no
   OBD-family composite spec for this protocol. Next sequential `0x0200`-
   namespace id (`0x023C`); `hw_protocol_override: None`; `bus_type_name:
   "SAE_J1708_UART"`, reusing `comparam_defaults.rs`'s existing but
   previously-unwired `sae_j1708_uart()` bustype default (`DATA_RATE =
   9_600`, already correct per clause 17.2.2's minimum-support requirement;
   its pre-existing `DATA_BITS = 6` value is left untouched — out of scope,
   since clause 17.3.2.2.1 does not list `DATA_BITS` as client-configurable
   and no native translation exists for it under this protocol either way,
   so the value stays inert regardless of correctness, same as before this
   phase touched it). Default pin: J1962 pins 3/11 — an editorial
   convenience default only, matching a commonly-cited real-world heavy-truck
   scan-tool J1962 wiring convention for J1708, **not sourced from clause 17
   or clause 6's own text** (which names no J1962 pins for this protocol at
   all, per the Context section above) — the least spec-grounded default
   this codebase has picked so far, flagged explicitly for revisit if a
   primary SAE J1708 electrical-layer reference becomes available. Connect
   always issues an explicit `SET_CONFIG(CONFIG_J1962_PINS)`, matching every
   prior no-true-default protocol's precedent.
3. **`names.rs` gains a new pin-resolution arm** for `J1708_PS`, positioned
   after the Honda DIAG-H arm. Structurally simpler than every predecessor:
   `is_empty()` returns the row default only when `resource_row.is_some()`
   (same "no default pin, always explicit" gate as SWCAN/FT-CAN/UART Echo
   Byte/Honda DIAG-H, grounded in clause 17.3.2.1's own text); the non-empty
   branch runs `compute_pin_select` and accepts its result **without any
   closed-set check** — 1 or 2 well-formed pins, whatever the generic
   mechanism already validates — since clause 17 documents no valid-pin
   table on the J1962 connector to enforce (Context section above).
4. **`comparam_support.rs` gains `is_j1708_param`**, checked in the same
   position as the Honda DIAG-H branch, allowing `DATA_RATE`/`LOOPBACK`
   (clause 17.3.2.2.1's explicit list) plus `PARAM_MESSAGE_PRIORITY`
   (`CP_MessagePriority` — already a registered ComParam with ISO 22900-2
   text specific to J1708 semantics; Decision 6 below gives it a genuine
   native translation for the first time in this codebase).
5. **`protocol.rs`'s TX/RX message size-range table gains a
   `J1708_PS`/`_CHx` entry**: TX `1..=4095`, RX `1..=4095` bytes (clause
   17.4.3 Table 67) — by far the largest range this codebase has
   implemented; single addressing mode.
6. **`rpc_primitive.rs::apply_resolved_tx_flags` gains a `J1708_PS`-gated
   `MSG_PRIORITY_VALUE` computation**, not a `comparam_id.rs`/`SET_CONFIG`
   translation — clause 17.4.5 places this in TxFlags (per-message,
   composed at TX time), not `SET_CONFIG` (per-link, device-persistent).
   Reads the link's own Active `PARAM_MESSAGE_PRIORITY` value, clamps it to
   `1..=8` (any value outside that range, including the ComParam's unset
   default of `0`, maps to `8` per clause 17.4.5's own text), and shifts it
   into bits 16-19 alongside the function's existing SCI/SW-CAN flag
   composition.
7. **`connect_flags` needs no new code.** `CHECKSUM_DISABLED` (bit 9) stays
   permanently unset for `J1708_PS`, via the existing `_ => 0` fallback —
   direct application of ADR-050's established ISO9141/ISO14230 policy
   (Context section above). This resolves the exact decision point Phase
   0's own progress notes flagged for this phase.
8. **RxStatus**: clause 17.4.5 states only the `TX_MSG_TYPE` RxStatus bit is
   meaningful for this protocol — no code change needed: ADR-098's existing
   5-low-bit `RxFlag` forwarding already covers it.
9. **Repeat Messaging (ADR-165) needs no new rejection.** Clause 14.1's
   default rule (supported on all protocols unless a protocol's own clause
   explicitly excludes it) applies — clause 17's text (§17.1-17.5) contains
   no such exclusion, verified directly rather than assumed.
10. **`J1939_PINS`/`J1708_PINS` (the SAE J1939-13 and dedicated SAE J1708
    connectors) are deferred**, per the Context section's scoping decision
    — clause 6.3.3.2's own "at least one" requirement makes J1962-only
    spec-conformant. Additional Channels remains deferred. Discovery-cache
    connect-time enforcement wiring for `DEVICE_INFO_J1708_SUPPORTED` was
    deferred at this phase, matching every prior phase's precedent at the
    time — later superseded by
    [ADR-185](ADR-185-discovery-cache-connect-time-enforcement.md) Stage 1
    (`_SIMULTANEOUS` and the clause-6 connector-validity queries remain
    unwired).

### Rejected alternatives

- **Attempting `J1939_PINS`/`J1708_PINS` support in this phase** — deferred,
  not rejected outright: clause 6.3.3.2 only requires "at least one"
  connector, J1962-only already satisfies conformance, and the code-scout
  investigation found genuine `ChannelKey`/`PinData`/resource-table
  structural questions with no existing seam (ADR-156's own explicit,
  unresolved deferral) — disproportionate to attempt without a dedicated
  design pass, the same reasoning that kept Additional Channels deferred in
  every prior phase.
- **A closed-set pin validation arm mirroring SWCAN/FT-CAN/Honda DIAG-H** —
  wrong: those three protocols' own clauses each document an explicit valid-
  pin table on the J1962 connector; clause 17 documents none, so inventing
  one would have no textual grounding.
- **Restricting `J1708_PS` to a single pin, mirroring UART Echo Byte** —
  wrong: ADR-170's single-pin restriction is grounded in clause 12's own
  single-wire K-line framing; clause 17 states no such restriction for
  J1708 on the J1962 connector, and J1708's own dedicated-connector pin
  table (clause 6.3.3.2, not used by this phase per the scoping decision)
  documents J1708+ and J1708- as a genuine differential pair, so assuming
  single-wire-only would likely be incorrect once real hardware is involved.
- **Translating `PARAM_MESSAGE_PRIORITY` via `comparam_id.rs::to_j2534_config_id`
  (a `SET_CONFIG` mapping)** — wrong: clause 17.4.5 places
  `MSG_PRIORITY_VALUE` in TxFlags (per-message), not `SET_CONFIG` (per-link);
  the translation belongs in TX-flag composition (Decision 6), not the
  native-config-id table every prior ComParam translation in this codebase
  used for a genuinely different (per-link) class of value.

## Consequences

- Establishes the third instance of the standalone-protocol
  `ChannelProtocol` pattern (UART Echo Byte, Honda DIAG-H, now J1708) and
  gives `PARAM_MESSAGE_PRIORITY` its first real native translation, closing
  a latent "registered but never wired" gap that predated this phase.
- Explicitly narrows this phase's connector scope to J1962 only — a
  documented, spec-conformant, precedent-consistent deferral, not a silent
  gap. A client whose hardware only exposes the dedicated SAE J1708
  connector or the SAE J1939-13 connector cannot pin-select through this
  service today; `J1939_PINS`/`J1708_PINS` support remains open for a
  future phase, which will need the `PinData` connector-discriminator and
  `ChannelKey`-widening design work this phase's own investigation
  characterized but did not attempt.
- The row-default J1962 pin-pair choice (pins 3/11) has no textual basis in
  clause 17 or clause 6 — an accepted residual, tracked explicitly in
  `j2534-0404-service/docs/implementation-notes.md`'s Prioritized Backlog for
  revisit if a primary SAE J1708 electrical-layer reference becomes
  available in this workspace.
- Closes clause 17. Discovery-cache connect-time wiring for
  `DEVICE_INFO_J1708_SUPPORTED` is superseded by
  [ADR-185](ADR-185-discovery-cache-connect-time-enforcement.md) Stage 1
  (now consulted at connect time). Its `_SIMULTANEOUS` companion bit and the
  clause-6 `J1708_PS_J1962`/`_J1939`/`_J1708` connector-validity queries
  remain unwired by both of ADR-185's stages, tracked in
  `j2534-0404-service/docs/implementation-notes.md`'s Prioritized Backlog.
