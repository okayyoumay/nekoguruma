# ADR-461: The Job Instruction Is Signed Bytes With a Versioned Body and an Agent-Side Gate

**Date:** 2026-11-11
**Status:** Accepted
**Affects:** design 5.3, 5.6, 5.7, 11.1, 12; `crates/shared-crypto` (`instruction`), `crates/shared-proto` (`JobInstruction`), `api/asyncapi.yaml` (`JobCommand`, `commandRejected`), `api/openapi.yaml`; the agent's instruction gate, the server's instruction key, registration and the idempotent-command, start-deadline and document-delivery work built on this record; annotates ADR-454 (items 1 and 2) and ADR-395 (item 2)

## Context

Design 11.1 says the server signs each job instruction with an instruction key the agent received at registration, and ADR-454 and ADR-395 each rely on "the signed instruction" to name documents and a plan by hash. Nothing said what is signed, in which layout, how the agent checks it, or what it does with one that fails. The control channel carried a three-field `SignedJob` and unsigned digest fields beside it, so a field could be changed without touching the signature. ADR-459 fixed the primitive (ECDSA P-256 with SHA-256, low-S, one tag per purpose) and recorded that a process holding the loopback port on the local profile can reach the agent but must not be able to issue jobs.

## Decision

1. **The signature covers the exact payload bytes, and the payload is opaque to the transport.** The agent verifies the bytes and only then parses them. Rejected: a transcript the verifier rebuilds from JSON fields (a field left out of the transcript is silently unsigned), RFC 8785 canonical JSON (a canonicalizer at both ends), and JWS or COSE (algorithm agility and dependencies, where ADR-459 fixes the algorithm).
2. **The body is a postcard struct, `shared_proto::JobInstruction`,** whose first field is `INSTRUCTION_VERSION` (1). Decoding reads the version alone first, then the whole struct, and refuses trailing bytes, as `diag_ir::plan` does for a plan (ADR-395 item 1). The payload is at most 64 KiB. An unknown version or enum variant is refused. It replaces `JobSpec` and `SignedJob`.
3. **The envelope is one blob (base64 in JSON):** a format byte `0x01`, the key fingerprint (SHA-256 of the signing key's SPKI DER, 32 bytes), the signature (r then s, low-S, 64 bytes), then the payload. The signature is `sign_tagged` over the payload under the tag `nekoguruma job instruction`, now a public constant of `shared_crypto::instruction`; the connection proof's tag stays its own. The format byte fixes the algorithm, so another algorithm is another format byte. A new format byte that keeps the algorithm also takes a new domain tag, so a signature relabelled with another format byte cannot verify under a differently read header. The fingerprint is a selector only and is not signed; a verifier compares it with the key it trusts and never takes a key from it. The unsigned `irDigests` and `artifactDigest` beside the blob in `JobCommand` are removed.
4. **Body version 1** holds: the version; the job ID as canonical UUID text (36 lowercase hyphenated characters, checked at decode because it reaches file paths); the ownership generation (ADR-229); the agent ID (ADR-229); the operator ID (design 6.6); the job kind, a closed enum that gains `Identify` (design 16.3, ADR-327 item 1); the VCI ID, the opaque string the agent itself reported; the VIN, optional (design 8.8); the document hashes, SHA-256, strictly ascending with no duplicate (ADR-454); the artifact hash, optional (ADR-336); the plan hash, optional (item 13); the issue time and the start deadline, Unix seconds (design 5.3). Strings are bounded to 1024 bytes and the required ones are not empty. Left out of version 1: parameters (the agent's job has none), an approval record (item 5), a remote flag, an execution window, a minimum agent version and a tenant. The rule: anything the agent acts on enters the body by a version bump, never beside it.
5. **No approval record in version 1.** It is added by a version bump, inline (level, approver, time), when the M4 confirmation levels and M6 approvals need it. Rejected: a hash of a server-held record, since the agent could check nothing offline.
6. **Expiry.** This record defines the two time fields; the start-deadline item enforces them. The rule handed to it: compare the deadline with the later of the device clock and the highest issue time verified so far (persisted). The server judges by its own receive time (design 16.3) and never delivers past the deadline. This is a staleness guard, not a defence against the device's own user (design 6.6).
7. **Key identity.** The key ID is the SHA-256 of the SPKI DER, as for the agent key (design 6.4). The agent trusts only the key pinned at registration: one key in M3, with the fingerprint as the selector that allows an overlap set later. There is no in-band key update; rotation is re-registration (design 11.1). There is one instruction key per deployment (the signing-service direction of design 16.3).
8. **Target binding is the agent ID only.** Every registration must therefore assign a fresh agent ID; otherwise an old instruction would verify again after a key reset that erased the journal's duplicate record. Rejected: binding the agent key's fingerprint.
9. **Placement and order.** `shared_crypto::instruction` holds the tag, `sign` and `verify` over bytes, and the envelope's split and join over bytes, mirroring `proof` and free of `shared-proto`; `shared-proto` holds the body. The agent's gate (`agent::instruction::open(envelope, trusted key, own agent ID)`, returning a `VerifiedInstruction` with private fields) checks, in order: length and format byte, fingerprint against the pinned key, signature parse, signature under the tag, body decode, agent ID equals its own. Design 5.3 gains the invariant that verification comes first, then the duplicate check and the journal record, then the ACK: a loopback port holder (ADR-459 Consequences) could otherwise send a forged instruction for job J with a high generation and get the real one dropped as a duplicate.
10. **Refusal.** An instruction that fails the gate is answered by a command-level rejection keyed by the command's ID, with a coarse reason, and an entry in the operational log. The reasons are `Malformed` (a missing or unparsable envelope, signature or body), `UnknownKey` (the fingerprint is not the pinned key's), `BadSignature`, `UnsupportedVersion` (an unknown format byte or body version) and `NotForThisAgent` (verified but names another agent). A job-scoped state exists only once the instruction verified and names this agent; an unusable VCI then ends as `PreconditionFailed`. A forged command naming a real job J would otherwise put a must-deliver terminal state in the outbox (design 5.6). A rotated server key shows as `UnknownKey`, which tells the server to ask for re-registration. `FailureCode::SignatureInvalid` is not used for this.
11. **The trusted key is a parameter of the gate.** Nothing in this record reads it from disk, the environment or the command line. Registration stores it as SPKI PEM in the per-mode state directory (ADR-460), written at registration only. ADR-454 item 6 already rejected a development key lifecycle.
12. **Authorization is unchanged.** The ADR-247 and ADR-331 ceiling stays until M6. The standalone `ngr-agent run` and `identify` stay unsigned local tools, read-only in a release build (ADR-398).
13. **The plan hash is the plan's signature.** The optional plan hash is the signature ADR-395 item 2 asks for: one signature, no second tag. The documents of an identification job are named through the plan. ADR-454 item 2 therefore reads: the agent runs only a document the instruction names, directly or through the plan it names. The plan-signature item does the agent's check.
14. **The server's signer is not part of this record.** Where the instruction key lives on the local profile, its create-once rule and its readers are the server's own record, which registration and the job queue need.

## Consequences

- Nothing may re-encode a decoded instruction and compare or hash the result: postcard accepts some non-canonical input, so the signed bytes are the only bytes that count, and the agent keeps the envelope byte-exact beside its journal and re-verifies it at resume.
- `shared-proto` compiles into both worker services; it gains `postcard` and `thiserror`, which the workspace already uses, and the six worker targets are covered by `worker-check`.
- The sibling commands (cancel, HMI response, seed-key response) stay unsigned, so a loopback port holder can still forge them; that closes with the local-profile server authentication item, which needs a third tag if it reuses the key.
- A journaled job that no longer verifies after re-registration is a case for the idempotent-command work.
- The server-side signer, the agent's gate and its tests, the start-deadline check and the delivery of documents are separate items in the backlog.
