# ADR-099: Tester-Present Discard Extends to Indication Frames (SOM / TX_DONE / Loopback), and Now Windows on Every Successful Send

**Date:** 2026-07-17
**Status:** Accepted (amends ADR-088, ADR-093; amended by ADR-100)
**Affects:** `j2534-0404-service` service, events

## Context

`CP_TesterPresentReqRsp = 1`'s response-discard mechanism (ADR-088, window-scoped and unified across both send modes by ADR-093) drops a frame in `poll_rx_inner` only when its **payload content** starts with the CLL's configured `CP_TesterPresentExpPosResp`/`CP_TesterPresentExpNegResp` prefix. ADR-097/ADR-098 (landed the same day as this ADR) separately classified the J2534 `RxStatus` bits `TX_MSG_TYPE` (`0x1`, CONFIG_LOOPBACK echo), `START_OF_MESSAGE` (`0x2`, SOM), and `TX_INDICATION` (`0x8`, TxDone) as *indication* frames — housekeeping notifications with an always-empty (or near-empty) post-header-split payload, as opposed to a genuine content-bearing response. ADR-097/ADR-098 excluded these from `ExpectedResponse`/pending-RC matching (`MatchProbe`) for exactly this reason, but never touched the tester-present discard check, which sits a few lines below in the same function.

Because an empty payload can never satisfy `payload.starts_with(&discard.pos)` for a non-empty configured prefix, these indication frames sail through the discard check unconditionally and are delivered to the client as ordinary unsolicited `ResultData` — including a SOM herald of the very ECU response ADR-088 discards, and a TX_DONE/loopback confirmation of tester-present's own outgoing request. This breaks the "tester-present is invisible to the client" intent `CP_TesterPresentReqRsp = 1` exists to provide (ISO 22900-2 has the MVCI protocol module itself drop the response) — a real MVCI module's internal tester-present state machine produces no client-visible `PDU_EVT_DATA` at all; SOM/TxDone/loopback frames only exist here because this adapter multiplexes tester-present traffic onto the same J2534 RX stream the client's own COPs read from.

This gap was found and confirmed while investigating a user question about whether SOM/TX_DONE notifications returned by `PassThruReadMsgs` were leaking into the RX queue during tester-present handling; `design-advisor` (fable) reviewed the mechanism and produced the design in this ADR. No existing test exercised this interaction: `tester_present_reqrsp.rs`'s tests only ever inject content-bearing frames, and `response_distribution.rs`'s SOM/TxDone tests (which do assert these frames ARE delivered, correctly, in the general non-tester-present case) never combine that with an armed tester-present CLL.

A related, narrower gap: TX-side indication frames (TxDone, loopback) are artifacts of tester-present's own *send*, not of whether a response is expected — `CP_TesterPresentReqRsp` governs only the response side. Before this ADR, `TesterPresentState::Armed::discard_until` (`DiscardWindow`) only opened when a send succeeded **and** `expects_response` was true at that send instant (ADR-088 second amendment), so under the default `CP_TesterPresentReqRsp = 0`, every tester-present send left no discard window open at all — its own TxDone/loopback echo would leak on every single cycle, not just occasionally.

## Decision

**The discard window now opens on every successful tester-present send, regardless of `CP_TesterPresentReqRsp`.** All three `DiscardWindow` write sites (`dispatch_due_tester_present`, `handle_start_comm`, `handle_update_param`, `events.rs`) construct `Some(DiscardWindow { .. })` whenever the send itself succeeded; `pos`/`neg` are frozen from the pre-send `CP_TesterPresentExpPosResp`/`ExpNegResp` snapshot only when that same snapshot's `expects_response` was `true`, and frozen empty (`Vec::new()`) otherwise. Empty `pos`/`neg` already can never content-match (existing `!discard.pos.is_empty()` guard), so this correctly keeps content/SOM discard gated on `expects_response` while unconditionally giving TX-side discard a window to work with.

**`TesterPresentDiscard` (`events.rs`) gains a `tx_can_id: Option<u32>` field** — tester-present's own outgoing TX CAN ID, taken as the leading 4 bytes of the armed `framed_data` (the same CAN-ID-prefixed layout `resolved.data` already uses). `Some` only for CAN-family protocols (`resolved.can_functional.is_some()`) with a long-enough `framed_data`; `None` otherwise. Populated in `build_cll_rx_entries` from the same per-arm-frozen `framed_data`/`resolved` fields `target_can_ids` already reads there — no new freezing mechanism, since `dispatch_due_tester_present`'s per-tick sends never re-resolve either between arms (the same lifetime argument ADR-088's amendment already established for `target_can_ids`).

**`poll_rx_inner`'s discard check becomes three arms, all still gated by `frame_cop_handle.is_none()` (a pending COP's own claim always wins, unchanged) and now unconditionally excluding `RX_BREAK`** (a bus condition, never a tester-present artifact, regardless of what other bits happen to be combined with it on a given frame):

- **(a) Content** — the reassembled response itself: unchanged from ADR-088/093, restricted to `is_content_frame` (the same `rx_status_flags & !RX_ISO15765_PADDING_ERROR == 0` predicate ADR-098's `MatchProbe` gate already uses — now hoisted into one shared `let` both sites consult) and the response-side `target_can_ids` gate.
- **(b) SOM herald** of that same response — `START_OF_MESSAGE` set, not also a TX-side bit, and only when a non-empty `pos`/`neg` was actually frozen for this window (proving the send that opened it expected a response) — gated by the same `target_can_ids` restriction as (a). An empty-payload SOM frame has no content to prefix-match, so eligibility is content-existence (non-empty configured pattern), not content-match.
- **(c) TX-side echo** of tester-present's own send — `TX_MSG_TYPE` and/or `TX_INDICATION` set — gated by the new `tx_can_id`, independent of `expects_response`/`pos`/`neg` (per the window-always-opens change above). Deliberately the OPPOSITE of `target_can_ids`'s `None`-means-unrestricted convention: `tx_can_id.is_some_and(...)` treats `None` (non-CAN-family) as "arm (c) never fires," not "unrestricted." `target_can_ids == None` has a real "no restriction" reading under functional/broadcast addressing (every routed ECU is a legitimate reply); `tx_can_id` has no analogous broadcast case — our own echo always bears exactly one TX CAN ID for a CAN-family protocol, so its `None` only ever means "not CAN-family, nothing to compare against." A first draft of this ADR used `is_none_or` here by direct analogy to `target_can_ids`, which a Codex review round on the implementing PR caught as wrong: it would have silently discarded every `TX_MSG_TYPE`/`TX_INDICATION`-flagged frame on a non-CAN-family armed CLL, including a genuine TxDone/loopback indication for a completely unrelated, concurrent client send on that same CLL — traffic ADR-098 requires to reach the client normally, since indication frames are never claimed by `MatchProbe` and so have no other protection.

RX_ISO15765_PADDING_ERROR is deliberately excluded from the indication-bit set (as ADR-098 already established): it tags a genuine, fully reassembled response whose final CAN frame happened to have fewer than 8 data bytes, not a housekeeping indication, and must remain eligible for content discard.

## Consequences

- Closes the confirmed leak: a SOM herald or TX_DONE/loopback echo of tester-present's own exchange no longer reaches the client as an unsolicited `ResultData`, restoring the "tester-present is invisible" intent for the indication-frame case, not just the content-response case ADR-088 already covered.
- **Behavior change beyond the reported symptom:** the discard window now opens on every successful tester-present send even under the default `CP_TesterPresentReqRsp = 0`, where previously no window opened at all. This is required for (c) — TX-side discard has no other window to key off — and is judged spec-consistent since TxDone/loopback are send-side artifacts, not response-side ones `CP_TesterPresentReqRsp` was ever meant to gate.
- **Accepted residual — TX-CAN-ID collision:** during an open window, a TX_DONE/loopback frame from a genuinely different, concurrent client send that happens to share tester-present's own TX CAN ID is also discarded. Bounded to `CP_P2Max` per tick, applies only to indication-type frames (never a content response — `MatchProbe`/ADR-098 guarantees `frame_cop_handle` is never attributed to an indication frame in the first place, so a pending COP's own wait can never be starved by this), same severity class as ADR-088's own accepted content-side residuals.
- **Accepted residual — SOM/content inconsistency:** a genuine, unrelated frame from the tester-present target ECU that arrives inside a `CP_TesterPresentReqRsp = 1` window and fails the `pos`/`neg` prefix match is still delivered as content (correct — arm (a) requires a match), but its own SOM herald (if the hardware emits one) IS discarded by arm (b), since (b)'s eligibility is "a response-shaped window is open," not "this specific reassembled frame will end up matching." Judged low-impact: `EventItem.timestamp` and the eventual content delivery still carry the same information a discarded SOM herald would have added.
- **RX_BREAK is now also excluded from case (a)'s content-discard path**, closing a latent combination the original ADR-088 check never explicitly excluded (`is_content_frame` already excluded it via the shared ADR-098 predicate before this frame could reach the `pos`/`neg` check, so this is a code-path clarification rather than a behavior change for (a) alone) — the explicit top-level guard exists specifically to keep an implausible-but-uncombination-validated `RX_BREAK | START_OF_MESSAGE` frame out of arm (b) too, per ADR-098's own "no combination validation" stance on real hardware.
- No change to any other ADR-088/093 residual: `CP_P2Max` window-sizing, the one-tick disarm window on `CoptStopcomm`, physical-vs-functional `target_can_ids` scoping, and the bare-`[0x7F]` non-service-scoped legacy-OBD residual all carry forward unchanged.
- **Accepted residual — case (c)'s reachability is narrower than `tx_can_id` alone suggests, pre-existing and not introduced by this ADR:** `route_frame` (`events.rs`) only routes an incoming frame to a CLL when its CAN ID matches a configured `UniqueRespIdTable` entry's `CP_CanRespUSDTId`/`CP_CanRespUUDTId`, or when the table is empty (ADR-007's no-table wildcard mode, which routes every CAN ID unconditionally). Tester-present's own TX CAN ID (`tx_can_id`, the source of the leading 4 bytes of `framed_data`) is a *request* identifier and is never itself a table entry for the common physically-addressed case (`CP_CanPhysReqId`, not a response ID) — so a genuine TX_DONE/CONFIG_LOOPBACK echo on that CAN ID is already dropped by routing, before it ever reaches the discard check case (c) adds, for any CLL with a non-empty `UniqueRespIdTable`. Case (c) is therefore reachable in practice only when the table is empty (wildcard mode) or the TX CAN ID happens to coincide with a configured response ID. This does not weaken the fix — it is dropped by routing either way, both before and after this ADR, so no leak survives it — but it does mean case (c)'s protection is narrower than a reader might assume from `tx_can_id`'s existence alone. Found while writing this ADR's regression tests (`create_functional_no_table_cll` exists specifically to construct a reachable case); closing it would mean teaching `route_frame` to also match `CP_CanPhysReqId`, a routing-layer change out of scope for a discard-mechanism ADR — tracked as backlog in `j2534-0404-service/docs/implementation-notes.md`, not fixed here.
- New regression coverage in `j2534-0404-service/tests/grpc_mock/tester_present_reqrsp.rs`: SOM discarded inside a window; TX_DONE/loopback discarded inside a window even under `CP_TesterPresentReqRsp = 0` (proving the always-open-window change); SOM/TxDone delivered once the window has expired or tester-present was never armed; `RX_BREAK` (alone and combined with SOM) never discarded; a TX-side-flagged frame on an unrelated CAN ID still delivered.
