# ADR-489: The Agent Records Every Job It Takes in a Received-Jobs Ledger and Acknowledges a Redelivery Without Taking It Again

**Date:** 2026-11-17
**Status:** Accepted
**Affects:** design 5.3, 6.7; `docs/glossary.md`, `api/asyncapi.yaml` (`receiveJob`); `crates/agent` (`received_jobs`, `control::channel`, `control::gate`, `control`, `connect`), `crates/agent/docs/ngr-agent.md`, `crates/agent/docs/operational-log.md`; details ADR-229 and ADR-461 item 9; annotates ADR-473 item 4, ADR-478 item 5 and ADR-486

## Context

The server delivers a job command at least once (ADR-476): a command whose acknowledgement is lost, or whose connection ends first, comes again after the lease, also after an agent restart. ADR-473 item 4 left the duplicate check to the intake, and ADR-478 item 5 accepted that a redelivery would append a second `received` event. Design 5.3 asks for more: the agent records a job's ID and ownership generation (ADR-229) before it acknowledges, and ignores a command for a job it has already taken. ADR-461 item 9 puts that record after verification, so a forged command can never occupy a job ID, and ADR-486 requires the duplicate check to precede the start-deadline check, or a job the agent holds would be reported as expired by its own redelivery. The write-job journal exists only for write jobs, and the instruction's envelope must be kept byte for byte so that whatever starts a job later can verify it again.

## Decision

1. **The ledger.** One file per agent ID, `<state>/registration/<agent-id>.received-jobs.v1`, holds one record per accepted job instruction: the job ID, the ownership generation and the signed envelope as delivered. It is opened as the issue-time mark is (ADR-486), and appended to as the outbox is (ADR-478): its own lock file `received-jobs.lock`, taken before the file is read and never deleted; an absent file is an empty ledger and the open creates nothing; the first record creates the file (a temporary file made at mode 0600, synced, renamed, the directory synced; on Windows the final file is reopened and synced), later records are appended and synced; a stale temporary file is ignored by the open and removed by the next creation; the mode of an existing file is not checked. The layout is the magic, a format version and frames of the journal's framing (length, CRC-32, payload): a header frame (the agent ID, a protection word that is 0), then one frame per record with consecutive numbers from 0. The open reads the file once and keeps only an index from job ID to the highest generation recorded; the index changes after a record's sync has returned and never otherwise, and nothing is ever removed. The agent ID must be a canonical UUID, since it names the file.
2. **The rule.** A verified instruction for job `J` at generation `g` is a duplicate when the ledger holds `J` at a generation `g'` with `g <= g'`, and new otherwise (no record, or only a lower one). A higher generation adds a second record and leaves the first. A duplicate is acknowledged and counted in `commands_acknowledged`; no event is appended, the intake is not called, nothing is written to the ledger and the device clock is not read. That holds whether the verified bytes equal the recorded envelope or differ from it (the first envelope stays), and after the start deadline has passed.
3. **The order.** The gate verifies the instruction (ADR-461 item 9); the mark is raised to its issue time; the operator check (ADR-483); the duplicate check; the deadline check (ADR-486); the mark is synced when behind, for every verified instruction, a duplicate included, before anything that follows; the record is made and synced; the intake takes the instruction; the first event is appended (`received`, or the terminal event of a refusal or an expiry); `commandAck` is written. A command that fails verification touches none of the ledger, the mark and the clock, whatever job ID and generation its bytes claim. The operator check comes first, so a command of an operator who is not allowed gets its terminal `preconditionFailed` even for a job that is recorded, and the record stays. A job refused for its operator or past its deadline is not recorded, so its redelivery is judged again and gets a second terminal event, as ADR-483 and ADR-486 say. The record is made on a blocking task raced with the agent's stop, as the mark's write is: a stop during it ends the connection as a stop, and the write finishes holding the store and its lock.
4. **The intake.** `Intake::take` returns a future that resolves to a result. It is called at most once per job ID and generation, returns promptly, and tolerates being dropped (a stop drops it). The channel awaits it inline with no timeout of its own, raced with the stop. An error leaves the record, appends no event, writes no acknowledgement and closes the connection with 1011 under the class `intake`, with one `warn` per `hello`; the redelivery is a duplicate.
5. **Failure of the ledger.** A write, sync, rename or directory sync that fails withholds the acknowledgement, calls no intake, appends no event, leaves the index as it was and closes the connection with 1011 under the class `ledger-write`, one `warn` per `hello`. The ledger then refuses every record (`ledger-poisoned`, also 1011) until it is opened again, since a failed sync can lose data the OS had accepted; its index still answers, so a duplicate is acknowledged even while the ledger or the outbox is poisoned or full. The session reopens a poisoned ledger before the next connection, as it does the outbox: a frame that reached the file counts (the redelivery is a duplicate), a torn one is cut (the redelivery is new). A reopen that finds the file corrupt ends the session with exit 1 (`Ended::LedgerUnusable`); one that fails for another reason warns once per `hello` and is tried again before each connection. A failure to write the mark before the record leaves no record; a duplicate that owes a mark write is not acknowledged until the write succeeds, and closes with 1011 under `mark-write` as before.
6. **At the session start.** `ngr-agent connect` opens the ledger after the issue-time mark and before the key, with its own lock. A torn last frame (a short frame, or a last frame that fails its checksum, with nothing whole after it) is cut off, the cut synced, with one `warn` that holds the byte count only. Anything else that does not read back is corrupt and never repaired: a wrong magic or version, a damaged header or another agent ID, a bad checksum before the last frame, damage followed by a whole record, numbers that are not consecutive, a record that does not decode, a job ID that is not a canonical UUID, an envelope that is empty or longer than the envelope format allows (97 bytes and 64 KiB). Corruption, an unusable agent ID and a path that is not a regular file are exit 1 with the advice to register again; a lock held, an unusable directory and a failed read or sync are exit 3.
7. **Re-registration.** A re-registration is a new agent ID (ADR-461 item 8), so the new agent has an empty ledger, and the old file is left alone.
8. **The log.** A duplicate is a `debug` entry with the job ID and the generation; one for an earlier generation than the recorded one is a `warn` the first time on a connection and `debug` after that, since the server should not send it; the end-of-connection line of refused instructions gives the counts `duplicate` and `earlier_generation`. An entry holds the job ID and the generation of a verified instruction only, never a `commandId`, an operator, an owner, a VIN, a time or a byte of the envelope.

## Consequences

- **A redelivered job gets no second `received` event, and a recorded job whose `received` was never appended never gets one.** Design 5.6 treats `received` as proof that the agent has the job; the acknowledgement of the redelivery gives the same proof, and the server's own handling of the delivery does not depend on the event. This replaces ADR-478 item 5's second event, ADR-473 item 4's expectation that the intake is idempotent, and ADR-486's first Consequence (the duplicate check now comes before the deadline check).
- **The outbox's admission bound delays a job's acknowledgement by one lease and no longer refuses the job.** A `received` append refused at the bound leaves the job recorded and handed over; the command is not acknowledged and the connection stays, and its redelivery is acknowledged with no event, even while the outbox is full.
- **A recorded job whose hand-over did not happen stays unrun.** An intake error, a stop or a crash after the record, a failed append of the event after it and a record whose frame counts at a reopen after a failed write all leave a job that the ledger holds and nothing has taken. Its redelivery is a duplicate, so nothing else will take it. The ledger, not the intake call, is the list of the jobs the agent holds; starting or resuming jobs from it, verifying the recorded envelope again and judging acceptance and the deadline again at that point is work that has not been done, since nothing starts a job from the control channel yet.
- **Two outcomes follow from the order.** A command of an operator who is not allowed for a recorded job is answered with the terminal refusal and leaves the record (the operator check is first); a later generation of a recorded job that is past its deadline is `expired` and not recorded, and the highest recorded generation is unchanged.
- **The ledger grows without a bound and is never pruned.** One record per accepted job, the envelope up to about 64 KiB; the open reads the whole file once. A size bound or pruning is a later decision.
- **The file's layout is a format version.** A change is a new version and a new file name suffix; an older agent ignores an unknown file name.
- **Each new job costs a second synced write** beside the event's (and the mark's, when it rises); a duplicate costs none.
