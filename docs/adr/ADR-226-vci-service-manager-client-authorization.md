# ADR-226: `vci-service-manager` Client Authorization — Peer-Identity Trust Root over Local IPC, Manager-Minted Session Tokens for TCP

**Date:** 2026-09-10
**Status:** Accepted
**Affects:** `vci-service-manager/src/main.rs`, `vci-service-manager/src/ipc.rs` (`GuardedUnixListener`/`GuardedUnixStream`, a same-user unauthenticated-connection DoS fix), `vci-service-manager/src/peer_identity.rs`, `vci-service-manager/src/allowlist.rs` (§3 amendment: directory-vs-file `AccessCheck` mask split), `vci-service-manager/Cargo.toml`, `vci-service-config/src/lib.rs` (§3 amendment: `system_config_dir()` replaces `config_root_dir()`), `vci-service-config/docs/implementation-notes.md`, `docs/QUICKSTART.md`, `docs/worker-crates.md`, `docs/glossary.md`, `vci-service-manager/docs/implementation-notes.md`, `docs/adr/ADR-221-vci-service-shared-listener-auth-and-proxy-removal.md` (two accepted residuals closed), `docs/adr/ADR-073-vci-service-manager-config-file.md` (`[config.manager]` gains `ipc`), `docs/adr/INDEX.md`

## Context

ADR-221 added bearer-token authentication + real `tonic-web` to each spawned service's own gRPC listener, and a global `Host`-header allowlist (`host_allowlist_middleware`, `main.rs:1665-1667`) covering every route the manager serves — closing the confirmed primary threat (a malicious browser page reaching the manager via DNS-rebinding/CSRF-style access). It left two accepted residuals in `vci-service-manager/docs/implementation-notes.md`'s Prioritized Backlog:

1. `POST /vci-libs/{id}/token` is callable by any local same-OS-user process — no client-identity check gates token issuance.
2. The manager's own REST routes (`GET /vci-libs`, `GET /vci-libs/{id}`, `GET/POST/DELETE /vci-libs/{id}/instance`, `GET /logs`) have the identical gap.

These are one gap, not two: the `Host` allowlist already blocks the browser threat on every route (it is a global router `.layer()`, not scoped to `/token`), so what is actually missing, on both surfaces, is a way to distinguish a legitimate local client process from an untrusted one — a same-OS-user attacker process can set a correct `Host` header and pass the allowlist trivially. The confirmed threat model (established with the user in an earlier round, recorded in `vci-service-manager/docs/WEB_API_IMPROVEMENT_PLAN.md`'s "運用前提の確定とクライアントモデル") is: `vci-service-manager` is never exposed directly to a remote network (a separate ASAM-SOVD-compliant service fronts that if ever needed); local same-OS-user processes are not trusted as a blanket rule, but a specific, extensible client set (an SOVD service, and other future local services, all running as the same OS user as the manager) must be authorizable.

That memo's "資格情報配布方式の設計" section, refined across roughly 30 Codex review rounds, already ruled out several approaches this ADR does not re-propose: a static shared secret in a config file or environment variable (readable by any same-user process); bare self-service registration with no unforgeable trust root (an attacker process can call the same endpoint); and any post-enrollment credential stored somewhere a same-user process can read (defeats the trust root one step later, the same way a static secret would). ADR-221's own spawn-time key delivery (a random key pushed over stdio when the manager spawns a child) does not generalize here either — a native client such as the SOVD service is not spawned by the manager, so there is no spawn-time channel to reuse.

Two constraints, settled explicitly with the user before this design was finalized, shape the Decision below:

- **(A) No platform ships with client authorization entirely absent.** An earlier draft of this design gated all non-`/healthz` routes behind a Unix-domain-socket/named-pipe listener using OS peer-credentials, but deferred Windows and macOS executable-identity verification to follow-up work — meaning release builds on those platforms could not use the admin routes at all until that follow-up landed. Rejected: this repository's primary deployment target is Windows. Verification found no genuine platform blocker for a baseline identity check (see Decision §2) — it was over-cautious phasing, not a real constraint.
- **(B) Browsers must retain direct TCP reachability to the admin/catalog routes.** `vci-service-manager/docs/WEB_API_IMPROVEMENT_PLAN.md`'s operational-scenario analysis and `docs/glossary.md` document a browser-dashboard capability that calls the manager's own REST API (at minimum `GET /vci-libs` for discovery) directly. A Unix domain socket or Windows named pipe is unreachable from a browser's `fetch`/XHR at all, so an IPC-only admin surface (the same earlier draft) silently eliminated that capability. Rejected: the admin/catalog routes must stay reachable over TCP.

## Decision

**1. Two listeners.** The existing TCP listener (`bind`, `Host` allowlist retained) serves `GET /healthz` unauthenticated; every other route requires a valid session bearer token (§4-5). A new local-IPC listener — `tokio::net::UnixListener` at `[config.manager].ipc` (default `$XDG_RUNTIME_DIR/vci-service-manager.sock`, falling back to `/tmp/vci-service-manager-<uid>.sock`; same scheme on macOS) on Linux/macOS, or a Windows named pipe (`\\.\pipe\vci-service-manager`, `reject_remote_clients(true)`, `first_pipe_instance(true)`) — serves the same `api` router plus one IPC-only route, `POST /auth/sessions`, behind peer-identity authorization (§2-3) instead of a session token. `DELETE /auth/sessions/{id}` is reachable on both listeners. A `#[cfg(debug_assertions)]`-only `VCI_MANAGER_INSECURE_NO_CLIENT_AUTH=1` disables both checks, compiled out of release builds (mirrors ADR-221's own debug-only override and ADR-073's environment-variable convention); under this bypass, `session::Via::Ipc` carries an explicit `bypass: true` flag (never inferred from the placeholder `exe_path`/`sha256` values that branch inserts) so `POST /auth/sessions` (§4) also skips its own allowlist-selector re-check for that request — without this, the bypass would still 403 every session-mint attempt via that re-check, defeating the one check it most needs to skip (Codex review finding). Before removing and rebinding an existing Unix socket file at the IPC path, `bind_unix_listener` first probes whether it is actually stale (a `UnixStream::connect` attempt; `ConnectionRefused` means stale, success means still-live) rather than assuming so — otherwise, a second manager instance whose IPC path resolves to the same default would silently steal the first, still-running manager's live socket (Codex review finding); a still-live socket, or a probe timeout, fails `bind_unix_listener` closed (`AddrInUse`/`TimedOut`) rather than stealing it. That probe-then-remove-then-bind sequence is itself protected end to end by an exclusive `flock` (`lock_socket_path`, on a sibling `<path>.lock` file, released via an RAII guard on every return path) — without it, two manager instances starting concurrently against a genuinely stale socket could each independently probe it, each correctly see `ConnectionRefused`, and then race on `remove_file`/`bind` themselves, with whichever bound last silently stealing the path out from under the one that bound first: the same "silent redirection" outcome the probe itself exists to prevent, just moved from a single-process check-then-unlink race to a cross-process one (Codex review finding, this mechanism's 2nd consecutive round of new findings). The lock file is never removed, the same "harmless leftover" convention already applied to a stale socket file itself — removing it would just reopen a race over the lock file's own existence for no benefit. `bind_unix_listener` itself returns a `GuardedUnixListener` (`ipc.rs`), not the raw `tokio::net::UnixListener` directly: without any bound on it, a same-user attacker could open connections and send no HTTP bytes (or trickle bytes to dodge a resettable timer) forever, exhausting the manager's file-descriptor limit and starving every legitimate native client from reaching IPC to mint or renew a session — this also affects the TCP listener and child-service spawning, not just IPC itself, since fd exhaustion is process-wide, and is worse than a first look suggests on Linux 6.5+, where `SO_PEERPIDFD` (§2) additionally pins a second fd (a pidfd) per connection (Codex review finding). `GuardedUnixListener::accept` acquires a semaphore permit (`MAX_INFLIGHT_UNIX_CONNECTIONS`, 64) BEFORE ever calling `inner.accept()`, so an over-cap connection simply dwells in the kernel's own accept backlog at zero fd cost to this process, rather than being accepted and then rejected; each accepted `GuardedUnixStream` additionally carries a fixed, non-resetting `IDLE_READ_TIMEOUT` (30s) deadline — checked at the top of every `poll_read`, never pushed forward on partial read progress — mirroring, and sharing the exact literal value and rationale of, the Windows named-pipe listener's own `ManagedPipeConnection::idle_deadline` described just below (a resettable deadline is defeatable by trickling one byte at a time). The two listeners differ only in how they cap concurrency: Windows already bounds it structurally via its fixed `MAX_INSTANCES` pool of pre-created pipe instances (see below), so no additional mechanism was needed there; an ordinary Unix listening socket has no such fixed-pool concept and an unbounded kernel accept backlog, so the semaphore-based cap is a Unix-only addition, while the idle-lifetime deadline itself is now shared identically by both listeners. On Windows, all `max_instances(N)` pipe instances are pre-created at startup (so no other same-user process can ever add an instance to the name), and — since a connecting client can attach to any currently-listening instance the instant it exists, not only one this process has designated "next" — every instance that isn't currently servicing a connection runs its own dedicated, perpetually-outstanding `ConnectNamedPipe` call in its own task for the listener's entire lifetime, rather than sitting idle in a pool waiting to be promoted; a connection's close spawns exactly one replacement instance-plus-listening-task before that connection is fully torn down (`vci-service-manager/src/ipc.rs`'s `windows_pipe` module doc comment carries the full invariant). Graceful shutdown is symmetric across both listeners: a single `tokio_util::sync::CancellationToken`, created once in `run()`/`main()` and cancelled by one shutdown-driver task (`ctrl_c()` → `append_log` → `stop_all_instances` → `.cancel()`), feeds a clone of itself into each listener's own `axum::serve(..).with_graceful_shutdown(..)` call (`cancelled_owned()`), and `main()` awaits both listeners' futures (via `tokio::try_join!`, so an abnormal failure in either one is not left stranding the other forever waiting on a signal that will never come) before returning. Before this fix, only the TCP listener had any graceful-shutdown wiring at all — the IPC listener (`spawn_ipc_listener`) ran fully detached, with no shutdown signal and no retained `JoinHandle`, so it kept accepting and fully processing brand-new requests (including `POST /auth/sessions` and `POST`/`DELETE /vci-libs/{id}/instance`) throughout the entire TCP-side drain, then had every in-flight request abruptly severed the instant the tokio runtime dropped when `main()` returned (edge-case-hunter finding).

**2. Peer identity (baseline — ships identically on Linux/Windows/macOS in this PR).** A `PeerIdentity` type (implementing axum's `Connected<IncomingStream<'_, L>>` for the IPC listener) captures, at accept time, the peer's pid and an accept-time timestamp (plus, on Linux, a pidfd and a directly-read system-uptime value -- see below). On a connection's first request, the manager resolves pid → executable path → SHA-256 of that file, using only inputs available on every platform without any code-signing API: `UnixStream::peer_cred()` (`SO_PEERCRED` on Linux, `LOCAL_PEEREPID` on macOS) or `GetNamedPipeClientProcessId` for the pid; `readlink /proc/<pid>/exe` (rejecting a `(deleted)` target), `QueryFullProcessImageNameW`, or `proc_pidpath` for the executable path; `/proc/<pid>/stat` field 22, `GetProcessTimes`, or `proc_pidinfo(PROC_PIDTBSDINFO)` for the process start time. A peer whose start time postdates the connection's accept instant, or whose executable path cannot be resolved, is rejected — this bounds, with a small tolerance, the pid-reuse TOCTOU window between accept and resolution, but (see below) does not by itself close it on the Unix listener path. On Linux specifically, that comparison is boot-relative, not wall-clock: `/proc/<pid>/stat`'s `starttime` is compared directly against `/proc/uptime`, both boot-relative to begin with, rather than composing two independently-sampled `SystemTime` values (an earlier version did `boot_time = SystemTime::now() - uptime`, then compared the derived `peer_start` against `accepted_at`) — a realtime-clock step (NTP correction, a manual `date` change) between accept and resolution could otherwise push that composition into either a false rejection or, more seriously, a false acceptance of an actually-reused pid, and Unix connections have no accept-to-first-request deadline bounding how long that window can stay open (Codex review finding). The `/proc/uptime` side of that comparison is captured directly and synchronously at accept time, inside `Connected::connect_info` (the same place the §2 pidfd below is captured), not read again later at resolution time — an earlier version of this fix instead read `/proc/uptime` at resolution time and reconstructed "uptime as of accept time" by subtracting `Instant::now().duration_since(accepted_instant)` (a monotonic-clock elapsed-time reading, captured at accept time) from it. That reconstruction silently composed two clocks with different suspend semantics: Linux's `std::time::Instant` is backed by `CLOCK_MONOTONIC`, which does NOT advance across a system suspend, while `/proc/uptime` DOES include suspended time — a suspend between accept and resolution would under-count elapsed time and over-estimate "uptime at accept," in the worst case letting a pid actually reused during/after the suspend appear to predate acceptance (a second, distinct Codex review finding against this same mechanism). Direct capture at accept time removes the reconstruction step, and the `Instant` it depended on, entirely. macOS's `proc_pidinfo`/`PROC_PIDTBSDINFO` and Windows's `GetProcessTimes` both report only a wall-clock start time with no boot-relative equivalent available without deeper platform APIs, so their own comparisons remain wall-clock-based, with the same (not newly introduced) exposure window a clock step already implied there — see "Accepted residuals" below.

On Linux 6.5+ specifically, the timing comparison above is no longer the sole defense against the accept-backlog pid-reuse window: `PeerIdentity`'s Unix `Connected::connect_info` implementation additionally queries `SO_PEERPIDFD` (`getsockopt(SOL_SOCKET, SO_PEERPIDFD)`) on the accepted socket, obtaining a pidfd the kernel pins to the peer's `struct pid` at the moment of the peer's OWN `connect()` call — not at the later, backlog-dependent moment `UnixListener::accept()` actually dequeues the connection and `connect_info` runs. `resolve_path` polls that pidfd (non-blocking, `POLLIN`) as its last check, after every other Linux check above has run: a still-not-readable pidfd is a hard, non-probabilistic guarantee the peer's pid has not been recycled, since a pidfd becomes readable only once the kernel has fully reaped the process — strictly after its pid number was freed for reuse. This is what actually *closes* the accept-backlog TOCTOU window an earlier version of this design (and of `PeerIdentity`'s own doc comments) claimed the Unix listener path already closed by virtue of having "no queueing gap": `UnixListener::accept()` handing the stream straight to axum only means no queueing gap in this crate's *own* architecture (no intervening channel, unlike the Windows path, which does have one) — it says nothing about the kernel's own accept backlog, which can still dwell a connection an unbounded amount of time between the peer's `connect()` and `connect_info` actually running. Conflating those two claims was itself a Codex review finding (the mechanism's 4th consecutive round of new findings), escalated to a `design-advisor` review whose output is what this paragraph describes. `getsockopt(SO_PEERPIDFD)` failing with anything other than `ENOPROTOOPT` (a pre-6.5 kernel — the only case treated as "unsupported") fails resolution closed rather than being silently folded into "unsupported". The same already-open `/proc/<pid>/exe` file handle — opened directly (not via a second `readlink`) before the pidfd poll, so its own opening is itself covered by that check — is also reused for the modified-after-start freshness check (`fstat` on the fd, not a path-based `stat`) and for hashing in `resolve()`, closing a re-open-by-path TOCTOU window that would otherwise exist between resolution and hashing. Where the pidfd primitive is unavailable — pre-6.5 Linux kernels, and macOS, which has no equivalent primitive at all — the timing comparison above remains the sole defense, unchanged in size from before this fix (see "Accepted residuals" below); Windows already has its own channel-threaded timestamp fix (§1) and is untouched by this mechanism.

The executable file's own `modified()` time is also checked against that same resolved start time (same platform-independent `stat`, same tolerance as the start-time comparison) and rejected if newer — a same-user attacker who atomically replaces (`rename()`) or overwrites the file at an already-running, allowlisted process's own path after that process started must not be able to make the still-running original process authenticate as whatever new content now sits at that path; this narrows, but does not eliminate, that residual (see "Accepted residuals" below). Path resolution (plus every check above) happens before hashing, and the IPC middleware checks the resolved path against the allowlist's `path` values alone (`AllowlistState::has_candidate_path`, no `sha256` comparison, no file I/O) before ever computing the SHA-256 hash — an unenrolled same-user process can therefore no longer force the manager to stream-hash an arbitrarily large file on every IPC connection it opens; only a path already present in `vci-clients.toml` triggers a hash at all. Resolution result is cached for the life of the connection. On Linux, a peer with `TracerPid != 0` in `/proc/<pid>/status` or `LD_PRELOAD` set in `/proc/<pid>/environ` is additionally rejected — this and a future Windows Authenticode / macOS code-signing-requirement selector (tracked as a backlog strength upgrade, not a gate) are hardening on top of the baseline, never a precondition for the baseline to function.

**3. Trust root: an admin-owned allowlist.** **Amended:** the allowlist's location is now a fixed, platform-specific path independent of the ADR-073 config root (`config_root()`) entirely, not `<config root>/vci-clients.toml` as originally specified — `%ProgramData%\vci-service-launcher\vci-clients.toml` on Windows, `/private/etc/vci-service-launcher/vci-clients.toml` on macOS, `/etc/vci-service-launcher/vci-clients.toml` on every other Unix (`vci_service_config::system_config_dir()`, `vci-service-manager/src/main.rs`'s `client_allowlist_path()`). This closes two verified bugs in the original design: (1) two of `config_root()`'s four Windows `config-root-win-*` options (`local-app-data`, `roaming-app-data`) resolve to a PER-USER directory (`%LOCALAPPDATA%`/`%APPDATA%`) the manager's own identity owns outright, permanently failing the trust-root check below and locking out every client on that build; (2) the non-Windows default (`config_root()` returning the bare filesystem root `/` when no Windows feature is active) is unusable on macOS specifically, since Catalina and later seal `/` as a read-only system volume an administrator cannot write to at all. `system_config_dir()` is not gated by any `config-root-*` Cargo feature and resolves to the same fixed location on every build of a given platform. `vci-clients.toml` holds `[[client]]` entries: a unique `name`, plus a `path` and `sha256` selector in this baseline (a Windows `authenticode_thumbprint` and a macOS code-signing `requirement` selector are reserved names for the future strength upgrade in §2, added without changing the enforcement point). At load, whenever the file's content hash changes, AND on every `AllowlistState::ensure_fresh` call regardless of whether the fingerprint changed (both listeners' middleware call `ensure_fresh` per request), the manager verifies that the allowlist file and *every* ancestor directory above it up to and including the filesystem root are **not** owned by, and **not** writable by, the manager's own effective identity — a full content reload additionally re-verifies every `path`-listed executable plus its own ancestor chain the same way. The fast path's own re-verification (`ensure_fresh` calling `verify_trust_root` on the allowlist file directly, before deciding whether to return early) is a fix, not part of the original baseline: `stat_fingerprint` cannot observe a `chown`/ACL change on its own — such a change touches none of the file's content — so gating the trust-root check on the fingerprint alone left a window where the file's ownership/ACL could change into a now-writable-by-the-manager state with no reload, and therefore no re-verification and no revocation, ever triggered by it (Codex review finding). `stat_fingerprint` itself was originally `{modified, len, ino}` on Unix and `{modified, len}` on Windows (timestamp/size/inode metadata, not file content); it is now a SHA-256 hash of the allowlist file's actual bytes on every platform (`struct Fingerprint`'s `content_hash`), a second, independent fix: a legitimate administrator or deployment tool can atomically install a same-length replacement file while preserving `LastWriteTime`/mtime (some deployment tools do this by design; an in-place edit followed by an explicit `utimes`/`futimens`/`SetFileTime` call restoring the original timestamp has the same effect, and on Unix also preserves the original inode for an in-place edit), which a timestamp/size/inode fingerprint cannot distinguish from "nothing changed" — the fast path would then never reload, leaving an already-revoked client's session live indefinitely (Codex review finding). This trades a full read-and-hash of the allowlist file on every `ensure_fresh` call for closing that gap; the allowlist file is expected to be small (a personal/organizational list of enrolled client entries), so this cost is cheap relative to the `verify_trust_root` ancestor-walk syscalls that already run inline on every call regardless. The fast path's own check failing now falls through to a full reload the same way a fingerprint change does, which independently re-runs `verify_trust_root` (redundant, but harmless) and correctly fails closed to an empty entries set, cascading to `removed_client_names` and session revocation exactly as any other verification failure does. The `Fingerprint` a full reload *stores* is now always derived from the exact byte buffer that reload itself read and parsed (a `LoadOutcome::Loaded` result's `content_hash`, computed inside the same `spawn_blocking` call before `parse_and_verify_entries` runs), never from a separately-read `stat_fingerprint` snapshot: an earlier version stored `ensure_fresh`'s own pre-check `stat_fingerprint` result instead, so if the file was atomically replaced (content A → B → A) between that pre-check and the full reload's own separate read, the stored fingerprint could describe A while the stored entries were actually parsed from B — a subsequent read of the real, current A content would then match the stored (also-A) fingerprint and wrongly take the fast path, serving B's stale entries indefinitely (Codex review finding, Finding A). Separately, a whole-file-level reload failure (`verify_trust_root` failing, or the file read itself failing with anything other than "not found") now sets a sticky `last_load_failed` flag on the in-memory state, distinct from a parse-level failure (malformed TOML, a duplicate `name`, or any other failure `parse_and_verify_entries` itself produces after a successful read, none of which are sticky): while set, `ensure_fresh`'s fast path unconditionally falls through to a full reload attempt on every call, regardless of whether the content fingerprint still matches or a trust-root re-check would newly pass, until a load actually succeeds. Without this, an administrator fixing a trust-root failure by restoring the file's (or an ancestor directory's) ownership/ACL — without touching the file's bytes at all — left every client locked out forever: the stored fingerprint from the failed reload matched the unchanged file's fingerprint on every subsequent call, so the fast path kept short-circuiting even after the underlying condition was fixed, and `guard.entries` (zeroed by the failed reload) was never repopulated until the file's content also happened to change (Codex review finding, Finding B). A parse-level failure is deliberately excluded from this stickiness: it is entirely determined by the file's content, so the existing fingerprint-based change detection alone is already sufficient to catch a fix (correcting a syntax error necessarily changes the file's bytes), and making it sticky too would instead waste a full reload and trust-root ancestor walk on every single request while the content stays unchanged. The same sticky `last_load_failed` flag is also set when a *per-entry* `verify_trust_root` check inside `parse_and_verify_entries` rejects one specific listed executable's own ownership/ACL, not only when the allowlist file's own trust-root check fails: `parse_and_verify_entries` now additionally returns whether its empty-entries result was caused by that one specific per-entry check (as opposed to malformed TOML, a duplicate `name`, a missing `path`+`sha256` selector, or an invalid `sha256` — every one of those stays non-sticky, for the same content-determined reasoning above), and `read_and_parse` reports `LoadOutcome::Failed` instead of `LoadOutcome::Loaded` whenever that signal is set. Without this, an administrator fixing a listed executable's own ownership/ACL — again, without ever touching the allowlist file's bytes — left every client on that allowlist locked out until the allowlist file's bytes happened to change for some unrelated reason, for exactly the same underlying reason the allowlist-file-level fix above exists: the recovery is entirely external to the allowlist file's own content, so ordinary fingerprint-based change detection can never notice it on its own (Codex review finding, Finding B). This closes only the *recovery* half of the residual noted in Consequences below (an already-`Failed` per-entry check now correctly keeps retrying until it succeeds); it does not add a fast-path, every-call re-check of each individual enrolled executable's trust root the way `ensure_fresh` already does for the allowlist file itself — a newly broken (but not yet detected) per-entry trust root is still only caught the next time a full reload runs, which remains the residual's own, separate open gap. The manager verifies whichever of the allowlist file, its ancestor chain, or an enrolled executable's own path and ancestor chain is in scope for a given check as **not** owned by, and **not** writable by, the manager's own effective identity (`fstat` + `faccessat(AT_EACCESS, W_OK)` on Linux/macOS — untouched by this amendment; owner SID plus an explicit `AccessCheck` on Windows — not a write-open probe, since a running executable returns a sharing violation there, not access-denied). **Amended:** the Windows `AccessCheck` mask is now NARROWER for an ancestor directory than for the final file (the allowlist file itself, or an enrolled executable's own path) — `DELETE | WRITE_DAC | WRITE_OWNER | FILE_DELETE_CHILD` for a directory, the full `FILE_WRITE_DATA | DELETE | WRITE_DAC | WRITE_OWNER | FILE_DELETE_CHILD | FILE_APPEND_DATA | FILE_WRITE_ATTRIBUTES` for the file — rather than the single combined mask originally applied identically to every path in the walk. This closes a verified bug found after the original design shipped: on NTFS, `FILE_WRITE_DATA`/`FILE_APPEND_DATA` are overloaded on a *directory* object as `FILE_ADD_FILE`/`FILE_ADD_SUBDIRECTORY` (same bit values, different meaning per the Windows API) and only ever grant adding a *new* child, never replacing or deleting an *existing* one — that requires `DELETE`/`FILE_DELETE_CHILD` on the parent, or `WRITE_DAC`/`WRITE_OWNER` to self-grant those; unlike POSIX, where directory write permission genuinely does permit unlinking or replacing any child regardless of that child's own permissions (which is why the Unix `faccessat(AT_EACCESS, W_OK)` check above is correct to treat "writable" as disqualifying for every ancestor uniformly, and was not touched by this amendment). Standard, default NTFS ACLs on a stock Windows install grant ordinary users exactly this "add a new child" right on well-known paths — `Authenticated Users:(AD)` (`FILE_ADD_SUBDIRECTORY`) on `C:\` itself, and `Users:(CI)(WD,AD,WEA,WA)`, container-inherited onto every subdirectory, on `C:\ProgramData` — so the original, undifferentiated mask spuriously flagged every ancestor walk from any standard Windows path as "writable by an untrusted identity" and failed closed, unconditionally, on a stock install, independent of which `config-root-win-*` feature was active or which concrete path was checked (this bug compounded with, and was independent of, the per-user-directory bug the location fix above addresses). `FILE_DELETE_CHILD` (in both masks) covers a directory ACL that grants only the right to delete/replace a child without granting any of the other bits; `FILE_APPEND_DATA` (file mask only) covers append-only access, enough on its own to append a duplicate/malformed `[[client]]` entry and force the next reload to fail closed and mass-revoke every session; `FILE_WRITE_ATTRIBUTES` (file mask only) covers the right to call `SetFileTime` alone — this originally mattered because this crate's Windows fingerprint was only `{modified, len}` (unlike Unix's `{modified, len, ino}`, which had an extra signal a same-length/same-mtime edit couldn't spoof): that bit alone could let a same-user attacker restore the file's original mtime after an administrator's same-length edit (e.g. correcting one client's `sha256`) and silently suppress the reload that edit was meant to trigger. Now that the fingerprint is a content hash on every platform (see above), a timestamp-only right can no longer spoof it on its own, but `FILE_WRITE_ATTRIBUTES` stays in the file mask regardless, as ordinary defense-in-depth against any other unwanted attribute-modification capability. `AccessCheck`'s `ClientToken` argument requires an *impersonation* token, not the *primary* token `OpenProcessToken` returns by default — this implementation duplicates the primary token into an impersonation-level one (`DuplicateToken` with `SecurityImpersonation`) before passing it to `AccessCheck`; passing the primary token directly fails every call with `ERROR_NO_IMPERSONATION_TOKEN`, which is a correctness bug, not a design choice, so it is noted here only because an earlier draft of this implementation shipped it and broke Windows trust-root verification entirely until caught by review. Checking only the immediate parent directory (an earlier version of this check) left a gap: renaming or replacing a directory only requires write access to *that directory's own parent*, not to the directory itself, so a same-OS-user attacker with write access to a higher ancestor could substitute a hostile tree further up the path. Each ancestor in that walk, and the final path itself, is additionally checked with a non-following stat (`lstat`/`symlink_metadata`) and rejected outright if it is a symlink, rather than transparently followed — a symlink's target was never itself verified by this walk, and could be swapped after the check passes; the same rejection applies to the resolved peer executable path just before it is opened for hashing (§2). On Windows, this check also rejects any other reparse point sharing the same `FILE_ATTRIBUTE_REPARSE_POINT` attribute bit — most notably a directory junction (`mklink /J`) — not just the ones `std::fs::FileType::is_symlink()` itself recognizes (`IO_REPARSE_TAG_SYMLINK` only); a junction redirects path resolution exactly the way a symlink does but uses a different reparse tag, so it would otherwise sail through the symlink-specific check untouched (Codex review finding). **Amended:** each entry's `path` is now also required to be absolute — checked in `parse_and_verify_entries` immediately after parsing it into a `PathBuf`, before `verify_trust_root` ever runs on it. Every peer-identity resolver this crate compares an enrolled entry against (`readlink /proc/<pid>/exe` on Linux, `QueryFullProcessImageNameW` on Windows, `proc_pidpath` on macOS; see `peer_identity.rs`) always returns an absolute path, so a relative `path` in `vci-clients.toml` would resolve and be verified against the manager process's own current working directory instead — `verify_trust_root` could genuinely succeed on such an entry, while it could never match any real peer at runtime, permanently locking out the client the allowlist appeared to have successfully enrolled, with no indication of the problem in the load-success log line. This also closes a second, subtler gap as a side effect: `paths_match_case_insensitive`'s own separator-agnostic component comparison (the fix noted above for the forward-slash/backslash mismatch) filters out empty path components, which makes a UNC path's doubled `\\` prefix (`\\server\share\client.exe`) component-collapse to the same sequence a superficially similar *relative* path (`server\share\client.exe`) would produce — rejecting non-absolute entries at parse time makes that ambiguity unreachable in practice, since only genuinely-absolute path forms are ever left to compare against each other, and an absolute local path and an absolute UNC path do not collide under that scheme (Codex review finding). A non-absolute `path` is rejected the same "fail closed, treat the allowlist as empty" way as every other content-determined parse error (malformed TOML, a duplicate `name`, a missing `path`+`sha256` selector, an invalid `sha256`) — it does not set the sticky `last_load_failed` flag described above, since it is entirely determined by the allowlist file's own bytes, not by any external, environment-dependent state. Any verification failure logs an error and treats the allowlist as empty for every client — fail closed, never fail open. Enrolling or revoking a client is therefore an act that requires elevated privileges to perform (editing a file this same-OS-user process cannot write), which is the actual trust root: no human-approval prompt or code-signing infrastructure is required as a precondition, unlike the alternatives this design rejects (an in-band consent prompt is forgeable by the same same-OS-user input-injection techniques ADR-221 already treats as out of scope for a headless manager). **Amended:** `main()` now calls `state.allowlist.ensure_fresh()` once, immediately after `AppState` is constructed, and logs the resolved allowlist path plus the initial load's outcome via the existing `append_log` mechanism — a diagnostics-only addition (every request already triggers `ensure_fresh` on its own via the IPC/TCP auth middlewares in §5, so this changes nothing about enforcement) that makes a misconfigured trust root visible in the manager's own log immediately at startup, rather than only surfacing as a string of confusing 403s once real client traffic arrives.

**4. Sessions.** An IPC-authorized client calls `POST /auth/sessions {scope, ttl_secs?}` and receives `{token, session_id, expires_at_ms, scope}`, where `token` is `vcis1.<base64url(32 CSPRNG bytes)>`. The manager stores only `SHA-256(token) → Session { session_id, client_name, issuer_session: Option<SessionId>, scope, expires_at, expires_at_instant }` in memory (`AppState.sessions: Arc<std::sync::Mutex<SessionTable>>`, the same lock discipline as `AppState.registry`) — the raw token is never stored or logged. `expires_at` (wall-clock `SystemTime`) is the source of truth for `expires_at_ms` in the mint response and for the issuer-TTL-capping arithmetic above, but is not, on its own, sufficient to decide expiry: a backward realtime-clock step (NTP correction, a manual `date` change) after issuance could otherwise let `SystemTime::now()` at validation time remain earlier than `expires_at` for arbitrarily long after the session's real TTL had actually elapsed, keeping an expired bearer token valid (Codex review finding). `Session::is_expired` therefore ORs the wall-clock comparison with a second, monotonic-clock one against `expires_at_instant` (a `std::time::Instant` computed from the same `ttl` at issuance) — `Instant` never moves backward regardless of what the wall clock does, so the monotonic half independently and correctly tracks real elapsed time and closes the gap. This is deliberately conservative in the other direction too: a forward wall-clock step might expire a session via the wall-clock half slightly before its monotonic deadline, a minor availability nuisance (an early re-authentication), never a security issue — this design always prefers expiring a session too early over too late. Two scopes: `admin` (every route, including minting further sessions) and `dashboard` (every route except `POST /auth/sessions`, `DELETE /auth/sessions/{id}` for a session other than itself, and `GET /logs`; `dashboard` may call the read routes — `GET /vci-libs`, `GET /vci-libs/{id}`, `GET /vci-libs/{id}/instance` — but not `POST`/`DELETE /vci-libs/{id}/instance` or `POST /vci-libs/{id}/token`, since a browser-scoped session is the lowest-trust caller this design authorizes; this default is a policy value in a per-route scope table, adjustable later without an architecture change). Only an `admin`-scoped session may mint a `dashboard`-scoped one, with `issuer_session` set to itself and a TTL capped at its own remaining lifetime — this is how a native client (already authorized via §2-3) hands a browser tab it launches a working credential. `POST /auth/sessions` re-checks the calling client's own allowlist membership immediately before minting, under the same `refresh_lock` acquisition described in §6 — the peer-identity check in §2-3 only proves the caller was allowlisted when `ipc_peer_auth_middleware` ran, earlier in the same request; without this re-check, a client removed from the allowlist by a concurrent request's reload in the window between that middleware check and the mint itself would still receive a valid, up-to-24h session (Codex review finding). This re-check matches on the caller's exact `path`+`sha256` selector (`AllowlistState::find_by_identity`, the same match `ipc_peer_auth_middleware` itself already performed), not on `name` alone: an admin changing an existing entry's `path`/`sha256` while keeping its `name` unchanged is already treated by `apply_reload` (§3) as a selector change that revokes the old executable's sessions on reload, and a name-only re-check here would miss that exact case, letting the old, now-deauthorized executable keep minting itself fresh sessions under its former name (Codex review finding). The session is recorded under whatever name that exact selector resolves to as of this reload, not a name the caller had on hand from earlier in the request. The exact bootstrap mechanics (how that token reaches the tab without becoming a long-lived, URL-visible credential) remain the separately tracked backlog item; this ADR defines only the enforcement point that item's output must satisfy. All sessions are memory-only and do not survive a manager restart, by design — there is nothing to persist and nothing for an attacker to steal from disk.

**5. Enforcement.** Two `axum::middleware::from_fn_with_state` layers, each producing one `Extension<AuthorizedClient { name, scope, via }>` on success: the IPC layer performs the §2-3 check (failure: `403 {"error":"client not authorized"}`, one generic message regardless of the specific reason, logged via `append_log` with the reason, pid, and resolved path); the TCP layer parses `Authorization: Bearer <token>` (case-insensitive scheme, matching the existing convention in `vci-service-launcher/src/vci_server.rs`), looks up `SHA-256(token)`, and checks expiry (failure: `401` with a `WWW-Authenticate: Bearer` header, same generic-message rule); a route called outside its caller's scope returns `403`. Existing handlers are otherwise unchanged, except `issue_token` uses `client.name` in place of the previous fixed token subject, and the lifecycle/`append_log` call sites gain the calling client's name for attribution. `ipc_peer_auth_middleware` itself calls `refresh_allowlist()` twice, not once: an early, cheap call before `has_candidate_path` (so an unenrolled peer is rejected before ever paying for a stream-hash of its executable, as above), and a second call immediately before the final `find_by_identity` authorization decision, after `identity.resolve()`'s (potentially slow, for a large executable) hash has completed — without the second call, a client revoked from the allowlist during that hash-computation window would still be authorized against the pre-hash-window snapshot, since nothing else re-triggers a freshness check between the hash finishing and the authorization decision itself (edge-case-hunter finding). This is the missing counterpart, for ordinary protected-IPC-route access, to the re-check §4 already describes for `POST /auth/sessions`' own mint path; severity here is narrower, since IPC re-derives authorization from scratch on every request rather than caching a long-lived token, so the exposure is at most one already-in-flight request slipping through before the very next request self-corrects.

**6. Revocation.** Editing `vci-clients.toml` to remove a client (itself requiring elevated privileges, per §3) drops every session with that `client_name` on the allowlist's next reload. `DELETE /auth/sessions/{id}` (available on either listener; a session may revoke itself or any session it is the `issuer_session` of, transitively) is immediate and cascades to descendants. Neither path requires restarting the manager. The reload-plus-cascade-revoke sequence and, for the TCP listener's bearer-token validation and `POST /auth/sessions`' own membership re-check-plus-mint (see §4), the subsequent session-table work are all serialized under one lock (`AppState.refresh_lock`) so a concurrent caller can never observe "reload already applied" (or validate a token, or mint a session) while that reload's own revocation is still in flight — an earlier implementation serialized only the reload-plus-revoke half, leaving a narrower version of the same race open first across `tcp_session_auth_middleware`'s separate reload and token-validation steps, and later across `create_session`'s complete lack of any re-check at all after `ipc_peer_auth_middleware`'s earlier authorization (both Codex review findings, fixed by combining reload, re-check, and the session-table mutation into one `refresh_lock`-held call per caller). Each of the two combined methods (`refresh_allowlist_and_validate_token`, `refresh_allowlist_and_issue_session`) also samples `SystemTime::now()` itself, as the very last step after the lock is held and the reload is done, rather than accepting it as a parameter captured by the caller before ever acquiring the lock — capturing it earlier could let the wait behind a concurrent caller, plus the reload itself, run long enough that a token or issuer session which had actually already expired by the time validation/minting ran was checked against a stale, too-early clock reading instead (Codex review finding). **Amended:** editing `vci-clients.toml` to remove a client now cascades through the *full descendant tree* of every session that client directly minted, not just the sessions whose own `client_name` matches the removed client — `SessionTable::revoke_by_client_name` used to `retain` purely on `client_name`, missing a session another, still-enrolled client had minted naming the removed client's own session as `issuer_session_id` (§4's cross-client delegation is intentional: any IPC-authorized caller may name any live session as its issuer, regardless of `client_name`), which left that delegated child's own `client_name` set to the *minting* client, not the removed one, so it survived the removal, orphaned but still fully usable until its own TTL expired even though the client its trust chain depended on had been completely deauthorized. `revoke_by_client_name` now seeds the removal set with every session the removed client directly owns and expands it to the same transitive-descendant closure `DELETE /auth/sessions/{id}`'s own cascade (`SessionTable::revoke_cascade`) already computed, via a shared helper (`SessionTable::revoke_ids_and_descendants`) both now call (Codex review finding).

## Consequences

- The admin and catalog routes remain reachable over TCP for every caller that holds a valid session token — including a browser tab, per constraint (B) — while a blind cross-origin request (no `Authorization` header at all) is now rejected structurally: requiring a non-simple header forces a CORS preflight the manager does not answer for an unlisted origin, making the previous CSRF-style exposure on these routes moot independent of the `Host` allowlist, which remains as defense in depth. A future dashboard served from its own origin needs an explicit-origin `CorsLayer` on the TCP router — additive, no change to the auth middleware described here.
- Native clients acquire authority purely by running as an allowlisted executable and connecting over the IPC listener; nothing is written to disk on either side, and per constraint (A) the same baseline mechanism ships on Linux, Windows, and macOS in this PR — no platform ships with client authorization absent.
- `docs/QUICKSTART.md` curl examples change (session minting via `curl --unix-socket`; TCP calls add `-H "Authorization: Bearer <token>"`); `docs/worker-crates.md`, `docs/glossary.md` (new terms: client allowlist, session token, scope), and `vci-service-manager/docs/implementation-notes.md` are updated in this same PR.
- `windows-sys` (already a dependency of `vci-service-config` and `vci-service-launcher`) gains the feature flags this needs in `vci-service-manager`; no new dependency family. The Windows TCP listener additionally binds with `SO_EXCLUSIVEADDRUSE` (via `socket2`, `TcpListener::from_std`) so a same-user process cannot co-bind the port and steal connections without first killing the manager (mio's default binds set neither `SO_REUSEADDR` nor `SO_EXCLUSIVEADDRUSE` on Windows) — the exact `socket2` setter is confirmed against a Windows checkout at implementation time, not assumed here.
- **Accepted residuals, not solved here** (tracked in `vci-service-manager/docs/implementation-notes.md`'s Prioritized Backlog):
  - Process injection into an allowlisted client's own process (ptrace-then-detach, `LD_PRELOAD` beyond the environ check, or `CreateRemoteThread` on Windows) inherits that client's identity and any in-memory session token it holds. macOS's hardened runtime and library validation resist this for a signed client; Linux and Windows do not. Same residual class as ADR-221's own ptrace note. A cheaper, same-user variant in this same class: the peer's pid stays alive the whole time (so Linux's pidfd liveness check, §2, never fires — the pid genuinely was not reused) but the process calls `exec()` into a different binary after connecting, before `resolve_path` runs (e.g. a shell script that `exec`s something else) — `/proc/<pid>/exe` then resolves to the *new* binary, and neither the pidfd check nor any existing check catches it, since nothing here observes the exec transition itself. Possible future narrowing, not attempted in the round that added the pidfd check: macOS's `LOCAL_PEERTOKEN`/pidversion (XNU bumps the pidversion on `exec()`), or Linux peer-fd-table `FD_CLOEXEC` inspection via `sock_diag`.
  - The replace-after-exec check in §2 (executable `modified()` time vs. the peer's own resolved start time) narrows, but does not eliminate, a same-user attacker replacing an allowlisted path's file while the original allowlisted process keeps running: a replacement landing in the same instant as, or fractionally before, the process's own start — or on a filesystem with coarse mtime resolution — could still slip through the timing comparison. A full close of this gap would need macOS code-signing/vnode-identity APIs (and a Windows-Authenticode equivalent), which is exactly the future strength-upgrade selector §2 already names as backlog work, not this baseline's scope.
  - `ensure_fresh`'s fast path (§3) re-verifies the ALLOWLIST FILE's own trust root on every call, closing the staleness window a fingerprint-only gate left open there — but each individual ENROLLED EXECUTABLE's own trust-root state (`verify_trust_root(&entry_path)` inside `parse_and_verify_entries`) is still only re-checked when a full content reload actually runs, i.e. only when the allowlist file's own fingerprint changes (or its fast-path re-check itself fails). A permission/ownership change on an enrolled executable's own path, in isolation — with the allowlist file itself untouched — is not caught by this fix, and remains open: a narrower instance of the exact same staleness class, not yet closed (Codex review finding, not attempted in the round that closed the allowlist-file half). A related but distinct gap — the manager's own *recovery* once such a per-entry failure has already been detected via a full reload — was separately closed by extending the sticky `last_load_failed` flag to a per-entry `verify_trust_root` failure, same as the allowlist file's own trust-root failure already had it (§3, Codex review finding, Finding B); that fix does not narrow this residual's detection-frequency gap, only the recovery path once a failure is detected.
  - The trust root is the OS elevation boundary: on a host where the manager's own user can elevate without a human step (UAC disabled, passwordless `sudo`, a user-owned install directory), it degrades — to fail-closed (an unverifiable allowlist), never to fail-open.
  - The manager's own identity is not attested to a client: a same-user process that pre-creates the named-pipe name before the manager starts, or squats the Unix socket path, can impersonate the manager to a connecting client (it gains no session token by doing so, and the named-pipe case makes the real manager refuse to start rather than silently share the name). Symmetric client-side verification of the server's peer identity is recommended but not enforced here.
  - On Windows, the gap between a closed named-pipe instance's handle actually releasing at the OS level (the underlying tokio/mio implementation defers this to a later reactor tick after the handle is dropped, once outstanding overlapped-I/O completion callbacks run) and the replacement `CreateNamedPipeW` call successfully completing is nonzero. A same-user process could in principle win a `CreateNamedPipeW` call for that pipe name in that sub-millisecond window. This composes with, rather than reopens, the "manager's own identity is not attested to a client" residual immediately above: a same-user process squatting a slot this way still gains no session token by doing so.
  - A session token held in a legitimate client's or a browser tab's memory is readable by a memory-inspecting same-OS-user process for the token's TTL. This design requires holding tokens memory-only (never in a URL, cookie, `localStorage`, or config file) but cannot enforce that requirement on a client it does not control.
  - Revocation does not invalidate a gRPC instance token already minted under ADR-221 (≤ `TOKEN_TTL_SECS` = 600s); rotating that instance's `set_auth_key` would also invalidate every other caller's tokens for that same instance, so it is not done automatically as part of session revocation.
  - The browser bootstrap flow itself (delivering a `dashboard`-scope session to a tab with no long-lived, URL-visible credential, including the command-line race a legitimate launch is exposed to) remains the separately tracked backlog item; this ADR guarantees only that its output is accepted by the enforcement point in §5 with no further architectural change.
  - §2's "postdates the accept instant" rejection has a 100ms implementation tolerance, not a mathematically strict zero-width comparison: the check compares a peer start time against either an accept-time `SystemTime::now()` (macOS/Windows) or, on Linux, a directly-captured accept-time `/proc/uptime` reading (see §2), each derived from two independent, not-quite-simultaneous reads (e.g. `/proc/uptime` plus `/proc/<pid>/stat` on Linux), which a strict comparison would spuriously fail on ordinary reading skew alone. 100ms is sized to comfortably exceed that skew (each read is microseconds of actual I/O; 100ms is roughly one scheduling quantum under load) while leaving only a 100ms-wide sliver of the pid-reuse window open, not the multi-second window an earlier, unjustified 2-second draft of this tolerance left open (edge-case-hunter finding). A same-user attacker would need to win a pid reuse within that 100ms sliver specifically to evade this check.
  - macOS's and Windows's own start-time comparisons remain wall-clock-based (see §2's Linux-specific boot-relative-comparison fix and why it doesn't extend to those two platforms) — a realtime-clock step between accept and resolution on those platforms specifically could in principle push a legitimate peer into a false rejection, or a genuinely-reused pid into a false acceptance, the way it could on Linux too before this PR's fix landed there. Not a newly introduced exposure, just one this PR narrowed on Linux only: macOS and Windows have no boot-relative start-time source available to apply the same fix against without deeper platform APIs.
  - The accept-backlog pid-reuse TOCTOU window itself (a client connects, buffers a request, exits, and the OS recycles its pid onto an unrelated process, all within the kernel's accept-backlog dwell) narrows to zero on Linux 6.5+ via the `SO_PEERPIDFD` pidfd-liveness check (§2) — a pidfd not readable is a hard, non-probabilistic guarantee against this. It remains open, exactly as before this fix (not newly introduced), on two cases with no equivalent primitive available: pre-6.5 Linux kernels (`PeerPidfd::Unsupported`, timing comparison only) and macOS (no pidfd-equivalent primitive at all). Windows is unaffected either way — its own channel-threaded timestamp fix (§1) addresses a different, already-closed gap in its own listener architecture.
  - `GuardedUnixListener`'s `MAX_INFLIGHT_UNIX_CONNECTIONS` cap (§1) bounds how many connections a same-user attacker can hold open at once, but does not guarantee any particular caller wins a given accept slot: under sustained reconnect churn (an attacker rapidly opening and abandoning connections to keep the cap saturated), a legitimate client can still lose the race for the next freed permit to the attacker's next connection attempt — the same class of residual already accepted above for Windows's own fixed pipe-instance pool (the `CreateNamedPipeW` handle-release-race bullet).
  - The same fixed `IDLE_READ_TIMEOUT` (30s) deadline that bounds an attacker's connection also bounds a legitimate one: a long-lived or keep-alive Unix IPC connection is closed once 30s elapses from accept, regardless of how many requests it already completed, and the client must reconnect for any subsequent request. Already true on Windows before this fix; now also true on Unix.
  - **(§3 amendment)** `C:\ProgramData`'s inherited `Users:(CI)(WD,AD,WEA,WA)` ACE grants ordinary users the right to add a new file or subdirectory there — a same-user attacker can race an administrator and pre-create the `vci-service-launcher\` subdirectory, or `vci-clients.toml` itself, before the administrator does. This does not defeat the trust root (the resulting file/directory is still owned by, and writable by, that same-user identity, so `verify_trust_root` correctly fails closed on it) but is confusing without checking the startup log this amendment adds (`main()`'s `ensure_fresh()` call, above) — an installer should create both `vci-service-launcher\` and `vci-clients.toml` itself as an elevated step, so no same-user process ever gets a chance to race it.
  - **(§3 amendment)** The manager cannot run as root/SYSTEM/an elevated administrator account itself: every ancestor in the trust-root walk would then be "owned by, or writable by, this process's own effective identity" and `verify_trust_root` could never pass. This was always implied by this section's own invariant ("not owned by, and not writable by, the manager's own effective identity") but is made explicit here: the manager must run as an ordinary, unprivileged same-OS-user account for client authorization to function at all.
  - **(§3 amendment)** A genuinely admin-less, fully per-user deployment — the actual reason an operator would pick `config_root()`'s `config-root-win-local-app-data` feature for the general `config.toml` file — cannot use client authorization at all under this design: `system_config_dir()` deliberately does not offer a per-user equivalent, since a per-user directory is, by construction, owned by the same identity the trust root must exclude. This is a documented consequence of the trust model (an unprivileged deployment has no elevation boundary to root a trust decision in), not an accidental gap.
  - **(§3 amendment)** This whole mechanism — both the location fix and the Windows `AccessCheck` mask split — remains host-unverified on Windows and macOS: no host of either platform is available in this development environment to actually run it, consistent with every other `UNVERIFIED` callout elsewhere in this file (`vci-service-manager/src/allowlist.rs`'s `windows_impl` module doc comments).
