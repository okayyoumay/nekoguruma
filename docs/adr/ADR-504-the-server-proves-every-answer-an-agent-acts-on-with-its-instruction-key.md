# ADR-504: The Server Proves Every Answer an Agent Acts on With Its Instruction Key

**Date:** 2026-11-22
**Status:** Accepted
**Affects:** design 5.2, 5.3, 6.4, 11.1, 13.3, 14.4, `crates/shared-crypto` (`answer`), `crates/server`, `crates/agent`, `api/openapi.yaml`, `api/asyncapi.yaml`; annotates ADR-456, ADR-459, ADR-461, ADR-466, ADR-467, ADR-468, ADR-471, ADR-478, ADR-493, ADR-495, ADR-497

## Context

The proof exchange authenticates the agent to the server, not the server to the agent (ADR-459, ADR-466). On the local profile the agent talks plain HTTP to `http://127.0.0.1:<port>`, and any process of another OS user that holds that port, because the server is down or has not yet started, can answer. Three things in the agent's behaviour depend on who answers:

- The part-URL answer of the data channel decides where the agent sends a job's bytes (ADR-493), and the download answer decides what it fetches (ADR-497). An impostor could receive diagnostic data.
- Other answers have real effects too: a forged `finished` from the begin, status or completion route removes a ledger entry (and a stored result's file), a second forged `failed` from the status or completion route sets an entry aside (ADR-493, ADR-495), and on the control channel a forged `eventAck` trims the outbox, so the real server never gets those events (ADR-478).
- The uploader opens one connection per request (ADR-495), so the process that holds the port can change between two requests; a check made once, at the exchange, covers nothing after it.

The agent already holds the one key that the server's own signatures verify under: the instruction key it took at registration after checking its fingerprint against the server key ID the operator passed out of band (ADR-461, ADR-463). Nothing else is needed to tell the server from a port holder, if each answer is bound to the request it answers.

## Decision

1. **One more signed purpose under the instruction key.** The server signs a transcript under the tag `nekoguruma server answer proof`, a fifth tag beside the connection proof's, the instruction's and the two registration tags (`shared_crypto::answer`, through `sign_tagged` and `verify_tagged`). The transcript is the layout version (1, 4 bytes), the audience (the canonical origin the agent pinned at registration, the rules of `proof`), the agent ID, the agent's 32-byte nonce, the request's method, the request target, the SHA-256 of the request body, the answer's status and the SHA-256 of the answer body. Variable-length fields are length-prefixed. There is no timestamp (design 16.3). Method, target and request digest bind an answer to the request it answers, so a recorded answer to one request is no answer to another; the agent's fresh nonce makes it an answer to this attempt. Each digest is over the body's content bytes, after transfer decoding; these routes use no content coding in either direction. The request digest is over the bytes read at the route's body step, and is the SHA-256 of zero bytes when there are none; the upgrade's request body is not read and counts as absent, and the 101 has no body. The request target is the path and query of the request target as the HTTP parser gives it: an origin-form target byte for byte, and for an absolute-form target its path and query (the audience carries the rest, and the request guard has judged the authority), not normalized. A fragment is not part of it. The agent sends origin-form targets only. The rule a target must meet is `answer::check_target` (1 to `MAX_TARGET_LEN` visible ASCII bytes, beginning with `/`), and the server's shape steps call that one function. No header of an answer is bound, so the agent takes nothing from a header of a proved answer but the proof: `Retry-After` is read only on statuses that are not results, where it can only lengthen a wait within 1 to 60 seconds, and `Sec-WebSocket-Accept` and `Sec-WebSocket-Protocol` are checked against what the agent itself sent. A route that would put a result in a header must put it in the body.
2. **Two headers.** The request carries `Ngr-Nonce`, the agent's 32-byte nonce in base64. The session route reads no such header: the nonce of its body is the nonce of its answer's proof, and every 200 of that route is proved; a header sent to it is not read, since a header that had to equal the body would add only a way to get it wrong (ADR-466 item 9 reasons the same way). The answer carries `Ngr-Server-Proof`, the base64 of the 64-byte signature. The server signs the exact bytes it sends; the agent verifies against the bytes it received, before it parses them.
3. **Which answers are proved.** The proof is required exactly where an answer is a result: the session route's 200, the control upgrade's 101 (the proof is a header of the 101), and on a data route the statuses it promises: begin 200 and 201, part URL 200, status 200, completion 200, 202 and 409, download 200. Such an answer without a valid proof is unproven. Any other status is classed by its status as before (ADR-471 items 3 and 4, ADR-495 item 1, ADR-497), with or without a proof, and the agent checks none on it. On the upload routes none of those classes changes anything durable: a pass-over is in memory and an abandon needs the agent's own check of the source (ADR-495 items 6 and 7). The download route differs, because its refusal ends the fetch: there every answer that would end it (400, 404, 413, 500, another 4xx, an answer the route does not promise) is taken only with a valid proof, and without one is unproven. The server proves every answer of a data route it sends after the token and the agent's row are judged, whatever its status, so ADR-497's 404 is proved; a refusal from before that point is unproven to the fetcher and is retried. Unproven and unanswered attempts count against a caller's bound; running out of them is a refusal of service, which this record does not prevent; the caller reports it as the server being unavailable, never as a refusal. Never an answer before the agent is authenticated, never the challenge, never registration (which has its own signed answer, ADR-463). A 401 on a data route, which the server cannot prove, stays `Reauthenticate`: the token is dropped, one exchange follows at once and the request is repeated once; a second 401 is a retry with the token dropped (the rule of `data_token::Holder::unauthorized`). An impostor that answers 401 thus gets one exchange, cannot prove its 200, and leaves the agent at `session-unproven` and the cap.
4. **The data routes and the upgrade prove only when asked.** Their answers are proved only when the request carries a nonce; a request with no nonce is served as before, so a browser or a script that calls them is unaffected. A nonce that is present and malformed (more than one header value, or not the canonical padded base64 of 32 bytes) is a 400 where the route judges the request's shape: on a data route at the shape step, after the request guard, the method and the body and before the token (ADR-493's order). It consumes nothing. On a data route a request that carries a nonce and whose target is one the transcript cannot take (`answer::check_target`) is a 400 at the same step, before the token and before the handler changes anything, so a nonce-bearing request that passes the shape step is always proved once the agent is authenticated. On the control upgrade the order is: the method (405), the token (401), the WebSocket request (400), the subprotocol (400), then, when the request carries a nonce, the nonce (400) and the target (400); a request refused before this record is refused the same way; then the proof is signed and the 101 answered. The session route judges the target at its shape step, on every request (every 200 of it is proved): a target that fails the rule is a 400 that consumes nothing, so the challenge is not taken. After these checks a transcript that still cannot be built is a defect and is handled as a signing failure: an unproved 503, logged without the target. If the proof cannot be made (the transcript or the signature), the answer is replaced by an unproved 503 and logged, never sent with its promised status; for the upgrade the server signs before upgrading, and for the session route the minted token is discarded.
5. **The proof rests on the listener's address being unshared.** The server's listener is bound to `127.0.0.1` itself, never the wildcard address, and sets no address-sharing option (`SO_REUSEPORT` anywhere, `SO_REUSEADDR` on Windows), so no other process can receive connections to that address while the server listens: a process can stand in the server's place, not beside it. Linux refuses any second bind of a listening address. On Windows the vendor's rules refuse another account's bind of an address whose first socket did not opt into sharing; whether they also refuse the server's own account is decided by the probe, and where it is not refused the listener takes exclusive address use (`SO_EXCLUSIVEADDRUSE`), which refuses every account. A process of the server's own account could read the instruction key in any case (ADR-462). The probe: the listener's local address is `127.0.0.1`; a second bind of that address with address reuse fails (on Unix also with port reuse); where a wildcard listener on the same port can be bound, every connection to `127.0.0.1` still reaches the server. Decision on the `core-windows` result: it passes with the default bind -> nothing more (record it in Consequences when it is known); a reuse bind succeeds or a connection reaches the wildcard listener -> the listener sets `SO_EXCLUSIVEADDRUSE` on Windows and the probe must then pass; the wildcard check still fails with exclusive use -> stop and ask the maintainer. The proof authenticates answers; it does not protect a connection against a party that can sit between the agent and a running server (an administrator who redirects loopback or debugs a process): such a party could forward requests and proved answers, read the token and a presigned URL, and write control frames after a forwarded 101, since only the 101 is proved. That is outside this record; TLS on the standard profile answers it.
6. **The agent requires the proof on every `http` origin.** It verifies against the pinned instruction key, with the audience from its registration record. `https` origins are left to the standard-profile work (ADR-463 item 13), where TLS and the proof can be combined or the proof waived by design.
7. **An unproven answer is not a result.** An answer that is required to carry a proof (item 3) and has a missing, malformed or wrong one is treated as no answer at all, retried at the 60-second cap of the existing back-off rather than the short steps, so a port holder is not hammered and a restarting server is found within a minute. The classes are `session-unproven` (the exchange), `upgrade-unproven` (the control upgrade) and, for the data routes, the retry class `Retry` with the reason "unproven", which also drops the session token. A status that is not a result keeps its own class and is not checked. One warning is logged per class until the class clears. No new exit code is added, and nothing ends the session or erases state: a forged answer never removes a ledger entry or trims the outbox, and an unproven one costs only time.
8. **The interfaces change in place.** `/api/v1` and the subprotocol `ngr-control.v1` gain the headers without a new version, because a request without a nonce is served as before, and the agent and the server change in the same series.
9. **A key reset stops connections until re-registration.** When the server's instruction key is replaced, every registered agent's proof check fails and it stays unproven until it registers again; the warning names re-registration. This is accepted: it is what the key's role in job instructions already costs (ADR-462, ADR-463).
10. **Built in three steps**, each a change of its own: this crate's module with the design text; then the server (`prove_answer`, one helper, wired into each proved route) and the API descriptions; then the agent's verification, its documentation and the tests with an impostor that holds a real loopback port.

### Alternatives rejected

- A proof at the exchange or at `hello` only: the port holder can change between requests, and the uploader's one connection per request makes that the normal case.
- A separate identity key for the server: a second key to register, pin and rotate for no property the instruction key lacks.
- A signature inside the JSON bodies: it would have to be checked after parsing, and the routes' bodies are not all JSON (the 101 has none).
- An HMAC under a session key: a second primitive beside the one signature scheme (ADR-459), and the server's session store would hold a live secret where it keeps only a token's hash (ADR-466).
- A delegated key (a per-session key signed by the instruction key): deferred; it would let the instruction key stay offline but adds a certificate to carry and check.
- A `hello` member of the first control frame for the upgrade: the 101 would then be unproven for the time before the first frame; a header proves it at once.

## Consequences

- The listener probe's first `core-windows` run (the server's listener bound with default options) refused a same-account bind of the listener's address with address reuse, so the server's listener takes no exclusive address use: item 5's first outcome. The probe keeps running there and decides again if the bind or the runner image changes.
- A process that holds the port in the server's place (the server is down or not yet started) can no longer be sent a job's bytes, direct a download, or have a forged answer, acknowledgement or command accepted. It can refuse service and read what the agent sends before the first unproven answer: the agent's proof, a token that died with the server that issued it, and one request body. Design 14.4 uses the same "in the server's place" wording.
- A proved "revoked" answer is not built: on the local profile a revoked agent's answer is a 401 like an expired token's and carries no proof, so the agent cannot yet tell revocation from an impostor. Erasure on revocation depends on it and is a backlog item.
- The object server's presigned part URL still names a loopback port of the server's child; a process that takes that port after the whole stack has died could receive a part. That window is a backlog item, and so is the pinned RustFS object server's listener options: whether another account can share its address is not yet checked. The server's own listener is covered by item 5.
- Every data-route handler gains one signing step after its judgement, which is async (the key may be behind a signer); the server's tests and the agent's fakes need a helper that signs.
- The wire gains two headers and the agent a verify step on four paths; the test harness of the agent's integration tests changes with them.
- Over the Internet, with TLS, the proof is redundant protection until the standard profile decides whether it stays.
