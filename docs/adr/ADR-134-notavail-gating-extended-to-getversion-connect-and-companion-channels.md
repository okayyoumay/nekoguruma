# ADR-134: `PDU_MODST_NOT_AVAIL` Gating Extended to `GetVersion`, `ConnectComLogicalLink`, and Every Companion-Channel Open (closes ADR-131's two recorded residuals)

**Date:** 2026-07-26
**Status:** Accepted (extends ADR-131)
**Affects:** `j2534-0404-service/src/service/rpc_module.rs`, `j2534-0404-service/src/service/rpc_link.rs`, `j2534-0404-service/docs/implementation-notes.md`, `j2534-0404-service/docs/iso22900-2-conformance-audit.md`, `docs/rpc-api-guide.md`, `docs/adr/ADR-131-module-connect-not-avail-recovery.md`

## Context

ADR-131 made `PDU_MODST_NOT_AVAIL` sticky until an explicit `ModuleDisconnect`: `rpc_module_connect` and `rpc_create_com_logical_link` both read `module_state.status` immediately after their `ensure_open_device_for` call succeeds, while still holding the returned `device_id` guard (closing the TOCTOU window a concurrent `ModuleDisconnect` would otherwise open), and reject with `PDU_ERR_MODULE_NOT_CONNECTED`/`PDU_ERR_FCT_FAILED` if the module is not `PduModstReady`.

ADR-131 explicitly deferred two gaps to `j2534-0404-service/docs/implementation-notes.md`'s Prioritized Backlog rather than closing them in that PR:

1. `rpc_get_version` (`rpc_module.rs::rpc_get_version`) calls `ensure_open_device_for` directly and never checks `module_state.status` — a `NotAvail` module's already-open device lets it lazily "succeed" through the no-op branch, returning stale version info instead of `PDU_ERR_MODULE_NOT_CONNECTED`.
2. `rpc_connect_com_logical_link` (`rpc_link.rs::rpc_connect_com_logical_link`) is not gated on `module_state.status` at all — a CLL created while the module was Ready, left unconnected, and only connected after the module went `NotAvail`, still successfully opens a physical channel and communicates. ADR-131's own text scoped this residual narrowly to `ConnectComLogicalLink` itself and called full closure ("auditing every code path that can reach `spawn_new_shared_channel`/an existing-shared-channel join for the same TOCTOU discipline") "a materially larger change... deferred rather than chased further here."

Auditing every call site reachable from `spawn_new_shared_channel` (`rpc_link.rs:1562`) for this PR found it has **three** call sites, not the one ADR-131's residual named:

- `rpc_link.rs:2033`, inside `rpc_connect_com_logical_link` itself (the primary channel — the one ADR-131's residual names).
- `rpc_link.rs:2530`, inside `ensure_uudt_companion_channel` (`rpc_link.rs:2416`), which is itself called from three places:
  - `rpc_link.rs:2116`, inside `rpc_connect_com_logical_link`'s own tail (same RPC invocation, after the primary channel connects).
  - `rpc_link.rs:2617`, inside `probe_can_channel_mode` (`rpc_link.rs:2604`), itself only called from within `rpc_connect_com_logical_link`.
  - `rpc_link.rs:2368`, inside `promote_unique_resp_id_table` (`rpc_link.rs:2305`), called from `events::handle_update_param` (`events.rs:8044`) as part of `CoptUpdateparam` execution on an **already-connected** CLL — entirely independent of `ConnectComLogicalLink`, reachable long after a module went `NotAvail` post-connect (e.g. a client sets a UUDT response id via `SetUniqueRespIdTable` on a CLL that connected before the hard error, opening a brand-new companion channel on a module the service's own status considers unavailable).

The third path sits squarely inside the scope ADR-131's backlog wording named ("every code path that can reach `spawn_new_shared_channel`... for the same TOCTOU discipline") even though ADR-131's own prose only discussed `ConnectComLogicalLink`. Gating only `rpc_connect_com_logical_link` would leave this path open and reproduce the same shape of gap that took four Codex review rounds to close on the original PR (#143).

**What the spec says about `GetVersion`.** ISO 22900-2:2009(E) §9.4.29.2 NOTE 1 lists exactly four functions a client may call before `PDUModuleConnect`: `PDUGetResourceIds`, `PDUGetObjectId`, `PDUGetConflictingResources`, `PDUGetStatus`. `PDUGetVersion` is not among them, and its own Table 13 lists `PDU_ERR_MODULE_NOT_CONNECTED` as a legal return — NOTE 1 mandates rejecting `PDUGetVersion` whenever the module is not `PDU_MODST_READY`, the same as every other module-scoped call this service already gates.

**What the spec says about `ConnectComLogicalLink`.** ISO 22900-2 §9.4.11.5's Table 19 lists `PDU_ERR_MODULE_NOT_CONNECTED` as a legal `PDUConnect` return.

## Decision

Extend ADR-131's check — a scoped read of `module_state.status` while holding the relevant `device_id` guard, rejecting via `Self::module_not_avail_status` when not `PduModstReady` — to three additional choke points:

1. **`rpc_get_version`** (`rpc_module.rs`): the check is inserted immediately after `ensure_open_device_for` succeeds, in its own scoped block, exactly mirroring `rpc_create_com_logical_link`'s existing shape. The block is dropped before the `api` lock is acquired a few lines later, preserving this service's `device_id` -> `module_state` -> `api` lock order (the reverse order is used elsewhere, so the scopes must not overlap).

2. **`rpc_connect_com_logical_link`** (`rpc_link.rs`): the check is inserted immediately after `ensure_open_device(handle)` succeeds (before the `shared_channels` lock and the existing-channel-vs-new-channel branch). The returned `device_guard` is held continuously from that point through the entire join-or-create decision and the native `PassThruConnect` call in `connect_new_physical_channel` (unchanged span), so no concurrent `ModuleDisconnect` — which needs the same `device_id` lock — can interleave between the check and the physical connect completing. `rpc_connect_com_logical_link` has no `module_handle` of its own (only `cll_handle`, and this service opens at most one device at a time — ADR-107), so the rejection's `requested` parameter is read from the guard's own `(u32, DeviceId)` content rather than from the request.

3. **`ensure_uudt_companion_channel`** (`rpc_link.rs`): the check is inserted immediately after its own `ensure_open_device(handle)` call, before its `shared_channels` lock. This single choke point covers all three of its callers uniformly — the two reachable from `rpc_connect_com_logical_link` (its own tail, and `probe_can_channel_mode`) and, critically, `promote_unique_resp_id_table`'s `CoptUpdateparam`-triggered path, which has no other gate anywhere in its call chain.

Gates 2 and 3 are both required and neither substitutes for the other: gate 3 does not cover the primary channel (the join branch or `connect_new_physical_channel`), and gate 2 does not cover the companion-channel open triggered by `CoptUpdateparam`, which never passes through `rpc_connect_com_logical_link` at all.

All three gates follow the same discipline as ADR-131's original two: a `{ ... }`-scoped `module_state.lock().await`, taken while already holding the operation's `device_id` guard and released before any other service lock (`shared_channels`, `logical_links`, `api`) is acquired — preserving the established `device_id` -> `module_state` -> everything-else order (ADR-107 addendum, ADR-131 Decision).

**Caller behavior on rejection**, already safe at every one of `ensure_uudt_companion_channel`'s call sites without further change: its two callers inside `rpc_connect_com_logical_link`'s tail (the direct call and `probe_can_channel_mode`) and `promote_unique_resp_id_table`'s call already treat a `Status` error from this function as a best-effort failure (`warn!` and continue, or `dual_capable = false`) rather than propagating it — none needed new error-handling to accommodate the new rejection path.

## Alternatives Considered

1. **Gate only `rpc_connect_com_logical_link`, leave the `CoptUpdateparam` path as a new, separate, narrower residual.** Rejected: the committed backlog wording explicitly scoped closure to "every code path that can reach `spawn_new_shared_channel`... for the same TOCTOU discipline," and the `CoptUpdateparam` path is inside that scope even though ADR-131's prose never mentions it. Leaving it open predictably reproduces the same shape of gap a fifth time.
2. **Gate each of `ensure_uudt_companion_channel`'s three callers individually instead of the function itself.** Rejected: three insertions instead of one, and any future caller of `ensure_uudt_companion_channel` would silently bypass the gate. Gating the function itself makes it the single, permanent choke point for every companion-channel open regardless of caller.
3. **Gate the whole of `rpc_connect_com_logical_link` before `autodetect_sae_j1850_flavor`** (which runs before the device-open call gate 2 attaches to). Rejected: `autodetect_sae_j1850_flavor` internally acquires `device_id` itself and is not reentrant with an outer `device_id` guard, so moving gate 2 earlier in that function would require restructuring that probe's own locking. Instead fixed at its actual source — see the Correction below — by gating `probe_sae_j1850_flavor` itself (which already acquires its own `device_id` guard at its own `ensure_open_device` call), the same shape as gate 3 inside `ensure_uudt_companion_channel`.
4. **Module-wide teardown of already-communicating channels the instant a module goes `NotAvail`.** Rejected: contradicts ADR-131's own per-channel hard-error scoping (`handle_channel_hard_error` tears down only the channel that actually failed, deliberately leaving sibling channels live). This ADR's line is the same one ADR-131 already drew: existing channels keep communicating; only *new* native opens/joins are rejected while `NotAvail`.
5. **Also harden `probe_can_channel_mode`'s cache write-back (`rpc_link.rs:2634-2635`) to additionally require `module_state.status == PduModstReady`.** Considered and taken as a small additional hardening (not a separate residual): the epoch-tagged cache already self-heals on the mandatory recovery path (a fresh `PassThruOpen` bumps `device_epoch`, invalidating any stale entry), but requiring `Ready` at write-back time closes even the narrow window where a hard error lands between this ADR's gate passing and the probe's own write-back, at negligible cost (one extra scoped `module_state` read already available from the surrounding function).

## Consequences

- `GetVersion`, `ConnectComLogicalLink`, and every path that can open or join a companion CAN channel now uniformly reject with `PDU_ERR_MODULE_NOT_CONNECTED` (`module_not_avail_status`) while a module is `PduModstNotAvail`, matching `ModuleConnect`/`CreateComLogicalLink`'s existing behavior and closing both of ADR-131's recorded backlog items (`implementation-notes.md` lines ~560-561, struck by this ADR).
- **Closed by the Correction below, not left as a residual:** `autodetect_sae_j1850_flavor`'s SAE J1850 flavor probe (`probe_sae_j1850_flavor`) runs inside `rpc_connect_com_logical_link` before gate 2, on every not-yet-connected `SAE_J1850`-family CLL. See the Correction section for why this is not the harmless, read-only residual this ADR originally described.
- **Accepted residual for the NEW-channel path only (Codex round 5, PR #149; supersedes this bullet's original "parity" wording, which was inaccurate; re-scoped by the round-6 Correction below, which closes the EXISTING-channel-join case this bullet's convergence argument did not actually cover):** the gates' `device_id` guard serializes against `ModuleDisconnect` only. `events::handle_channel_hard_error` never acquires `device_id`, so a hard error on another channel can set `NotAvail` between a gate passing and the gated native work completing — a window materially wider than `rpc_module_connect`/`rpc_create_com_logical_link`'s, whose post-check work is negligible (the original wording's "identical race" claim did not hold up). Accepted for a fresh `PassThruConnect` because no lock can close it and the outcome stays convergent: the handler is only the *detector* — the physical loss precedes it by up to one poll interval, so serializing against it (or re-checking `module_state` before each native call) would only reorder the report without preventing a connect from completing on an already-dead module; `PassThruConnect`'s own result is the freshest health evidence available and is already consulted (a genuinely dead device fails the native call and the RPC errors out regardless), and a channel that slips through this way is torn down by its own first RX poll via the same `handle_channel_hard_error` sequence once the poll task actually runs against it. Serializing the detector on `device_id` was considered and rejected: it would block the RX-poll hard-error path (and the `LOST_COMM` event/CoP-cancellation/tx-suspension-recompute sequence it drives) behind whichever RPC currently holds `device_id` across native connect/probe timeouts, delaying loss-of-comm delivery to every client for zero closure of the actual physical race. One that slips through on a device that's merely lost comm on a DIFFERENT channel is exactly the healthy-sibling case ADR-131's per-channel isolation design already permits.
- The existing regression test `rpc_link.rs::tests::connecting_an_already_created_cll_does_not_clear_not_avail_status` (added by ADR-131's Amendment to pin that `ConnectComLogicalLink` succeeded on a pre-existing CLL without corrupting `module_state`) is rewritten: its premise — that the connect succeeds — is inverted by this ADR's gate 2. It now asserts the connect is rejected with `PDU_ERR_MODULE_NOT_CONNECTED` and that `module_state` remains `NotAvail`.
- **Deliberately not gated, raised and confirmed intentional during Codex review, PR #149:** `rpc_connect_com_logical_link`'s pre-existing `if link.connected { return Ok(...) }` idempotent no-op (ADR-126, unrelated to this ADR) runs before gate 2 and is not itself checked against `module_state.status`. This is reachable only by a CLL whose own channel was never hit by a hard error: `events::handle_channel_hard_error` clears `connected = false` for every CLL on the channel that actually failed, so a CLL reaching this fast path with `connected == true` is, by construction, a genuinely-unaffected sibling still communicating on a healthy channel — exactly the case ADR-131's per-channel isolation design says should keep working. Returning success here is a true statement about that one CLL, not a stale/unrevalidated claim about the module the way `ModuleConnect`'s original bug was, and no native call or new channel open/join happens on this path for gate 2 to guard.

## Correction (Codex review, PR #149): the J1850 autodetect residual was mischaracterized as read-only — it transmits on the vehicle bus

This ADR's Alternative #3 and its first Consequences bullet originally accepted `autodetect_sae_j1850_flavor`'s pre-gate-2 window as harmless because its probe was described as "read-only." That description is wrong for the `ISO_15031_5_ON_SAE_J1850` (OBD-active) resource: `probe_sae_j1850_flavor`'s `active_probe` branch (`rpc_link.rs`) builds and transmits a real OBD-II functional Mode 01 PID 00 request via `api.write_messages`, on a freshly `api.connect`-opened probe channel, for each VPW/PWM candidate — genuine bus traffic, not a passive listen. So a `ConnectComLogicalLink` call on an unconnected `SAE_J1850`-family CLL created before its module went `NotAvail` would still transmit this probe request once per candidate before gate 2 (added by this ADR, running immediately after `autodetect_sae_j1850_flavor` returns) went on to reject the connect — exactly the class of gap this ADR exists to close, just one step earlier in the same function.

**Fix:** `probe_sae_j1850_flavor` already acquires its own `device_id` guard via its own `ensure_open_device` call (needed regardless, to reach `device_id` for `api.connect`) — the same shape `ensure_uudt_companion_channel` (gate 3) uses. A fourth gate is added there, immediately after that guard is acquired and before the candidate-probing loop: if `module_state.status != PduModstReady`, the function returns `J1850ProbeOutcome::Fallback(J1850VPW)` without opening any probe channel or transmitting anything, the same fallback the pre-existing "could not open device at all" branch a few lines above already uses. `Fallback` (unlike `Conclusive`) is never written back to the `j1850_bus_flavor` cache (per that cache's own doc comment), so this cannot poison the cache with a conclusion no real candidate was actually probed for. `ConnectComLogicalLink`'s own gate 2, immediately after this function returns, still rejects the connect as before — this fourth gate only prevents the wasted (and, for the OBD-active resource, bus-visible) probe traffic from happening first.

This is not a new residual, an amendment layered on top of an accepted trade-off, or a narrowing of scope — it is a factual correction to this ADR's own reasoning, now closed in the same PR that found it.

## Correction (Codex review round 6, PR #149): the accepted-residual convergence argument was false for the existing-channel-join branch

The round-5 accepted-residual bullet above justified leaving the `device_id`/hard-error TOCTOU window open by arguing the post-race state is always convergent: "a channel that slips through on a truly dead device is torn down by its own first RX poll via the same `handle_channel_hard_error` sequence." That argument is correct for a *fresh* `PassThruConnect` (a genuinely dead device fails the native call outright, and the RPC errors out with no channel ever created), but false for the **existing-channel-join** branch in `rpc_connect_com_logical_link` and `ensure_uudt_companion_channel`: joining reuses `sc.channel_id` from the `shared_channels` map entry with no native call and no liveness check at all. If a hard error on that exact channel has already run `handle_channel_hard_error`'s per-CLL teardown (clearing `connected`/`channel_id` on the CLLs that owned it) but the gate's `module_state` read lands in the gap before `module_state` is set to `NotAvail`, the join branch sees a `SharedChannel` entry that still looks live — `ref_count`, `channel_id`, `tx_queue` all present — and publishes a brand-new CLL as `connected` on it. But that channel's poll task is exiting (or has already exited): there is no future RX poll to ever "torn it down" the way the round-5 argument assumed. The result is not a transient, self-healing race — it is a **permanent, silent hang**: the CLL reports `connected`/`PDU_CLLST_ONLINE`, every COP queued against it goes into a `tx_queue` whose receiving poll task is gone, and nothing in this service ever revisits or corrects it.

This is not something ADR-134's gates introduced: at the pre-PR commit, `rpc_connect_com_logical_link` had no `module_state` gate at all, so the same zombie-join was reachable deterministically, for an unbounded window, by any concurrent connect after any hard error — this PR's gates *narrowed* the window from unbounded to milliseconds, they did not create it. But ADR-131's backlog wording, which ADR-134 claims to close in full, scopes the work as covering "every code path that can reach `spawn_new_shared_channel`/**an existing-shared-channel join** for the same TOCTOU discipline" — the join branch's TOCTOU discipline is squarely this PR's committed scope, and the round-5 bullet's own convergence claim, now shown false for that branch, is this repo's own bar (per the J1850 Correction above) for fixing in-PR rather than deferring.

**Fix:** `SharedChannel` gains a `dead: bool` field (`service.rs`), `false` at construction (`spawn_new_shared_channel`). `handle_channel_hard_error` (`events.rs`) now marks the entry matching the failed `channel_id` as `dead = true`, inside the same `shared_channels`-holding critical section it already uses for its per-CLL teardown (before `module_state` is ever touched) — so no interleaving connect can observe a live-looking entry for a channel that critical section has already processed. Both existing-channel-join branches (`rpc_connect_com_logical_link`, `ensure_uudt_companion_channel`) check `sc.dead` first, before their own reciprocal-filter checks, and reject with `module_not_avail_status` if set. The entry is deliberately **not removed** from `shared_channels` at hard-error time (only marked): CLLs whose channel just failed keep their `channel_key` (pre-existing behavior, unchanged) specifically so a later `Disconnect`/`Destroy` can still find and release the shared-channel ref via `release_shared_channel_ref` — removing the entry early would let a fresh connect reinsert at the same key, after which that stale CLL's later teardown would decrement (and potentially natively disconnect) the *new* channel out from under a live CLL. `release_shared_channel_ref` already no-ops gracefully if its key is absent, so it tolerates the entry being pruned normally once the last referencing CLL disconnects.

Alternatives considered and rejected: making the NotAvail transition literally atomic with teardown (Codex's literal suggestion) would require every gate to hold `module_state` across `shared_channels` too, a codebase-wide lock-order change for the same closure the tombstone gets far more cheaply; a native liveness probe before joining doesn't exist (J2534 v04.04 has no health-check primitive, per ADR-131's own Alternative #2); pruning the map entry at hard-error time was rejected above for corrupting a later CLL's ref-release.

Regression tests: `rpc_link.rs::tests::connect_com_logical_link_rejects_a_dead_shared_channel_even_when_module_is_ready`, `::ensure_uudt_companion_channel_rejects_a_dead_shared_channel_even_when_module_is_ready` — both insert a `dead: true` `SharedChannel` directly and confirm the join is rejected while `module_state.status` is deliberately left `Ready`, pinning that the `dead` check itself (not the pre-existing `module_state` gate) is what rejects the join.

**Regression test, and its own honestly-scoped limitation** (a second Codex review round on this same fix): `rpc_link.rs::tests::probe_sae_j1850_flavor_skips_the_active_probe_when_module_marked_not_avail` must register `HANDLE` as a live entry in `logical_links` before calling — without it, `ensure_open_device`'s `cll_liveness` check rejects the handle as unknown before this gate ever runs, returning the identical `Fallback(J1850VPW)` value via the wrong branch entirely, which would have let the test pass even with the new gate deleted. With `HANDLE` live, the test still cannot fully prove "zero native calls occurred" — only that the function returns `Fallback`, which a genuinely-run-but-inconclusive probe against the mock's default silent bus would also return — because closing that gap needs a `MockBackdoor`-style raw FFI dlopen of the mock library this unit-test module doesn't have. Recorded as a P3 test-coverage residual in `implementation-notes.md`; the fix's correctness itself was verified by direct code inspection, independent of this test's own coverage boundary.
