# ADR-486: The Agent Judges a Job's Start Deadline Against the Later of Its Clock and a Persisted Highest Issue Time

**Date:** 2026-11-17
**Status:** Accepted (the first Consequence, that the duplicate check must come before the deadline check, done by ADR-489)
**Affects:** design 5.3, 6.7; `docs/glossary.md`, `api/asyncapi.yaml` (`jobState`, `ackCommand`); `crates/agent` (`deadline`, `control::channel`, `control::gate`, `connect`), `crates/agent/docs/ngr-agent.md`, `crates/agent/docs/operational-log.md`; details ADR-461 item 6, reuses ADR-483's path

## Context

ADR-461 item 6 gave the agent a rule for the start deadline in a signed instruction: compare it with the later of the device clock and the highest issue time verified so far, and persist that time. Nothing enforced it, so a command delivered after its deadline would have been taken. The server never delivers past a deadline (it judges by its own receive time, design 16.3), so the agent's check is a staleness guard for a command that waited in a redelivery, a restart or a reconnect; it is not a defence against the device's own user (design 6.6). The device clock can be wrong (a reset to 1970, a battery-less board, a user's change), and the highest issue time is the one fact the signed bytes give that a wrong clock cannot take back. The operator refusal of ADR-483 already records a terminal job state before the acknowledgement, and the expiry reuses that path.

## Decision

1. **The file.** The highest issue time is kept in `<state>/registration/<agent-id>.issue-mark.v1.json`, one JSON object with the format version, the agent ID and the value (`highest_issued_at`, Unix seconds, a `u64`). The file is named after the agent ID and holds it again, so a re-registration (a new agent ID, ADR-461 item 8) reads no file and starts at 0, leaves the old file alone and needs no change to `register`. It is written whole: a temporary file made at mode 0600, written and synced, renamed over the file, the directory synced (on Windows the file is reopened and synced, as the registration record and the outbox do). A stale temporary file is removed by the next write; one that cannot be removed fails that write. The store takes its own lock file `issue-mark.lock` in the same directory, as the outbox does, so a write still running after a stop makes the next open fail as in use.
2. **The reader.** Opening reads the file once, after the connection and registration locks are held. An absent file is 0 and is not created; only the first write of a value above 0 creates it. A file that does not read back is corrupt and is never repaired or read as 0: it is not a regular file (a symbolic link or a directory, by `symlink_metadata`, as `Record::read` does), is over 1 KiB, is empty or not the expected object, has an unknown or a missing field, another version, another agent ID, or a value that is not a `u64`. A corrupt file refuses the session start with exit 1 and the advice to register again, as a corrupt outbox does; a file that cannot be read (permission, I/O) is exit 3. The mode of an existing file is not checked, as the record's is not; the next write leaves 0600. A file that is read is made durable before its value counts as written: the open syncs its directory entry, as the outbox's open does, since a crash after the rename or a failed directory sync can leave a new file whose entry a power loss would take back; a sync that fails is exit 3.
3. **The comparison and its boundary.** The deadline `D` is expired when `max(clock, mark) >= D`. The boundary is the server's keep rule for a queued job (`start_deadline > now()` keeps it), so a job whose deadline equals the time is expired on both sides. There is no skew allowance and no check that the issue time is not after the clock: an issue time ahead of the clock raises the mark and is accepted when its deadline lies after it. An issue time at or after its own deadline is `expired`, not `Malformed`: the instruction verified, and the server signed it. The clock reads as 0 when it is before the epoch, so the mark decides. The mark is not a replay check: an instruction whose issue time is below the mark is still accepted when its deadline is after `max(clock, mark)`, and it does not lower the mark or write the file. A far-future value, from a server clock that is wrong, is taken as it is, with no cap; every instruction then expires until the agent is registered again (Consequences).
4. **The order on the command path.** (1) The gate verifies the instruction (ADR-461 item 9), and a refusal leaves the mark, the file and the clock untouched, whatever its body says; `NotForThisAgent` is a refusal too. (2) The mark is raised in memory to the instruction's issue time, by a maximum and in one place, for every instruction that verified, the operator-refused and the expired ones included. (3) The operator check (ADR-483): an instruction whose operator is not allowed ends as `operatorNotAllowed`, never as `expired`, and the clock is not read for it. (4) The deadline is judged, the device clock being read once, here. (5) If the file holds less than the mark in memory, it is written and synced. (6) The intake takes an accepted instruction. (7) The first event is appended: `received`, the operator refusal's `preconditionFailed`, or the terminal `expired` with no failure code and no detail, under the same admission bound as `received`. (8) `commandAck` is written. The acknowledgement still settles the delivery, not the job (ADR-483 item 4); `commands_acknowledged` counts an expired job and `commands_rejected` does not.
5. **Failure handling.** A write, a sync, a rename or a directory sync that fails withholds the acknowledgement, hands nothing to the intake, records no event, and closes the connection with 1011 under the class `mark-write`, with one `warn` per `hello` and `debug` after that, since the next redelivery of the same command repeats it. The mark in memory stays raised and the known file value does not change, so the next verified command writes again, even one whose issue time is not above the mark. A stop during the write ends as a stop (no intake, no event, no acknowledgement); the write goes on and the file, old or new, is valid. A full or failed outbox is handled as ADR-478 and ADR-483 say: the mark is already raised and synced, and the redelivery writes no file.
6. **The log.** The first expired job on a connection is a `warn` with the job ID and the state, the repeats are `debug`, and the connection's end line counts them. An entry holds no time, no operator and no `commandId`. One further `warn` per connection says that the highest issue time and not the device clock decided an expiry, which is the sign of a device clock that is behind. A mark that could not be written is item 5's entry.
7. **Placement.** The device clock is a trait (`deadline::Clock`) with a production implementation, and the store and the judgement are in `agent::deadline`, outside the control channel's files, which read no wall clock (a test scans them). `Opened::start` takes the store and the clock. The gate carries the issue time of an operator-refused instruction in `Admitted`, so the one call that raises the mark in the channel sees every verified instruction.

## Consequences

- **The duplicate check must come before the expiry check once a real intake exists (D3).** Today an accepted job whose acknowledgement was lost is redelivered after its deadline and is answered `expired` after its `received`, and the intake is not handed it again. When the intake journals a job and ignores a duplicate (design 5.3), a redelivery of a job the agent already holds must be recognised as a duplicate first, or a job that is running would be reported as expired by its own redelivery.
- **A clock set back can accept a redelivered expired command (D4).** A command judged expired by the clock alone leaves the mark at its issue time, below the deadline; if the clock is set back and the command is delivered again, it is accepted. The rule is a staleness guard, as ADR-461 item 6 says, and the mark protects against a clock that is behind from the start of a session, not against one moved by the device's user.
- **A reset clock after a restart (R2 residual).** After a restart with the clock reset to 1970 the mark in the file decides: an instruction whose deadline is at or below it is expired, and one whose deadline is above both is accepted, so a stale instruction with a late deadline passes. This is the residual of ADR-461 item 6; a stronger guard needs a time the agent can trust.
- **A server clock that is wrong expires every job (T13).** A signed issue time far in the future raises the mark to it, and every later instruction expires until the agent is registered again, since nothing lowers the mark. This is accepted, with no cap, because a cap is a second clock to be wrong; the `warn` of item 6 shows it.
- **Offline packages and resume call the same raise (W6).** The logged form of the gate (`instruction::open`), which an offline package and a restart's re-verification will use, has no caller yet. When it has one it must raise the mark with the same call and judge the deadline with the same function, so a job whose deadline passed before its resume is expired by one rule. The deadline that passes between the acknowledgement and the real start of a job is not judged here; nothing starts a job from the control channel yet.
- A change of the mark file's layout is a new format version and a new file name suffix; an older agent finds an unknown file name and ignores it.
- The file adds one small synced write per instruction that raises the mark and none for a redelivery or a lower issue time.
