a handover whose summary lacks the RequestTransferExit marker tears down passively without an ECUReset; a handover whose summary records the post-transfer steps as complete but was written before a later recovery attempt was reserved (that recovery cleared the progress and started a new erase, then failed before uploading) is treated as incomplete, tears down passively and redoes the transfer instead of going to read-back verification, while a current summary that records them as complete still goes to the default-session confirmation and read-back verification after the receiver's own reservation; a former owner that comes back and starts a prefetched offline job it had not started yet raises the former-owner alert; a failed device that crashed after sending the first erase or RequestDownload but before recording its response hands over a summary carrying the transfer-start marker, and the receiver takes the restart order (teardown and checks) rather than a plain start, and so does a receiver whose summary lacks that marker because the failed device crashed after committing it locally and sending the request but before uploading it (passive teardown before any erase); a handover whose summary lacks the hardware part number or the pre-erase software version ends in `OnSiteInterventionRequired` without contacting the ECU. Blocked on: the agent's write-job journal (`crates/agent`) and the server's control channel (M3).
- **P2**: Journal protection (design 5.5, ADR-229): encrypt the journal and local cache with an OS-credential-store key, delete the body after job and sync completion, erase on agent-key revocation, and make the journal tamper-evident (a signature or MAC over its entries) so that an edited resume count or an upload after reconnection is detected. Not needed for the local E2E milestone. Done when: each of the four behaviours has a test.
- **P3**: A 32-bit `ngr-agent` on Windows looks only in its own registry view (`crates/agent/src/launch.rs`, `j2534-0404-registry` exposes the two explicit views only to 64-bit builds), so a VCI registered only in the 64-bit view is not found although design 7.1 asks for both views. Done when: the agent reads both views whatever its own bitness, and a unit test covers the 32-bit agent's resolution order.
- **P3**: `ngr-agent` and the worker it launches can read different `config.toml` files when they were built with different `config-root-*` features (`crates/agent/docs/ngr-agent.md`, "Configuration file"), so the library the agent resolved for the ABI need not be the one the worker loads. Done when: the worker reports the library path or config file it resolved (for example in `get_status`), the agent refuses a launch where it differs from its own, and a test shows the refusal.
- **P3**: Requests whose positive response is suppressed (for example tester present `3E 80`) end in `NoResponse` in the agent's host (ADR-235 consequences). Done when: a suppressed-response request succeeds without an answer, and one that does get a negative response returns it.
- **P3**: The agent's link supports only 11-bit CAN IDs and sets no CAN frame padding or addressing format ComParam (ADR-235 item 4 and consequences); `sim-ecu` needs none of them, but real ECUs may. Done when: `LinkConfig` carries the ID format (11 or 29 bits), the padding and the addressing format, `link::open` sets `CP_CanPhysReqFormat` / `CP_CanRespUSDTFormat` and the padding, and a 29-bit link reaches an ECU.
- **P3**: Protect write images at rest on the device (ADR-229): an image copied off the device can be written to other vehicles with a third-party tool, outside the VIN binding of signed instructions. Decide whether images are stored encrypted and decrypted only while a job runs, or accept the risk. Done when: the decision is recorded in the design document or an ADR.
