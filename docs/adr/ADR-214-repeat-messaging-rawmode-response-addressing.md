# ADR-214: SAE J2534-2 Clause 14 Repeat Messaging — RawMode Response-Template Addressing

**Date:** 2026-09-03
**Status:** Accepted (partial supersession: ADR-199 Decision item 3's third reuse of the shared `raw_mode_addressing_flags` fold — the mask/pattern response template's own addressing basis — is superseded by this ADR; ADR-199's Consequences accepted-residual bullet is closed)
**Affects:** `j2534-0404-service/src/service/rpc_misc.rs` (`unpack_repeat_message_setup`, `pack_repeat_message_setup`, `ioctl_start_repeat_message`), `j2534-0404-service/tests/grpc_mock/harness.rs`, `j2534-0404-service/tests/grpc_mock/repeat_message.rs`, `docs/rpc-api-guide.md`, `j2534-0404-service/docs/implementation-notes.md`, `docs/adr/INDEX.md`

## Context

ADR-199 gave SAE J2534-2 clause 14 Repeat Messaging (`PDU_IOCTL_START_REPEAT_MESSAGE`) RawMode support, but left an accepted residual open in its own Consequences section: the packed `REPEAT_MSG_SETUP` wire format this crate hand-packs (`unpack_repeat_message_setup`/`pack_repeat_message_setup`, `rpc_misc.rs` — a bytearray predating and independent of the frozen `service.proto`, ADR-178) carries exactly one `tx_flag_bits` field, shared by all three `RepeatMsgData` spans (`repeat_msg_data`, the transmitted message; `mask_data`/`pattern_data`, the device-side comparison template). Under RawMode this single field folds (via `rpc_primitive::raw_mode_tx_flag_bit_to_j2534`) into `raw_mode_addressing_flags`, reused for both the transmitted message's own `TX_EXTENDED_ID`/`ISO15765_ADDR_TYPE` TxFlags and the response template's own addressing basis (`response_tx_flags`). A real ECU that transmits requests on one CAN-ID width and responds on a different width — already proven real and already supported in the RawMode=OFF path by this crate's own regression coverage — cannot be expressed under RawMode: the client has only one field to set both from, so the device-side matcher (which keys a template's own addressing bits against each incoming frame's `RxStatus` width/addressing bits) silently misclassifies genuine matches as non-matches, misses genuine stop conditions, or misclassifies an unrelated coinciding-data frame as a match.

SAE J2534-2 clause 14.2.2.1 gives each of the three `RepeatMsgData` spans its own `TxFlags`, requiring only that `mask_data`'s and `pattern_data`'s agree with each other — nothing in the spec ties either to `repeat_msg_data`'s own `TxFlags`. This confirms ADR-199's own residual framing: sharing one field across all three spans was this crate's own simplification, not a spec requirement, and the response template's own addressing basis is a genuine input this adapter must supply correctly, not something derivable from the transmitted message.

Two derivation alternatives ADR-199 already considered and rejected, both independently re-confirmed for this ADR: (1) sniffing the template's own CAN-ID byte values for 29-bit-ness — the raw 4-byte CAN ID encoding carries no width-indicating bit distinct from an 11-bit value's own legal encoding as a 29-bit value, and the client's own mask can zero the ID bytes out entirely; (2) consulting `CP_CanRespUUDTFormat`/`CP_CanRespUSDTFormat` (or a connect-time flag) under RawMode for just this one bit — both are ComParam/connect-flag-derived, splitting addressing authority away from the client's own TxFlags channel, which ADR-196 Decision item 2 established as the RawMode client's sole addressing-metadata channel; `CAN`'s own connect flags are additionally uninformative regardless (always `CAN_ID_BOTH`).

A closely related bug, of the identical general shape (a response-side addressing basis wrongly derived from request-side input), was already found and fixed in this same function for SAE J1939 (the "ADR-200 close-out" fix, `rpc_misc.rs`): J1939 frames are always 29-bit on the wire, but under RawMode the response template's addressing basis came entirely from the client's request-side fold, so a RawMode J1939 CLL's template never carried the width bit regardless of client intent. That fix forces the bit unconditionally for J1939 specifically; it does not address the general CAN/ISO15765 case this ADR closes.

## Decision

1. **The packed `REPEAT_MSG_SETUP` wire format gains an optional trailing v2 section**: after the existing `tx_flag_bits` array, an optional `u32 response_tx_flag_bits_count` followed by that many `u32`s (the same raw `TxFlagBit` wire-value shape `tx_flag_bits` already uses). No explicit version field — detection is by remaining-bytes, exactly the mechanism ADR-199's own Consequences section anticipated: `unpack_repeat_message_setup` already rejects any payload with bytes remaining after `tx_flag_bits` (ADR-178's "no trailing garbage" guarantee), so a v1 client's payload always ends exactly at `tx_flag_bits`'s last byte and a v2 client's payload is unambiguously distinguishable by having more bytes there. `RepeatMessageSetup` gains `response_tx_flag_bits: Option<Vec<i32>>` — `None` when no v2 section is present, `Some(vec)` (possibly empty) when one is. The new section's own count+array read reuses `unpack_repeat_message_setup`'s existing widened-`u64`-arithmetic overflow-safety pattern (the same one `tx_flag_bits_count`'s own read already uses), factored into one shared helper so the two count+array reads cannot drift apart. The final strict "no trailing bytes" check moves to after the new section.

2. **`None` (v1, or a v2 client that omits the section) preserves today's behavior exactly**: the response template's addressing basis continues to inherit the request-side `raw_mode_addressing_flags` fold, byte-for-byte unchanged for every currently-deployed RawMode client. **`Some(bits)` (v2, section present) makes that array the response template's own sole, self-contained addressing basis** — folded through the identical `rpc_primitive::raw_mode_tx_flag_bit_to_j2534(raw_mode_can_family, raw_mode_iso15765, ..)` gate the request-side fold already uses, so the same protocol-family gating (e.g. `ISO15765_ADDR_TYPE` staying suppressed on a base-CAN link) applies identically to both. An empty `Some(vec![])` is a genuine, meaningful value — "the response template carries neither addressing bit" — not a synonym for `None`'s "inherit the request side": a client whose request is 29-bit and whose response is 11-bit has no other way to express "response has no width bit" than an explicit empty array, since an inherit-on-empty semantics would leave that exact asymmetry (present-request-flag, absent-response-flag) permanently unrepresentable.

3. **Only the response-template call site changes.** `ioctl_start_repeat_message`'s three current uses of `raw_mode_addressing_flags` (the periodic-cap size-range check on the transmitted message, the transmitted message's own TxFlags, and the response template's own `response_tx_flags`) split: the first two stay driven by the existing request-side fold — they are genuinely about the transmitted message, unaffected by this ADR — and only the third is redirected to the new field, falling back to the request-side fold when `response_tx_flag_bits` is `None`. `response_tx_flag_bits` itself is never applied to the transmitted `repeat_msg_data` message's own TxFlags (mirroring ADR-165 PR #42 round 7's own rule that pass-through TX flags never apply to the mask/pattern messages).

4. **SAE J1939's existing unconditional `TX_EXTENDED_ID` force is unchanged and still applies on top**, for both `None` and `Some` response fields: `base_protocol_id` gives J1939 no CAN/ISO15765 collapse (unlike FT-CAN/SW-CAN/CAN FD), so `raw_mode_can_family`/`raw_mode_iso15765` are both already `false` for a J1939 link, meaning neither fold path (request-side or the new response-side one) ever contributes this bit for J1939 regardless of what a client submits in either field — the force remains the sole source, exactly as today.

5. **RawMode=OFF CLLs parse but ignore the new section**: wire-format validity is mode-independent (a malformed v2 section is still rejected regardless of `raw_mode`), mirroring how `tx_flag_bits`'s own addressing bits are already parsed-but-inert on a RawMode=OFF link today.

6. **Documentation**: `docs/rpc-api-guide.md`'s `PDU_IOCTL_START_REPEAT_MESSAGE` paragraph is updated to describe the new optional section and its `None`/`Some([])`/`Some([bits])` semantics, replacing the existing "RawMode clients with this asymmetry MUST NOT rely on device-side matching" warning (the workaround this ADR makes unnecessary for a v2 client; a v1 client not sending the new section keeps the identical limitation and should keep seeing guidance to that effect). `j2534-0404-service/docs/implementation-notes.md`'s P2 backlog entry for this residual is deleted per this repo's own Prioritized Backlog Entries convention, since this ADR closes it — its own text is fully superseded by this ADR's Context/Decision above, so nothing needs extracting into a new bullet.

## Consequences

- A v1 RawMode client (no v2 section) is completely unaffected — byte-for-byte identical parsing and behavior to before this ADR.
- A v2 RawMode client can now correctly express an asymmetric-addressing-width ECU, closing the exact bug class ADR-199's own accepted residual described and this crate's own RawMode=OFF regression tests already prove is a real, supported configuration.
- **Incidental correctness fix**: the response template's own size-range validation (`response_extended_addressing`, downstream of `response_tx_flags`) now correctly reflects the response-side addressing width instead of the request-side one for a v2 client — a request-normal/response-extended ISO15765 link's template is now validated against the wider `5..=4100` range instead of the narrower `4..=4099` one, previously silently wrong in the same direction as the matching bug itself.
- The new wire-format section's own malformed-payload handling (truncated count, count exceeding remaining bytes, stray bytes after a valid section) reuses the exact overflow-safe pattern already proven for `tx_flag_bits_count`, so no new class of integer-overflow or out-of-bounds hazard is introduced.
- **Adjacent, explicitly out of scope for this ADR**: a RawMode ISO15765 CLL's own ability to actually *receive* a 29-bit-addressed response at the transport level still depends on `can_connect_flags` (ComParam/URID-derived, set at connect time, per ADR-196/198) — a client that declares a 29-bit response in the new `response_tx_flag_bits` field on a channel connected without the matching `CAN_29BIT_ID`/`CAN_ID_BOTH` connect flag would never receive that frame in the first place, so the device-side matcher this ADR fixes would simply never see a candidate to (correctly or incorrectly) match. This is a pre-existing connect-time configuration concern, not something this ADR's own wire-format fix can or should address; worth a follow-up check, not a residual this ADR carries.
