# ADR-160: SAE J2534-2 Mixed Format Frames on a CAN Network — a `"native-mixed"` CAN Channel Mode (Phase 3 Stage 3c)

**Date:** 2026-08-05
**Status:** Accepted (Consequences' `CAN_MIXED_FORMAT_ALL_FRAMES` deferral fulfilled by ADR-217)
**Affects:**
- `vci-service-config` (new `CanChannelMode::NativeMixed` variant, `find_can_channel_mode` unchanged)
- `j2534-0404-service/src/service/can_mode.rs` (`CanChannelMode::NativeMixed`)
- `j2534-0404-service/src/service/rpc_link.rs` (`connect_new_physical_channel`'s creator-only `SET_CONFIG(CAN_MIXED_FORMAT)` step, `install_point_to_point_fc_filters`'s UUDT-fallback branch gains a native-mixed alternative, a new per-UUDT-id `PASS_FILTER` installer)
- `j2534-0404-service/src/service/events.rs` (`poll_rx_inner`'s `RxEntryKind::Hardware` arm gains a per-frame ProtocolID branch when the channel is native-mixed; the native RX frame struct gains a `ProtocolID` field)
- `j2534-0404-service/src/service/resources.rs` or `rpc_link.rs` (new local `CAN_MIXED_FORMAT_OFF`/`_ON`/`_ALL_FRAMES` constants — the native header defines `CONFIG_CAN_MIXED_FORMAT` but no value constants)
- `j2534-0404-mock/src/lib.rs` (per-channel `can_mixed_format` state, `SET_CONFIG`/`GET_CONFIG` simulation, `ERR_NOT_SUPPORTED` toggle, RX injection gains an explicit ProtocolID)
- `j2534-0404-service/tests/grpc_mock/mixed_format_can.rs` (new)

## Context

SAE J2534-2 clause 8, "Mixed Format Frames on a CAN Network," lets a single ISO15765 channel carry both segmented ISO15765 messages and unformatted/raw CAN frames simultaneously, via a new `SET_CONFIG`/`GET_CONFIG` parameter `CAN_MIXED_FORMAT` (0 = OFF, 1 = ON, 2 = ALL_FRAMES). Frames are distinguished by the native `PASSTHRU_MSG.ProtocolID` field: `FLOW_CONTROL_FILTER`-matched frames become ISO15765 messages (`ProtocolID` = an ISO15765 id); `PASS_FILTER`/`BLOCK_FILTER`-matched frames stay unformatted CAN (`ProtocolID` = a CAN id). `CAN_MIXED_FORMAT` is only valid on an ISO15765-family channel — `ERR_NOT_SUPPORTED` on any other channel type, or on a device that doesn't implement the feature at all.

**Two facts, confirmed directly against the spec text and current code (not re-derived from summary), drive this design:**

1. **This D-PDU service has no client-facing surface that could ever call `SET_CONFIG(CAN_MIXED_FORMAT)` directly.** Neither ISO 22900-2 edition (2009(E), 2022 — both checked directly, zero hits) defines any concept resembling clause 8's protocol-format mixing. The D-PDU `PDU_IOCTL_*` namespace is a closed, curated enum (`service_params.rs`'s `PDU_IOCTL_BASE` block) that does not expose arbitrary native `SET_CONFIG`/`GET_CONFIG` IDs — every native CONFIG id this service ever sets reaches hardware either through the ComParam-translation pipeline (`to_j2534_config_id`) or a fixed connect-time step (like ADR-158's `CONFIG_FD_CAN_DATA_PHASE_RATE`), never through a client-issued raw IOCTL passthrough. **Clause 8 is therefore a service-internal mechanism in this codebase, not an API surface a D-PDU client can toggle** — the only party that will ever call `SET_CONFIG(CAN_MIXED_FORMAT)` is this service itself, deciding once, at connect time, whether to use it.
2. **The D-PDU semantic clause 8 serves — delivering both ISO15765 (USDT) and unformatted (UUDT/raw) CAN traffic to a client on what is, from the client's point of view, one ISO15765-family ComLogicalLink — is exactly the gap [ADR-046](ADR-046-can-channel-mode.md) already exists to work around.** ADR-046's own Context section names this directly: some devices deliver UUDT frames on an ISO15765 channel "only through the non-conformant UUDT `FLOW_CONTROL_FILTER` workaround (ADR-041), or not at all." That workaround — installing a `FLOW_CONTROL_FILTER` for a UUDT response id anyway, even though ISO 22900-2/J2534 v04.04 never define a FLOW_CONTROL_FILTER as valid for anything but genuine flow-controlled USDT/UUDT exchanges — plus the heavier `"dual-channel"` mode (a whole second physical raw-CAN channel just to catch UUDT/raw traffic) and `"software-isotp"` mode (this service's own ISO-TP engine over a raw channel) are three different-cost answers to devices that lack clean native support for exactly what clause 8 defines. Bringing clause 8 into scope means this service can, for a genuinely clause-8-capable device, replace the ADR-041 workaround with the conformant mechanism the workaround was always standing in for.

**Locked scope for this stage**, and why each cut is a legitimate stage boundary rather than an incomplete implementation of clause 8:

- **`CAN_MIXED_FORMAT_ON` (1) only, not `_ALL_FRAMES` (2).** `_ALL_FRAMES` additionally delivers every individual ISO15765 protocol frame (including flow control) a *second* time, in parallel, as a raw CAN frame if it also matches a PASS_FILTER. This service has no D-PDU consumer for a parallel raw echo of USDT traffic — a client wanting raw bus monitoring already gets that from an ordinary raw-CAN CLL. Deferred, not implemented.
- **RX-only. TX is unchanged.** `transmit_request_inner` (`events.rs`) always tags an outgoing message's `ProtocolID` with the connected channel's own `hw_protocol_id` — there is no existing mechanism for a single write call to choose a *different* `ProtocolID` than the channel's own, and this service's only raw-CAN-frame producer (D-PDU CLLs connected directly to a raw `CAN` resource) already writes on its own channel, not a mixed-format ISO15765 one. Clause 8's `ERR_MSG_PROTOCOL_ID`/queue-clearing-on-SET side effects (8.2.2.2/8.2.2.3, Table 5) are consequently unreachable under this design — see Decision 4.
- **No auto-detection.** `can_channel_mode = "native-mixed"` is explicit deployer configuration, the same shape every other mode ADR-046 introduced. `"auto"`'s existing dual-channel probe (ADR-047) is not extended to also try native-mixed — that reopens ADR-047's own probe-cache design for a feature this stage hasn't yet proven deployment value for. Deferred.
- **`FD_ISO15765_PS` (ADR-159) links are excluded**, even though clause 22.2.2.d explicitly requires clause-8 support on FD ISO15765 channels too. This stage's `PASS_FILTER`-per-UUDT-id mechanism (Decision 3) has no answer yet for a raw CAN 2.0-vs-CAN-FD frame-format distinction (clause 22.2.2.a/d/g's own mixed-format requirements, which Stage 3b's own ADR-159 already deferred as Stage 3c's job — see ADR-159's Decision 5). Treating `is_fd_protocol_id` as a native-mixed disqualifier, mirroring ADR-159 Decision 4's own companion-gate pattern, keeps this stage's scope to Classic ISO15765 and leaves FD-connected links on ADR-159's existing fallback `FLOW_CONTROL_FILTER`. A genuine follow-up, not a silent gap.
- **Discovery-cache wiring deferred**, matching Stage 3a/3b's own identical deferral (ADR-153 precedent — "no connect-time enforcement wiring yet"). An unsupporting device's `SET_CONFIG(CAN_MIXED_FORMAT)` call itself fails `ERR_NOT_SUPPORTED` at connect time (Decision 2), which is already a correctly-surfaced connect error, just not a pre-emptive discovery-time one.
- **Filter-count minimums (64 `FLOW_CONTROL_FILTER` + 10 `PASS_FILTER`/`BLOCK_FILTER`, combined, per ISO15765 channel) are a device-conformance requirement, not something this service enforces.** This service is the J2534 *caller*; it never artificially caps how many filters it installs (`install_point_to_point_fc_filters` installs one per table entry with no cap, warn-logging any individual failure) and adds no new capacity-tracking. An 11th simultaneous UUDT id under native-mixed mode hitting a real device's own limit surfaces as a native `ERR_EXCEEDED_LIMIT`, warn-logged the same way an FC-filter install failure already is — an accepted residual, not a new failure mode this stage introduces.

**Naming collision, deliberately avoided:** `PARAM_CAN_MIXED_FORMAT` (`service_params.rs:419`, D-PDU `CP_CanMixedFormat`, `ComParamId(0x80B9)`) already exists in this codebase — but it is a project-invented, ISO-22900-2-absent ComParam (confirmed: zero hits for "CanMixedFormat" in either spec edition) that means something completely different: whether a CAN channel accepts *both* 11-bit and 29-bit CAN ID widths simultaneously (J2534's `CAN_ID_BOTH` connect flag, ADR-065), consulted only in `rpc_link.rs::can_connect_flags` at connect time. This ADR's `CAN_MIXED_FORMAT` is SAE J2534-2 clause 8's *protocol*-format mixing (ISO15765 vs. raw CAN) — an unrelated concept that happens to share very similar English wording with the pre-existing CAN-ID-*width* mixing ComParam. The new mode is named `"native-mixed"` (not anything containing "CanMixedFormat") specifically to keep this distinction unambiguous in config, code, and docs.

## Decision

### 1. A fourth `CanChannelMode` variant, `"native-mixed"`, added the same way ADR-047 added `"auto"`

`can_mode.rs`'s `CanChannelMode` enum gains `NativeMixed`, parsed the same way the existing three/four values are (`find_can_channel_mode`'s config-key priority is unchanged). The existing `SingleChannel`/`DualChannel`/`SoftwareIsoTp`/`Auto` modes are **byte-for-byte unchanged** — this is a new mode alongside them, not a modification of any of them, mirroring exactly how ADR-047 added `Auto` without touching ADR-046's original three.

An ISO15765-family CLL connecting under `native-mixed` gets its primary `ISO15765`/`ISO15765_PS` channel `SET_CONFIG(CAN_MIXED_FORMAT, ON)`'d once, at physical-channel creation — never per-CLL, and never re-issued for a CLL that joins an already-open shared channel (mirroring ADR-158's `fd_data_phase_rate` connect-time step, which is likewise a creator-only, conditional insertion into `connect_new_physical_channel`, not an unconditional reorder). `ERR_NOT_SUPPORTED` from this `SET_CONFIG` call fails the connect outright (disconnecting the just-opened channel first, the same rollback-on-failure shape `fd_data_phase_rate`'s own failure path already has) — no silent fallback to the ADR-041 workaround. A raw-CAN CLL, or an ISO15765 CLL under any other mode, is entirely unaffected.

Enabling unconditionally at creation — even before any CLL has staged a `CP_CanRespUUDTId` — is deliberate, not wasteful: with `CAN_MIXED_FORMAT_ON`, the spec's own Figure 1 discards an unformatted CAN frame that matches no `PASS_FILTER` (falls through the PASS_FILTER check to the discard path), so "ON with zero PASS_FILTERs installed" is behaviorally identical to OFF until the first UUDT id actually appears. This buys the invariant Decision 4 depends on: the `SET_CONFIG` call happens exactly once per physical channel, at creation, strictly before any filter, queued message, or periodic transmission exists on it — so clause 8's per-SET side effects (Table 5: clear TX/RX queues, delete all `PASS_FILTER`/`BLOCK_FILTER`s, delete CAN-tagged periodics) are all vacuous no-ops the one time this service ever triggers them. (This "unconditional" framing was never literally true for a pin-selected/`_CHx`-qualified link — see the "Correction (2026-08-17, part 2)" section below, which makes the qualified-link exclusion explicit and enforced in code.)

### 2. `CAN_MIXED_FORMAT`'s three values need local constants, not a header edit

`j2534-0404-sys/src/bindings/j2534_v0404.h` already defines `CONFIG_CAN_MIXED_FORMAT` (`0x8000`, added in Phase 0/ADR-152 alongside every other J2534-2 constant) but no `CAN_MIXED_FORMAT_OFF`/`_ON`/`_ALL_FRAMES` value constants — these are ordinary `u32` values (0/1/2) passed as a `SET_CONFIG` payload, not distinct native IDs, so they belong as plain `const`s local to this service (mirroring how this codebase already defines small service-local constants for native value enums elsewhere), never a header/bindgen change.

### 3. Per-UUDT-id `PASS_FILTER`, replacing the ADR-041 workaround for native-mixed links only

`install_point_to_point_fc_filters` (`rpc_link.rs`) already has a `dual_channel` boolean that, when true, skips installing the ADR-041 UUDT `FLOW_CONTROL_FILTER` fallback (because dual-channel mode's companion raw-CAN channel catches UUDT traffic instead). This gains a parallel `native_mixed` condition (computed the same "before `api` is locked" way as `dual_channel`, for the same AB-BA-deadlock reason already documented on that variable): when the connecting link's channel is native-mixed, the UUDT fallback branch installs a genuine `PASS_FILTER` (address-narrowed to the UUDT response id, mirroring `install_point_to_point_fc_filter`'s own per-address `CanAddress`/mask-pattern construction, just with `j2534_0404::PASS_FILTER` as the native filter type instead of `FLOW_CONTROL_FILTER`) instead of the `FLOW_CONTROL_FILTER` fallback. `dual_channel` and `native_mixed` are mutually exclusive by construction (a channel's `CanChannelMode` resolves to exactly one variant), so exactly one of "companion channel," "FC-filter workaround," or "native PASS_FILTER" ever applies to a given UUDT id.

The `PDU_IOCTL_CLEAR_MSG_FILTERS`/`PDU_IOCTL_RESET` reinstall path (ADR-008/ADR-114) must rebuild these new UUDT `PASS_FILTER`s alongside the existing `FLOW_CONTROL_FILTER`s it already rebuilds — unlike the dual-channel companion's own PASS_FILTER (ADR-046's Consequences: "not rebuilt by that path," since it lives on a separate channel this reinstall function doesn't touch), these new filters live on the *primary* channel this reinstall path already targets, so skipping them would be a new, avoidable regression, not an existing accepted one.

### 4. RX: a per-frame `ProtocolID` branch inside the existing `RxEntryKind::Hardware` arm — no new `RxEntryKind` variant

`RxEntryKind` describes a *channel's* relationship to a CLL (which physical channel it reads from, and how); which format a given *frame* is tagged with is a per-frame fact, not a channel fact, so it becomes a branch inside the existing `Hardware` arm rather than a fourth `RxEntryKind` variant. The native RX frame struct (currently dropping the native message's `ProtocolID` field at the read boundary, since nothing has ever needed it before) gains a `protocol_id: u32` field, threaded through from the raw `PassThruReadMsgs` result. In `poll_rx_inner`'s `Hardware` arm, when the owning channel is native-mixed: a frame tagged with a CAN protocol id routes exactly like `RxEntryKind::Companion` already does (delivered only if it matches a `CP_CanRespUUDTId` table entry; everything else dropped for this CLL, since it belongs to a `PASS_FILTER` that isn't this CLL's own); a frame tagged with an ISO15765 protocol id takes the existing `Hardware`-arm path unchanged. For a non-native-mixed channel, this new branch never triggers — the frame's `ProtocolID` is read but not consulted, since it's already guaranteed to equal the channel's own connect-time id.

Duplicate delivery is excluded by clause 8's own `CAN_MIXED_FORMAT_ON` semantics (Figure 1): a received frame is either/or — a `FLOW_CONTROL_FILTER` match builds an ISO15765 message, or (only when it doesn't match any `FLOW_CONTROL_FILTER`) a `PASS_FILTER`/`BLOCK_FILTER` evaluation decides raw delivery — never both for the same frame, unlike `_ALL_FRAMES` (out of scope, Context above).

### 5. Mock support

`j2534-0404-mock` gains per-channel `can_mixed_format: u32` state (default `CAN_MIXED_FORMAT_OFF`). `SET_CONFIG`/`GET_CONFIG(CAN_MIXED_FORMAT)`: `ERR_NOT_SUPPORTED` on any non-ISO15765-family channel; on an ISO15765-family channel, stores the value and performs the observable Table 5 side effects (clears any recorded TX/RX queue state, deletes recorded `PASS_FILTER`/`BLOCK_FILTER`s) so a test can assert them directly if it chooses to exercise the (currently unreachable in this service's own usage) side-effect path. A new `__mock_set_can_mixed_format_unsupported(bool)` toggle (mirroring `__mock_set_max_channels`'s shape from ADR-047) lets tests drive the `ERR_NOT_SUPPORTED`-at-connect-time failure path without needing a real non-conformant adapter. RX message injection for tests gains an explicit `ProtocolID` parameter so a test can inject both an ISO15765-tagged and a CAN-tagged frame on the same mock channel.

## Consequences

- **Deferred, not implemented, each recorded as a follow-up:** `CAN_MIXED_FORMAT_ALL_FRAMES` (2); TX-side per-message `ProtocolID` selection and its `ERR_MSG_PROTOCOL_ID` error; `"native-mixed"` auto-detection (an `"auto"`-mode extension, or a `GET_CONFIG(CAN_MIXED_FORMAT)` capability probe, is a clean future in-band signal — cleaner than `"software-isotp"`'s own unprobeable case, ADR-047's Context); discovery-cache wiring for clause-8 support bits; `FD_ISO15765_PS`-on-native-mixed (clause 22.2.2.d requires it; this stage's `PASS_FILTER`-per-UUDT-id mechanism has no CAN-2.0-vs-FD raw-frame-format answer yet).
- **`ERR_MSG_PROTOCOL_ID` and clause 8's per-SET queue/filter/periodic-clearing side effects are unreachable under this design** (Decision 1's "exactly once, before any traffic" invariant) — documented explicitly here so a future TX-tagging follow-up knows exactly which invariant it will need to revisit once a live mid-session `SET_CONFIG(CAN_MIXED_FORMAT)` (not just the one at connect time) becomes possible.
- **Filter-count minimums (64 FC + 10 PASS/BLOCK) bind the device, not this service** — no capacity-tracking or pre-emptive rejection logic added; an `ERR_EXCEEDED_LIMIT` from a real device surfaces the same way any other native filter-install failure already does (warn-logged, that one UUDT id's capture silently absent — matching this service's existing best-effort posture for individual FC-filter install failures).
- **The ADR-041 `FLOW_CONTROL_FILTER` UUDT workaround, `"dual-channel"` mode, and `"software-isotp"` mode are all untouched** — `"native-mixed"` is a fourth option a deployer opts into explicitly, not a replacement forced on existing deployments. A device that cannot use clause 8 (or a deployer who hasn't verified it can) keeps using whichever of the other three modes already fits.
- Existing `grpc_mock.rs`/integration suites for the three pre-existing modes are unaffected — this ADR adds no field, branch, or default that changes their behavior.

## Correction (2026-08-17): connect-time `SET_CONFIG` order between `CAN_MIXED_FORMAT` and pin assignment on a qualified/`_PS` link

Decision 1's original text described the `CAN_MIXED_FORMAT` `SET_CONFIG` step only in relation to `PassThruConnect` and to ADR-158's `fd_data_phase_rate` step ("once, at physical-channel creation"), without saying anything about its ordering relative to `CONFIG_J1962_PINS` pin assignment on a pin-selected/`_CHx`-qualified link. `connect_new_physical_channel` (`rpc_link.rs`) accordingly issued the `CAN_MIXED_FORMAT` `SET_CONFIG` before the pin-assignment `SET_CONFIG`.

A post-merge J2534-2 audit found this ordering violates SAE J2534-2 clause 6.3.2.7 (`vehicle-comm-specs/j2534-2-0404/J2534-2_202012 - Optional Pass-Thru Features.md:316`): on a qualified link, every `PassThruIoctl` other than the pin-assignment `SET_CONFIG` itself must be rejected with `PDU_ERR_PIN_INVALID` until pins are bound. Decision 1 correctly modeled the *FD* data-phase-rate step's own pre-pins position on clause 21.3.2.5.1's explicit carve-out for that one parameter (`:2851`) — but clause 8 (SS8.2.1, `:405`) grants `CAN_MIXED_FORMAT` no equivalent exception, so clause 6.3.2.7's general rule applies to it unmodified. Every pin-selected ISO15765 connect under native-mixed mode would fail on a clause-6.3.2.7-conformant device.

Fix: `connect_new_physical_channel` now issues `SET_CONFIG(CONFIG_CAN_MIXED_FORMAT)` after `SET_CONFIG(CONFIG_J1962_PINS)` rather than before it — the FD data-phase-rate step's own position (before pins) is unchanged, since that ordering remains spec-mandated. `j2534-0404-mock`'s `IOCTL_SET_CONFIG` handler gains a matching clause 6.3.2.7 gate so a qualified channel's `CAN_MIXED_FORMAT` `SET_CONFIG` is rejected with the mock's `PDU_ERR_PIN_INVALID` helper whenever pins are not yet assigned, closing the mock-infidelity gap that had let this ordering go unpinned by any test. Decision 1's remaining text (the once-per-physical-channel, creator-only, rollback-on-failure shape) is otherwise unaffected. See `j2534-0404-service/docs/implementation-notes.md`'s Prioritized Backlog for the closed P2 entry this correction resolves. (This "after `CONFIG_J1962_PINS`" framing is itself superseded for a qualified/`_PS`/`_CHx` link by the "Correction (2026-08-17, part 2)" section immediately below, which skips this `SET_CONFIG` for such a link entirely rather than merely reordering it.)

## Correction (2026-08-17, part 2): connect-time `SET_CONFIG(CAN_MIXED_FORMAT)` also skipped entirely for a qualified/`_PS`/`_CHx` link

The ordering fix above (part 1) let a pin-selected/`_CHx`-qualified ISO15765-family link's connect actually succeed under native-mixed mode for the first time — which exposed a second, previously-unreachable defect a Codex review on that same fix caught: `connect_new_physical_channel` still unconditionally issued `SET_CONFIG(CONFIG_CAN_MIXED_FORMAT, ON)` on a qualified link's physical channel, even though `install_point_to_point_fc_filters` and both ADR-162 collision checks (Decision 3, `rpc_link.rs`) already exclude a qualified link from the native-mixed `PASS_FILTER` treatment and keep the ADR-041 `FLOW_CONTROL_FILTER` fallback instead. With `CAN_MIXED_FORMAT_ON` set on the channel, clause 8 Figure 1 (`vehicle-comm-specs/j2534-2-0404/J2534-2_202012 - Optional Pass-Thru Features.md:411-424`) routes any frame matching a `FLOW_CONTROL_FILTER` into ISO15765 reassembly unconditionally, before `PASS_FILTER` evaluation ever runs — so every UUDT response on a qualified link's channel would be silently misparsed or lost on real conformant hardware, for no corresponding benefit (nothing downstream ever consulted `CAN_MIXED_FORMAT` being on for a qualified link's own traffic).

Fix: the `native_mixed_format` value passed into `NewPhysicalChannelParams` (and from there into the connect-time `SET_CONFIG` gate) is now `native_mixed_format && link_pin_select.is_none() && link_channel_index.is_none()` — the exact same qualified-link exclusion expression Decision 3's `PASS_FILTER` installer and both ADR-162 collision checks already use, applied to the one remaining call site that still passed the raw, unexcluded boolean through. A qualified link's physical channel now never has `CAN_MIXED_FORMAT` turned on at all, closing the clause-8-Figure-1 hazard outright rather than trading it for the alternative direction (extending `PASS_FILTER`/collision handling to qualified links) — that alternative remains undecided/out of scope, since skipping the `SET_CONFIG` loses no capability a qualified link ever used. This also makes explicit, for a qualified link, that Decision 1's "enabling unconditionally at creation" framing was never literally true — see the note added at that paragraph. Closes the "P2 (J2534-2 audit, CAN FD family area, ADR-worthy)" backlog entry in `j2534-0404-service/docs/implementation-notes.md`'s Prioritized Backlog that tracked this as an open, undecided-fix-direction item.
