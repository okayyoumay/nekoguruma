# ADR-215: `CP_TesterPresentMessage` Length Validation

**Date:** 2026-09-03
**Status:** Accepted
**Affects:** `j2534-0404-service/src/service/rpc_link.rs` (`rpc_set_com_param`'s Bytefield arm), `j2534-0404-service/src/service/rpc_primitive.rs` (`resolve_tester_present`, a new shared `sae_tx_size_range` helper factored out of `resolve_send_recv_tx`), `j2534-0404-service/src/service/events.rs` (`frame_tester_present_data`'s single-frame check becomes defensive-only), `j2534-0404-service/tests/grpc_mock/*`, `docs/rpc-api-guide.md`, `j2534-0404-service/docs/implementation-notes.md`

## Context

`CP_TesterPresentMessage` (`PARAM_TESTER_PRESENT_MSG`, `service_params.rs`) is a client-settable ISO 22900-2 Bytefield ComParam with no length validation anywhere in this service, for any protocol — a pre-existing gap noted in `implementation-notes.md`'s backlog (P2, edge-case-hunter, PR #30 round 4) and confirmed still live by direct reading of `resolve_tester_present`'s own current code comments.

Two independent specs bound this ComParam's length, and satisfying one does not guarantee the other:

- **ISO 22900-2's own ComParam-level constraint**: `CP_TesterPresentMessage` is declared `PDU_PT_BYTEFIELD` with `ParamMaxLen = 12` on the raw payload (explicitly excluding any header/checksum bytes, per the ComParam's own Description). This is a fixed property of the ComParam's own MDF-style declaration (§B.3.3.1's `ParamMaxLen` field), not something that varies per protocol.
- **SAE J2534-1's own per-protocol composed-message TX size range** (Figure 42): the TOTAL message (header + payload) a given protocol's `PassThruWriteMsgs` accepts. This crate already models this table exactly as `ChannelProtocol::tx_message_size_range` (`protocol.rs`, lockstep-tested against the spec table), and already enforces it for ordinary `CoptSendrecv` sends via `resolve_send_recv_tx`'s own `size_range` check — but never for tester-present.

For most protocols the SAE ceiling comfortably exceeds ISO's 12-byte payload plus any header, so ISO's own cap is the binding constraint. For CAN and J1850PWM specifically, the reverse is true: CAN's own composed-message ceiling is 12 bytes total (a 4-byte CAN-ID header leaves only 8 payload bytes), and J1850PWM's is 10 bytes total (a 3-byte header leaves only 7). An ISO-22900-2-legal 9-12-byte tester-present payload is therefore SAE-J2534-1-illegal on either of these two protocols. Neither constraint alone closes the gap: enforcing only the ISO cap still lets an over-the-SAE-ceiling payload reach the wire on CAN/J1850PWM; enforcing only the SAE range still admits an ISO-illegal payload on every wider protocol (ISO15765, K-line, J1850VPW, the SCI family, etc.).

A CAN-FD-connected link additionally needs the same DLC-quantized padding `resolve_send_recv_tx` already performs for an ordinary `FD_CAN_PS` send (ADR-159) — tester-present's own composed message currently gets the `TX_FD_CAN_FORMAT`/`TX_FD_CAN_BRS` flags (ADR-158 round 4) but no equivalent padding, so an unpadded FD tester-present frame can reach the wire with a DLC-illegal length.

Two ISO 15765-2 single-frame constraints already exist for tester-present, but are enforced too late and too weakly to serve as this fix's own check: `frame_tester_present_data` (`events.rs`) rejects an oversized *software* ISO-TP tester-present payload, but only at actual send time (deep inside the poll task, well after `CoptStartcomm`/`CoptUpdateparam` already succeeded and the keep-alive was armed) — the failure is a logged warning that silently disables tester-present, never a synchronous or even an asynchronous client-visible error. No equivalent single-frame check exists at all for *hardware* ISO15765 functional addressing, despite `resolve_send_recv_tx` already enforcing the identical constraint for ordinary functionally-addressed `CoptSendrecv` sends (ADR-055).

This crate has no existing precedent for enforcing a Bytefield ComParam's own declared maximum length anywhere — the one existing fixed-size Bytefield, `CP_J1939Name`, is silently zero-padded/truncated to its 8-byte width at read time (`events_j1939_claim.rs`), the opposite policy from this crate's own established precedent of rejecting an invalid ComParam value outright rather than masking it (e.g. `CP_UartConfig`/ADR-071, `CP_Parity`/ADR-027, `CP_BlockSizeOverride`, all rejected synchronously in `rpc_set_com_param`'s Unum32 arm). This is therefore a new validation category for this Bytefield ComParam specifically, not a mechanical port of an existing Bytefield-length check.

Severity: no memory-safety risk exists regardless — `j2534-0404::PassThruMessage::new` already hard-rejects any composed message over the PASSTHRU_MSG struct's own 4128-byte data capacity. The gap this ADR closes sits entirely below that ceiling: a payload that is ISO-22900-2-legal-but-SAE-J2534-1-illegal for its protocol either reaches the wire as an out-of-protocol-spec frame (native/mock-dependent, unvalidated by this service) or fails late and unclearly (a repeating async TX-error event at best, a silently-disabled software-ISO-TP keep-alive at worst) instead of a clear, immediate rejection naming the actual constraint violated.

## Decision

1. **`ParamMaxLen = 12` is enforced synchronously at `SetComParam` time**, in `rpc_set_com_param`'s existing Bytefield arm (`rpc_link.rs`, guarded by `comparam_support::is_bytefield_param`), the same place and idiom this crate already uses for other per-ComParam value validation (`CP_UartConfig`/`CP_Parity`/`CP_BlockSizeOverride`, all in the neighboring Unum32 arm). `CP_TesterPresentMessage` specifically is checked; other Bytefield ComParams are unaffected. This is mode-independent (RawMode and non-RawMode alike) — `ParamMaxLen` is a property of the ComParam's own declared type, not of how the resulting message gets composed. A `bytes.len() > 12` write is rejected `INVALID_ARGUMENT` before it ever reaches `link.working.bytes`.

2. **SAE J2534-1's composed-message size range is enforced at `CoptStartcomm`/`CoptUpdateparam` resolution time**, inside `resolve_tester_present` (`rpc_primitive.rs`), on the same composed `data` (header + payload) `resolve_send_recv_tx` already validates for ordinary sends — because the composed length depends on state (RawMode, the `UniqueRespIdTable`, staged FD/addressing ComParams) that is only fully known at resolution time, not at the moment `CP_TesterPresentMessage` itself is set. The `size_range` computation `resolve_send_recv_tx` already performs (`rpc_primitive.rs`, ~line 1027-1044: the `fd_can_tx_message_size_range`/`fd_iso15765_tx_message_size_range`/K-line-manual-checksum branches over the base `ChannelProtocol::tx_message_size_range` table) is factored into a shared helper, `sae_tx_size_range`, called identically from both functions — one source of truth for "what composed length this protocol/addressing/FD configuration accepts," rather than a second, independently-drifting copy. Tester-present's own call passes `kline_manual_checksum_iso14230 = false` (tester-present's `checksum_mode` is not threaded into this function at all today, and the only wire-visible difference that flag makes — SAE J2534-1's manual-checksum row widening the ceiling from 259 to 260 bytes — is unreachable once Decision item 1 caps every tester-present payload at 12 bytes) and no TP2.0-broadcast branch (`CP_TesterPresentHandling` is unreachable for TP2.0, confirmed by `is_tp20_param`'s existing exclusion). A length outside the resulting range is rejected via the same `Err(String)` idiom `resolve_tester_present` already uses for `CP_TesterPresentSendType`/`CP_TesterPresentTime` validation, so both existing call sites get the correct handling for free: `CoptStartcomm` (`rpc_primitive.rs`) surfaces it synchronously as `Status::invalid_argument`; the `CoptUpdateparam` re-arm path (`events.rs`) surfaces it as an async `PDU_ERR_EVT_TESTER_PRESENT_ERROR`, matching the dual sync/async architecture this function already has for its two other resolution-failure cases. The check is skipped entirely when the payload is empty (`CP_TesterPresentHandling` effectively disabled — no message is ever composed or sent in that case).

3. **An FD-connected `FD_CAN_PS` link's composed tester-present message is padded to the next DLC-legal length**, mirroring `resolve_send_recv_tx`'s existing `CP_CanFillerByte`-driven padding (ADR-159) exactly — applied only after the range check in Decision item 2 confirms the unpadded length already fits the link's staged `CP_CANFDTxMaxDataLength`, so padding never grows the message past its own ceiling. `FD_ISO15765_PS` is excluded (the native adapter's own ISO15765 state machine pads/segments its own frames; this service must not double-pad).

4. **The ISO 15765-2 single-frame constraint is enforced at the same resolution point**, for both addressing paths tester-present can use: software ISO-TP (any protocol with `link.software_isotp` set) and hardware ISO15765 with functional addressing (mirroring `resolve_send_recv_tx`'s own existing ADR-055 functional-addressing check). Both reuse the identical `Addressing::max_sf_payload`/`fd_max_sf_payload` calculation `resolve_send_recv_tx` already uses, keyed off the same addressing/FD-TX-DL derivation. This makes `frame_tester_present_data`'s own existing software-ISO-TP oversize check (`events.rs`) purely defensive from this point forward — it can no longer be reached by a payload that ever should have armed successfully, but is left in place rather than removed, since it costs nothing to keep as a second line of defense against a future regression in the new resolve-time check.

5. **Not addressed by this ADR, recorded as backlog follow-ups instead** (`implementation-notes.md`): `CP_TesterPresentExpPosResp`/`CP_TesterPresentExpNegResp` carry the identical ISO 22900-2 `ParamMaxLen = 12` declaration but are out of this ADR's scope (a distinct pair of ComParams, not exercised by the gap this ADR closes); and `CP_J1939Name`'s own silent-truncation policy remains inconsistent with the reject-outright precedent this ADR extends, but changing an already-shipped ComParam's behavior is a separate, riskier decision than adding a new check to a previously-unvalidated one.

## Consequences

- Effective non-RawMode payload ceilings after this fix: CAN 8 bytes, J1850PWM 7 bytes, `FD_CAN_PS` `min(12, the link's own effective FD TX data length)` (8 when `CP_CANFDTxMaxDataLength` is unset/0/8, else 12), software-ISO-TP and functionally-addressed hardware ISO15765 the single-frame payload capacity for the resolved addressing mode (6 or 7 bytes depending on extended vs. normal addressing, or the FD single-frame capacity for `FD_ISO15765_PS`), every other protocol 12 bytes (ISO's own cap, never reached by SAE's own wider ceiling).
- A RawMode J1850 tester-present configuration gains a real floor it did not have before (the existing RawMode minimum-prefix check, `compute_tx_prefix`, already clamps to at most 3 bytes for J1850 and so cannot by itself catch an under-floor length).
- `frame_tester_present_data`'s own software-ISO-TP oversize check becomes unreachable in the normal case (Decision item 4 rejects earlier) but is kept as defense-in-depth.
- No change to any already-legal configuration: every protocol whose SAE ceiling already exceeds ISO's 12-byte cap is bound only by the (unchanged, already-enforced-nowhere-differently) 12-byte cap; no previously-accepted, genuinely spec-legal payload becomes rejected.
- This closes `implementation-notes.md`'s P2 backlog entry for this gap; the two source comments in `rpc_primitive.rs` describing the gap as open and unfixed (near `resolve_tester_present`'s FD-flags block and its RawMode-prefix-check block) are rewritten to describe the fix instead of the residual.
