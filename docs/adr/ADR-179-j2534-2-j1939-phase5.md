# ADR-179: SAE J2534-2 SAE J1939 Protocol (Phase 5)

**Date:** 2026-08-14
**Status:** Accepted (Decision 3's claim-registration atomicity/timeout-cancel mechanism and optional-CoptStartcomm-message scoping superseded by ADR-180)
**Affects:** `j2534-0404-service/src/service/protocol.rs`, `resources.rs`,
             `names.rs`, `comparam_support.rs`, `comparam_defaults.rs`,
             `comparam_id.rs`, `service_params.rs`, `rpc_link.rs`,
             `rpc_primitive.rs`, `events.rs`, `events_rx_routing.rs`,
             `tx_header.rs`, `j2534-0404/src/lib.rs`, `j2534-0404-mock`

## Context

`docs/j2534-2-support-plan.md`'s Phase 5 covers SAE J2534-2 clause 16, the
SAE J1939 heavy-duty-vehicle protocol: 250 kbps, 29-bit CAN identifiers, and
— unlike every J2534-2 phase shipped so far — a device-owned address
claim/defend negotiation (SAE J1939-81) with a genuinely new asynchronous
failure mode. The plan flagged this phase as needing a `design-advisor`
consult up front, for the address-claim/defend state machine, the new
`ERR_ADDRESS_NOT_CLAIMED` failure mode, and spec interpretation generally.
This ADR records that consult's decisions, cross-checked directly against
the in-workspace ISO 22900-2:2022 text before being accepted.

**Substantially pre-built ComParam scaffolding, but entirely unreachable.**
Unlike every prior phase, most of this phase's ComParam vocabulary already
existed before this ADR — apparently minted during an earlier, general ISO
22900-2 ComParam-table authoring pass, well before this session's
phase-by-phase J2534-2 rollout began. `service_params.rs` already mints
`PARAM_J1939_ADDR_CLAIM_TIMEOUT`, `_ADDR_NEG_RULE`, `_DATA_PAGE`,
`_MAX_PACKET_TX`, `_PDU_FORMAT`, `_PDU_SPECIFIC`, `_SOURCE_ADDRESS`,
`_TARGET_ADDRESS`, `_PREFERRED_ADDRESS`(+`_ECU`), `_NAME`(+`_ECU`),
`_SOURCE_NAME`, `_TARGET_NAME`; `names.rs::map_comparam_name_transport`
already registers shortnames for all of them; `comparam_defaults.rs`'s
`j1939_can_common()` helper already seeds spec-matching defaults for all of
them, consumed by two already-present protocol-name presets,
`iso_obd_on_sae_j1939_73()` and `sae_j1939_73_on_sae_j1939_21()`. None of
this was reachable: `resources.rs`/`protocol.rs` had zero `ChannelProtocol`
identity or resource-table row referencing J1939 at all, so nothing in
`rpc_link.rs::rpc_create_com_logical_link`'s resource-resolution path could
ever select these presets, and `comparam_id.rs::to_j2534_config_id` had zero
J1939 entries — none of these ComParams forwarded to hardware. Phase 0
(ADR-152) did add the raw header constants: `PROTOCOL_J1939_PS`/`_CH1..128`,
`ERR_ADDRESS_NOT_CLAIMED`, `IOCTL_PROTECT_J1939_ADDR`,
`CONFIG_J1939_T1`/`_T2`/`_T3`/`_T4`/`_BRDCST_MIN_DELAY`,
`RX_FLAG_J1939_ADDRESS_CLAIMED`/`_LOST` (bits 16/17), and the
`DEVICE_INFO_J1939_PS_J1962`/`_J1939` discovery bits — all inert until this
phase's wiring. `j2534-0404/src/lib.rs` does not yet re-export
`PROTOCOL_J1939_PS` (unlike `PROTOCOL_J1708_PS`, added by ADR-175).

**Standalone protocol, not a CAN bus-type variant.** SWCAN (ADR-164) and
FT-CAN (ADR-168) each added a new bus-type *variant* of an existing CAN-family
`ChannelProtocol`, via `hw_protocol_override` — that shape fit because their
framing, addressing, and COP behavior are literally CAN's own. J1939 is not:
it has its own message framing (a 5-byte ID+destination-address prefix ahead
of payload, clause 16.4.3), its own unique-response-address extraction rule
(source address, not a `CP_CanResp*` id), and — the central new mechanism —
its own StartComm-driven address-claim negotiation with no CAN-family
analogue. `names.rs`'s existing "uses standard CAN hardware channel"
comments describe physical-channel *sharing* (the same raw CAN transceiver
hardware), not protocol *identity* — reusing `ChannelProtocol::Can` would
smear `is_j1939`-gated special cases through every CAN-family code path
instead of confining them to one new, self-contained identity. This phase
therefore follows the UART Echo Byte (ADR-170) / Honda DIAG-H (ADR-174) /
SAE J1708 (ADR-175) precedent — a genuinely new, standalone
`ChannelProtocol` — not the SWCAN/FT-CAN one.

**Address claim/defend: device-owned, service-negotiated, not a raw IOCTL
passthrough.** SAE J1939-81's claim/defend handshake is entirely
device-internal — the adapter transmits/monitors the actual J1939 Address
Claim messages and arbitrates priority; this service never sees that traffic
directly. ISO 22900-2:2022 (verified directly, lines ~8353-8494 and 8936)
defines the D-PDU-facing surface precisely: a claim is triggered by
`PDU_COPT_STARTCOMM` when `CP_J1939AddressNegotiationRule`'s bit 1 requests
it, using `CP_J1939Name` and a *list* of candidate addresses in
`CP_J1939PreferredAddress`; the first address that survives arbitration stays
claimed for the life of the CLL's communication; on losing to a
higher-priority claimant the tester must retry with the *next* list entry;
the address that ultimately succeeds is written back into
`CP_TesterSourceAddress` for client readback after `StartComm` completes.
The native surface (`IOCTL_PROTECT_J1939_ADDR`) is a thin, non-blocking,
one-address-at-a-time primitive with no retry-list concept of its own — this
service owns the retry-over-the-list policy; the device owns claim/defend
execution and arbitration.

**`RX_FLAG_J1939_ADDRESS_CLAIMED`/`_LOST` are native RxStatus bits, not
D-PDU-level indication flags this service synthesizes.** They sit in
`j2534_v0404.h` under the header's existing "J2534-2 RxStatus bits" grouping,
bit-position-overloaded with `RX_FLAG_SW_CAN_HV_RX`/`_HS_RX` (SWCAN),
`RX_FLAG_LINK_FAULT` (FT-CAN), and the future TP2.0 connection bits at the
same bit positions (16-18) — the same reuse-by-protocol-context pattern this
codebase's RxStatus/RxFlag forwarding already disambiguates for SWCAN vs.
FT-CAN (`events.rs`'s protocol-gated dispatch). Clause 16.4.6 (Table 63)
confirms: the *device* delivers the claim outcome as an RxStatus-flagged
message through the ordinary read path, `Data[0]` carrying the affected
source address, `DataSize`=1 — this service consumes them from the native RX
stream, it does not raise them itself. This corrects an initial
misreading in the design-advisor brief (which had these as locally-computed
D-PDU RxFlag constants); the correction changes how the state machine
(Decision 2) and RxStatus routing (Decision 6) are wired, so it is recorded
here explicitly.

**`CP_T3Max`/`CP_T4Max`/`CP_T5Max` → native `J1939_T1..T4`/`BRDCST_MIN_DELAY`
resolve non-ordinally, closing the gap PR #71 left open.** PR #71 ("Register 16
of 19 previously-unregistered ComParam shortnames") left `PARAM_T3_MAX`/
`_T4_MAX`/`_T5_MAX` deliberately unregistered: their D-PDU shortnames
(`cp_t3max`/`cp_t4max`/`cp_t5max`) collide with a pre-existing, unrelated,
already-tested native SCI hardware-timer mapping in
`map_comparam_name_native`, tried first in the dispatch chain — and that
PR's own investigation, verified directly against ISO 22900-2:2022, found
`CP_T3Max`/`CP_T4Max`/`CP_T5Max` are each ONE ComParam with per-protocol
default values (SAE_J2610_SCI vs. SAE_J1939_21), not two distinct ComParams —
the actual bug being that this codebase models the J1939-context values as
separate Rust constants from the SCI-context native mapping instead of one
ComParam with a protocol-conditional default. Re-reading ISO 22900-2:2022's
own `CP_T3Max`/`_T4Max`/`_T5Max`/`CP_Cr`/`CP_Cs`/`CP_Bs`/`CP_Br` entries
directly (verified in this ADR, not merely asserted) resolves the mapping
completely — and it is **not** an ordinal T1↔T1/T2↔T2/... correspondence:

| ISO ComParam | ISO's stated SAE J1939-21 equivalent | Native `CONFIG_J1939_*` | ISO default | Native default |
|---|---|---|---|---|
| `CP_Cr` (already `PARAM_N_CR`) | T1 | `CONFIG_J1939_T1` | 750 000 µs | 750 ms |
| `CP_T5Max` | T2 | `CONFIG_J1939_T2` | 1 250 000 µs | 1250 ms |
| `CP_T4Max` | T3 | `CONFIG_J1939_T3` | 1 250 000 µs | 1250 ms |
| `CP_Bs` (already `PARAM_N_BS`) | T4 | `CONFIG_J1939_T4` | 1 050 000 µs | 1050 ms |
| `CP_Cs` (already `PARAM_N_CS`) | min. inter-packet delay (J1939-21 §5.12.3) | `CONFIG_J1939_BRDCST_MIN_DELAY` | 50 000 µs | 50 ms |
| `CP_T3Max` | Tr (ECU response delay) | *(none — Table 60 has no Tr slot)* | 200 000 µs | — |
| `CP_Br` (already `PARAM_N_BR`) | Th/Thold | *(none)* | 500 000 µs | — |

Every default lines up exactly once the correct (non-ordinal) equivalence is
used — confirming `j1939_can_common`'s already-seeded values were correct
all along; the earlier apparent mismatch was purely an ordinal-position
misreading. This also means no new D-PDU ComParam vocabulary needs minting
for native `J1939_T1`/`_BRDCST_MIN_DELAY` — ISO 22900-2 deliberately reuses
the existing ISO15765-TP-timer ComParams (`CP_Cr`/`CP_Cs`/`CP_Bs`/`CP_Br`)
with J1939-specific per-protocol defaults, the same "one ComParam, several
per-bustype defaults" shape this codebase already uses correctly elsewhere.

## Decision

1. **New standalone `ChannelProtocol::J1939_PS`**, value `0x0000800C`
   matching `PROTOCOL_J1939_PS` directly (self-mapping, the same shape as
   `UART_ECHO_BYTE_PS`/`HONDA_DIAGH_PS`/`J1708_PS`), plus an
   `is_j1939_protocol_id()` funnel covering the `_CH1..128` range
   (`0x9700`-`0x977F`) the same way `is_j1708_protocol_id` does.
   `j2534-0404/src/lib.rs` gains the missing `PROTOCOL_J1939_PS` re-export.
   `J1939_CHx` Additional Channels are **deferred**, matching every prior
   phase.

2. **Two new resource-table rows, not one** — unlike every other standalone
   protocol (UART Echo Byte, Honda DIAG-H, J1708), ISO 22900-2 already names
   two distinct J1939-based application stacks as separate protocol-name
   presets (already present in `comparam_defaults.rs`:
   `"iso_obd_on_sae_j1939_73"` and `"sae_j1939_73_on_sae_j1939_21"`), which
   differ in ComParam preset (`PARAM_MESSAGE_PRIORITY`/ISO15765-TP-timer
   scope) — the same pattern the existing `ISO_15765_2` vs.
   `ISO_OBD_on_ISO_15765_4` sibling rows already use. Next sequential
   `0x0200`-namespace ids (`0x025D`/`0x025E`, following Analog Inputs'
   `0x025C`). **New standalone bus type** `BUSTYPE_SAE_J1939 = 0x030F`
   (following ADR-175's own `BUSTYPE_SAE_J1708` pattern, not SWCAN/FT-CAN's
   variant-of-an-existing-bus-type shape); `bus_type_name:
   "SAE_J1939_11_DWCAN"`, reusing the existing, previously-unwired
   `bustype_default_params("SAE_J1939_11_DWCAN")` → `sae_j1939_11_dwcan()`
   250 kbps physical-layer default. `hw_protocol_override: None` for both
   rows. No default pins (clause 16.3.2.1's statement that the physical layer stays
   unconnected until a `SET_CONFIG` selects cable and pins, the same no-default-pin shape
   every prior `_PS` protocol without a spec-documented default uses);
   connect always issues an explicit `SET_CONFIG(CONFIG_J1962_PINS)`.
   `CONFIG_J1939_PINS` (the SAE J1939-13 connector) stays deferred, per
   ADR-156/ADR-175's existing "at least one connector" scoping — J1962-only
   is spec-conformant.

3. **Address-claim state machine**, owned per-CLL with per-channel routing:
   - `LogicalLinkState` gains a claim record (`claimed: Option<u8>`,
     `cursor` into the `CP_J1939PreferredAddress` list) alongside the CLL's
     existing state.
   - **`PDU_COPT_STARTCOMM` drives the claim** when
     `CP_J1939AddressNegotiationRule` bit 1 requests it: issue
     `PROTECT_J1939_ADDR(addr = list[cursor], NAME = CP_J1939Name)` (never
     byte[0] = 255 — clause 16.3.3.2 defines 255 as the conceptual power-on
     default only, and both 254 and 255 return `ERR_INVALID_IOCTL_VALUE` if
     ever issued as an explicit claim target), then wait — bounded by the
     already-seeded `CP_J1939AddrClaimTimeout` (1 250 000 µs) — for the
     matching `RX_FLAG_J1939_ADDRESS_CLAIMED`/`_LOST` indication for that
     address (Decision 6 covers how the indication reaches this state
     machine). `_LOST` advances `cursor` and retries the next list entry;
     list exhaustion fails the StartComm COP. `_CLAIMED` writes the claimed
     address back into `CP_TesterSourceAddress` (via the existing Active-set
     writeback machinery StartComm already uses for other negotiated values)
     and records `claimed = Some(addr)`.
   - **A later, spontaneous `_LOST`** (the device was out-defended after a
     successful claim) re-enters the same retry loop from the RX-polling
     path; exhausting the list surfaces a CLL error event rather than
     silently going unaddressed.
   - **Routing**: because indications carry only the affected address in
     `Data[0]` (Table 63), and multiple sibling CLLs sharing one physical
     channel may each hold a distinct claim (the device must protect at
     least 10 addresses per clause 16.2.2), a per-`SharedChannel` map
     `address -> (cll_handle, connect_generation)` resolves each indication
     to its owning CLL. Entries are tagged with the owning CLL's existing
     `connect_generation` (ADR-086) — no new generation-style mechanism is
     needed; a stale indication surviving a disconnect/reconnect simply
     fails the existing generation comparison and is dropped, the same as
     every other `connect_generation`-guarded site in this codebase.
   - **Cancellation**: on CLL disconnect while the shared physical channel
     survives, issue the zero-NAME cancel form (byte[0] = the address,
     NAME all-zero) for each address that CLL owns, matching ISO's
     rule that a claimed address stays held for the remainder of the ComLogicalLink's communication.
     When the last CLL on a channel disconnects, `PassThruDisconnect`
     already tears down device state — no explicit cancel is needed there.
     A later `StartComm` after `StopComm` on the same CLL simply re-runs the
     claim loop from `cursor = 0`.

4. **`ERR_ADDRESS_NOT_CLAIMED` is not duplicated service-side.** The
   service's own claim-state cache is inherently staleable in the
   claimed-to-lost direction (defense is asynchronous and device-internal),
   so a service-side pre-check could pass while the device correctly
   rejects — it can never be more than a false gate, never a guarantee. The
   native `PassThruWriteMsgs`-equivalent error return is authoritative and
   is mapped through the existing ADR-026 error path (`j2534-0404/src/
   error.rs`'s `ERR_ADDRESS_NOT_CLAIMED` display mapping already exists from
   Phase 0) into the COP's error result. Separately, this service *does* own
   ISO's own StartComPrimitive-time gate: `CP_J1939TargetAddress == 0xFFFF`
   fails the StartComPrimitive outright (a spec-mandated check, not
   discretionary).

5. **`comparam_id.rs::to_j2534_config_id` gains five J1939-gated
   translations**, per the Context section's table:
   `CP_Cr`→`CONFIG_J1939_T1`, `CP_T5Max`→`CONFIG_J1939_T2`,
   `CP_T4Max`→`CONFIG_J1939_T3`, `CP_Bs`→`CONFIG_J1939_T4`,
   `CP_Cs`→`CONFIG_J1939_BRDCST_MIN_DELAY`, each gated on
   `is_j1939_protocol_id(hw_protocol_id)` and using the existing ADR-072
   µs→native-resolution conversion. `PARAM_T3_MAX`/`_T4_MAX`/`_T5_MAX`
   (`service_params.rs`) are **retired** — their previously-unregistered
   D-PDU shortnames are removed, and every reference switches to the
   existing native `ComParamId(j2534_0404::T3_MAX/T4_MAX/T5_MAX)` ids,
   matching how the codebase already models every other
   shared-ComParam-different-bustype-default case (`comparam_defaults.rs`).
   This makes `map_comparam_name_native`'s existing `cp_t3max`/`cp_t4max`/
   `cp_t5max` arms correct for both the SCI and J1939 contexts at once — the
   collision PR #71 flagged dissolves rather than needing a workaround.
   `CP_T3Max`/`CP_Br` have no native `CONFIG_J1939_*` counterpart (Table 60
   defines none) — left ComParam-only, an accepted residual matching every
   prior phase's "registered but not natively forwarded" precedent for
   values with no native slot.

6. **Message framing**: a new `tx_header.rs` composer builds the 5-byte
   prefix (29-bit CAN ID assembled from `CP_MessagePriority`/
   `CP_J1939DataPage`/`CP_J1939PDUFormat`/`CP_J1939PDUSpecific`-or-target-
   address for PF≥240 per clause 16.4.3/16.4.4, source = the CLL's claimed
   address per Decision 3) plus the destination-address byte
   (`CP_J1939TargetAddress`, `0xFF` selecting BAM per clause 16.4.4) ahead of
   client-supplied payload — the client supplies payload bytes only, mirroring
   every prior protocol-specific header composer (ADR-050 family). A matching
   RX-side parser strips the 5-byte prefix and extracts the source address
   for unique-response-id routing through the existing ADR-007/068 table
   machinery (`PARAM_J1939_SOURCE_ADDRESS`, already registered as a
   UNIQUE_ID-class ComParam). BAM/Connection-Management multi-frame
   segmentation (SAE J1939-21) is handled entirely by the adapter once an
   address is claimed (clause 16.1) — this service does not implement J1939
   transport-layer segmentation itself, it passes the up-to-1790-byte buffer
   straight to the native write call. `protocol.rs`'s TX/RX size-range table
   gains a `J1939_PS`/`_CHx` entry: `5..=1790` both directions (Table 62) —
   comfortably inside the existing 4128-byte `PASSTHRU_MSG` data array, no
   buffer-sizing change needed. **Deferred (new scope, not previously
   flagged by the support plan)**: NAME-based target/source resolution
   (`CP_J1939TargetName`/`CP_J1939SourceName`) needs a bus-wide
   Name↔Address network-management table built from observed Address-Claim
   traffic — out of scope for this phase; `CP_J1939TargetAddress`-only
   operation is explicitly spec-sanctioned as the fallback (ISO 22900-2's
   own NOTE on this ComParam pairing). `CP_J1939AddressNegotiationRule`'s
   bit 0 (negotiate vs. don't) and bit 2 (defend vs. don't-defend) have no
   native knob — `PROTECT_J1939_ADDR` always negotiates-and-defends;
   accepted residual, ComParam-only.

   **Round-11 amendment (Codex review, PR #72 round 11), two findings on
   this same message-framing mechanism:**
   - **`TX_EXTENDED_ID` was never actually set on a J1939 transmission.**
     `rpc_primitive.rs::apply_resolved_tx_flags` (the one function every TX
     path — `CoptSendrecv`, the optional `CoptStartcomm` message, and
     tester-present — funnels its flags through) always clears
     `TX_EXTENDED_ID`/`ISO15765_ADDR_TYPE` and replaces them with whatever
     `tx_header::can_addressing_tx_flags` derives from
     `tx_header::resolve_can_addressing`'s result — a CAN-family-only
     resolution keyed on `CP_CanPhysReqId`/`CP_CanFuncReqId`, which J1939
     never configures (it resolves addressing from
     `CP_J1939TargetAddress`/the claim state machine instead, per this
     Decision's own framing). `resolve_can_addressing` therefore always
     returns `None` for J1939, `can_addressing_tx_flags(None, ..)` always
     returns `0`, and every J1939 send was submitted as an 11-bit
     transmission despite this Decision's own 29-bit CAN ID assembly — the
     native library could reinterpret or reject it. Fixed by forcing
     `TX_EXTENDED_ID` in `apply_resolved_tx_flags` whenever `hw_protocol_id`
     is J1939, the same "objective fact this service already resolved, not
     caller preference" treatment `sci_tx_flags`/`sw_can_tx_flags`/
     `msg_priority_tx_flags` already get there. **`edge-case-hunter`
     verification pass on this same round's own diff found a second,
     independent site with the identical gap**: SAE J2534-2 clause 14
     Repeat Messaging's own actually-transmitted `RepeatMsgData[0]` message
     is composed by `rpc_misc.rs::ioctl_start_repeat_message`'s own inline
     TxFlags logic, independently of `apply_resolved_tx_flags` (mirroring
     that same function's own local SW-CAN/J1708 gates, both already
     duplicated there for the identical "independent composition" reason)
     — so a J1939 repeat slot's transmitted frame still went out 11-bit
     after the fix above. Fixed with the identical unconditional
     `TX_EXTENDED_ID` OR at that second call site.
   - **`CP_MessagePriority`/`CP_J1939DataPage` were unvalidated one-field
     wire values.** `j1939_header_bytes` packs `CP_MessagePriority` into
     byte 0 bits 4-2 (`priority & 0x07`) and `CP_J1939DataPage`'s low bit
     into byte 0 bit 0 (`data_page & 0x01`) — an out-of-range value (e.g.
     priority `8`, data page `2`) silently masked to a different in-range
     value on the wire (changing arbitration priority and/or the selected
     PGN) while `GetComParam` kept reporting the untruncated value, the
     same silent-truncation shape `CP_J1939PDUFormat`/`CP_J1939PDUSpecific`
     already had fixed (round 8). Fixed in `rpc_link.rs`'s `SetComParam`
     handler, mirroring that existing check's position and shape:
     `CP_J1939DataPage` (J1939-only in `comparam_support`'s own allowlists)
     rejects any value `> 1` unconditionally; `CP_MessagePriority` rejects
     any value `> 7`, but only when `protocol.is_j1939_family()` — unlike
     `CP_J1939PDUFormat`/`_Specific`, `CP_MessagePriority` is allowlisted on
     several unrelated protocol families too
     (`comparam_support::is_can_param`/`is_kwp_param`/`is_j1850pwm_param`/
     `is_j1850vpw_param`), none of whose own composers read it via this
     J1939-specific 3-bit mask, so a non-J1939 link's own (wider, currently
     unvalidated) use of the same ComParam ID is left untouched — mirroring
     `CP_TesterSourceAddress`'s own round-8 family-gated check, made
     necessary by the identical "same ComParam ID, different per-protocol
     truncation risk" shape.
   - New regression tests:
     `tests/grpc_mock/j1939.rs::ordinary_send_sets_tx_extended_id`,
     `::coptsendrecv_rejects_out_of_range_message_priority`,
     `::coptsendrecv_rejects_out_of_range_data_page`,
     `::repeat_message_transmitted_frame_sets_tx_extended_id` (the
     `edge-case-hunter`-found second site), each confirmed to catch the
     regression by temporarily reverting the fix and observing the test
     fail.

7. **RxStatus routing**: `events.rs`/`events_rx_routing.rs` gain a
   `is_j1939_protocol_id`-gated arm, positioned alongside the existing
   SWCAN/FT-CAN RxStatus-bit disambiguation (bits 16-18 already mean
   different things per protocol family), that withholds a J1939 claim
   indication from ordinary content/COP matching (the ADR-172 withhold
   precedent — `DataSize`=1, `Data[0]`=address is not vehicle-frame content)
   and routes it into Decision 3's state machine instead. **These bits are
   not forwarded into D-PDU `RxFlag`** — ISO 22900-2 defines no
   address-claim `RxFlag` bit (the existing ADR-097/098 set), and the
   client-visible surface is the StartComm COP's own result plus
   `CP_TesterSourceAddress` plus (on later loss) a CLL error event, not a
   content-frame flag. This is a genuinely different mechanism from the
   already-open "`RxFlag` byte needs widening for bits 16+" backlog item
   (SWCAN's own RxStatus-forwarding residual, `implementation-notes.md`
   Prioritized Backlog) — that item covers forwarding SWCAN/FT-CAN's own
   *content-adjacent* transition indications into `RxFlag`, which this phase
   does not touch, does not resolve, and does not need.

8. **Repeat Messaging (ADR-165) needs no new rejection** — clause 14's
   default-supported rule applies; clause 16's text contains no exclusion,
   verified directly.

9. **`tx_header::response_header_bytes`'s J1939 arm exact-matches only the
   responding ECU's source address; every other header byte is wildcarded**
   (Codex review PR #72 round 9, `design-advisor` consult). Decision 8
   established Repeat Messaging (ADR-165) needs no *rejection* for J1939,
   but `response_header_bytes` itself — the composer that prepends the
   expected-response header to a client's Repeat Messaging stop-condition
   template — had no J1939 arm at all, falling through to the generic empty
   default and leaving every client payload byte misaligned against the
   wire frame's 5-byte prefix (Decision 6). Unlike CAN/KWP/J1850's
   composers, only byte 3 (the responding ECU's own SAE J1939 source
   address, the swapped-direction counterpart of `CP_J1939TargetAddress`)
   is knowable from ComParams at repeat-slot setup time: bytes 0-2
   (priority/PGN) and byte 4 (destination) all depend on the ANSWERING
   message's own PGN, which no ComParam records — there is no "expected
   response PGN" ComParam (`comparam_support::unique_id_params` has no
   J1939 branch at all), and this CLL's own `CP_J1939PDUFormat`/
   `CP_J1939PDUSpecific` are its OUTBOUND request PGN, not necessarily the
   response's. Byte 4 has a second, independent reason to wildcard: SAE
   J1939-21 PDU2 (broadcast/BAM) responses — the common case, since most
   requested PGNs are PDU2 — carry the global address there regardless of
   who asked, so exact-matching this CLL's own claimed address would make
   a repeat slot never see a broadcast answer. The new arm therefore
   returns a 5-byte template with only byte 3 exact-matched (mask `0xFF`,
   pattern = `CP_J1939TargetAddress as u8`) and the rest wildcarded (mask
   `0x00`), `TX_EXTENDED_ID` set unconditionally (clause 16.4.3: J1939
   frames are always 29-bit), and rejects (mirroring the KWP/J1850/CAN
   functional-addressing `Err`s: "a repeat slot always targets one
   physical ECU") when `CP_J1939TargetAddress` is unconfigured (the
   `0xFFFF` sentinel, Decision 4) or `0xFF` (BAM/global, clause 16.4.4 — no
   single expected responder). A useful side effect: with byte 4 wildcarded
   and byte 3 pinned to the ECU's OWN address rather than this CLL's
   claimed one, the resulting template contains no byte derived from this
   CLL's own address — it is invariant under a reclaim (see ADR-180
   Decision 10, which handles the separate concern of the template's
   *validity window* rather than its byte content).

   **Round-11 amendment (Codex review, PR #72 round 11):** this arm's
   `Some(addr) => addr as u8` cast for byte 3 had no upper-bound check of
   its own, unlike `rpc_primitive.rs`'s `StartComPrimitive`-time
   `CP_J1939TargetAddress` gate (round 6/7) that this Decision's byte-3
   resolution otherwise mirrors. `PDU_IOCTL_START_REPEAT_MESSAGE` requires
   only a connected CLL, not `comm_started` — so this arm is reachable
   BEFORE `StartComPrimitive`'s own range gate ever runs, and an
   out-of-range `CP_J1939TargetAddress` (e.g. `0x100`) fell through to the
   cast, silently truncating to a different responder than `GetComParam`
   still reports. Fixed by adding the identical one-byte-range rejection
   here (`addr > 0xFF`), mirroring `StartComPrimitive`'s own check and
   message. New regression test:
   `tests/grpc_mock/j1939.rs::repeat_message_setup_rejects_out_of_range_target_address`,
   confirmed to catch the regression by temporarily reverting the fix and
   observing the test fail.

10. **`rpc_link::connect_flags`/`can_filter_tx_flags` gain a `PROTOCOL_J1939_PS`
    arm each, both unconditionally 29-bit-only** (Codex review, PR #72 round
    18). Decision 6 already established `TX_EXTENDED_ID` set unconditionally
    for PER-MESSAGE framing (clause 16.4.3: J1939 frames are always 29-bit),
    but the CHANNEL-LEVEL mechanics — `PassThruConnect`'s own `Flags`
    argument (ADR-065) and the pass-all/client-message hardware filters
    installed at connect time — were never given a matching J1939 arm.
    `connect_flags`'s `match` fell through to its catch-all `0` for
    `PROTOCOL_J1939_PS` (no arm at all, unlike CAN/ISO15765/K-line's own
    explicit arms), so a J1939 channel connected as if it only ever carried
    11-bit CAN Ids — on a conforming adapter that enforces `Flags` against
    actual wire traffic, this could reject or corrupt every J1939 frame
    despite this phase's own per-message framing already building a correct
    29-bit identifier. `can_filter_tx_flags` (ADR-065, shared by
    `install_pass_all_filter`/`install_client_message_filters`) had the
    identical gap one level down: even after fixing `connect_flags`, its own
    29-bit branch special-cased `protocol_id == CAN` only, so the pass-all
    filter `ConnectComLogicalLink` installs for every channel would still be
    built at `TxFlags = 0`, leaving the channel deaf to its own 29-bit
    traffic on hardware that filters by ID width.

    Fixed by adding one arm to each: `connect_flags`'s new
    `PROTOCOL_J1939_PS => CAN_29BIT_ID` arm (flat, never `CAN_ID_BOTH` —
    unlike raw CAN, ADR-065's own reasoning for `CAN_ID_BOTH` is "the set of
    widths a bare `(CAN, baud)` channel will ever carry is unknowable at
    connect time," which does not apply to J1939: SAE J1939-21 never sends an
    11-bit frame, so there is no unknowable second width to accept); and
    `can_filter_tx_flags`'s 29-bit branch widened to recognize
    `PROTOCOL_J1939_PS` alongside `CAN`, so the connect-time `CAN_29BIT_ID`
    it now sees actually reaches the filter it selects. Both `_PS` ids are
    passed to their respective function as `base_hw_protocol_id()`
    (`connect_flags`) or `resources::base_protocol_id(protocol_id)`
    (`can_filter_tx_flags`, at both existing call sites) — `PROTOCOL_J1939_PS`
    self-maps under `resources::base_protocol_id` (no separate unqualified
    base J1939 id exists, the same self-mapping `is_j1939_protocol_id`'s own
    Decision 1 already establishes for Honda DIAG-H/J1708/UART Echo Byte), so
    both new arms match on the `_PS` id directly rather than a distinct base
    constant. New regression tests:
    `tests/grpc_mock/j1939.rs::connecting_a_j1939_cll_sets_the_can_29bit_id_connect_flag`
    (asserts `server.backdoor.connect_flags_log() == vec![0x100]`) and
    `::connecting_a_j1939_cll_installs_a_29bit_pass_all_filter` (asserts
    exactly one installed filter, `TxFlags == TX_EXTENDED_ID`). Both
    confirmed to catch the regression by temporarily reverting `connect_flags`'s
    new arm to `0` and observing both tests fail, then restoring it.

### Rejected alternatives

- **Reusing `ChannelProtocol::Can` + `hw_protocol_override`** (the
  SWCAN/FT-CAN shape) — rejected: J1939's framing, unique-response-address
  rule, and address-claim state machine are not CAN's; forcing the reuse
  would scatter `is_j1939` special cases through CAN-family code instead of
  confining them to one new, self-contained identity.
- **Exposing `PROTECT_J1939_ADDR` directly as an ADR-079-style `L`-scoped
  IOCTL command** — rejected: ISO 22900-2 already defines the claim surface
  as ComParams (`CP_J1939Name`/`_PreferredAddress`/`_AddressNegotiationRule`)
  plus `StartComm`, not a raw IOCTL passthrough; bypassing that would skip
  the retry-list and writeback semantics ISO actually specifies.
  `PROTECT_J1939_ADDR` stays an internal primitive this service's own
  StartComm handling drives, never exposed to clients directly (matching how
  `SET_CONFIG` for other protocols is driven internally, not IOCTL-exposed).
- **A service-side `ERR_ADDRESS_NOT_CLAIMED` pre-check** — rejected: the
  service's claim cache can be stale relative to the device's live defense
  state in the claimed→lost direction; only the native return is
  authoritative.
- **Minting new D-PDU ComParam vocabulary for native `J1939_T1`/
  `_BRDCST_MIN_DELAY`** — rejected once the correct (non-ordinal) ISO
  equivalence was found: ISO 22900-2 already assigns `CP_Cr`/`CP_Cs` to
  these exact native parameters; minting new vocabulary would duplicate
  existing spec vocabulary, the class of mistake ADR-170 only accepted for
  UART Echo Byte's `UEB_T*` parameters because ISO 22900-2 genuinely defines
  no equivalent there.
- **Forwarding `RX_FLAG_J1939_ADDRESS_CLAIMED`/`_LOST` into a widened D-PDU
  `RxFlag`** — rejected: no ISO 22900-2 `RxFlag` bit exists for address-claim
  indications to forward into; doing so would invent D-PDU surface ISO does
  not define, and would incorrectly conflate this phase's own mechanism with
  the still-open, unrelated SWCAN RxFlag-widening backlog item.

## Consequences

- Establishes the fourth instance of the standalone-protocol
  `ChannelProtocol` pattern (UART Echo Byte, Honda DIAG-H, J1708, now
  J1939) and the first genuinely asynchronous, multi-round negotiation state
  machine in this codebase's protocol layer — distinct in kind from the
  single-`ConnectComLogicalLink`-call variant-selection shape every prior
  "state machine" precedent (SAE J1850 auto-detect, CAN FD substitution)
  used.
- Closes the gap PR #71's `PARAM_T3_MAX`/`_T4_MAX`/`_T5_MAX` shortname
  collision left open completely: the collision dissolves once the codebase models
  `CP_T3Max`/`_T4Max`/`_T5Max` as the single ISO-defined ComParam each
  already is, rather than two Rust constants.
- Leaves the SWCAN/FT-CAN `RxFlag`-widening backlog item (bits 16-18)
  untouched — this phase's own RxStatus consumption is a distinct
  mechanism and does not resolve it. (That item was later substantially
  resolved, by decision, by ADR-191; this phase's own J1939 bits stay
  unforwarded per Decision 7 above, unaffected by that later ADR.)
- Defers `J1939_CHx` Additional Channels, `CONFIG_J1939_PINS` (the SAE
  J1939-13 connector), Discovery-cache connect-time enforcement wiring, and
  NAME-based (as opposed to address-based) target/source resolution — all
  tracked in `j2534-0404-service/docs/implementation-notes.md`'s Prioritized
  Backlog, matching every prior phase's identical deferrals.
- `CP_T3Max`/`CP_Br` remain ComParam-only with no native forwarding (Table
  60 defines no native slot for either) — an accepted residual, not a gap
  introduced by this phase.
- Decision 9's effect IS independently testable and deterministic:
  `tests/grpc_mock/j1939.rs::repeat_slot_stop_condition_wildcards_pgn_and_destination_exact_matches_source_address`
  proves both halves in one flow — an injected frame with the wrong source
  address never stops a live slot even when its PDU Format byte happens to
  equal this CLL's own `CP_J1939PDUFormat`, and a frame with a DIFFERENT
  PDU Format/Specific/destination than anything this CLL configured DOES
  stop it as long as the source address matches, confirming bytes 0-2/4
  are genuinely wildcarded rather than merely defaulted to a value the
  fixture happens to satisfy.
- Closes clause 16.
